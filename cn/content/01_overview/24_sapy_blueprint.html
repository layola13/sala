1. 愿景

AI 正在写下越来越大比例的新代码，但主流语言仍要求作者——无论人还是 AI——手工写明参数类型、返回类型、生命周期、所有权、释放与转换。SA-Py 是我们的回答：一门编译型语言，具备 Python 语法、真正的动态类型、编译器推导的所有权，以及完全无任何形式的 GC，经 SA AOT 编译到原生与 WASM。

一句话版本：Python Syntax. Dynamic Types. Zero GC. Verified Memory Safety.（Python 语法、动态类型、零 GC、经验证的内存安全。）程序员（或生成代码的 AI）写尽可能少的代码；编译器推导类型与所有权；SA Referee 在任何代码运行之前验证内存安全。无法证明或不支持的东西一律是响亮的编译期错误——绝不静默兜底，绝不把运行时意外偷运过检查器。

设计优先级如下，且任何优化不得以 P0、P1 为代价：

优先级目标
P0内存安全（每个程序都通过 SA Referee）
P1完全无 GC（无追踪、无标记清扫、无后台回收线程、无停顿回收）
P2作者要写的代码最少（AI 优先的人机工程）
P3动态类型 + 可选静态约束
P4快速 AOT 编译
P5高性能原生 / WASM 产物

v1 验收门刻意定得窄且可测：(a) 语法覆盖与绝大部分 Python 语法兼容；(b) 性能在 bench 题集上打败 CPython——静态面先行，动态面建成后须以动态写法的同一题集复测。

定位：给 AI 的工具调用语言

SA-Py 程序的预期主要作者是 AI，预期主要负载是工具调用：智能体生成一小段程序，解析 JSON 载荷、调用 HTTP 服务与其它工具、变换数据、返回结构化结果。现行技术栈把这类生成代码跑在解释器上，唯一的安全网是运行时错误处理：程序写错了，要等它崩溃才被发现——或者更糟，悄悄写坏数据而不崩溃。

SA-Py 把这个顺序倒过来。生成代码在运行之前先过检查器与 SA Referee：所有权与越界在编译期裁定，证明不了的在执行前响亮拒绝。产物是原生二进制——无解释器、无 GC 停顿、资源占用确定、冷启动快——这同时也是工具进程应有的形状：有界、可杀、可重启。编译期验证，就是 AI 生成代码目前缺失的那道安检。

这个契合是结构性的，不是修辞。工具载荷是 JSON，而 JSON 的值模型（null、布尔、数字、字符串、数组、对象）与动态面的标签值（5.3 节）同构：解析 JSON 就是构建动态值，输出 JSON 就是遍历动态值。补齐这一定位的库工程是 psa_std 里的库工作、不是编译器工作，排期见第 7 节（L1–L3）：建在动态容器之上的 json 模块；Python 形状的网络接口（socket、http.client，以及 requests 形状的接口——AI 生成代码最常写的正是这个形状），底下是 sa_std 里已有的协议核；以及 NumPy 接口（类型化、带步长的数组 + 广播），它让海量数值类 Python 以很低的痛感转化——数值类 Python 是离本底座最近的一种 Python 方言，它本来就写在定宽类型数组上，而不是任意精度整数与不受限的动态性上。

这一定位的速度指标，既不是峰值吞吐，也不是内核基准。工具程序都很小——几十行、写出来跑一次即弃——因此计费的是总周转时间：生成、编译、执行、返回。2026-11-25 同一窗口内在当前基准集上实测：小程式用 psa 编译约 0.2 秒，而最接近的可比对象、同为预先编译的 Python 编译器 Codon 约需 3.9 秒，其单程式成本由工具链主导、几乎不随程式大小变化；静态程式的执行两家同档，动态风格程式则由 psa 以 Python 语义原生运行，而该预先编译对比对象在此静默分叉。解释器不付编译时间，但要以执行速度偿还、且没有安全门。工具循环里数秒级的编译是结构性成本，不是调优细节：它在每一次调用上都要付一遍。

一条诚实条款，先于评审者发问而声明：这一定位中"安全"的一半，今天是对设计的断言；

只有当静默错值类缺陷清零时，它才成为对产品的断言——目前尚未清零（见第 8 节，如 (xxiv)）。因此库工程排在缺陷队列与 D2 之后，不在它们之前。

2. 在 SA 生态中的定位

SA-Py 是 SA 生态的第二门高级语言，不是 SLA 的替代品。三层职责分明、共享同一套经验证的地基：

层职责明确不归它管
SA寄存器与所有权模型、借用/移动/释放规则、Referee 安全验证、原生/WASM 代码生成依赖任何一门具体高级语言的类型系统
SLA静态类型、精确资源控制、系统编程、性能敏感任务为迁就 SA-Py 而变成动态语言
SA-PyAI 生成代码、快速业务开发、动态数据处理、Web 后端、自动化、快速原型绕过 Referee，或把动态语义引入 SLA

SLA 与 SA-Py 前端独立。两者共享 SA 基础设施——一套安全验证体系、只维护一份——且任何一门语言的语义都不泄漏到另一门。

3. 设计原则

  1. 动态类型不等于动态内存管理。变量可以改变所持值的类型；这改变的是值的语义，永不改变所有权规则。每个动态值在每个程序点仍有确定的类型标签、表示、所有者、生命周期与可访问性。
  2. 类型推导不等于垃圾回收。编译器推导类型与所有权，免得作者去写；推导失败永不退回到回收器。静态推导失败时退回的是动态值表示（第 5.3 节），其内存仍是确定性管理的。
  3. 零 GC 是架构约束，不是选项。不能被开关、运行时模式或库打开。动态面采用 Perceus 式引用计数 + 机会性原地复用，且只限于动态值（第 5.3 节）——这是由编译器所有权账本指挥的确定性纪律，不是追踪式回收器；静态面根本不进入计数体系。
  4. 响亮失败优于静默近似。编译器不支持的任何东西——语法形态、类型组合、标准库角落——都是具名的编译期错误。只覆盖语料恰好用到的形状的简化实现，不算支持。
  5. 编译器负责推导，Referee 负责裁决。AI 可以生成代码、可以依据编译器的所有权诊断改代码，但任何 AI 产物、任何前端结论都不被信任：每个程序在降低后都由 SA Referee 重新验证。
  6. 不假设未经审计的基座能力。实现从审计 SA、Referee 与 SLA 管线今天实际能做什么开始（第 6.1 节）；特性只建在已审计的地面上，基座缺口登记为缺陷（第 8 节），不掩盖。

4. 语言

4.1 语法面

Python 的表面习惯：def、class、if/elif/else、for、while、return、import、async/await、try/except；缩进定界代码块；无 let/mut 声明关键字。源文件后缀 .psa；编译器二进制名 psa，与 SLA 编译器名 sla 的命名法一致。v1 目标是与绝大部分 Python 语法兼容——约 55 个构造逐项普查的现状汇总见第 6.2 节。

4.2 类型模型：一个程序里的三种模式

  • 推导静态。def add(a, b): return a + b——无注解时，编译器从使用与调用点推导参数、局部变量与返回类型。推得出唯一静态类型处，值就是普通的 SA 层值，走零成本静态路。
  • 注解约束。def add(a: i64, b: i64) -> i64——注解是编译期约束；传入约束外的值是类型错误，绝不静默运行时转换。
  • 动态。推导钉不住单一类型处（异构返回、异构容器、动态调用形态），变量或函数为动态：值携带运行时标签、运算按标签派发，错误语义明确——类型非法的运算响亮 panic，形态如 Python 的 TypeError。动态函数必须保留通用路径：一个整数调用点不得把函数永久特化成整数函数（可以生成特化副本，通用路径必须保留）。

静态/动态边界按变量与函数签名逐个划定，两面在同一程序内共存；跨界自动装箱/拆箱，拆箱带运行时类型断言。

4.3 所有权模型

所有权从值的用法推导，建在 SA 既有的移动/借用/释放规则之上——SA-Py 不另造一套所有权系统。已定案且已实现：标量值是 Copy；容器参数由编译器按函数体推导只读借用还是消费型移动（只读的参数借用、被消费的参数移动，移动后再用是具名诊断的编译错误）。以下仍是待最终裁定的提案，凡出现处均如此标注：从容器中提取元素、动态调用只借用语义、作用域绑定（不逃逸）借用。容器默认赋值是移动语义——b = a 转移所有权、之后再用 a 是错误——刻意不采用 Python 的别名赋值；可变对象的长期共享必须走显式的、SA 认可的安全共享机制，绝不把隐式引用计数偷运进普通赋值。强所有权环在构造上不被允许；动态面在引用环上的已知边界声明在第 8 节。

4.4 值与容器

规划的值种类：None、bool、int（v1 为 i64；任意精度是已登记缺口，溢出响亮报错、绝不静默回绕）、float、str（不可变；小字符串内联、拥有型缓冲、不可悬空的只读切片）、bytes、list、dict、set、tuple、类实例、函数/闭包、任务。容器拥有其元素；移动容器即移动整棵所有权树；释放容器即确定性释放其所拥有的一切——永远不需要扫描对象图。容器扩容可能搬移存储，因此任何已验证的元素借用都不得跨越扩容操作。

4.5 函数、类、异常、并发

  • 函数：今天支持位置参数；默认值、关键字参数、*args/**kwargs、lambda 与闭包在实现清单上（第 7 节）。闭包捕获服从同一套所有权规则：逃逸的闭包必须拥有其所保留之物；不许用隐藏的引用计数糊弄捕获生命周期。
  • 类：v1 支持实例、字段、方法、构造函数、受限单继承与方法覆盖。无元类，不允许任意运行时修改对象结构。
  • 异常：Python 形态的 try/except/finally/raise，降低为显式控制流 + 异常槽 + 边界检查（SA 无展开机制）；每条异常退出路径必须执行与正常路径相同的确定性清理。
  • 并发：SA-Py 复用 SA 的任务与同步机制（goroutine 式 spawn、channel、select）。不可变值自由共享；可变值默认独占；经 channel 发送拥有型对象即转移所有权。

5. 编译器架构

5.1 管线

                 .psa 源码
                      |
               psa 前端（Rust）
        词法 -> 语法 -> AST -> 名字解析
                      |
        类型推导 + 动态分析
                      |
        所有权 / 借用分析
                      |
              发射 SLA 源码
                      |
        sla 管线：检查器 + SA 发射
                      |
                 SA Referee
                      |
              sa 工具链（build-exe）
                      |
               原生 / WASM

前端是独立的：其词法、语法、AST、推导与所有权分析都是 SA-Py 自己的代码，不依赖 SLA 检查器的内部实现。降低目标是 SLA 源码，因此每个 SA-Py 程序都原样经过既有 SLA 检查器与 SA Referee——不存在绕过验证的 SA-Py 专用后门。实现策略是刻意选定的：psa 编译器由整树复制 Rust 版 SLA 编译器后在其上修改而成，而非从零开始——已审计的检查器、发射与裁判机械被继承，SA-Py 特有的工作集中在新的前端 crate（词法、语法、AST）与发射层。

5.2 静态面

推导证明静态类型处，值就是普通的 SLA 值：整数在寄存器里、容器是 sa_std 容器、调用是直接调用。无标签、无派发、无计数——这是快路径，第 6.3 节的当前 bench 数字即来自于此。

5.3 动态面

动态值用显式标签结构体 PsaVal 表示：一个标签加有效载荷槽（已落地实现中载荷是分槽的——整数槽与浮点槽——因为标准库没有 f64 位转换原语；堆种类入场后指针走整数槽）。动态运算（算术、比较、真值、下标、调用）发射为运行时模块 psa_std 的函数调用，该模块随 sapy 仓维护、与 SLA 发射层解耦；每个运行时函数内先行 int/float 快路径，这正是编译型动态面能赢解释器逐字节码派发之处。堆对象共用统一头部（引用计数、种类），种类体分别为 str/list/dict/set/tuple/object/function。

动态值的内存管理——且仅限动态值——是 Perceus 式：引用计数 + 机会性原地复用，由编译器既有的所有权账本指挥。消费型操作在计数为一时原地复用存储而不重新分配；静态值永不进入计数体系；静态值装箱为动态值计一次数，拆箱断言标签。这是项目章程下的主会话工作决定，也是提交评审的问题之一（第 10 节）。

5.4 标准库

独立建设的标准库，不是 CPython 绑定。分期：(1) io、string、bytes、math、collections、json、errors；(2) filesystem、networking、http、tcp/udp、database、async、channel、同步；(3) crypto、compression、序列化、process、高级集合。每个资源型 API 必须声明其所有权与释放规则；任何库组件不得引入 GC。

每期的验收口径预先定死：正例端到端真跑、与 CPython 同源同输出逐字节对拍；负例响亮失败且诊断具名；bench 题集以动态写法复测且不许输给 CPython。

8. 已知限制与上游阻塞

以下为底层 Rust 版 SLA 工具链 build-exe 路的已登记缺陷，每条都以独立于 psa 的手写 SLA 探针复现。列在这里，是让评审者清楚 SA-Py 的哪些拒绝是基座的限制、而非语言的决定：

编号缺陷对 SA-Py 的当前影响
(xxiii)build-exe 路打印 f64 时截断小数部分（值本身正确）float 打印响亮拒绝；动态 float 打印 panic（77030），不打印错值
(xxiv)Vec<f64> 元素访问在两个 SLA 实现上均误编译（静默错值）list[float] 编译期响亮拒绝
(xxv)字符串绑定在 build-exe 路无法降低（参数、局部变量、返回值）字符串变量响亮拒绝；print 位置的字符串字面量可用
(xxvi)自引用调用赋值泄漏寄存器psa 内部以临时变量路由绕行；直接形态仍是上游缺陷
(xxvii)SAB 降低中聚合变量不可整体重赋值、块作用域局部在块退出时不退役动态层以显式 stage 模式（逐字段拷入 + void 汇点）存储而不用普通赋值；语义精确保持的绕行，上游修复落地后简化掉
(xxviii)Box::new/into_raw 分配惯用法在 build-exe 路泄漏宏展开临时阻塞 D2 堆种类；自声明 realloc extern 能过检查能链接但运行时段错误——根因未隔离，旁路在被证明之前不用
(xviii)底层 SLA 当前在两个实现上对 and/or 均为急切求值（实测）静态布尔运算在上游修复前继承基座语义；动态层自己保留短路。短路是否为语言既定语义尚待裁定

语言层边界，如实声明而非留待发现：v1 整数为 i64（溢出响亮报错；任意精度是 v1 后项）；动态值的引用环在 v1 不回收、泄漏到进程退出（CPython 有循环 GC；关闭此项是 D7 评估项）；源码制表符响亮拒绝，与 CPython 不同。

9. 明确不做的事

  1. 任何形式的 GC——追踪式、分代、后台式、可选式，一概不做。
  2. 把隐式引用计数作为普通值的默认管理方式（计数只存在于动态面的 Perceus 纪律内、由编译器指挥）。
  3. CPython C 扩展兼容与 Python C API。
  4. 元类与任意运行时修改对象结构。
  5. 不受限制的 eval 与动态代码加载。
  6. 未经验证的 unsafe 逃逸与用户代码中的裸指针。
  7. v1 不做 JIT（只做 AOT；静态特化与内联是 v1 的性能杠杆）。

10. 提交评审的问题

  1. 动态面内存纪律。Perceus 式计数 + 原地复用、只限于动态值、由编译器所有权账本指挥——这是对"零 GC"的成立读法吗？它最先会在哪里破（异常路径、闭包捕获、容器扩容）？
  2. 所有权提案组。第 4.3 节未定案各项（提取元素、动态调用只借用、作用域绑定借用）：能否在 SA 既有 Referee 规则内表达、无需新原语？
  3. 异常机制。异常槽 + 每个动态调用点边界检查，与返回码纪律相比：哪个让 Referee 的工作更简单？各自对静态面的成本是多少？
  4. 标签值表示。分槽载荷是被缺失的 f64 位转换原语逼出来的。基座应补这个原语（回到单载荷表示），还是分槽布局可长期接受？
  5. 边界粒度。静态/动态按变量与签名逐个判定。这个粒度对吗，还是应按函数判定、整函数动态作为唯一回退？
  6. 整数政策。i64 响亮溢出 + bigint 后置——对一门声称"绝大部分 Python 兼容"的 v1 可接受吗，还是兼容性主张要求 bigint 从一开始就在？
  7. AI 工具调用主张。第 1 节把 SA-Py 定位为给 AI 生成工具代码用的、带编译期检查的执行语言。编译器之门（检查器 + Referee）是生成代码的正确安全边界吗——它可证明地排除了生成程序的哪些失败类、又排不掉哪些？
