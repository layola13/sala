SLA / SA 缓存

SA / SLA 工具链有多处缓存。它们大多只按文件内容作键——不含编译器或插件版本—— 因此编译器或插件重编之后，陈旧缓存会静默回放旧编译器产出的制品。症状在两个方向上都骗人： 真修复看起来毫无效果，或者健康的树看起来是坏的。

本章分两部分：前半部分是现状下的排查与绕行（位置、键、症状、清理）； 后半部分是根治路线——让工具链自己判定缓存是否陈旧，而不是靠人判读。 每处根治落地后，对应的绕行内容即可删除（见「维护约定」）。

通则：验证任何编译器或插件改动之前，先清下面全部六个缓存面。 门禁或金丝雀结果与树的状态矛盾时，清缓存是调查的第一步，不是最后手段。 清缓存永远安全——所有缓存都会再生，唯一代价是重编时间。

1SLA 宏索引缓存sa_plugin_sla 树内的 .sla-cache/ （macros/*.idx）宏文件路径 + 长度 + 源码哈希；不含编译器分析版本 编译器改动后仍回放旧宏展开，修好的编译器会继续以原样崩溃或出错。 删该树的 .sla-cache。注意：SLA_NO_FRESHNESS_CACHE=1 不覆盖此缓存。需手动
2宿主前端缓存默认 ~/.cache/sa/frontend。解析顺序（已按 sci 现行源码 broker_runtime.zig 的 frontendCacheRoot 核实）：SA_FRONTEND_CACHE_DIR 整体改道优先，其次 $XDG_CACHE_HOME/sa/frontend，最后 $HOME/.cache/sa/frontend 仅源码文件 sha256；不含插件 / 编译器版本插件重编后，编译未改动的 .sla 会回放首次编译的产物，修复可以连续数轮看起来完全无效。删解析出的缓存根（默认 ~/.cache/sa/frontend；设了上面两个变量的机器按解析结果删）。需手动
3构建图缓存插件树内的 .zig-cache/ 与 zig-out/ Zig 构建图，含配置时捕获的优化模式构建或安装时若环境带 SA_PLUGIN_DEV=1， 构建图会记下 Debug 配置：插件 .so 膨胀（约 129 MB，而 ReleaseFast 约 37 MB）， 且此后直接 zig build 会 0 秒退出、什么都不重编。.zig-cache 与 zig-out 两者都删（只删其一不够），构建 / 安装用 env -u SA_PLUGIN_DEV。运行时仍需 SA_PLUGIN_DEV=1——构建与运行环境不同。需手动
4sa test 产物缓存各测试目录内的 .sa_cache/test/<hash>/artifact.sa.bc 测试源码哈希；不含编译器版本 sa test 回放旧编译器构建的 bitcode 产物；同一测试文件会因自身缓存持续失败或崩溃， 而字节相同的副本在别处却能通过。 删受影响测试目录内的 .sa_cache。需手动
5独立版 CLI 新鲜度缓存工作目录下的 .sla-cache/fresh/ （{stem}-{key}.bin 产物 + .json 清单；已按 sla-cli 现行源码 freshness.rs 核实） 文件路径 + 编译选项摘要 + 版本戳（cache-key 版本常量 + crate 版本号）；不含构建身份—— 同一版本号的重编不被区分编译管线直接返回缓存的 .sa 并整体跳过前端， 新编译器行为根本不会运行。删工程目录下的 .sla-cache/fresh/，或运行时带 SLA_NO_FRESHNESS_CACHE=1。该变量只覆盖这一个缓存面， 名字虽像总开关，但管不到 #1–#4、#6。需手动
6工程 / demo 目录产物缓存demo 与工程目录内的 .sa_cache/ （与 #4 同一存储、不同位置；可能在插件树之外）同 #4 build-exe 回放旧编译器留下的陈旧 artifact.sa.bc—— 曾让健康树上的金丝雀格子假红一整天。 金丝雀或门禁运行前，删 demo / 工程目录内的 .sa_cache。需手动

清理清单

按顺序执行。只扫描插件树会漏掉插件树外 demo / 工程目录里的 .sa_cache（#6）， 重建时还要去掉 SA_PLUGIN_DEV（#3）；以下清单已补全。

# 0. 按本机修改路径
PLUGIN="<sa_plugin_sla 树路径>"
ROOTS=("$PLUGIN" "<demo 根目录>" "<工程根目录>")   # 所有可能含 .sa_cache 的根目录

# 1. 插件树：宏索引 + 构建图（#1 #3）
rm -rf "$PLUGIN/.sla-cache" "$PLUGIN/.zig-cache" "$PLUGIN/zig-out"

# 2. 宿主前端缓存（#2）：默认路径如下；设了 XDG_CACHE_HOME / SA_FRONTEND_CACHE_DIR 的机器改删解析出的根
rm -rf ~/.cache/sa/frontend

# 3. 所有产物缓存（#4 #6）——插件树外也要扫
for r in "${ROOTS[@]}"; do
  find "$r" -type d -name .sa_cache -prune -exec rm -rf {} +
done

# 4. 重建并安装：构建环境去掉 SA_PLUGIN_DEV（#3）
(cd "$PLUGIN" && env -u SA_PLUGIN_DEV sa plugin install --dev .)

# 5. 装机确认（见同族陷阱第 1 条）：已装 .so 的 mtime / 大小已变，
#    且本轮新引入的字符串字面量能在 .so 内 grep 命中
ls -l "$HOME/.local/share/sa_plugins/installed/"
grep -c "<本轮新增的字符串>" "$HOME/.local/share/sa_plugins/installed/<插件 .so>"

# 6. 运行：运行环境需要 SA_PLUGIN_DEV=1；独立版 CLI 另加新鲜度开关（#5）
SA_PLUGIN_DEV=1 SLA_NO_FRESHNESS_CACHE=1 <你的命令>

同族陷阱（同属静默陈旧）

以下陷阱不是缓存面，但症状相同。每条末尾的「根治」为提案，未实现。

  • sa plugin install --dev 会吞构建错误。构建失败时它可以退出码 0 并保留旧 .so。装机后必须双确认：已装 .so 的 mtime / 大小已更新，且本轮新引入的字符串字面量 能在 .so 内 grep 命中。md5 要在装机静置后取，且只许在同一轮构建 → 装机内比对： 插件 .so 字节跨重编不可复现，跨轮 md5 比对没有意义。新机器上裸形式还可能要求显式路径： sa plugin install --dev .
    根治：构建失败时如实返回非零退出码并拒绝安装；新增 sa plugin info 显示已装插件的 build-id，替代 md5 / grep 判读。
  • dev 模式加载的是已安装插件，不是工作树。 sa sla check / test 跑的是 $HOME/.local/share/sa_plugins/installed/ 下的插件，只在树内改源码 + zig build 不会改变任何行为。任何 A/B 对照必须先把被测树装进该轮 HOME 并 md5 核对已装 .so。
    根治：启动时若已装插件与当前工作树不一致，打印提示；提供参数直接从工作树加载插件。
  • zig build test 会缓存成功运行。先前成功的一轮会被静默回放 （rc=0、日志为空、--summary all 下显示 run test cached）；失败不缓存， 所以这个陷阱很容易漏看。判读规则见下节「判读一次运行」。
    根治：在 build.zig 中把测试步骤标记为有副作用、每次真跑 待核实 对应 API 以项目所用 Zig 版本为准。
  • sa-std-static 归档新鲜度。zig build sa-std-static 不把 sa_std/*.sa 追踪为步骤输入，暖重编可能回放旧归档。新鲜度以归档 mtime / 大小变化 加行为复证判读，不以构建退出码判读。
    根治：在构建步骤中把 sa_std/*.sa 登记为输入文件。
  • SA_PLUGIN_DEV 构建与运行含义相反。构建时带它会记下 Debug 配置（#3），运行时却必须带它。
    根治：构建不读该环境变量，优化模式只由 -Doptimize 决定。

判读一次运行

一轮运行须同时满足四项才算真跑：rc=0；输出含预期结果行；失败名字集为空；双路特性两路都过。 rc=0 + 空日志不算一次运行。

何时清理

  • 任何编译器 / 插件源码改动之后、跑验证之前。
  • 金丝雀 / 门禁运行之前；门禁结果与树状态矛盾时作为调查第一步。
  • 两份相同源码行为不一致时——缓存不对称是头号嫌疑。
  • 装机或重编看起来毫无效果时。

根治路线（提案，未实现）

以下命令、变量与行为均为提案，当前工具链中不存在。目标：缓存是否陈旧由工具链确定，而不是靠人判读。

1. 缓存键加入工具链指纹

编译器与插件在构建时嵌入 build-id（例如 git 提交号 + dirty 标记，或 .so 哈希）。 所有缓存键改为「源码哈希 + 工具链 build-id」，宏索引另加分析器版本。换了编译器，缓存自动失效。

覆盖：#1、#2、#4、#5、#6。验收：重编插件后，未改动的源码首次编译必然未命中缓存。 落地后可删：通则中的「验证前先清全部缓存」、症状速查前三行、清理清单步骤 1–3 的大部分。

2. 统一的缓存命令

提案作用替代现在的
sa cache status列出全部缓存面的位置、大小与对应的工具链 build-id逐个记位置、手动查找
sa cache clean [--all]一条命令清掉全部缓存面，含插件树外的 .sa_cache清理清单步骤 0–3
SA_NO_CACHE=1一个开关关闭所有缓存只管 #5 的 SLA_NO_FRESHNESS_CACHE
SA_CACHE_TRACE=1命中缓存时打印缓存键与产物来源的 build-id，陈旧不再「静默」靠症状反推
sa plugin info显示已装插件的 build-id、构建时间、优化模式md5 / grep 字符串 / 看 .so 大小

3. 构建侧修复

即「同族陷阱」各条的「根治」项：install 退出码、构建不读 SA_PLUGIN_DEV、测试步骤每次真跑、sa-std-static 登记输入。

4. 缓存写入原子性 待核实

确认各缓存面写入是否「先写临时文件再改名」。若不是，中途中断会留下半个产物，并行测试同时写同一缓存也可能互相覆盖——这会成为另一类静默错误。

维护约定

  • 某项根治落地时，把缓存表「状态」列改为 已根治（版本），并在对应同族陷阱条目注明版本。
  • 当最低支持版本已包含该根治，删除对应行、症状速查条目与清理步骤，避免本章只增不减。
  • 新增缓存面时，必须同时补齐：位置、键（是否含工具链版本）、症状、清理方法、状态。
