反向可变性模型：默认可变、显式冻结

新特性预览 · 正在开发中。本章描述的是正在设计中的语法与语义 （SLA Reversed Mutability Model，2026-11-24 定名），尚未在任何已发布版本中实现： 本章示例均为设计语法，不能用现有编译器编译通过。规则细节仍在评审中， 定稿后本章将随实现一并更新。本章之外的其他章节描述的都是已实现的现状。

理念：把可变性模型反过来

Rust 的可变性模型是「默认不可变，显式声明可变」：绑定默认只读， 要修改必须标注 mut，写权限经 &mut 借用传递。 SLA 采用相反的声明方向——默认可变，显式声明不可变： 普通绑定与字段默认可写，只有需要保护的位置才标注约束。 这不是把 mut 换成 const，而是把整个可变性模型的声明方向反转。

场景SLA（反向模型）Rust
普通变量默认可变默认不可变
可变字段默认可变受绑定及借用规则约束
永久不可变字段const 字段（字段级语法）无完全对应的字段级语法
临时只读字段lock .&field（调用期共享只读租约）&T 借用
独占修改普通独占访问（所有权保证）&mut T
多任务共享读取lock .&field 计数式共享持有&T

声明反向，纪律同向。反转只发生在声明层（谁需要写标注）， 安全层不反转：别名纪律、所有权、字段冲突与并发访问检查与 Rust 同级， 由编译器负责。SLA 不为语法简洁牺牲别名安全保证。

这套模型要回答的核心问题是：能不能让内存安全不再要求初学者 首先理解一套复杂的可变性规则？Rust 的路线是先限制修改、再明确开放修改； SLA 的路线是先允许正常开发、再明确表达哪些地方不能修改。 Rust 强调让程序员显式管理可变性；SLA 强调让程序员显式声明不可变性， 同时由语言负责维护安全边界。这是两种不同的设计哲学。 一条红线：不为让 SLA 看起来简单，就把安全问题推给运行时或程序员—— 证明不了的访问，编译器必须响亮拒绝，而不是运行时兜底。

四条原则

  • 默认可变：不要求开发者声明 mut；SLA 没有 let mut。
  • 显式冻结：通过 const 保护永久不允许修改的字段。
  • 临时只读：通过 lock .&field 声明函数调用期间的共享只读权限。
  • 安全优先：编译器负责字段冲突、别名、生命周期和并发访问检查。

第一层：默认可变

struct User {
    const id: u64,
    name: String,
    age: u32,
}

fn update(user: User) {
    user.age += 1;   // 普通字段默认可写，无需任何标注
}

第二层：字段级永久不可变 const

const 写在结构体定义里、紧贴字段名之前，属于类型本身： 该字段在构造完成后永久不可写。构造有一个明确的封印点（seal）： 封印前可以写入（初始化），封印后对象才可以逃逸到其他任务。 冻结是传递性的：const profile: Profile 连同 profile 内部的 自有字段一并冻结，防止经嵌套对象绕过；但不横向蔓延到同级字段， 也不穿透引用/共享句柄指向的对象。确需在冻结对象内保留可变通道的字段， 使用内部可变类型（Cell / RefCell / Mutex）， 经其 API 访问——这是唯一的活口。别名、指针、方法调用均不得绕过 const， 检查在字段写入操作一级强制执行。

第三层：调用期临时只读 lock

lock 写在参数的类型内部，是对该绑定的访问权限描述： 它不产生指针、不创建新类型，只声明「本次调用期间，该字段路径只读」。 当前函数不得写入被锁路径（编译期按实际 store 检查，且该限制沿调用链向下传递： 被调用函数可能写被锁路径即报错）；其他任务可以同时读取； 其他任务要写入被锁路径必须等待全部持有释放（写者排队后新读者不得插队， 防止写者饥饿）。函数返回时自动释放，无需手动解锁。

fn inspect(a: Account(lock .&balance)) {
    print(a.balance);   // 只读，合法
    print(a.name);      // 未锁字段不受影响
}
语法语义
lock .&balance锁定单个字段
lock .&balance, .&name同时锁定多个字段
lock .&锁定整个对象（调用期整体只读）
lock .&profile.age锁定嵌套字段路径

锁定默认深及字段值的自有内部（如 balance 内部的 currency），到引用边界止步。路径之间按包含关系判断重叠： 锁父路径即覆盖其子路径；兄弟路径互不相交。动态索引路径第一版按整个数组处理。 建立 lock 视图即借出该路径：视图存续期间，原绑定对该路径的写权限挂起。 第一版附加两条硬规则：lock 租约不得跨越 await 或阻塞点（编译拒绝）； 持有读租约者禁止原地升级为写（须先释放再申请）。

多任务共享读取

当对象是共享句柄（经 Arc / channel 共享到多个任务）时， 多个任务可以同时以 lock 持有同一字段的只读租约并行读取； 租约计数由运行时在共享句柄上管理，从未被共享的对象零开销。 注意判据是字段的访问者集合，不是任务数量： 单个任务持有两个可写别名照样冲突，两个任务写不相交字段照样并行。

go inspect(shared_account);
go inspect(shared_account);
go inspect(shared_account);   // 三个任务同时读取 age/balance，互不阻塞

静态先行，动态兜底

实现分三层，成本递增、能静态解决的绝不留给运行时： （1）静态字段访问分析：编译器按函数汇总字段路径级读写集， 在 spawn 点证明两任务访问不相交（Bernstein 条件）时直接放行共享， const 字段的写集静态为空、读取天然无锁； （2）显式 lock 契约：签名声明的只读路径在编译期校验、 运行期以计数租约兜住跨任务写入； （3）动态自适应层（研究中）：静态证明不了的共享访问， 由运行时按（对象， 字段路径）维护访问状态——Adaptive Field Mutability， 属后续研究阶段，不在第一版范围内。

修订（已采纳的补充方案）：经共享句柄共享的对象，第（1）层不再作放行判据—— 改由补充方案的类型规则与入口加锁管辖；第（2）（3）层不变。

分层上，本特性只增加在 SLA 层（前端检查 + SLA 级运行时库， 建立在 SA 已有的原子操作、任务身份与同步原语之上）；SA 保持冻结： 不新增指令、不把字段语义塞进 SA；如需底层加强，优先增强验证器（Referee），不动 ISA。

为什么这对 AI 编程有利

约束面正比于危险面，不正比于代码面。Rust 的 mut 标注量 随代码总量增长（每个要改的绑定都要标）；SLA 的 const / lock 标注量 只随需要保护的字段数增长。AI 默认直接写业务逻辑， 安全约束只出现在真正重要的位置——既减少代码量，又让约束本身成为信息。

必须证明的五件事

本章的主张在以下五点被实现并验证之前都只是设计目标，缺一不可—— 这也是本章保持「预览」标记的原因：

  • 别名安全：任何别名都不能绕过 lock 与 const， 检查按对象身份与字段路径执行，不按变量名。
  • 跨函数安全：被调用函数不能偷偷修改已锁定的字段； 调用方的只读限制沿调用链向下一路生效，访问集未知即保守拒绝。
  • 异步安全：任务挂起、取消、异常退出时，临时只读租约必须可靠释放， 计数不泄漏、不悬挂。
  • 运行时成本：字段级并发控制不能让普通访问都付出原子操作成本； 静态可证明的访问零开销，未共享对象零开销。
  • 可证明性：在不依赖 GC 的前提下，编译器能证明生命周期与内存安全； 这是 SLA 最值得坚持的原则。

补充方案：sync 字段（已采纳，v2）

已采纳（2026-11-24）；同日修订为 v2。本节是本章模型的补充部分，示例同为设计语法。 一句话：保留「默认可变 + const 冻结」，在字段上新增 sync 修饰表达「允许并发写」； 加锁范围、读写模式、阻塞性全部由编译器从语法唯一推出，无法判定即编译报错； lock .&field 保留为可选的只读契约声明。本节与本章第一版范围有三处实质差异， 以下三处以本节为准（第一版范围相应修订）：（1）经共享句柄可达的对象不再一律只读—— 除 Mutex / 原子等内部可变通道外，新增 sync 字段这一条语言级并发写通道； （2）不再以静态字段访问分析（spawn 点 Bernstein 不相交证明）作为共享放行判据，改为下述类型规则， 代价是同一共享对象上写不相交字段的两个任务不再并行（整对象一把锁）； （3）加锁函数在 v1 即在入口真实加锁（未共享对象的零开销推迟到 v2 双份编译），并新增 panic 中毒语义。 本节对检查器现状的描述依据帮助文档（所有权与借用、goroutine 运行时等章） 以及对 Rust 版检查器源码的阅读（check_spawn_guard.rs、check_go.rs、check_borrow_origin.rs）——仅阅读，未编译验证； 下文 6.1 的前置缺陷 F1–F3 为待核实主张，验证程序见附录 A。

字段三态

struct Account {
    const id: u64,          // 永久冻结：构造封印后不可写
    sync  balance: i64,     // 允许并发修改：只能在加锁函数中访问
    sync  total_in: i64,
    sync  total_out: i64,
    name: String,           // 默认：被共享期间只读
}
修饰含义被任务共享时
（无）默认可变所有人只读；写入即编译报错
const永久不可变随时可读，无锁
sync可变、允许并发只能在编译器推断出的加锁函数中读写

可选 lock 契约：不写时由编译器推断；写了即成为 API 契约， 实现中出现对应路径的写入即编译报错，推断结果与声明不一致也报错。 函数是否阻塞由编译器沿调用链精确推断；可显式写 noblock 固定契约， extern fn ... noblock 是唯一需要信任的声明，与 unsafe 同级，是代码中可见的信任边界。

fn inspect(a: &Account(lock .&balance)) -> i64 {   // 可选：锁定「只读 balance」契约
    a.balance
}

extern fn crc32(p: ptr, n: u64) -> u32 noblock;   // 信任边界
trait Hasher { fn hash(&self) -> u64 noblock; }    // 每个实现都会被检查

八条规则（R1–R8）

  • R1 字段三态：每个字段恰好处于默认、const、sync 之一。 sync 字段可以是任意类型（含 String、Vec 等带堆内存类型），因为本方案只有悲观加锁一种模式，无需回滚。
  • R2 被共享时默认字段只读——以 Arc 为唯一判据：对象放入 Arc 即视为被共享（永久）， 所有持有者对其默认字段只能读。现有检查已禁止借用跨越任务边界（go 的 GoBorrowPayload、 thread::spawn 的 BorrowEscape），因此在安全代码中 Arc 是跨任务共享的唯一途径，共享与否由类型唯一确定。 不做静态字段访问分析——原方案依赖「证明两任务访问不相交」，结论取决于分析精度，属于「靠猜」，本方案改为类型规则。 裸指针不在保证范围内：把 Box 转成裸指针交给 goroutine 属于所有权转移（发送方此后不再访问），是现有规则认可的用法； 两边同时经裸指针访问则与 unsafe 同级，由使用者负责。
  • R3 加锁范围由语法唯一确定：一个函数直接读写了 sync 字段，即成为加锁函数。 被访问字段所在对象必须从起点出发、只经过 const 字段可达；起点为函数参数以及全局 static； 这些对象构成加锁集合：只读 → 读锁；任一写入 → 写锁；访问 const 集合中的元素 → 锁该集合全部元素。 锁覆盖对象的自有内部（内联字段、Box），到引用边界为止，与本章 lock 的深度规则一致； 递归遍历树结构无需逐节点加锁。未共享的局部对象在放入 Arc 之前可直接读写其 sync 字段、不加锁， 保证初始化与单线程代码零标注。推断结果写入接口元数据，IDE 悬停可见。在函数内按 ID 查对象再写其 sync 字段会被拒绝 （如 bank.find(id).balance -= 1）——改法是在调用方查好、作为参数传入。
  • R4 持锁函数不能阻塞：加锁函数及其调用链中不得出现阻塞点。阻塞点集合与 goroutine 运行时一致： 通道 send / recv / select（timeout(0) 与 default 分支除外）、join、sleep、网络等待、Mutex 加锁、yield，以及 .await。 每个函数的阻塞性沿调用链精确推断，pub 函数写入接口；由 noblock 变为阻塞视为不兼容变更。 extern 与 dyn 默认阻塞，除非声明 noblock。本方案需新增调用链阻塞性分析 pass，作为 R4 的基础。 前提：sa_std 内存分配器须为 noblock，否则加锁函数内拼接 String、Vec::push 都会被拒 （待核实，见待决问题）；std 另提供 noblock 的缓冲日志，用于持锁时调试输出。 IDE 提供「提取为加锁函数」重构，处理最常见的 R4 报错（如 worker 循环里 recv 之后直接改 sync 字段）。
  • R5 不能嵌套加锁：被调函数的加锁集合必须是调用方已持有集合的子集， 且模式不高于调用方（读锁内不能调用需写锁的函数）。满足时直接沿用，不再申请；不满足即编译报错。 由此每个任务同一时刻只有一个获取点，破坏死锁必要条件中的「持有并等待」。
  • R6 禁止先查后改：源自 sync 字段的值被用作参数或条件、传给需要写锁的函数， 且同时满足以下条件时编译报错：调用方本身未持有该对象的锁（持锁函数内调用只读辅助函数再写回，不检查）； 读与写作用于同一变量路径（读 a、写 a；读 A 写 B 不检查）； 「源自」按数据依赖判定，并穿过函数调用与 .await——函数返回值一律视为依赖其全部实参 （不分析函数体，结论确定）。改法是合成一个函数，在同一次加锁中完成。 检查范围写入规范：只追踪函数体内局部变量的数据依赖；不追踪经堆存储的值； 不追踪控制依赖（如「按余额选出账户再写」）；不追踪不同变量在运行时指向同一对象。 范围外属业务一致性——不检查，也不发出警告。代价：withdraw(a, amt + calc_fee(balance(a))) 也会被拒， 改法是把手续费计算移入 withdraw。
  • R7 出错退出：加锁函数内 panic 时，运行时释放其全部锁，并将被写锁的对象标记为中毒； 之后访问中毒对象的加锁函数返回错误，需人工或监督任务恢复。这是确定的运行时行为，不属于「猜」。
  • R8 async 函数不能直接访问 sync 字段：调用 async 函数只创建 future， 函数体在被 poll 时才执行，加锁时机与调用点脱节，R5 的调用点检查随之失效。 因此 async 函数体内直接读写 sync 字段即编译报错，访问须提取为普通函数。 可选 lock 契约写在 async 函数上：锁的是 sync 字段 → 与 R8 冲突，报错； 锁的是默认字段 → 仅为编译期只读承诺，可跨 await。 加锁函数内不可能出现 .await（R4），future 永远不会在持锁时挂起或被丢弃，取消、丢弃 future 不会泄漏锁—— 本章「异步安全」一项由结构保证。在系统线程上运行的执行器获取锁时可能短暂阻塞，但不会死锁： 获取时不持有其他锁（R5），持锁方不挂起（R4），等待有上限。

运行时语义

  • 获取：函数入口对加锁集合按对象身份排序，一次全部获取；同一对象出现多次合并为一把，读写冲突升级为写锁。
  • 释放：函数返回（含 panic 路径）时释放。
  • 公平：写者排队后新读者不得插队，防止写者饥饿。
  • 粒度：每个对象一把锁，覆盖其全部 sync 字段及自有内部（自动成组，跨字段不变量天然一致）。
  • 实现：复用 sa_std 现有 park queue（与 RwLock 同源），等待时挂起而非自旋；须先修复 F3（见 6.1）。
  • 开销：v1 加锁函数一律加锁；无争用时约一次原子操作；未出现 sync 字段的对象零开销。
  • 内存模型：一次锁释放 synchronizes-with 同一对象上的下一次获取；释放前对 sync 字段的全部写入，对后续获取者可见。

与现有特性的关系：go 参数规则——现有检查要求被调函数须为具名普通函数（非 async）， 仅一个参数且为一个字长（标量、指针、Chan），借用不得跨越；共享状态装入结构体、Box::new 后以指针传入。 thread::spawn——闭包不得借用、写入外层变量（BorrowEscape）；Arc 克隆与 future 可移入（见 F1）。 持锁函数不阻塞（R4）即不让出，协作式调度下锁占用时长只取决于计算量，可预估； 监督 / recover 后进程继续，故 R7 的释放 + 中毒必须保留；async 中 .await 属于阻塞点（R4）， async 函数不直接访问 sync 字段（R8）；跨 async fn 边界的嵌套 await 已支持（帮助文档尚未同步更新）； Arc 负责生命周期，也是「被共享」的唯一判据（R2），sync 只负责并发写权限； Chan 发送普通 T 为所有权转移，无需锁，通道互等死锁不在本方案范围，交给运行时死锁检测； 在加锁函数内调用 Mutex 加锁属阻塞点（R4 拒绝），持有 Mutex 时调用加锁函数编译报错，避免混合成环； 两边同时经裸指针访问不在保证范围内，与 unsafe 同级。 本方案只改 SLA 前端检查与 sa_std 运行时库，不新增 SA 指令（SA 冻结）。

完整示例：并发转账

4 个工作任务处理 1000 笔转账请求，1 个审计任务定期核对，结束时检查总额守恒。 v2 示例已按现有 go 规则改写：共享状态经 Arc，任务参数为指向 Box 上下文的单个指针。 全程只有 3 个 sync 标注，worker、auditor、main 均无并发标注。 select 分支、Box::from_raw、random_tx 等写法为示意，以 SLA 实际语法为准； 若 Chan 句柄为移动语义，构造上下文时改为复制或克隆句柄。

struct Account {
    const id: u64,
    sync balance: i64, sync total_in: i64, sync total_out: i64,
    name: String,
}
struct Bank      { const accounts: Vec<Account> }
struct WorkerCtx { bank: Arc<Bank>, reqs: Chan<TxReq>, res: Chan<TxRes> }
struct AuditCtx  { bank: Arc<Bank>, n: i64, done: Chan<u64> }
const INIT: i64 = 1000;
const N_TX: u64 = 1000;

// 加锁函数：入口写锁 {x, y}，同一账户自动合并
fn transfer(x: &Account, y: &Account, amt: i64) -> Result<(), TxErr> {
    if x.balance < amt { return Err(Insufficient); }
    x.balance -= amt;  x.total_out += amt;
    y.balance += amt;  y.total_in  += amt;
    Ok(())
}
// 加锁函数：入口读锁 {a}
fn check_one(a: &Account) { assert(a.balance == INIT + a.total_in - a.total_out); }
// 加锁函数：入口读锁 bank.accounts 全部元素 → 全行一致快照
fn total(bank: &Bank) -> i64 {
    let sum = 0;
    for a in bank.accounts { sum += a.balance; }
    sum
}

fn worker(p: *WorkerCtx) {
    let c = Box::from_raw(p);                       // 取回上下文所有权
    loop {
        let (r, closed) = c.reqs.recv();            // 阻塞点，未持锁
        if closed { break; };
        let out = match (c.bank.find(r.from), c.bank.find(r.to)) {
            (Some(x), Some(y)) => transfer(x, y, r.amt),
            _ => Err(NoAccount),
        };
        c.res.send(TxRes { tid: r.tid, ok: out });  // 阻塞点，锁已释放
    }
}

fn producer(reqs: Chan<TxReq>) {                    // Chan 为一个字长，可直接传
    for t in 0..N_TX { reqs.send(random_tx(t)); };
    reqs.close();
}

fn auditor(p: *AuditCtx) {
    let c = Box::from_raw(p);
    loop {
        select {
            c.done.recv() => return,
            timeout(10ms) => {
                for a in c.bank.accounts { check_one(a); }   // 逐个加锁
                assert(total(&c.bank) == c.n * INIT);       // 一次全锁
            }
        }
    }
}

fn main() -> i32 {
    let n = 100;
    let bank = Arc::new(Bank { accounts: make_accounts(n, INIT) });
    // make_accounts 在放入 Arc 前直接初始化 sync 字段（R3）
    let reqs: Chan<TxReq> = Chan::new(64);
    let res:  Chan<TxRes> = Chan::new(64);
    let done: Chan<u64>   = Chan::new(0);
    let hs = vec();
    for _ in 0..4 {
        let ctx = Box::new(WorkerCtx { bank: bank.clone(), reqs: reqs, res: res });
        hs.push(go worker(Box::into_raw(ctx)));
    }
    let actx = Box::new(AuditCtx { bank: bank.clone(), n: n, done: done });
    let ha = go auditor(Box::into_raw(actx));
    let hp = go producer(reqs);
    let ok = 0;
    for _ in 0..N_TX {                               // 请求数已知，无需关闭结果通道
        let (r, _) = res.recv();
        if r.ok.is_ok() { ok += 1; };
    }
    done.send(1);
    for h in hs { sa_task_join(h); };
    sa_task_join(ha); sa_task_join(hp);
    assert(total(&bank) == n * INIT);               // 总额守恒
    println("{}", ok);
    return 0;
}

会被编译拒绝的写法：

写法规则
go worker(&bank, reqs, res)现有检查：参数多于一个、借用跨越 goroutine
transfer 中插入 log.send(..)R4 持锁阻塞
transfer 调用的函数里间接 sleepR4 调用链阻塞
main 中 bank.accounts[0].name = "x"R2 Arc 内对象默认字段只读
a.id = 5R1 const 字段
total() 中调用 transferR5 读锁内需要写锁

忘记写 sync 只会编译报错，不会悄悄出错：单线程代码与只读共享都不需要 sync； 只有「被共享又要写」时编译器才要求。报错同时指出三处：写入位置、放入 Arc 的位置、字段定义， 并给出固定改法（改成 sync、在放入 Arc 之前完成写入、或不放入 Arc、经通道转移所有权交给单任务独占）。 无法给第三方结构体加 sync 时，标准做法有两种：用自定义结构体以 sync 字段包装它； 或交给单个任务独占，其他任务经通道发送修改请求。心智模型一句话： 共享的东西要改就写 sync，相关函数按编译器提示拆小——四个习惯： 改 sync 字段的函数短小、不含 print / send / .await；要改的对象作为参数传入； 先查后改写在同一函数中；在 async 函数里把对 sync 字段的访问提取成普通函数 （R8，async 代码最常见的报错，IDE 可一键提取）。

保证范围、代价与待决问题

问题结论
数据竞争✅ 编译期全部拦截
锁之间的死锁✅ 编译期全部拦截（R5 + 入口排序）
持锁时阻塞✅ 编译期全部拦截（仅信任 extern noblock 声明）
future / 闭包携带借用跨任务⚠️ 依赖前置修复 F1、F2（见 6.1）
先查后改⚠️ 同一函数体内的数据依赖（穿过调用与 await），范围写入规范（R6）
经裸指针跨任务同时访问❌ 不在保证范围，与 unsafe 同级
通道之间互相等死❌ 不检查，交给运行时死锁检测
跨字段、跨阻塞点的业务一致性❌ 不检查，使用冻结 + 线性凭证模式

代价：会拒绝部分其实安全的代码。每类拒绝都有固定改法，编译器可直接提示： 在函数内按 ID 查对象再写 sync 字段 → 调用方查好后作为参数传入； 读锁函数内调用写锁函数 → 外层改为写锁函数，或拆开调用； 加锁函数内打日志 / 发消息 → 改用 noblock 缓冲日志，或把阻塞操作移到加锁函数返回之后； 需要锁的对象数量运行时才确定 → 放入 const 集合（整体加锁），或改用通道交给单任务处理； async 函数内直接访问 sync 字段 → 提取为普通函数（R8）； withdraw(a, amt + calc_fee(balance(a))) → 把依赖余额的计算移入 withdraw； 在闭包 / 迭代器适配器中访问 sync 字段 → 改写为 for 循环（v2 评估为 std 适配器标注元素来源）。

被否决的备选方案否决理由
Shared<T> + lock/excl + 锁组（共享写进类型、租约写进签名）用户概念过多，标注遍布签名；其运行时机制保留并转为编译器推断
STM atomic 块（参考 Haskell）大块包裹违背设计原则；有日志与重跑开销
隐式段边界 + 乐观执行（阻塞点之间自动成事务）引入重跑、撤销日志、串行模式、版本号等，复杂度反超 Shared；边界不可见
静态字段访问分析结论取决于分析精度，属「靠猜」，改为 R2 类型规则
go 借用捕获 + 自动 join允许 go f(&a)、函数返回前自动 join，与现有「借用不跨任务」规则冲突；改为以 Arc 为唯一共享判据

// F1：future 携带借用跨线程
async fn bump(v: &i32) -> i32 { *v += 1; return *v; }
fn main() -> i32 {
    let n = 100;
    let fut = bump(&n);                         // future 内藏 &n
    let h = thread::spawn(^|| block_on(fut));   // 守卫只看到 fut，不是借用

    h.join();
    return 0;
}

    n = 0;                    // 应报错：fut 仍持有 &n
