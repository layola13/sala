Release 与 npm 发布

本章把「本机构建成功」推进到「用户可直接安装」：先产出 6 平台二进制， 再发 GitHub Release，最后按依赖顺序发布 npm 包。示例版本为 sa 0.1.8 / sla 0.1.8，命令中的 <VER>、<SLAVER> 替换成当次版本号 （裸版本号，不带 v）。两个仓库按同一版本线发布，但仍是独立 npm 包：sla 用精确 pin 依赖同代 sa，版本号不能靠 ^ 漂移。

版本号一致性

发版前先把所有会写进产物的版本号对齐；漏一处就会出现 「包是新的、二进制还是旧版」或 npm 依赖解析到旧平台包。

仓库必须同步的位置
scibuild.zig.zon 的 .version； npm/packages/*/package.json（7 个：6 个平台包 + meta 包）； git tag；Release 资产名
sa_plugin_slabuild.zig 的默认 sla_version；npm/packages/*/package.json（7 个）； meta 包的 optionalDependencies；meta 包对 @salang/sa 的精确依赖；fetch-*-binaries 的默认版本； npm/README.md；git tag；Release 资产名
# 构建机预检：6 个平台二进制是否都已 stage（缺文件则非零退出）
cd sci && sh npm/tools/check-versions.sh
cd sa_plugin_sla && sh npm/tools/check-sla-versions.sh

# 依赖关系必须精确 pin，不能出现 ^ 或跨版本
node -p "require('./sci/npm/packages/sa/package.json').version"
node -p "require('./sa_plugin_sla/npm/packages/sla/package.json').dependencies['@salang/sa']"

sla 的 meta 包依赖 @salang/sa 的同一代 编译器（例如 0.1.8），因为 sla build-wasm 需要 sa 具备 LLVM-C；因此发布顺序永远是 sa 先、sla 后。

1. 构建 6 平台产物

Linux x86_64 原生构建默认启用 LLVM-C（需 llvm-14-dev）， 产物可完整支持 build-wasm；交叉目标用 -Dllvm=false 走 bootstrap，体积小但 wasm 只能走 C 回退。显式传 -Dversion，这样 tag 早晚都不影响二进制内嵌版本。

cd sci

# Linux x86_64（LLVM 启用；放最后构建，避免 artifacts 被交叉构建覆盖）
zig build -Dversion=<VER> -Doptimize=ReleaseSafe \
  -p /tmp/sa-dist/linux-x86_64

# 交叉目标（bootstrap）
zig build -Dtarget=aarch64-linux-gnu -Dllvm=false -Dversion=<VER> \
  -Doptimize=ReleaseSafe -p /tmp/sa-dist/arm-aarch64
zig build -Dtarget=aarch64-macos -Dllvm=false -Dversion=<VER> \
  -Doptimize=ReleaseSafe -p /tmp/sa-dist/mac-aarch64
zig build -Dtarget=x86_64-macos -Dllvm=false -Dversion=<VER> \
  -Doptimize=ReleaseSafe -p /tmp/sa-dist/mac-x86_64
zig build -Dtarget=x86_64-windows-gnu -Dllvm=false -Dversion=<VER> \
  -Doptimize=ReleaseSafe -p /tmp/sa-dist/windows-x86_64

# FreeBSD（需要 sysroot，见 FreeBSD 章节）
SA_VERSION=<VER> sh tools/build_freebsd.sh --prefix /tmp/sa-dist/freebsd-x86_64

sla 的每个平台构建都要指向同平台 sa 标准库目录；交叉构建漏了 -Dsa-std-dir 会链接到宿主机库。

cd sa_plugin_sla
for t in linux-x86_64 arm-aarch64 mac-aarch64 mac-x86_64 windows-x86_64 freebsd-x86_64; do
  zig build -Dversion=<SLAVER> -Doptimize=ReleaseSafe \
    -Dsa-std-dir=/tmp/sa-dist/$t/lib -p /tmp/sla-dist/$t
done

# 冒烟：只有 Linux / 当前主机产物能直接执行
/tmp/sla-dist/linux-x86_64/bin/sla --version        # sla <SLAVER>
/tmp/sa-dist/linux-x86_64/bin/sa --version          # sa <VER>
file /tmp/sla-dist/windows-x86_64/bin/sla.exe       # PE32+
file /tmp/sla-dist/mac-aarch64/bin/sla              # Mach-O arm64

2. 打包 Release 附件

附件名是 fetch-*-binaries 的硬契约，不能改名： sa-<VER>-<target>.zip 与 sla-<SLAVER>-<target>.zip。sa 的 zip 至少含 sa/sa.exe，建议连 hubproxy 一起带； sla 的 zip 含 bin/ 与 lib/（插件库和 sap.json），拉取脚本会从任意路径里取 sla/sla.exe。

cd /tmp/sa-dist
for d in linux-x86_64 arm-aarch64 mac-aarch64 mac-x86_64 \
         windows-x86_64 freebsd-x86_64; do
  (cd "$d/bin" && zip -q "/tmp/sa-<VER>-$d.zip" sa* hubproxy*)
done

cd /tmp/sla-dist
for d in linux-x86_64 arm-aarch64 mac-aarch64 mac-x86_64 \
         windows-x86_64 freebsd-x86_64; do
  (cd "$d" && zip -qr "/tmp/sla-<SLAVER>-$d.zip" bin lib)
done

unzip -l /tmp/sa-<VER>-windows-x86_64.zip   | grep -E 'sa\.exe|hubproxy'
unzip -l /tmp/sla-<SLAVER>-windows-x86_64.zip | grep -E 'sla\.exe|sla\.dll'

3. 提交、打 tag、发 GitHub Release

cd sci
git add build.zig.zon npm/packages <本次源码文件>
git commit -m "release: sa <VER>"
git tag -a <VER> -m "SA <VER>"
git push origin main <VER>          # 需要可写 token

GH_TOKEN="$GIT_TOKEN" gh release create <VER> /tmp/sa-<VER>-*.zip \
  --repo layola13/sci --title "SA <VER>" --notes "..."

cd sa_plugin_sla
git add build.zig npm sap.json src
git commit -m "release: sla <SLAVER>"
git tag -a <SLAVER> -m "SLA <SLAVER>"
git push origin master <SLAVER>

GH_TOKEN="$GIT_TOKEN" gh release create <SLAVER> /tmp/sla-<SLAVER>-*.zip \
  --repo layola13/sa_plugin_sla --title "SLA <SLAVER>" --notes "..."

tag 推送后检查附件是否为 6 个 zip，并抽查一个 URL 返回 200； fetch 脚本直接拼这个 URL，缺附件会在发布机上 404。

4. npm 发布（Windows 11 实机流程）

Windows 发布机不需要重新编译，只从 Release 拉取已构建二进制。 脚本门槛是 PowerShell 5.1（Win11 自带）或 7 均可；当前脚本已去掉 7.0 硬性限制并显式启用 TLS 1.2。

4.1 登录与预检

cd E:\projects\sla\sci
git pull
npm login
npm whoami        # 必须是有 @salang / @slalang 发布权限的账号

4.2 先发 @salang/sa（逐包发布）

cd E:\projects\sla\sci\npm
powershell -ExecutionPolicy Bypass -File tools\fetch-binaries.ps1
# 默认 <VER>；版本不同则加 -Version <VER>
# 输出 [ok] all platform binaries staged under npm/packages/*/bin

cd packages
cd sa-linux-x64;     npm publish --access public
cd ..\sa-linux-arm64; npm publish --access public
cd ..\sa-darwin-arm64; npm publish --access public
cd ..\sa-darwin-x64;  npm publish --access public
cd ..\sa-win32-x64;   npm publish --access public
cd ..\sa-freebsd-x64; npm publish --access public
cd ..\sa;             npm publish --access public

一次只发一个包，确有失败时能立刻停在上一个成功点。顺序固定为 6 个 @salang/sa-<platform> 在前、@salang/sa meta 包在最后；每个 scope 包都要带 --access public。

4.3 再发 @slalang/sla（逐包发布）

cd E:\projects\sla\sa_plugin_sla
git pull
cd npm
powershell -ExecutionPolicy Bypass -File tools\fetch-sla-binaries.ps1
# 默认 <SLAVER>；同时把 sla_std/ 拷进 meta 包

cd packages
cd sla-linux-x64;     npm publish --access public
cd ..\sla-linux-arm64; npm publish --access public
cd ..\sla-darwin-arm64; npm publish --access public
cd ..\sla-darwin-x64;  npm publish --access public
cd ..\sla-win32-x64;   npm publish --access public
cd ..\sla-freebsd-x64; npm publish --access public
cd ..\sla;             npm publish --access public

不要用循环/批量脚本一口气发：一旦某个平台包已存在同版本，npm 会返回 403 并中断，后面的包状态难以判断。逐包执行时，失败后从下一个未发的包继续。

4.4 可选写法与 2FA

# 已安装 PowerShell 7：脚本命令把 powershell 换成 pwsh
pwsh -File tools\fetch-binaries.ps1

# 账号强制 2FA：给每条 npm publish 追加 OTP
npm publish --access public --otp=123456

5. 发布后验证

npm view @salang/sa version
npm view @salang/sa-linux-x64 version
npm view @slalang/sla version
npm view @slalang/sla-linux-x64 version

# 干净目录安装，验证 launcher + 平台包 + sa 依赖链
mkdir %TEMP%\sla-npm-test
cd /d %TEMP%\sla-npm-test
npm init -y
npm i @slalang/sla
npx sa --version
npx sla --version
npx sla help

再跑一次最小构建（Windows 上 build-wasm 会走 C 回退， build-c 与 build-js 正常）：

npx sla build-c demo.sla -o demo.c
npx sla build-js demo.sla -o demo.js
npx sla build-wasm demo.sla -o demo.wasm   # 仅 C 回退覆盖的语法

6. 常见坑

现象原因 / 处理
script cannot be run because it contained a "#requires" statement for Windows PowerShell 7.0 用了旧脚本或旧 checkout：git pull 后重跑；新脚本为 #Requires -Version 5.1，也可改用 pwsh
The argument 'npm\tools\...' to the -File parameter does not exist 当前目录已在 npm 里，路径别再带 npm\； 从 npm 目录用 tools\fetch-binaries.ps1
Invoke-WebRequest 连接被关闭 PS 5.1 未启用 TLS 1.2；脚本已设置，仍失败则升级 PowerShell 7
403 Forbidden / E404（scope 包） 账号不在 @salang/@slalang 组织，或首次发布漏了 --access public（脚本已带）
npm ERR! 403 ... You cannot publish over the previously published versions npm 版本不可覆盖。已发过 <VER> 就递增 patch 后重走全流程， 不要只改 tag；也不要只给已发过的平台包换版本，7 个 sla 包必须同版
安装后 @slalang/sla 报平台包缺失 平台包没先发，或 meta 的 optionalDependencies 与本次版本不一致； 先发 6 个平台包再发 meta
libLLVM-14.so.1: cannot open shared object file（Linux） 0.1.8 Linux 资产动态链接 LLVM 14：用户装 llvm-14/libllvm14t64，或把 libLLVM-14.so.1 一起放进平台包 bin/； check-versions.sh 会对此告警
macOS/Windows 上 build-wasm 报 LLVM-C 不可用 这两个平台的官方资产是 -Dllvm=false bootstrap；需完整 wasm 就在本机装 LLVM 14 后原生构建，或使用 C 回退支持的子集
Windows 解压后 bin/sla 没有执行位 launcher 在 spawnSync 前自动 chmod 0755； 不要绕过 sla 命令直接执行二进制
artifacts/sa_std/libsa_std.a 出现在 diff 里 构建副作用；仅验证时 git checkout -- artifacts/sa_std/libsa_std.a 还原， 要随版本发布则显式提交并说明

7. 一条龙清单

  1. 对齐版本号 → check-versions.sh / check-sla-versions.sh 预检。
  2. 构建 6 平台 sa（Linux 最后、LLVM 启用）→ 构建 6 平台 sla。
  3. 打 6+6 个 zip，抽查 Windows/Linux 条目。
  4. 提交、打 tag、推送；创建两个 GitHub Release 并确认 12 个附件。
  5. Win11：git pull → npm login → fetch sa → 逐包发 sa。
  6. Win11：fetch sla → 逐包发 sla（务必在 sa 之后）。
  7. npm view + 干净目录安装 + npx sla help + 最小构建回归。
  8. 文档同步：本章与 sci/docs/release_process_cn.md 的版本/命令保持一致。
