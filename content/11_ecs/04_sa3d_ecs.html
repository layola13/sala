The SA-Level 3d_ecs Plugin Contract

This page introduces the 3d_ecs.sal contract provided by sa_plugin_3dengines/sa_plugin_3d_ecs: layout constants, query access flags, and the SA function surface. After reading it you will be able to use these #def definitions and function names correctly at the SA assembly level.

WarningThis is something at another layer. sa_plugin_3d_ecs is an SA contract plugin (a member of the 3D engine plugin family, providing ABI constants and SA functions); sla_ecs, by contrast, is an SLA application-layer library. There is no basis for a merged narrative of a calling relationship between the two; do not treat the SA3D_ECS_* constants as the API of sla_ecs, and do not assume that the SLA-layer TableErased combination family depends on this .sal.

The family README positions it as “ECS ABI, lowest-priority behavior pending” — i.e. the layout contract has taken shape, while the behavior surface has the lowest priority in the family. At the same time, the README’s completion threshold explains: layout constants alone do not constitute a complete module; each module also needs callable behavior and behavior tests bound to the responsibilities of the nearest Bevy crate.

Function Surface

3d_ecs.sal has 40 SA functions in total, with signatures of the form:

@sa3d_ecs_entity_id_init(&entity: ptr, index: i64, generation: i64) -> void:

All function names start with @sa3d_ecs_; the table below only lists the remainder after removing that prefix, grouped by purpose:

  • EntityId: entity_id_init, entity_id_get_index, entity_id_get_generation, entity_id_equal;
  • Constructors: component_desc_init, query_term_init, query_desc_init, world_desc_init, world_state_init / world_state_init_with_free_list;
  • Access-flag predicates: query_access_is_data, query_access_is_required_data, query_access_has_write, query_access_reads_all, query_access_writes_all, query_access_is_filter, query_access_is_valid;
  • Conflict determination: query_terms_conflict, query_term_write_overlaps_read, query_term_requires_with, query_term_is_without, query_desc_has_required_with, query_desc_has_without, query_descs_have_data_conflict, query_descs_filters_disjoint, query_desc_has_filter_terms, query_desc_set_has_with, query_desc_set_has_without, query_filter_sets_ruled_out, query_descs_filters_dnf_compatible, query_descs_filters_dnf_compatible_for_a_set, query_descs_compatible, query_desc_validate;
  • world behavior: world_desc_get_entity_capacity, world_desc_has_components, world_state_get_alive_count, world_state_get_dead_count, world_spawn, world_contains_spawned, world_despawn.

The conflict-determination group is the core value of this contract: given two QUERY_DESC values, it can determine whether data accesses conflict and whether filter sets are mutually exclusive (including combination judgments in DNF form), which is exactly the read/write mutual-exclusion basis needed when scheduling systems in parallel.

Tests

tests/3d_ecs_layout_test.sa contains 10 @test functions; it imports the contract via @import "../3d_ecs.sal", allocates with alloc SA3D_ECS_*_SIZE according to the constants, and then asserts field by field; failure paths use the panic(31xx) series of error codes. This is a direct example for verifying “layout constants are consistent with function behavior”.

NoteHow to write ECS systems at the SLA application layer and how queries are combined belongs to the topic of sla_ecs Architecture; the constants and functions on this page are only used when directly writing or reviewing SA assembly, and when checking engine plugin ABIs.
