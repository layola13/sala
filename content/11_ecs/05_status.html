Known Issues and Regression History

This page collects the sla_ecs-related defects and regressions recorded in the sa_plugin_sla documents: three fixed issues, the Module Table real-project retest, and dated performance micro-observations. After reading it you will understand the basis and current status of these records.

WarningAll performance numbers are uncalibrated development-process observations, from current_plan.md and the regression issue documents, in an environment of a local sla-local-cli or the installed dev plugin. The documents themselves state multiple times that “there is noise between samples” and “it cannot be claimed on this basis that a latency target is closed”. These numbers may only be used for order-of-magnitude judgments and must not be cited as benchmark conclusions.

issue035: UseAfterMove from a Repeated Field Load in the Rescan Summary

  • Date / status: 2026-07-16, fixed and verified.
  • Symptom: the generated-SA backend reported error[UseAfterMove] when compiling the focused ready-batch rescan test (function @sla__ecs_executor_ready_batch_rescan_summary_deep3, register tmp_3969); the default backend and sa sla check both passed — the fault is in SLA SA text code generation, not in ECS scheduling behavior itself.
  • Downstream reproduction: tests/test_ecs_lib_executor_multi_threaded_deep_isolated.sla, filtered case mt_deep_ready_batch_rescan_records_three_skipped_slots.
  • Root cause: SA text field lowering treated the generated register name as an ownership heuristic; an assigned aggregate local variable may resolve to a tmp_* register, but it is still a local binding and should not be released after every field projection. It shares the same field-base lifetime root cause as issue034.
  • Fix: src/lowering_rules.zig added the shared rule fieldBaseResultNeedsRelease() — when a generated tmp_* register is the resolved binding of an identifier it is kept alive, while a genuine temporary field base is released as before; src/codegen.zig uses this rule in three places: tuple fields, manually dropped struct fields, and ordinary struct fields.

issue038: UseAfterMove from a Stack-Slot Aggregate Call in Scope Completion

  • Date / status: 2026-07-16, fixed.
  • Symptom: the default / direct-SAB backends reported error[UseAfterMove] on the focused scope-completion test (register sla__ecs_scope_completion_complete_pending_at_i32__param_0_queue); sa sla check succeeded. The same defect also reproduced in earlier scope-completion tests, showing it is unrelated to the newly introduced panic/catch cases.
  • Downstream reproduction: lib/task_scope_completion.sla, filtered case scope completion pending first task blocks result drain.
  • Minimal reproduction shape: pass a QueueState containing two Vec fields to a read-only helper, then continue reading and writing the original aggregate; direct SAB emitted @sla__queue_len(^sla__complete_pending__param_0_queue), and the move-prefixed call consumed the parameter early.
  • Root cause: direct-SAB call lowering can preserve a plain aggregate that is still needed later by shallow-copying the outer ABI slots, but its eligibility check rejected any aggregate containing a standard owner (such as Vec) — even when the owner is only a pointer ABI slot inside the outer aggregate — and so fell back to moving the original aggregate.
  • Fix rule: a top-level standard owner remains non-copyable; only the single case of “a plain outer aggregate shallow-copying a nested owner slot for a temporary by-value call argument” is allowed, and the shallow copy only directly stores the nested owner slot, without recursively copying its interior.

issue044: CodegenError from a Repeated let Function-Pointer Alias

  • Date / status: 2026-07-17, fixed.
  • Symptom: the default and generated-SA backends failed before execution: SAB Error: failed to lower SLA through SA-compatible SAB path: error.CodegenError; the first failing monomorphized function located by generated-SA was ecs_parallel_task_pool_scope_run_tasks_shared_serial_i32_i32.
  • Downstream reproduction: tests/test_ecs_parallel_runner_scope_executor_isolated.sla, filtered case sharing scope executor ticks scope; the existing regression tests/test_ecs_mut_parallel.sla’s task pool scoped task set external only stays off pool failed the same way.
  • Trigger shape: take a function pointer from a Vec, and in each of two loops do let run = runs[i] and then call run(...).
  • Root cause one: the repeated let binding was lowered via generated binding aliases, while the function-pointer call path looked up local_binding_types directly using the original source name; the inferred function-pointer type was registered under the active alias, the lookup returned null, and so a bare CodegenError was emitted. The alias-aware localBindingTypeForName should be used.
  • Root cause two: after fixing the lookup, generated-SA further exposed error[MemoryLeak]: live registers remain at function exit — a generated register held the function-pointer vtable address passed to Vec.push; the specialized vec(...) / Vec.push(...) path used callArgNeedsRelease, which only looks at AST identifier nodes, and must instead use callArgResultTempNeedsRelease.
  • Fix commits: adf98e2 (alias-aware lookup), e2406dc (release generated temporaries).

Background: after the Module Table / imported macro direct-callee pruning / synthetic benchmark work was completed, a retest was switched, as required, to the real sla_ecs project; the synthetic benchmark passed, but the real large project exposed multiple regression points. Other Compiler-Side Fixes on 2026-07-19

  • SA vec.push no longer incorrectly ^-consumes POD structs containing pure enums; component_register_table’s push(info); return (registry, info) passes again.
  • By-value Vec parameters that must stay alive inside a loop are cloned at SA/SAB call sites, eliminating find_archetype-class PhiStateConflict; strict SAB lib/parallel_table_erased.sla focused passed.
  • The SA full path for parallel_table_erased focused still exposes another class of CapabilityMismatch (the ecs_box_drop prefix), recorded as a remaining SA backend problem.
