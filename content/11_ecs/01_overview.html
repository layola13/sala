What sla_ecs Is: Positioning and Scale

Zig 0.17This plugin is built with Zig 0.17: the 0.17 branch builds successfully with Zig 0.17 and passes the Zig unit tests; the old 0.14.1 branch is left untouched.

This page explains where sla_ecs sits in the SA ecosystem, its real scale, and why the sa_plugin_sla compiler treats it as a “real regression target”. After reading it you will be able to distinguish the layering relationship between sla_ecs (an SLA application-layer ECS library) and other ECS-related artifacts.

Positioning: A Bevy-Style ECS Library Written in the SLA Language

sla_ecs is a Bevy-style ECS (entity-component-system) library written in SLA, with its source repository located at the WSL path /home/vscode/projects/sla_ecs. It is a real, large project, not a toy example created to demonstrate syntax; precisely because it is large enough, its import graph complex enough, and its macro expansions numerous enough, it has become the preferred host for verifying compiler performance and correctness.

NoteThe sla_ecs source is not inside the Windows help-documentation workspace; all facts in this chapter come from documents and contract files under D:/projects/sla that reference it, and its source is not read directly.

Special Status: The Compiler’s “Real Regression Target”

The development plan file of sa_plugin_sla places an explicit constraint on its role:

- Implementation workspace: /home/vscode/projects/sa_plugins/sa_plugin_sla
- Do not switch implementation or planning into /home/vscode/projects/sla_ecs;
  use /home/vscode/projects/sla_ecs/lib/parallel.sla only as a host regression target.

This has two implications:

  • Implementation and planning only happen inside the compiler repository; sla_ecs does not carry compiler changes;
  • Files such as lib/parallel.sla serve only as a host regression target, used to verify the behavior of a real large project outside synthetic benchmarks.

This distinction has practical consequences: the Module Table retest record states explicitly — after the synthetic benchmark passed, switching to a retest on the real sla_ecs project still exposed multiple frontend crashes and SAB blockers. In other words, all-green synthetic fixtures do not equal meeting the bar on a real large project. For the related history, see the Known Issues and Regression History page.

Relationship with Rust / Bevy

  • The reference point is Bevy’s bevy_ecs. The macro evaluation document uses Bevy as the comparison, counts the macro forms actually used by bevy_ecs, and quantifies the gap between SLA and Rust’s macro system. The document gave two different estimates for the share of Bevy’s conciseness that comes from derive macros (one place says 90%+, another says 50%); the shared conclusion is that derive is a key source.
  • SLA will never support proc-macro. The multi-arm patterns, fragment types, and arbitrary compile-time code execution of macro_rules! are intentionally excluded, consistent with SA’s minimal-frontend philosophy.
  • ECS semantics belong to the library, not the compiler. The architecture correction of 2026-06-23 made this explicit: the proposal to hard-code ECS derives such as Component/Resource/Event/Bundle into the compiler has been withdrawn; the compiler may only provide language-neutral capabilities (such as @expand_tuple, generic attribute parsing, value-semantics @derive(copy, eq, ord, hash, debug)), and engine keywords and game logic must stay in sla_ecs.
  • The current @derive(Component) is only an annotation. The compiler parses and records these names, but generates no code; the real ECS metadata comes from hand-written impl methods. For the improvement direction, see the Macro Usage Patterns and the Compiler Improvement Path page.
WarningDo not confuse sla_ecs with the SA contract plugin sa_plugin_3d_ecs: the former is an SLA application-layer library, the latter is an SA ABI contract in the 3D engine plugin family; the two belong to different layers. See the The SA-Level 3d_ecs Plugin Contract page for details.
