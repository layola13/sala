Macro Usage Patterns and the Compiler Improvement Path

This page summarizes the three kinds of macro capabilities actually used by sla_ecs and their frequencies, and the list of sa_plugin_sla compiler improvement recommendations proposed on the basis of those usage patterns. All numbers and entries come from the macro-gap analysis document sla_ecs_macro_gap_analysis_and_recommendations_cn.md (v0.1 / 2026-07-01).

@expand_tuple Is the Core Pillar

@expand_tuple covers all variable-length expansion scenarios in sla_ecs; for the main expansion kinds, see the combination-family table in Architecture and Module Surface (TableErasedAnyOf$N 2..8, TableErasedCombination$N 2..16, etc.). The template variables it can use include: $N (current arity), $TYPES/$TYPE_PARAMS, $I/$T (current item index and type name), $ORD (ordinal field name), and the per-arity repeated @each(T) and the concatenation @join(T, ", "). It does not support token-tree matching, multi-arm patterns, recursive macros, or arbitrary compile-time code execution.

Implementation Boundary of $ORD

  • $ORD is implemented in sa_plugin_sla/src/source_expand.zig up to index 15 (sixteenth), so the 2..16 range is usable.
  • Splitting field naming into two segments in sla_ecs — (2..4) using named parameter fields, (5..8) using numeric fields — is a library-side code style choice, not a compiler limitation:
// 现状：两个范围，字段命名不一致
@expand_tuple(2, 4, T) { $ORD_value: $T }   // first_value, second_value, ...
@expand_tuple(5, 8, T) { value_$I: $T }     // value_0, value_1, ...

// 可统一为：
@expand_tuple(2, 8, T) { $ORD_value: $T }   // 一行即可

Why the macro Keyword Is at 0

SLA’s macro swap(a, b) form only accepts identifier parameters and cannot handle type parameters or expression parameters, so it has no value for sla_ecs code generation. This is the result of intentionally not introducing a more complex macro system (SA’s minimal-frontend philosophy), not a feature gap to be filled.

Key Points of Recommendation A (P0)

  • Each ECS type currently needs about 5 hand-written lines of impl (such as fn component_type_id() -> i32, component_storage_kind(), component_name()); there are already about 30 such hand-written metadata sites in the examples.
  • The proposal is to add expansion rules in the compiler for allowlisted derive names: type_id uses a deterministic hash of the compile-time type name (candidates such as FNV-1a / xxHash / murmur3, guaranteeing cross-file consistency, stability, and low collision); component_storage_kind() returns 0 (table) by default, overridable by an extra attribute (such as @component(storage = "sparse")).
  • No user-writable derive macro system is introduced — only a compiler-internal allowlist is added; all names stay language-neutral, and the compiler does not hard-code ECS semantics.
  • Estimated change surface: src/codegen.zig about +120 lines, src/sab_codegen.zig about +80 lines, src/type_checker.zig about +30 lines, src/ast.zig about +10 lines, plus tests.

Key Points of Recommendation B (P1)

  • Current workaround: lib/entity_set.sla hand-writes entity_hash(entity: Entity) -> i64, and debug sites hand-write debug_entity(...) returning []const u8.
  • The direction is field-by-field traversal generation of hash combinations and debug string concatenation; the prerequisite is confirming that these two signatures can be type-checked correctly (debug involves codegen support for string concatenation).

Key Points of Recommendation C (P2)

system-param runners are a Cartesian product of parameter-type combinations rather than an arity template, which @expand_tuple cannot express. The document compared two paths and gave a conclusion:

  • Path 1 (recommended): put a generation script inside sla_ecs (such as tools/generate_system_params.py), define the parameter combination matrix, and generate files such as system_param_table_erased.sla; zero compiler changes.
  • Path 2 (optional but not recommended): add a generic @expand(min, max, var) template engine to the compiler, at an engineering cost of about 500 lines of Zig, and it may not cover all variants.

Items Explicitly “Not Done”

  • Extending the macro keyword — conflicts with SA philosophy;
  • User-defined derive — conflicts with SA philosophy;
  • macro_rules! multi-arm pattern macros — conflicts with SA philosophy.
NoteThe status of that document is “recommendation draft, development after approval”; the above is a roadmap, not delivered capability; the current compiler still only provides semantic expansion for copy/eq/ord. If these changes land, what they affect is compiler behavior; for the verification flow with sla_ecs as the regression target, see the Known Issues and Regression History page.
