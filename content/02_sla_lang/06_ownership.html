Ownership and Lifetimes

SLA inherits SA's Move/Borrow semantics, but leaves all cleanup to compiler-managed handling. This page explains: why user code needs no drop, the respective roles of the three symbols &/^/!, the automatic borrow/automatic move rules for method receivers, and the current state of &mut T. After reading this page, you can understand where the UseAfterMove-class errors SLA reports come from.

Managed cleanup: no drop

SLA source uses compiler-managed lifetime cleanup by default:

  • User-facing .sla code does not need explicit release statements;
  • The generated .sa/SAB still contains ! instructions; those are SA's ownership primitives, injected by the compiler;
  • SLA deliberately provides no drop keyword or drop() function.

At branch merge points the compiler performs live-variable analysis and automatically supplies symmetric releases for values "consumed on only some branches", to avoid Phi state conflicts in the SA verifier; stack allocations inside for loop bodies are also automatically hoisted to a single allocation outside the loop.

Three symbols: &, ^, !

SymbolSemanticsStatus in SLA source
&xCreates a borrowing view, automatically unlocked at the end of the scopeKept; can be written directly (e.g. sum(&values))
^xExplicit ownership transfer (move)Kept; can be written when a transfer needs emphasis; most scenarios are covered by automatic moves
!xReleases/consumes a registerAppears only in compiler output; ordinary source does not write it; the old-style !x; still parses, only as a debugging escape hatch

A moved variable is marked Consumed in the frontend, and using it again yields a clear UseAfterMove compile error — consistent with the SA Referee's interception, just moved earlier to the SLA layer.

Address-of & and stack homing

The SLA compiler "homes" function parameters and let bindings to stack slots: after lowering you will see x = stack_alloc 8, and the register holds the slot address rather than the value. This brings two semantic rules:

  • Automatic load in value contexts: when a homed variable is used in an expression, the compiler automatically inserts load x+0 as u64. Writing ch yields the character value, with no manual load needed;
  • &x directly gives the stack slot address: taking the address of a homed variable creates no temporary, and directly returns its stack slot address. This is exactly how extern function OUT parameters are written: 
    let kind = 0;
let code = 0;
let st = sa_tui_read_event(handle, timeout_ms, &kind, &code);
// 插件写入的就是 kind/code 自己的栈槽，调用后可直接读取
NoteMacros doing textual replacement must be aware of homing: when a macro parameter appears in a value context, the expansion body needs an explicit load to fetch the value, otherwise what gets stored is the slot address rather than the variable's value. See the macros section of the Extension Mechanisms page.

Method calls: automatic borrowing and automatic moves (UFCS)

For x.method(y), the compiler statically expands by the receiver signature:

First parameter of the signatureRewrite resultExample
&Tmethod(&x, y) (automatic borrowing)v.len() → len(&v)
Tmethod(^x, y) (automatic move)v.push(1) → push(^v, 1)
// 链式调用会被展平为嵌套函数调用
let final_v = v.push(10).push(20);
// 等价于 push(^(push(^v, 10)), 20)
NoteThe premise of chained calls is that the method returns the receiver type or a new object. If a method consumes the receiver by value and does not return it, the chain ends there.

&self covers reads and writes; &mut not yet introduced

The design decision of the current version (Phase 1) is:

  • &self/&T cover both reads and writes: write methods are also declared with &self; measured demos (such as fn inc(&self) in demos/rosetta/59_method_counter/main.sla executing self.value.set(current + 1) internally) all work normally;
  • Read/write is not enforced at the SLA source layer at compile time; after lowering, the SA Referee dynamically judges Locked_Read/Locked_Mut from the store operations;
  • &mut T/&mut self belong to the Phase 2 plan; the trigger is the ECS parallel scheduler needing static read/write sets; an automated migration tool will be provided then;
  • The let mut x = ... spelling will never be introduced — SLA's let is mutable by default, and const is immutable.

Replace semantics for place-to-place assignment

When the right-hand side of an assignment is a deep handle value read out of a place (whose type drop plan is .buffer — a String or a scalar-element Vec; or .deep_vec — a deep-element Vec), and all of the following hold:

  • The right-hand place (after stripping move wrappers) is a field / index / dereference place;
  • The place root is owned (an identifier root whose type is non-borrowing, a raw-pointer dereference, an owned container index);
  • The target is a non-identifier place (a field / index / dereference target);
  • The source place and the target place are not the same place;

then the assignment is a transfer, and the emission order, unified across both backends (text / SAB), is:

  1. Evaluate the right-hand side;
  2. Deep-drop the target place's old value;
  3. Store the new value into the target place;
  4. Write an empty handle (the canonical empty value of Vec/String) back into the source place — i.e. mem::replace semantics.

After the transfer the value has exactly one owner (the target place); the source place holds an empty handle, whose later drop degenerates to a shallow release and no longer touches the transferred buffer. This rule plugs the double deep release of "the same Vec buffer being deep-dropped once by each of two owners": in the slaredis goroutine model, the source place (*req).batch was not nulled after assignment, and (*st).cur_batch and the connection side's batch teardown deep-dropped the same buffer one after another, crashing the process within roughly 1.5k–3.5k replies; after replace landed, the same probe survived all 20000. The judgment is implemented in the checker's walkTaintAssign (the assign_replace_src annotation + retiring the source place's drop taint), and emission is the unified tail sequence of both backends' genAssign; the source address is recomputed from the existing field/index/deref address forms, and since the same statement's right-hand read already did the bounds check, it is not checked again.

Out-of-domain cases behave unchanged:

  • Identifier targets: keep the current move / clone rules, no replace;
  • Reads from borrowed roots (& / borrow places): keep clone-on-extract; the source is not nulled (borrowing does not transfer ownership);
  • Freshly constructed right-hand values (Vec::new(), etc.): not place reads, do not trigger nulling;
  • Same-slot index aliasing: v[i] = v[j] is read as a move-out when i == j at runtime (the source slot is nulled); the static same-place case is excluded by the checker; this is documented semantics, not undefined behavior;
  • .deep_struct places (struct values containing owned fields): not covered by this section — a struct has no canonical empty value to leave behind. A known hole, with a DEF on record; the settled form is DS2 = loud rejection by the checker + an explicit take API, to be implemented in a separate batch. Until DS2 lands, place-to-place assignment of deep structs keeps the current semantics, and users must not rely on its ownership uniqueness.

Addendum: Vec inline storage and push copy materialization (batch B)

When the element is a struct of exactly 8 bytes with all-primitive fields, Vec's element storage model changes from "slots store record pointers" to inline storage: the slot directly holds the element value itself (one word); the handle layout (ptr/cap/len) is unchanged, and the stride is still 8. The criterion is structDeclIsInlinePod (shared by both backends): non-opaque, non-union, non-generic, all fields primitive, and abi size exactly 8; structs smaller or larger than 8 bytes, or containing non-primitive fields, keep the record model.

  • Literal pushes take a two-phase direct store (DPS): all fields are evaluated first, then a slot is reserved, the fields are stored directly into the raw slot at their layout offsets, and finally len is published — with zero record allocation throughout; other arguments take the whole-word push (loading one word from the source record into the slot).
  • &v[i] is the slot address: the borrow address of an inline element is the slot address itself (LEA-ized, without loading through the record pointer), and field reads/writes through the borrow reach the fields inside the slot directly; an index read materializes a new record. The same batch unified the semantics of &v[i] across both backends as "the address of the i-th element" (for record-type elements, the record pointer stored in the slot), fixing the previously stored borrows being systematically off by one element.
  • Push argument copy materialization: push is a copy consumer — when an identifier argument is a record-type element, a shallow-copy materialization is done before emission; the Vec holds that copy, and the source binding's release at scope exit no longer touches the elements inside the Vec. Previously the push-specific emission arm skipped this materialization: a struct literal bound with let and then pushed formed a double ownership; after the binding was released, the elements were reclaimed and reused by the allocator, and on read-back all elements aliased each other.
  • Orthogonal to vec_packed: vec_packed is a byte-mirror helper on explicit export boundaries (for consumption by C-shaped externs); inline storage is Vec<POD>'s own storage model; neither replaces the other.

Addendum: deep cloning at non-consuming ownership transfer points (DEF-AOF-EXIT69)

In the checker's semantics, both extracting a field from an owned root and passing a named local by value are non-consuming transfers: the source binding stays alive and deep-drops its heap handles as usual at scope exit. This creates an implementation obligation (inheriting the clone_on_extract settled by DEF-5): such transfer points must materialize an independently owned deep clone, and must not alias the same handle to a second owner. Previously both code generators (text and SAB) materialized these two places as aliases — field extraction bound the same Vec/String handle directly, and by-value argument passing shallow-copied records field by field, sharing all handle fields — so the same allocation was dropped once by each of two owners (sa_vec_free releases both the buffer and the handle cell). The visible symptom of this defect is at the application layer: every startup-failure exit of slaredis after the store is established (AOF open failure / corrupt AOF → 69, port in use → 66, illegal LOOP_MODEL → 70) segfaulted midway through the teardown deep drop instead of returning an exit code.

  • Record copying (genShallowCopyCallArgValue, both backends): when copying a record, Vec/String/GrowVec fields are now truly cloned, and nested structs recurse through the same routine; one upgrade covers all call sites — preserved-value argument passing, the SAB move path's shallow copy, struct literal fields, container element copies, and slot value loads.
  • Field extraction (cloneBorrowedHandleFieldValue, both backends): clone-on-extract is no longer limited to "the root is a borrow/deref"; owned roots are cloned too; when the extraction result is a struct containing owned handles, it is deep-cloned through the copy routine, while pure POD structs keep the in-place view.
  • Registered residuals (behavior unchanged, handled as separate cases): handles inside array fields and Map/Set/Box/Rc fields in copied records are still copied by handle; cloning of Vec handle elements is still buffer-level (the same limit as the existing Vec clone).
