所有权与生命周期

SLA 继承 SA 的 Move/Borrow 语义，但把清理工作全部交给编译器托管。这一页说明： 用户代码为什么不需要 drop、&/^/! 三个符号各自的角色、 方法接收者的自动借用/自动移动规则，以及 &mut T 的现状。读完这一页， 你能理解 SLA 报出的 UseAfterMove 类错误的来源。

托管清理：没有 drop

SLA 源码默认使用编译器托管的生命周期清理：

  • 用户面 .sla 代码不需要显式释放语句；
  • 生成的 .sa/SAB 中仍会出现 ! 指令，那是 SA 的所有权原语，由编译器注入；
  • SLA 有意不提供 drop 关键字或 drop() 函数。

编译器在分支汇合点做活跃变量分析，自动为“只在部分分支被消费”的值补齐对称的释放， 以规避 SA verifier 的 Phi 状态冲突；for 循环体内的栈分配也会被自动提升到循环外单次分配。

三个符号：&、^、!

符号语义在 SLA 源码中的地位
&x创建借用视图，作用域结束时自动解锁保留，可直接书写（如 sum(&values)）
^x显式所有权转移（move）保留，可在需要强调转移时书写；多数场景由自动移动代替
!x释放/消费寄存器仅出现在编译器输出，普通源码不写；旧式 !x; 仍可解析，仅作调试逃生口

被移动后的变量在前端即标记为 Consumed，再次使用会得到明确的 UseAfterMove 编译错误——与 SA Referee 的拦截一致，只是提前到了 SLA 层。

取地址 & 与栈驻留（stack homing）

SLA 编译器把函数参数和 let 绑定“驻留”（home）到栈槽： lowering 后你会看到 x = stack_alloc 8，寄存器里存的是槽地址而非值。 这带来两条语义规则：

  • 值上下文自动取值：在表达式里使用已驻留变量时，编译器自动插入 load x+0 as u64。写 ch 就得到字符值，不需要手动 load；
  • &x 直接给栈槽地址：对已驻留变量取地址不创建临时变量， 直接返回其栈槽地址。这正是 extern 函数 OUT 参数的写法： 
    let kind = 0;
let code = 0;
let st = sa_tui_read_event(handle, timeout_ms, &kind, &code);
// 插件写入的就是 kind/code 自己的栈槽，调用后可直接读取
注意宏（macro）做文本替换时必须感知驻留： 宏参数在值上下文出现时，展开体需要显式 load 取值， 否则存入的是槽地址而非变量的值。见扩展：宏一节。

方法调用：自动借用与自动移动（UFCS）

对 x.method(y)，编译器按接收者签名静态展开：

签名首参改写结果示例
&Tmethod(&x, y)（自动借用）v.len() → len(&v)
Tmethod(^x, y)（自动移动）v.push(1) → push(^v, 1)
// 链式调用会被展平为嵌套函数调用
let final_v = v.push(10).push(20);
// 等价于 push(^(push(^v, 10)), 20)
注意链式调用的前提是方法返回接收者类型或新对象。 若方法按值消费了接收者且不再归还，链条就到此为止。

&self 覆盖读写，&mut 尚未引入

当前版本（Phase 1）的设计决策是：

  • &self/&T 同时覆盖读写：写型方法也用 &self 声明， 实测 demo（如 demos/rosetta/59_method_counter/main.sla 中 fn inc(&self) 内部执行 self.value.set(current + 1)）均正常工作；
  • 编译期不在 SLA 源码层强制区分读/写，SA Referee 在 lowering 后根据 store 操作动态判定 Locked_Read/Locked_Mut；
  • &mut T/&mut self 属于 Phase 2 计划，触发点是 ECS 并行调度器需要静态 read/write 集； 届时会提供自动化迁移工具；
  • let mut x = ... 写法永久不引入——SLA 的 let 默认可变，const 不可变。
