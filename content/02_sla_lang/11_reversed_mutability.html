Reversed Mutability Model: Mutable by Default, Frozen by Declaration

Feature preview · under development. This chapter describes syntax and semantics currently in design (the SLA Reversed Mutability Model, named 2026-11-24). It is not implemented in any released version: all examples are design syntax and will not compile with current compilers. Details are still under review; this chapter will be updated together with the implementation. Every other chapter describes the implemented status quo.

The idea: reverse the mutability model

Rust's mutability model is "immutable by default, mutable by declaration": bindings are read-only unless annotated mut, and write permission flows through &mut borrows. SLA takes the opposite declaration direction — mutable by default, immutable by declaration: ordinary bindings and fields are writable, and only the positions that need protection carry an annotation. This is not swapping mut for const; it reverses the declaration direction of the whole mutability model.

Declarations reversed, discipline not. The reversal happens only at the declaration layer (who has to write an annotation). The safety layer is not reversed: aliasing discipline, ownership, field-conflict and concurrent-access checking are at Rust's level and are the compiler's job. SLA does not trade alias safety for brevity.

The core question this model tries to answer: can memory safety stop requiring beginners to first understand a complex system of mutability rules? Rust's route is to restrict mutation first and open it explicitly; SLA's route is to allow normal development first and declare explicitly where mutation is forbidden. Rust asks the programmer to manage mutability explicitly; SLA asks the programmer to declare immutability explicitly, while the language maintains the safety boundary. These are two different design philosophies. One red line: never push safety problems onto the runtime or the programmer just to make SLA look simple — an access the compiler cannot prove must be rejected loudly, not papered over at runtime.

Four principles

  • Mutable by default: no mut declaration is ever required; SLA has no let mut.
  • Explicit freezing: const protects fields that must never change.
  • Temporary read-only: lock .&field declares a shared read-only permission for the duration of a call.
  • Safety first: the compiler owns field conflicts, aliasing, lifetimes and concurrent-access checks.

Layer 1: mutable by default

struct User {
    const id: u64,
    name: String,
    age: u32,
}

fn update(user: User) {
    user.age += 1;   // ordinary fields are writable with no annotation at all
}

Layer 2: field-level permanent immutability — const

const sits in the struct definition, immediately before the field name, and is part of the type: after construction the field is permanently unwritable. Construction has an explicit seal point: writes are legal before the seal (initialisation), and the value may escape to other tasks only after it. Freezing is transitive: const profile: Profile freezes profile's own owned internals with it, so the freeze cannot be bypassed through nested objects; it never spreads sideways to sibling fields, and it stops at reference/shared-handle boundaries. A field that must stay mutable inside a frozen object uses an interior-mutability type (Cell / RefCell / Mutex) and is accessed through its API — the only live exception. Aliasing, pointers and method calls must not bypass const; enforcement happens at the field-store operation level.

Layer 3: call-scoped temporary read-only — lock

lock sits inside a parameter's type and is an access-permission description on that binding: it produces no pointer and no new type, it only declares "for the duration of this call, this field path is read-only". The current function must not store to a locked path (checked statically against actual stores, and the restriction propagates down the call chain: a callee that may write a locked path is a compile error); other tasks may read concurrently; a task that wants to write a locked path waits until all holds are released (once a writer queues, new readers are not admitted, so writers cannot starve). Holds release automatically on return — there is no manual unlock.

fn inspect(a: Account(lock .&balance)) {
    print(a.balance);   // read-only, legal
    print(a.name);      // unlocked fields are unaffected
}
SyntaxMeaning
lock .&balanceLock a single field
lock .&balance, .&nameLock several fields at once
lock .&Lock the whole object (call-scoped whole-object read-only)

Locking is deep by default: it covers the field value's owned internals (e.g. currency inside balance) and stops at reference boundaries. Paths are compared by inclusion: locking a parent path covers its sub-paths; sibling paths are disjoint. Dynamic index paths are treated as the whole array in v1. Creating a lock view borrows the path: while the view lives, the original binding's write access to that path is suspended. Two hard rules in v1: a lock lease must not cross an await or a blocking point (compile-time rejection), and a read-lease holder may not upgrade in place to a write (release first, then apply).

Shared reads across tasks

When an object is a shared handle (shared to several tasks via Arc / channels), several tasks may hold read leases on the same field through lock and read in parallel; lease counts are managed by the runtime on the shared handle, and never-shared objects pay zero cost. The criterion is the field's accessor set, not the number of tasks: one task holding two writable aliases still conflicts, and two tasks writing disjoint fields still run in parallel.

go inspect(shared_account);
go inspect(shared_account);
go inspect(shared_account);   // three tasks read age/balance concurrently, none blocks

Static first, dynamic as fallback

The implementation has three layers of increasing cost; anything provable statically never reaches the runtime: (1) static field-access analysis — the compiler summarises field-path read/write sets per function, and at spawn sites proves two tasks' accesses disjoint (Bernstein conditions) and admits the sharing directly; const fields have statically empty write sets, so their reads are lock-free by construction; (2) explicit lock contracts — signature-declared read-only paths are verified at compile time and backed at runtime by counted leases against cross-task writes; (3) a dynamic adaptive layer (research) — for sharing that cannot be proven statically, the runtime maintains access state per (object, field path): Adaptive Field Mutability, a later research phase, out of v1 scope.

Amendment (adopted supplement): for objects shared through shared handles, layer (1) no longer admits sharing — the sync-field supplement's type rules and entry locking govern instead; layers (2)–(3) are unchanged.

Layering: this feature is added in the SLA layer only (frontend checking plus an SLA-level runtime library built on SA's existing atomics, task identity and synchronisation primitives). SA stays frozen: no new instructions, no field semantics pushed into SA; if the lower layer ever needs strengthening, the verifier (Referee) is enhanced, not the ISA.

Why this helps AI-written code

The annotation surface is proportional to the danger surface, not the code surface. Rust's mut annotations grow with the total amount of code (every binding you modify must be marked); SLA's const / lock annotations grow only with the number of fields that need protection. AI writes business logic directly by default, and safety constraints appear exactly where they matter — less code, and the constraints themselves carry information.

Five things that must be proven

Until all five are implemented and verified, the claims of this chapter are design goals, not facts — this is why the chapter carries the preview label:

  • Alias safety: no alias may bypass lock or const; checks key on object identity and field path, never on variable names.
  • Cross-function safety: a callee must not secretly modify a locked field; the caller's read-only restriction propagates down the whole call chain, and unknown access sets are rejected conservatively.
  • Async safety: on task suspension, cancellation or abnormal exit, temporary read leases must be released reliably — no leaked counts, no dangling holds.
  • Runtime cost: field-level concurrency control must not tax ordinary accesses with atomic operations; statically proven accesses and never-shared objects cost zero.
  • Provability: lifetimes and memory safety must be provable by the compiler without any GC; this is the principle most worth holding.

Supplement: sync fields (adopted, v2)

Adopted (2026-11-24); revised to v2 the same day. This section is a supplementary part of this chapter's model; its examples are design syntax as well. In one sentence: keep "mutable by default + const freezing", and add a sync field modifier meaning "concurrent writes allowed"; lock scope, read/write mode and blocking-ness are all derived uniquely by the compiler from the syntax, and anything it cannot decide is a compile error; lock .&field is retained as an optional API contract declaration. This section differs from this chapter's v1 scope in three substantive ways, and this section governs those three points (the v1 scope below is amended accordingly): (1) an object reachable through a shared handle is no longer read-only without exception — besides interior-mutability channels such as Mutex / atomics, sync fields add a language-level concurrent-write channel; (2) static field-access analysis (Bernstein disjointness proofs at spawn sites) is no longer the admission criterion for sharing — the type rules below replace it, at the cost that two tasks writing disjoint fields of the same shared object no longer run in parallel (one lock per object); (3) locking functions take real locks at entry already in v1 (zero cost for never-shared objects is deferred to v2 dual compilation), and panic poisoning semantics are added. Statements in this section about the current checker rest on this documentation's ownership / borrowing and goroutine chapters plus a read of the Rust checker's sources (check_spawn_guard.rs, check_go.rs, check_borrow_origin.rs) — read only, not compile-verified; the pre-existing defects F1–F3 in §6.1 below are claims pending verification with the Appendix A programs.

Eight rules (R1–R8)

  • R1 Three field states: every field is in exactly one of default, const, sync. A sync field may have any type (including heap types such as String and Vec), because the scheme has exactly one mode — pessimistic locking — and never needs rollback.
  • R2 Default fields are read-only while shared — Arc is the criterion: an object placed in an Arc counts as shared (permanently), and every holder may only read its default fields. The existing checks already forbid borrows from crossing task boundaries (go's GoBorrowPayload, thread::spawn's BorrowEscape), so in safe code an Arc is the only route to cross-task sharing, and sharedness is determined by the type alone. No static field-access analysis — the original scheme relied on proving two tasks' accesses disjoint, whose outcome depends on analysis precision, i.e. on guessing; this scheme replaces it with a type rule. Raw pointers are outside the guarantee: turning a Box into a raw pointer and handing it to a goroutine is an ownership transfer (the sender no longer accesses it), an accepted use under the existing rules; accessing through raw pointers from both sides at once is at the unsafe level and is the user's responsibility.
  • R3 Lock scope is determined uniquely by syntax: a function that directly reads or writes a sync field becomes a locking function. The objects owning the accessed fields must be reachable from a starting point — a function parameter, or a global static — through const fields only; those objects form the lock set: reads only → read lock; any write → write lock; accessing an element of a const collection locks all of its elements. A lock covers the object's owned interior (inline fields, Box) up to the reference boundary — the same depth rule as this chapter's lock — so recursive tree traversals need no per-node locking. An unshared local object may read and write its sync fields directly, without locking, before it is placed in an Arc, keeping initialisation and single-threaded code annotation-free. The inferred result is written into interface metadata and visible in IDE hovers. Looking an object up by ID inside the function and then writing its sync field is rejected (e.g. bank.find(id).balance -= 1) — the fix is to look it up in the caller and pass it in as a parameter.
  • R4 A locking function must not block: no blocking point may appear in a locking function or anywhere in its call chain. The blocking-point set matches the goroutine runtime: channel send / recv / select (except timeout(0) and default branches), join, sleep, network waits, Mutex locking, yield, and .await. Every function's blocking-ness is inferred precisely along the call chain and recorded in the interface for pub functions; changing from noblock to blocking is a breaking change. extern and dyn are blocking by default unless declared noblock. The scheme needs a new call-chain blocking-analysis pass as the foundation of R4. Premise: sa_std's allocator must itself be noblock, otherwise string concatenation or Vec::push inside a locking function would be rejected (to be verified, see the open questions); the standard library also provides a noblock buffered log for debug output while holding locks. The IDE provides an "extract into a locking function" refactoring for the most common R4 error (writing a sync field right after a recv in a worker loop).
  • R5 No nested locking: a callee's lock set must be a subset of the caller's already-held set, and its mode no higher than the caller's (a function needing a write lock may not be called under a read lock). When satisfied, the callee simply reuses the held locks and acquires nothing; otherwise it is a compile error. Each task therefore has exactly one acquisition point at any moment, which breaks the "hold and wait" condition for deadlock.
  • R6 No check-then-act: a value originating from a sync field, when used as an argument or condition of a call that needs a write lock, is a compile error when all of the following hold: the caller does not itself hold that object's lock (calling a read-only helper and writing back inside a locking function is not checked); the read and the write act on the same variable path (reading A and writing B is not checked); and "originating" is judged by data dependence, through function calls and across .await — a function's return value counts as depending on all of its arguments (function bodies are not analysed, so the verdict is deterministic). The fix is to fuse the check and the act into one function under one lock acquisition. The checking scope is part of the spec: only data dependence of local variables in the function body is tracked; values stored on the heap are not tracked; control dependence (choosing an account by balance, then writing it) is not tracked; two different variables that happen to point at the same object at runtime are not tracked. What lies outside the scope is business consistency — not checked, and no "might be a problem" warning is emitted either. The documented cost: withdraw(a, amt + calc_fee(balance(a))) is also rejected; the fix is to move the fee computation into withdraw.
  • R7 Error exit: when a locking function panics, the runtime releases all of its locks and marks every object it write-locked as poisoned; a locking function that later accesses a poisoned object returns an error, and recovery is left to a human or a supervisor task. This is a deterministic runtime behaviour, not a guess.
  • R8 Async functions must not access sync fields directly: calling an async function only creates a future; its body runs when polled, so the locking moment decouples from the call site and R5's call-site checks fail with it. Directly reading or writing a sync field inside an async function body is therefore a compile error; the access is extracted into a plain function. An optional lock contract written on an async function: locking a sync field conflicts with R8 and is an error; locking a default field is only a compile-time read-only promise and may span an await. Because a locking function can contain no .await (R4), a future never suspends or is dropped while holding a lock, so cancellation or dropping a future cannot leak a lock — this chapter's "async safety" item holds structurally. An executor running on a system thread may block briefly while acquiring, but cannot deadlock: it holds no other lock while acquiring (R5), the holder never suspends (R4), and waiting is bounded.

Runtime semantics

  • Acquisition: at function entry the lock set is sorted by object identity and acquired all at once; the same object appearing several times merges into one lock, and a read/write conflict upgrades to a write lock.
  • Release: on function return, including the panic path.
  • Fairness: once a writer queues, new readers are not admitted, so writers cannot starve.
  • Granularity: one lock per object, covering all of its sync fields and its owned interior (grouped automatically, so cross-field invariants hold naturally).
  • Implementation: reuse sa_std's existing park queue (the same source as RwLock); waiting suspends instead of spinning. F3 below must be fixed first.
  • Cost: in v1 locking functions always lock; uncontended, this is about one atomic operation; objects with no sync fields at all cost zero.
  • Memory model: a lock release synchronizes-with the next acquisition on the same object; all writes to sync fields made before the release are visible to the next acquirer.

Relation to existing features: go's parameter rules — the callee must be a named plain function (not async) taking exactly one word-sized argument (scalar, pointer or Chan), and borrows may not cross; shared state is packed into a struct, Boxed, and passed as a single pointer. thread::spawn — closures may not borrow or write outer variables (BorrowEscape); Arc clones and futures may move in (see F1). A locking function never blocks (R4), hence never yields, so under cooperative scheduling its lock hold time depends only on computation and is predictable. Because supervision / recover lets the process continue, R7's release + poisoning must be kept. In async code .await is a blocking point (R4) and async functions do not access sync fields directly (R8); nested awaits across async fn boundaries are supported (this documentation has not caught up yet). Arc owns lifetimes and is also the sole criterion for "shared" (R2); sync governs only the concurrent-write permission. Sending a plain T over a channel transfers ownership and needs no lock, while channel-versus-channel deadlock is out of this scheme's scope and left to runtime deadlock detection. Calling a Mutex lock inside a locking function is a blocking point (rejected by R4), and calling a locking function while holding a Mutex is a compile error, so the two mechanisms cannot form a cycle. Simultaneous access through raw pointers from both sides is outside the guarantee, at the unsafe level. The scheme changes only the SLA frontend checks and the sa_std runtime library; it adds no SA instructions (SA stays frozen).

Complete example: concurrent transfers

Four worker tasks process 1000 transfer requests, one auditor task re-checks periodically, and the end state verifies total conservation. The v2 example is rewritten to the existing go rules: shared state travels via Arc, and a task's argument is a single pointer to a Boxed context. There are exactly three sync annotations in the whole program; worker, auditor and main carry no concurrency annotations at all. Spellings such as the select branches, Box::from_raw and random_tx are illustrative and follow SLA's actual syntax; if Chan handles have move semantics, context construction copies or clones the handles instead.

struct Account {
    const id: u64,
    sync balance: i64, sync total_in: i64, sync total_out: i64,
    name: String,
}
struct Bank      { const accounts: Vec<Account> }
struct WorkerCtx { bank: Arc<Bank>, reqs: Chan<TxReq>, res: Chan<TxRes> }
struct AuditCtx  { bank: Arc<Bank>, n: i64, done: Chan<u64> }
const INIT: i64 = 1000;
const N_TX: u64 = 1000;

// locking function: write-locks {x, y} at entry; the same account merges automatically
fn transfer(x: &Account, y: &Account, amt: i64) -> Result<(), TxErr> {
    if x.balance < amt { return Err(Insufficient); }
    x.balance -= amt;  x.total_out += amt;
    y.balance += amt;  y.total_in  += amt;
    Ok(())
}
// locking function: read-locks {a} at entry
fn check_one(a: &Account) { assert(a.balance == INIT + a.total_in - a.total_out); }
// locking function: read-locks every element of bank.accounts -> a bank-wide consistent snapshot
fn total(bank: &Bank) -> i64 {
    let sum = 0;
    for a in bank.accounts { sum += a.balance; }
    sum
}

fn worker(p: *WorkerCtx) {
    let c = Box::from_raw(p);                       // take back ownership of the context
    loop {
        let (r, closed) = c.reqs.recv();            // blocking point, holding no lock
        if closed { break; };
        let out = match (c.bank.find(r.from), c.bank.find(r.to)) {
            (Some(x), Some(y)) => transfer(x, y, r.amt),
            _ => Err(NoAccount),
        };
        c.res.send(TxRes { tid: r.tid, ok: out });  // blocking point, locks already released
    }
}

fn producer(reqs: Chan<TxReq>) {                    // a Chan is one word: passable directly
    for t in 0..N_TX { reqs.send(random_tx(t)); };
    reqs.close();
}

fn auditor(p: *AuditCtx) {
    let c = Box::from_raw(p);
    loop {
        select {
            c.done.recv() => return,
            timeout(10ms) => {
                for a in c.bank.accounts { check_one(a); }   // locks one by one
                assert(total(&c.bank) == c.n * INIT);       // one full lock
            }
        }
    }
}

fn main() -> i32 {
    let n = 100;
    let bank = Arc::new(Bank { accounts: make_accounts(n, INIT) });
    // make_accounts initialises sync fields directly, before the Arc (R3)
    let reqs: Chan<TxReq> = Chan::new(64);
    let res:  Chan<TxRes> = Chan::new(64);
    let done: Chan<u64>   = Chan::new(0);
    let hs = vec();
    for _ in 0..4 {
        let ctx = Box::new(WorkerCtx { bank: bank.clone(), reqs: reqs, res: res });
        hs.push(go worker(Box::into_raw(ctx)));
    }
    let actx = Box::new(AuditCtx { bank: bank.clone(), n: n, done: done });
    let ha = go auditor(Box::into_raw(actx));
    let hp = go producer(reqs);
    let ok = 0;
    for _ in 0..N_TX {                               // request count is known: no need to close res
        let (r, _) = res.recv();
        if r.ok.is_ok() { ok += 1; };
    }
    done.send(1);
    for h in hs { sa_task_join(h); };
    sa_task_join(ha); sa_task_join(hp);
    assert(total(&bank) == n * INIT);               // total conservation
    println("{}", ok);
    return 0;
}

Forgetting sync only ever produces a compile error, never a silent mistake: single-threaded code and read-only sharing need no sync at all; the compiler asks for it only for "shared and written". The error points at three places — the store, the point where the object entered the Arc, and the field definition — and offers the fixed remedies (make it sync, finish the writes before placing the object in the Arc, or do not use an Arc at all and transfer ownership over a channel to a single task). When a third-party struct cannot be annotated, the two standard remedies are to wrap it in a custom struct with a sync field, or to give it to a single owning task and let the others send change requests over a channel. The mental model in one sentence: if a shared thing must change, write sync, and split the functions that touch it small, as the compiler suggests — four habits: functions that modify sync fields stay short and contain no print / send / .await; the objects to modify arrive as parameters; check-then-act lives inside a single function; and inside async functions, accesses to sync fields are extracted into plain functions (R8 — the most common async error, and the IDE can extract in one click).

The cost: some code that is actually safe is rejected. Every rejection class has a fixed remedy the compiler can print: looking an object up by ID inside a function and writing its sync field → look it up in the caller and pass it in; calling a write-lock function from a read-lock function → make the outer function a write-lock function, or split the calls; logging / messaging inside a locking function → use the noblock buffered log, or move the blocking operation after the locking function returns; a lock set whose size is known only at runtime → put the objects in a const collection (locked as a whole), or switch to a channel feeding a single task; accessing a sync field inside an async function → extract a plain function (R8); withdraw(a, amt + calc_fee(balance(a))) → move the balance-dependent computation into withdraw; accessing a sync field inside a closure or iterator adapter → rewrite as a for loop (v2 evaluates annotating std adapters with element origins).

Appendix A: F1 / F2 verification programs

The programs below are expected to pass sla check before the fix (that is the gap); after the fix they must be rejected, and they join the test_error_* regression corpus next to test_error_spawn_closure_borrow_capture.sla. block_on is spelled as in demo 314.

// F1: a future carrying a borrow across a thread
async fn bump(v: &i32) -> i32 { *v += 1; return *v; }
fn main() -> i32 {
    let n = 100;
    let fut = bump(&n);                         // the future hides &n
    let h = thread::spawn(^|| block_on(fut));   // the guard sees fut, not a borrow
    n = 200;                                    // the main thread writes n at the same time -> data race
    h.join();
    return 0;
}

// F2: mutating the borrowed object while a same-thread future is unfinished
async fn bump(v: &i32) -> i32 { *v += 1; return *v; }
fn main() -> i32 {
    let n = 100;
    let fut = bump(&n);
    n = 0;                    // must error: fut still holds &n
    let r = block_on(fut);
    return 0;
}
