Modules and @import

This page introduces SLA's code organization units: mod modules, pub visibility, @import imports of SLA source files and SA contracts (.sai/.sal/.sa), and using static extensions. After reading this page, you can split code across multiple files and reference sa_std correctly.

mod and pub

mod 名称 { ... } defines a namespace inside a file, and members are accessed via :: paths; only items marked pub are visible externally (demos/rosetta/41_module_imports/main.sla):

mod math {
    pub fn double(x: i32) -> i32 {
        x * 2
    }
}

let value = math::double(21);   // 42

The three @import targets

TargetExample (real source)Description
SA contract .sai@import "sa_std/io/print.sai"Reads extern function signatures and registers them as strongly typed functions
Layout contract .sal@import "sa_std/rc.sal"Reads external struct layout offsets, guaranteeing ABI compatibility
SLA / SA source file@import "score_math.sla", @import "sa_std/string.sa"Brings in the modules, functions, and macros defined there

The real spelling in a multi-file project (demos/syntax_sugar/combined/main.sla and its companion file score_math.sla):

@import "sla_std/cmp.sla"
@import "../using_module_import/score_math.sla"

@import "score_math.sla"   // using_module_import/main.sla 中使用相对路径

// score_math.sla 内容：
mod score_math {
    pub fn add_bonus(value: i32, bonus: i32) -> i32 {
        return value + bonus;
    }
}
NoteSLA directly reuses sa_std's contract files; the frontend has built-in .sai/.sal parsers, so types and ABI share the same data source as the low-level verifier, with no dual-declaration drift. A third-party plugin with standard contracts can be called in a strongly typed way with a single @import line.

Where sa_std is resolved

Paths of the form sa_std/... are resolved by default from the environment variable SA_STD_DIR (when set), and otherwise fall back to the local conventional sci/sa_std directory. The compiler loads all imported contracts before type checking, so extern functions are directly usable from SLA code.

using: static extensions

using 模块名; registers the visible functions of that module as static extension methods: a value whose first parameter type matches can call these functions in chained form. This is a pure frontend call rewrite and introduces no runtime dispatch (demos/syntax_sugar/using_module/main.sla):

mod score_math {
    pub fn add_bonus(value: i32, bonus: i32) -> i32 {
        return value + bonus;
    }
    pub fn double(value: i32) -> i32 {
        return value + value;
    }
}

using score_math;

@test "using module turns functions into chainable calls"() {
    let base: i32 = 10;
    let score = base.add_bonus(5).double();   // 30
    if score != 30 { panic(34000); };
}

using also acts on modules brought in via @import (demos/syntax_sugar/using_module_import/main.sla), and can be layered with impl methods:

using math;

impl Meter {
    fn double(self) -> i32 {
        return self.value.double();   // 调到 using 进来的扩展
    }
}
WarningModule-level method-style calls must explicitly declare using; without using, a chained call to a non-impl method reports "method not found" in the frontend.

The resolution order of method calls is fixed: inherent (impl) methods → trait methods → using static extensions → loudly undefined; multiple candidates within the same layer report an ambiguity error (Ambiguous static extension call), with no fallback rerouting.

Top-level const and the initialization contract

SLA has no top-level mutable state form: top-level declarations contain only const, with no var / global declaration node. The "top-level initialization" contract therefore splits into a compile-time const side and a runtime globals side:

  • const is compile-time constructed, with no runtime evaluation order: the checker runs a dedicated pass before examining functions, registering top-level consts one by one in expanded declaration order, checking the initializer and defining the symbol at registration time. A reference can only reach what is already registered: referencing a const that comes later fails on the code path with UndefinedVariable (this failure form is inferred from the code path and has not been probe-verified); alias cycles (const A = B; const B = A;) fail the same way — loudly, but the diagnostic name is undefined variable, with no dedicated cycle diagnostic.
  • Codegen folding is independent of declaration order: scalar consts (literals, scalar aliases, scalar binary expressions) are folded hop by hop with an iterative fixed point and inlined at use sites, generating no runtime code. This forms a name/reality mismatch with the checker's registration order: the folder could handle forward references, but the checker rejects first — that is the current state; when writing programs, go by registration order.
  • Non-scalar consts are static data: string / array / struct literals and vtable forms (including @embed desugaring products) are emitted as SA @const static data into the data section; there is no evaluation action at program start and no order to speak of.
  • Import expansion order: depth-first, dependencies first, each module expanded only once; import cycles terminate naturally through deduplication (no error, no repeated expansion). The expansion order is the cross-module part of the const registration order.
  • Runtime globals (sa_global_*) have no static initialization: there is no initialization section before main; entries are created lazily at the execution point by the first runtime set / add / set_once, and a get on an unbuilt key returns the status code NOT_FOUND=3 and does not write the out-parameter. Hence the "initialization order" of globals is the program execution order itself. Spellings that expect a 0 value from a get on an unbuilt key do not conform to this contract (the gap in the syntax batch's signature D came from this). For the synchronization discipline of globals, see section 12, the memory model, of the goroutine runtime page.
