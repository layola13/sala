bc2sa — LLVM Bitcode Reverse Translator

Zig 0.17This plugin is built with Zig 0.17: the 0.17 branch builds with Zig 0.17 and passes the Zig unit tests; the old 0.14.1 branch is kept unchanged.

sa_plugin_bc2sa reverse-translates a conservative subset of LLVM bitcode into SA text; it is one of the three cross-language entry points the sci homepage promises externally (alongside ts/deno/node/sla):

Rust / C++ → clang / rustc → LLVM bitcode → sa bc2sa → SA 文本 → sa build-exe

Its positioning is "letting real C/C++/Rust projects plug into the SA pipeline", not a complete C memory-safety prover — the upstream FAQ states this boundary explicitly. This plugin has no README; the authoritative materials are sap.json, src/llvm2sa.zig, docs/bc2sa_evaluation_cn.md (a completeness self-assessment), and tests/install_smoke.sh.

Basic facts

ItemContent
Capability segment / commandbc2sa <file.bc> (also accepts .ll text input); the translation result is written to stdout
Interface contractNo .sai/.sal — translation happens via the CLI/stdout and does not enter the runtime
PermissionsRead the project directory; the child-process whitelist has exactly one entry: /usr/bin/llvm-dis-14 -o - * (a hard dependency on this exact path; see the Windows note below)
DependenciesNo other plugin dependencies; the LLVM 14 llvm-dis/llvm-as toolchain

Usage flow

# 冒烟用法（来自 tests/install_smoke.sh）
llvm-as-14 install_smoke.ll -o install_smoke.bc   # 或 clang -emit-llvm -c foo.c -o foo.bc
SA_PLUGIN_DEV=1 sa bc2sa install_smoke.bc
# 预期输出包含 @export main() -> i32: 与 return 0

# 典型完整路径
clang --target=x86_64-linux-gnu -O0 -emit-llvm -c add.c -o add.bc    # O0 避免 phi（见限制）
sa bc2sa add.bc > add.sa                                             # 翻译为 SA 文本
sa build-exe ...                                                     # 与手写 SA 相同的后续管线

# rustc 路线（同样建议关闭优化）
rustc --emit=llvm-bc -C opt-level=0 lib.rs -o lib.bc
NoteBitcode input is disassembled into .ll by the llvm-dis-14 child process and then parsed; giving a .ll file directly skips this step. -O0 is not a style preference but a hard constraint: O1 and above generate large amounts of phi, and phi is not yet supported.

Static rejection policy and diagnostics

When a getelementptr can be proven to cross a fixed array bound, it directly returns StaticMemoryOverflow, and the CLI exits with the structured diagnostic SA-CLI-019. This policy only covers statically resolvable constant offsets and fixed array bounds; it does not promise a full proof of complete C memory safety; other undecidable cases are handled as UnsupportedInstruction.

Current state and maturity

  • progress.md marks Overall 100%, but its scope is "the 4 declared features" (the permission list, static GEP out-of-bounds detection, the SA-CLI-019 mapping, the install smoke test); it does not represent translation coverage.
  • The evaluation document's honest conclusion: the missing phi is a blocking defect — any bitcode at O1 or above, or with rustc's default optimizations, will fail; the missing switch/select knocks out another large share of real C/Rust expressions; test coverage is low; call translation lacks ownership-prefix inference; error diagnostics are coarse-grained.
  • Conclusion: treat it as an experimental tool, suitable for plugging in small, unoptimized, floating-point-free leaf functions; it should not be advertised as a general Rust/C++ migration channel. The P0 improvement route is to complete a minimally usable baseline for phi/switch/select.
WarningOn Windows, the /usr/bin/llvm-dis-14 whitelist path is in Linux form; using bc2sa on this machine requires providing a compatible child-process environment (WSL, etc.), or explicitly allowing the local llvm-dis path in the sap.json permissions. The packaging script only warns about missing llvm-dis/llvm-as; it does not block packaging.

FFI or bc2sa: how to choose between the two access paths

There are two opposite-direction paths for bringing external code into SA; see FFI vs bc2sa for details: FFI (@extern "C" exports/imports + unsafe calls, connecting directly to native code via the ABI at runtime, see the rosetta demo 111_extern_c_abi) suits calling ready-made dynamic libraries; bc2sa translates external source in as SA text, suiting a small amount of in-house C/Rust source that must be included in SA verification/release artifacts. The former is mature and usable; the latter is still experimental.
