The Problem: The Plugin Classification Is Missing “Language Frontend”

When the plugin system was first designed there was only one plugin shape — tools that register CLI subcommands (vm, db, and so on). Forcing SLA into that model is a classification error: in theory SLA is an independent language, and its relationship to the host is not “the host gains one more command” but “the host gains one more source language”. The mismatch has already produced real costs:

  • A language frontend has to guess where its standard library is. Discovery of the std surface once relied on probing multiple candidates relative to the exe path — the host should hand the std location, the target list, and capability information to the frontend explicitly; probing is a symptom of a missing interface.
  • The language's user experience is cut in two. Checking SLA code means typing sa sla check (host command → plugin subcommand → the plugin's own subcommand), so .sla is a second-class source file and only .sa is first-class.
  • Compiler-level responsibilities are reinvented inside the plugin. Compilation-pipeline infrastructure such as the freshness gate and cache keys grew inside the SLA plugin; a second frontend in future would have to build it all again.

The fix is not a hidden special case for SLA (if name == "sla" is the worst solution), but completing the plugin classification.

Improvement 1: Plugins Get a kind, and SLA Becomes a Language Frontend

kindMembersContract with the host
commandvm, db, framework-wrapper plugins (current state, unchanged)Registers CLI subcommands; dynamic command dispatch ABI
language (new)SLA (the first, and currently the only one)Compilation service protocol; see below
  • Manifest frontend declaration: kind, the owned extensions (.sla), language version, compatible SA version range, and compilation entry point.
  • The host dispatches by extension: sa check app.sla, sa build-exe app.sla, and sa build-wasm app.sla reach it in one step — the host recognizes that the extension belongs to a language frontend, calls it first to lower to SA/SAB, then runs the rest of the pipeline in the same invocation, with diagnostics merged into one output (the existing structured JSON format). The two-level sa sla * commands are kept during a transition period with a deprecation hint, and eventually deleted; the standalone sla command is kept as a thin alias.
  • The frontend contract is a compilation service, not a subcommand: the host explicitly passes in the source file, the target triple, the std directory, and the current capability and policy context; the frontend returns SA/SAB artifacts + structured diagnostics + cache-key information. What the host knows, the frontend must not guess again.
  • Caching moves up: the freshness mechanism based on content hashes + the dependency graph becomes a general host cache service that frontends consume by declaring inputs and outputs; SLA's freshness gate is its first user.
  • Versions and tests are treated by language-spec standards: a frontend ABI change counts as a toolchain event (with migration notes); the host's four-backend matrix runs “via the SLA frontend” as a first-class path. The classification is tailored to SLA's real needs; no abstractions are reserved for an imagined second language.

Improvement 2: Dev Mode and Formal Mode — Division of Labor Retained, Order Unchanged

First, the current state (the actual decisions in sci plugins.zig):

Formal mode (default)Dev mode (SA_PLUGIN_DEV=1)
InstallationThe permissions declared in the manifest are confirmed and rendered into a permissions.lock stored in the install directorysa plugin install --dev <directory> installs directly from a local source directory, and the lock carries a dev marker
RunningFor a privileged plugin, all three are indispensable: the lock exists, runtime sandbox/broker enforcement is active, and it was not dev-installed (a dev-installed plugin is named and rejected separately in formal mode)Setting the environment variable counts as a trusted development environment; the formal-mode interceptions are exempted as a whole
Trust assumptionThe plugin is foreign code: declare first, get confirmation, lock it, and be enforced at runtimeThe code is your own: safety rests on “you trust it”, not on enforcement

Decision: the two permission systems do not conflict; both are retained. There was once a concern that permissions.lock overlaps with the runtime permission system and should be merged; that was a misjudgment — their meanings differ:

  • permissions.lock is the install-time confirmation layer: like an APK install asking the user to confirm permissions, it sets the ceiling of “the most a plugin may ask for”.
  • The runtime permission system is the runtime detection layer: what this run actually allows is checked case by case, by policy, context, and one-time tokens, at the moment an effect occurs.
  • What a run actually allows = the intersection of the two layers: runtime policy cannot amplify permissions that were not confirmed at install time; this is the same principle as “authorization flows top-down and can only tighten”, in two instances.

Dev mode is retained for now. Its tension with the new permission system is real (an environment variable that turns off enforcement vs “every running state must have a policy with a clear provenance”), but the handling order is locked and no step may be skipped: frontend kind lands → runtime permission system phase 1 lands → dev's replacements (the official dev preset policy: enabled in one line, going through the same auditing; and workspace plugin declarations: a project configuration explicitly declares a directory as the workspace version of a plugin, committed to the repository and reviewable) mature in our own workflow → only then is deleting dev even discussable. One discipline applies while it is retained: no new feature may be built on top of dev mode; existing usage is frozen, and the migration surface only shrinks, never grows.

Improvement 3: Failure Diagnostics Must Be Written for Large Models

In development, the operator of the toolchain is often an LLM: why a plugin install/run failed, and how to switch to dev after a failure, must be explained by the error message itself. The specification requires all three parts:

  1. Cause: which gate intercepted it, and exactly which item (lock missing / a dev-installed plugin entered formal mode / sandbox not active), with a machine-readable error code, in the existing structured diagnostics format.
  2. Development-path remedy: a directly executable command — SA_PLUGIN_DEV=1 sa plugin install --dev <directory> — together with a verification command (sa plugin list), so copying it just works.
  3. Formal-path remedy: how to confirm permissions and how to reinstall formally, with the full steps.
WarningError-message wording trains the operator's behavior. If every failure pushes only the dev path, a large model will learn “on any failure, apply dev first”, and formal mode will be hollowed out by its own error messages. Remedies must therefore be labeled per scenario: the dev path always carries an “only for trusted development” warning, and the formal path gives the full steps — the operator chooses by context, not by convenience. The current state is half done: the dev-installed error has both cause and remedy, while the permissions.lock-missing one has only the cause and no next step, and needs to be completed to this specification.

Improvement 4: The Confirmation Layer Belongs to the Host, Decoupled from Distribution Channels

Plugins have not yet been formally published to any package repository, so the model is settled correctly here first: permission confirmation is the host's (the sa runtime's) responsibility, not the distribution channel's. Take npm as an example — npm's model is “install means trust”: permissions are at most self-declared in package.json, install scripts execute automatically, and there is no conversational confirmation anywhere. If confirmation were bound to one channel's install flow, changing channels would break the defense.

  • The confirmation moment moves to the host's first load: wherever a plugin comes from (sa plugin install, npm, manual copying, git), it passes through the same gate at the host — if the manifest declaration matches the stored lock, it loads; if there is no lock, confirmation is triggered and a lock is generated.
  • A declaration change must be re-confirmed: if a plugin upgrade adds permission declarations, the old lock cannot cover the new parts. This is the core lesson learned from Android/Chrome's “re-prompt when an update adds permissions”.
  • Non-interactive environments have no dialog to pop up: use an explicit confirmation command (such as sa plugin confirm <name>) + a clear error, executed proactively by the operator. Never pass silently — no confirmation record means no load.
  • The iron rule for a future npm route: a package must be inert during npm installation — it only drops files and executes no code (a postinstall runs before confirmation and with the user's full authority; that is a hole). Code may execute for the first time only when the host confirms and loads the plugin.

Improvement 5: Plugin Namespaces — References Must Be Qualified by Plugin Name

The current plugin system is a flat top-level space on all four surfaces (source-verified on 2026-10-25): interface imports try each plugin's import root in turn by bare path, with the first hit winning silently, so when two plugins carry a same-named interface file the importer has no way to qualify it and the host reports no error; extern symbols form a single global space, and at install time any cross-plugin same-named symbol is refused outright, so once a symbol name is taken it can never be reused globally; CLI commands are claimed by each plugin's command handler in load order for unknown top-level commands, with no declaration and no conflict diagnostics; plugin identity and dependencies are single-segment names + bare-name references. The consequence is exactly the “renaming import problem”: renaming a plugin does not carry its interface files along, renaming an interface file silently breaks all importers, and changing a declaration order for a same-named file swaps the implementation. By contrast, standard-library imports have long had the reserved sa_std/ prefix and package imports have an identity system — only plugin interface imports use bare names.

Decision: all references are qualified by plugin name, with each of the four surfaces closed off separately.

  • Qualified import names (the core): a plugin interface import is written plugin/<plugin name>/<relative path>, a reserved prefix isomorphic to sa_std/; resolution happens only inside that plugin's import root, and if the named plugin does not exist or has no such file, it is clearly unresolved, with no fallback to other plugins and no fallback to bare-name search. The plugin name is derived from the import-root layout (installed/<name>/current/sa, with workspace staging isomorphic).
  • Symbol prefix convention: extern symbols exported by new plugins should be prefixed with sa_plugin_<name>_; refining the install-conflict criterion (a same name counts as a conflict only when the prefix belongs to different plugins) is phase 2; phase 1 establishes the convention first.
  • Command declaration: sap.json gains an optional commands declaration and the host builds a command index; when multiple plugins claim the same command word, a diagnostic is produced at load time naming the claimants and the winner. Phase 2.
  • Identity: single-segment names are kept, with no scope syntax introduced; a rename counts as a new plugin, and dependents explicitly change their declarations and qualified imports — the purpose of a namespace is precisely to make the whole cost of a rename appear at the reference sites, rather than as a silent misalignment.

Phasing: phase 1 = qualified-name imports (landed; see the status note) + the decision in this section; phase 2 = explicit diagnostics for bare names hitting the same name in multiple roots, install hints for extern prefixes, and the commands declaration and index (landed; see below); phase 3 considers retiring bare names, depending on migration.

Phase 2 implementation status (2026-10-25): First, bare-name ambiguity diagnostics — the resolver's ResolveOptions gained a diagnostics callback; after a bare-name import hits in the first import root, the remaining roots are scanned in an existence-only way (the same normalization and in-root containment checks, without reading files), and if a same-named provider is found, one diagnostic is produced: naming the import path, the winning plugin, and the shadowed plugins, and suggesting a rewrite to plugin/<plugin name>/...; the CLI wires the callback to stderr in both compilation and source-graph resolution options, and a diagnostic never makes resolution fail. pkg-core-test gained cases: with two roots carrying the same name, the first root wins and exactly one diagnostic naming both sides is produced; a single-root provider and a qualified-name import produce no diagnostic. Second, extern prefix install hints — after the conflict check, install validation adds an advisory check: the canonical prefix is sa_plugin_<name>_ (hyphens in the plugin name become underscores); the existing sa_<name>_ family and sa_std_ count as already inside a namespace; symbols matching none of the three are listed one by one in the install output with renaming guidance, hint only, never blocking installation. plugin-host-smoke gained cases covering a loose name being called out, and canonical and legacy-family names producing no hint. Third, the commands declaration and command index — sap.json can declare commands (single-token validation: an empty string or one containing whitespace/slashes makes the manifest invalid); at plugin load time the runtime registers declarations into the command index, the first claimant wins, a later same-named claim is skipped and produces a load diagnostic (naming the command and both plugins); at dispatch time a declared command goes straight to its claimant whose response (including unknown_command) is authoritative, while undeclared commands keep the original load-order claiming. plugin-host-smoke gained registry cases and two-plugin dispatch cases (including the interaction with the language-frontend deprecation hint).

Distribution Channel: npm Publishing and Installation (Supported by Default)

On 2026-10-25 the user set the tone: all plugins must support npm publishing and installation by default. This implements the forward-looking decision made earlier in this page's confirmation-layer section — confirmation belongs to the host and is channel-independent; a channel is only responsible for dropping files. The two sides take the following shape.

  • Publishing side: each plugin repository root carries a publishable package.json: package name sa-plugin-<plugin name> (underscores become hyphens), version in sync with sap.json; the files allowlist covers sap.json, build.zig, src, and all build inputs actually referenced by that plugin's build.zig (verified per repository with npm pack --dry-run, nothing missing); never any lifecycle scripts (preinstall/install/postinstall) — the package must be inert. Repositories that already used a package.json for tools (the *-tools of mui/react/sax) have been merged into the same manifest: tool scripts and devDependencies are kept (they are not lifecycle scripts and do not run at install time), private is removed, and the name is changed to the distribution name.
  • Installation side: sa plugin install npm:<name>[@<version>]. The host fetches package metadata from the registry (default registry.npmjs.org, overridable with SA_NPM_REGISTRY), selects a version (defaulting to dist-tags.latest), downloads its tarball, first verifies the bytes against the integrity issued by the registry (sha512 SRI; sha1 when only shasum is present), then unpacks, checks for lifecycle scripts (refusing installation with a stated reason if any exist), and finally hands the source tree to exactly the same install pipeline as a local path — build, permissions.lock, and first-load confirmation do not change with the channel.
  • Formal-mode threshold (the same as the git/archive remote channels): an npm install must write an exact version (a floating version is a moving target, allowed only in dev), and must confirm the registry target verbatim, by registry page URL, in a TTY; a registry response missing an integrity digest is always refused — there is no “no digest but still trusted” fallback.
  • Known constraint: except for mui, the existing plugins' build.zig files reference host modules (plugin_api, sa_io, etc.) via ../sci/..., which holds in the source-tree layout but not after relocation. So on the npm channel these plugins are currently “publishable, installable up to just before the build step”; a passing build awaits each repository making its build self-contained, after which they will be verified one by one; mui has already passed end-to-end measurement. This constraint also applies to the existing git/archive remote channels; it is not unique to npm.
