http-server — Embedded HTTP Server

Status (2026-10-24)The HTTP server kernel is now built into sa_std: the implementation lives in sci src/runtime/sa_http_server.zig (shipped with libsa_std.a, 46 sa_http_server_* symbols), and the declarations live in sa_std/http_server.sai. You do not need to install this plugin to use the full server capability; sa_plugin_http_server (since v0.3.0) now keeps only a framework-layer wrapper. A plugin is only a wrapper for interface usage habits, and does not mean the substance should be pushed down into a plugin (see the architecture principles in the Plugin Reference Overview).
Zig 0.17This plugin is built with Zig 0.17: the 0.17 branch builds successfully with Zig 0.17 and passes the Zig unit tests; the old 0.14.1 branch is left untouched.

This page gives the complete reference for sa_plugin_http_server: the localhost-only permission boundary under the install policy, install verification, the sap.json permission model, the v1 and v2 ABIs' signatures and semantics item by item, the complete usage of the scaffold/serve commands, and end-to-end examples taken from real repository files. After reading this page you can write a complete server loop of “accept → read request → send response (one-shot or streaming) → close”, and know clearly what it does not intend to do.

http-server provides an HTTP/1.1 server embedded in an SA program: it lets .sa code accept connections directly, read requests, and send responses. This directory has no README; the authoritative sources are sap.json, sa_http_server.sai, the shared core implementation src/vite_api.zig, and docs/plugin_evaluation_cn.md (a copy of the four-plugin joint evaluation document, evaluation date 2026-06-15).

Positioning: Install Permissions Are localhost-only; the Source ABI Accepts IP Hosts

  • sap.json declares only two listening targets: http://localhost and http://127.0.0.1. While the plugin permission policy is unchanged, the installed capability remains loopback-only and cannot be treated as a public listener.
  • The source ABI's actual boundary differs: sa_http_server_start(_v2) takes a host string and a port, and the core parses the IP via std.net.Address.parseIp(host, port); the source layer does not hardcode the host to localhost, so IPs such as 0.0.0.0 can be parsed and handed to the listener. Whether use is allowed is still decided by sap.json and host policy.
  • Why this is right (evaluation document §1.3): for internal microservices, the SAX dev server, and localhost-only IPC this is the correct choice; at the same time, “no https:// listening” is consistent with the declaration — the server has no TLS, but sap.json does not pretend it can do TLS either, which is an honest declaration; TLS is borne by a reverse proxy.
  • Known gap: the manifest has no IPv6/non-loopback net permission, so under policy control [::1], 0.0.0.0, and other public addresses still cannot be relied on; in addition, this plugin provides no TLS. That the source can parse an address does not mean install permission has been opened. The evaluation document explicitly noted that “no documentation made this boundary clear” was a shortcoming at the time; this page records the distinction between source capability and manifest capability together.
  • The host argument must be an IP literal: the implementation goes through std.net.Address.parseIp(host, port) (HttpServer.startWithOptions in src/vite_api.zig), and a hostname string will not be resolved. start always carries reuse_address = true.
  • The same core is also reused by vite: vite's sap.json pins 18 sa_http_server_* symbols for static serving and SSE live signals.
  • Application facades such as deno — Deno-Compatible API Plugin / node — Node.js Compatibility Facade likewise reference a small number of symbols as needed (deno references sa_http_server_new / _resp_set_content_type / _resp_stream_write).

Build and Install Commands

This repository's README gives no verification steps; the following flow matches the READMEs of same-generation plugins and corresponds exactly to the build.zig in the directory (the same test step, the same SCI dependency), executed inside the plugin source directory:

# 在 D:/projects/sla/sa_plugin_http_server 目录内
timeout 300s env SA_PLUGIN_DEV=1 zig build test     # tests/plugin_test.zig 全部测试
timeout 300s env SA_PLUGIN_DEV=1 zig build          # 生成 zig-out/lib/libhttp-server.so
timeout 120s env SA_PLUGIN_DEV=1 sa plugin install --dev .
timeout 30s  env SA_PLUGIN_DEV=1 sa plugin list     # 验证已注册
  • The Zig build uses the sibling SCI checkout (../../sci) by default; override with -Dsci-root=/absolute/path/to/sci when needed.
  • At compile time, build.zig reads in the full text of sa_http_server.sai and injects it as the constant interface_source — this is exactly the source of the interface file the scaffold command writes out, guaranteeing that scaffold output matches the real contract byte for byte (asserted by a test).
  • At runtime a SIGPIPE handler is installed, so an SSE client disconnecting does not kill the whole process with a signal (the test is named http server runtime installs SIGPIPE handler for broken SSE sockets).

NoteThe ABI uses opaque handles (ptr) plus explicit _free release, an ownership style conforming to the plugin ABI constraints in design.md §1.7.1; v1 return values follow the host descriptor's AbiStatus (ok=0 / failed=2 etc.), while v2 returns the independent seven network status codes (see the status-code table on the http-client — HTTP Client page; the two plugins share the same table). The polling interest/event bits are likewise readable=1, writable=2, closed=4.

Streaming Response Form (5)

SignatureSemantics
sa_http_server_resp_stream_new(req: ptr, status: u16, &out_resp: ptr) -> u32Immediately sends the streaming response headers. The default header is content-type: text/event-stream, with transfer-encoding: chunked and connection: close always appended — naturally suited to SSE

The v2 Increment Surface (21 Externs)

SignatureIncrement over v1
sa_http_server_new_v2(&out_server: ptr) -> u32 / sa_http_server_start_v2(server, &host, host_len, port)Same shape as v1, returning network status codes
sa_http_server_accept_v2(server: ptr, timeout_ms: u32, &out_req: ptr) -> u32Pollable accept: with timeout_ms=0 and no connection it returns would_block(1); a positive timeout expiring returns timeout(3); a partial request (only part of the headers sent) is likewise treated as a timeout. The request-body limit is raised to max_v2_message_bytes (16 MiB), and the receive timeout is set from the remainder of the total budget after deducting time already spent in poll
sa_http_server_resp_new_v2(req, status, &out_resp)Status-code validity check: outside 100..599 it returns invalid(5) (v1 has no such check)
sa_http_server_req_free_v2(req: ptr) -> u32Releases the request
sa_http_server_resp_send_v2(resp: ptr, &body: ptr, body_len: u64, timeout_ms: u32) -> u32 / sa_http_server_resp_free_v2(resp: ptr) -> u32Sending with a millisecond timeout; when the response body exceeds the message limit, sending is refused with too_large(4) (tests confirm a small response body can still be sent normally afterwards)
sa_http_server_resp_add_header_v2(resp, &name, name_len, &value, value_len) -> u32Arbitrary response headers: the value is copied (the caller rewriting the original buffer afterwards does not affect the stored value); same-named headers may repeat (e.g. two set-cookie headers); a header with a CRLF injection attempt returns invalid(5)
sa_http_server_resp_stream_new_v2 / _add_header_v2 / _write_v2(..., timeout_ms) / _flush_v2 / _end_v2(..., timeout_ms) / _free_v2The streaming form gains “arbitrary headers can be added before headers are sent” and a per-chunk write timeout; the rest behaves as the v1 streaming form
sa_http_server_free_v2(server: ptr) -> u32Releases the server
sa_http_server_websocket_upgrade_v2(req: ptr, &out_ws: ptr) -> u32On top of the v1 validation it additionally requires sec-websocket-version: 13 and a legitimate key, then switches the socket to non-blocking mode; failure returns invalid(5); on success the request handle is consumed
sa_http_server_websocket_poll_v2(ws, interests, timeout_ms, &events)Polls by readable/writable/closed interest bits; zero-timeout not-ready is would_block
sa_http_server_websocket_read_v2(ws, max_len, &opcode, &data, &len)Non-blocking read, reassembling fragmented messages, with the limit max_v2_message_bytes (16 MiB)
sa_http_server_websocket_write_v2(ws, opcode, &data, data_len, &written) -> u32Non-blocking write: when the socket send buffer fills it returns would_block(1) with written=0 (backpressure is observable); over-limit returns too_large(4); writing after close returns closed(2)
sa_http_server_websocket_close_v2(ws, code: u16, &reason, reason_len) -> u32Performs the protocol-level close handshake
sa_http_server_websocket_free_v2(ws: ptr) -> u32Closes and releases

The backpressure recovery path: write fills → would_block is received → poll with the writable interest bit, and continue writing once ready. This behavior has a dedicated test (http server v2 websocket reports and recovers from bounded backpressure, in which SO_SNDBUF is squeezed to 4096 bytes to manufacture backpressure).

CLI Commands: scaffold and serve

sa http-server scaffold <dir>

Generates a concrete HubProxy starter project. There is a single argument, the target directory; three files are produced (the implementation is runHttpServerCommand in src/plugin.zig):

OutputContent
<dir>/sa_http_server.saiThe compile-time embedded interface_source, byte-for-byte identical to the plugin's real contract (a test asserts the consistency)
<dir>/main.saAn entry skeleton @export hubproxy_main(): L_ENTRY: panic(102)
<dir>/README.mdGenerated explanatory text: fill in the HTTP handler and connect it to sa_http_server; and noting that “http-server serve is this plugin's minimal runtime smoke test”

On success, stdout prints the directory name and exits with 0; a usage error hints in the form usage: sa http-server scaffold <dir>, and an unknown subcommand hints “supported HTTP server subcommands are scaffold and serve”. CLI errors uniformly carry the prefix error[SA-HTTP-SERVER-CLI]: plus a help: line.

sa http-server serve <host> <port> [max-requests]

usage: sa http-server serve <host> <port> [max-requests]
  • After the third operand there may be an optional maximum request count; without it the loop is infinite (poll interval 1000ms), with it the process exits with 0 after handling N requests (poll interval 100ms).
  • The listening socket is established with reuse_address + force_nonblocking; each accepted connection is switched back to blocking mode with a 2000ms receive timeout.
  • Three built-in routes (handleRoute):
    • /echo — reads in the request body and sends it back as-is, with the request's content-type; stdout records route=echo path=/echo body=<n>.
    • /stream — chunked SSE: pushes data: first\n\n then data: second\n\n in turn (sleeping 10ms between chunks); stdout records route=stream path=/stream.
    • Other paths — replies 404 not found\n, and stderr prints error: unknown route <path>.
  • Port and address behavior: the host must be parseable by parseIp (e.g. 127.0.0.1), and the port is a decimal u16. When the host is not an IP literal or the port is not a legitimate number, it reports error[SA-HTTP-SERVER-CLI]: invalid HTTP server path or address plus a usage line; other listen errors, such as the port already being in use, are not in this CLI diagnostic mapping and end with a plugin failure status rather than diagnostic output with a help line.
  • The serve loop itself handles requests serially on a single thread: one request is fully handled before the next is accepted. It is a smoke tool, not a concurrent server.

SSE / Streaming Feature Summary

  • Streaming responses are fixed to text/event-stream + chunked + connection: close, connecting to EventSource with no hand-assembled headers.
  • SIGPIPE is already handled at the runtime layer, so a client disconnecting midway does not kill the process.
  • The request-side body limit is 2 MiB (the v1 default accept behavior); the response-side v2 message limit is 16 MiB.
  • For a real SSE consumer-side example, see the vite plugin: the browser receives reload/error events via the /__sax_live SSE channel, whose server side is exactly this plugin's core.

    hdr_status  = call @sa_http_server_req_get_header(req, &HDR_KEY, 12, &hdr_ptr_slot, &hdr_len_slot)

The v2 WebSocket Server Form

The repository has no SA source-level example for v2 WebSocket yet, only Zig tests (http server v2 websocket polls fragmented messages and performs protocol close in tests/plugin_test.zig). The call order based on the contract signatures is as follows:

srv = sa_http_server_new_v2()
sa_http_server_start_v2(srv, "127.0.0.1", 18087)
req = sa_http_server_accept_v2(srv, 1000)          ; would_block / timeout / ok
ws  = sa_http_server_websocket_upgrade_v2(req)     ; 要求 Sec-WebSocket-Version: 13
                                                    ; 成功后 req 已被消费，勿再 free
loop: st = sa_http_server_websocket_poll_v2(ws, 1 /*readable*/, 250, &events)
      st == 0 且 events & 1 时：
        opcode/data = sa_http_server_websocket_read_v2(ws, 16MiB)
        written     = sa_http_server_websocket_write_v2(ws, 1, reply)
      写满得到 would_block 时改 poll writable(2) 等恢复
sa_http_server_websocket_close_v2(ws, 1000, "done")
sa_http_server_websocket_free_v2(ws)
sa_http_server_free_v2(srv)

Boundaries: What Is Explicitly Not Done

WarningThe following items are explicitly placed out of scope in the documentation (evaluation document §1.4, §6.4): no TLS/HTTPS listening (the positioning states it relies on an nginx/caddy reverse proxy); no production listening (0.0.0.0 or custom port ranges are not allowed); no IPv6 [::1]; no reverse proxy, mTLS, HTTP/2 / HTTP/3; no large-file multipart streaming upload; no connection-timeout / keep-alive tuning API, access log, or metrics hook; handler routing and middleware abstractions are not done at the native layer (a macro facade layer in sa_std is recommended). Completeness scores (2026-06-15 caliber): ABI design 95%, HTTP/1.1 subset 80%, TLS/WebSocket 0% at the time, production listening 0%, test coverage 30%, documentation 10%, security model 100%, overall about 60-65% — the positioning is a localhost dev / internal IPC server, not a production-grade HTTP server.
Another source needs its caliber distinguished: on the SCI side, docs/http_server_plugin.md describes “route dispatch, a middleware pipeline, multi-tenant forwarding (Proxying), and io_uring zero-copy” as target architecture directions, and its example APIs (such as sa_http_server_route, sa_http_req_from_ticket, returning -> i32!) do not match the plugin repository's real sa_http_server.sai; that document itself also states that “the real implementation is defined by that project's source and smoke tests”. When judging current capability, therefore, take the .sai contract and the source cited on this page as authoritative; capabilities such as a reverse proxy belong to design direction, not the current state.
