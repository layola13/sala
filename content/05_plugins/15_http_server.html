http-server — 内嵌 HTTP 服务端

本页给出 sa_plugin_http_server 的完整参考：安装策略下的 localhost-only 权限边界、 安装验证、sap.json 权限模型、v1 与 v2 两套 ABI 的逐条签名与语义、 scaffold/serve 命令的完整用法，以及取自真实仓库文件的端到端示例。 读完本页你可以写出「accept → 读请求 → 发响应（一次性或流式）→ 关闭」的完整服务端循环， 并清楚知道它不打算做什么。

http-server 提供 SA 程序内嵌的 HTTP/1.1 服务端：让 .sa 代码直接 accept 连接、 读请求、发响应。该目录没有 README，权威资料是 sap.json、sa_http_server.sai、 共享核心实现 src/vite_api.zig 与 docs/plugin_evaluation_cn.md （四插件合并评估文档的一份拷贝，评估日期 2026-06-15）。

定位：安装权限是 localhost-only，源码 ABI 接受 IP host

  • sap.json 只声明两处监听目标：http://localhost 与 http://127.0.0.1。在插件权限策略不变时，安装后的能力仍是 loopback-only， 不能把它当成公开监听器。
  • 源码 ABI 的实际边界不同：sa_http_server_start(_v2) 接收 host 字符串和端口，核心通过 std.net.Address.parseIp(host, port) 解析 IP；源码层并没有把 host 写死为 localhost，因此 0.0.0.0 等 IP 可以被 解析并交给监听器。是否允许使用，仍由 sap.json 和宿主策略决定。
  • 为什么这样是对的（评估文档 §1.3）：对内部 microservice、SAX dev server、 localhost-only IPC 而言这是正确选择；同时「无 https:// 监听」与声明一致—— server 没有 TLS，但 sap.json 也没假装能做 TLS，属于诚实声明，TLS 由反向代理承担。
  • 已知缺口：manifest 没有 IPv6/非回环 net 权限，因此策略控制下的 [::1]、0.0.0.0 或其他公开地址仍不可依赖；此外本插件不提供 TLS。 源码能解析地址不等于安装权限已经开放。评估文档明确指出「没有文档说清楚这个边界」 是当时的不足，本页同时记录源码能力和 manifest 能力的区别。
  • host 参数必须是 IP 字面量：实现走 std.net.Address.parseIp(host, port) （src/vite_api.zig 的 HttpServer.startWithOptions）， 传主机名字符串不会解析。start 固定带 reuse_address = true。
  • 同一份核心也被 vite 复用：vite 的 sap.json 钉死了 18 个 sa_http_server_* 符号做静态服务与 SSE 实时信号。
  • deno / node 等应用门面同样按需引用 少量符号（deno 引用 sa_http_server_new / _resp_set_content_type / _resp_stream_write）。

构建与安装命令

本仓库没有 README 给出验证步骤，以下流程与同代插件的 README 一致，且与目录内的 build.zig 完全对应（同样的 test step、同样的 SCI 依赖），在插件源码目录内执行：

# 在 D:/projects/sla/sa_plugin_http_server 目录内
timeout 300s env SA_PLUGIN_DEV=1 zig build test     # tests/plugin_test.zig 全部测试
timeout 300s env SA_PLUGIN_DEV=1 zig build          # 生成 zig-out/lib/libhttp-server.so
timeout 120s env SA_PLUGIN_DEV=1 sa plugin install --dev .
timeout 30s  env SA_PLUGIN_DEV=1 sa plugin list     # 验证已注册
  • Zig 构建默认使用同级 SCI checkout（../../sci），需要时用 -Dsci-root=/absolute/path/to/sci 覆盖。
  • build.zig 在编译期读入 sa_http_server.sai 全文并注入为常量 interface_source —— 这正是 scaffold 命令写出的接口文件来源， 保证脚手架产物与真实契约逐字节一致（有测试断言）。
  • 运行时会安装 SIGPIPE 处理器，避免 SSE 客户端断开导致整个进程被信号杀死 （测试名即 http server runtime installs SIGPIPE handler for broken SSE sockets）。

v1 函数详表（18 个核心 extern，签名逐字摘录）

Server 生命周期（4 个）

签名语义
sa_http_server_new(&out_server: ptr) -> u32创建服务器句柄（首次调用同时装好 SIGPIPE 处理器）
sa_http_server_start(server: ptr, &host: ptr, host_len: u64, port: u16) -> u32在 host:port 上开始监听；host 必须是 IP 字面量；重复 start 是 no-op（已有 listener 时直接返回）
sa_http_server_accept(server: ptr, &out_req: ptr) -> u32阻塞 accept 一个连接并把请求头解析完毕。默认请求体上限 2 MiB（超限报错）；请求头缓冲 4096 字节；body 按 content-length 一次读全
sa_http_server_free(server: ptr) -> u32关闭监听 socket 并释放服务器

Request 读取（5 个）

签名语义
sa_http_server_req_get_method(req: ptr, &out_method: ptr, &out_len: ptr) -> u32借出方法字符串（如 "POST"）与其长度
sa_http_server_req_get_path(req: ptr, &out_path: ptr, &out_len: ptr) -> u32借出路径；target 中第一个 ? 之前的部分，即查询串已被剥掉
sa_http_server_req_get_header(req: ptr, &key: ptr, key_len: u64, &out_val: ptr, &out_len: ptr) -> u32按名查头（大小写不敏感）；找不到返回 failed
sa_http_server_req_get_body(req: ptr, &out_body: ptr, &out_len: ptr) -> u32借出完整请求体（accept 阶段已读入内存）
sa_http_server_req_free(req: ptr) -> u32释放请求（含其连接资源）。升级为 WebSocket 成功后会消费掉 request 句柄，此后不得再 free

Response 一次性形态（4 个）

签名语义
sa_http_server_resp_new(req: ptr, status: u16, &out_resp: ptr) -> u32以给定状态码构造响应
sa_http_server_resp_set_content_type(resp: ptr, &content_type: ptr, content_type_len: u64) -> u32设置唯一的响应头 content-type
sa_http_server_resp_send(resp: ptr, &body: ptr, body_len: u64) -> u32发送完整响应体并收尾。长度为 0 时允许传空指针（测试覆盖 204 + content-length: 0）
sa_http_server_resp_free(resp: ptr) -> u32释放响应对象

状态码文本映射由核心提供：200 OK、201 Created、204 No Content、 400 Bad Request、401 Unauthorized、404 Not Found、 500 Internal Server Error，其余状态一律回落为 OK。

Response 流式形态（5 个）

签名语义
sa_http_server_resp_stream_new(req: ptr, status: u16, &out_resp: ptr) -> u32立即发出流式响应头。默认头为 content-type: text/event-stream，并固定追加 transfer-encoding: chunked 与 connection: close —— 天然适配 SSE
sa_http_server_resp_stream_write(resp: ptr, &body: ptr, body_len: u64) -> u32写入一个 chunk：先写十六进制长度行，再写载荷与 \r\n
sa_http_server_resp_stream_flush(resp: ptr) -> u32刷新（当前实现为直写 socket，flush 是保持 ABI 形状的空操作）
sa_http_server_resp_stream_end(resp: ptr) -> u32写出终结块 0\r\n\r\n 结束 chunked 传输；重复调用安全
sa_http_server_resp_stream_free(resp: ptr) -> u32释放流式响应对象
注意流式形态的头部一旦发出便不可更改（v1 只有 content-type 可设）；需要额外响应头时应改用 v2 的 _resp_stream_add_header_v2， 或在 v2 里用延迟发头的方式先加头再写体。

遗留 WebSocket 导出（4 个，阻塞语义）

签名语义
sa_http_server_websocket_upgrade(req: ptr, &out_ws: ptr) -> u32校验 upgrade: websocket、connection 含 Upgrade token、存在 sec-websocket-key，计算 accept 值并回复 101 Switching Protocols；成功后 request 句柄被消费
sa_http_server_websocket_read(ws: ptr, max_len: u64, &out_opcode: ptr, &out_data: ptr, &out_len: ptr) -> u32读一帧（阻塞）
sa_http_server_websocket_write(ws: ptr, opcode: u8, &data: ptr, data_len: u64) -> u32写一帧（阻塞）
sa_http_server_websocket_free(ws: ptr) -> u32关闭底层 stream 并释放句柄

v2 增量面（21 个 extern）

签名相对 v1 的增量
sa_http_server_new_v2(&out_server: ptr) -> u32 / sa_http_server_start_v2(server, &host, host_len, port)同 v1 形状，返回网络状态码
sa_http_server_accept_v2(server: ptr, timeout_ms: u32, &out_req: ptr) -> u32可轮询的 accept：timeout_ms=0 无连接时返回 would_block(1)；正超时到期返回 timeout(3)；半截请求（只发了部分头）同样按超时处理。请求体上限提升到 max_v2_message_bytes（16 MiB），接收超时按总预算扣除 poll 已耗时后的余量设置
sa_http_server_resp_new_v2(req, status, &out_resp)状态码合法性校验：100..599 之外返回 invalid(5)（v1 无此校验）
sa_http_server_req_free_v2(req: ptr) -> u32释放请求
sa_http_server_resp_send_v2(resp: ptr, &body: ptr, body_len: u64, timeout_ms: u32) -> u32 / sa_http_server_resp_free_v2(resp: ptr) -> u32发送带毫秒超时；响应体超过消息上限时拒绝发送并返回 too_large(4)（测试确认随后仍可正常发送小响应体）
sa_http_server_resp_add_header_v2(resp, &name, name_len, &value, value_len) -> u32任意响应头：值会被复制（调用方随后改写原缓冲不影响已存值）；同名头可重复出现（如两条 set-cookie）；含 CRLF 注入企图的头返回 invalid(5)
sa_http_server_resp_stream_new_v2 / _add_header_v2 / _write_v2(..., timeout_ms) / _flush_v2 / _end_v2(..., timeout_ms) / _free_v2流式形态获得「发头前可加任意头」与逐块写超时；其余行为同 v1 流式
sa_http_server_free_v2(server: ptr) -> u32释放服务器
sa_http_server_websocket_upgrade_v2(req: ptr, &out_ws: ptr) -> u32在 v1 校验之上额外要求 sec-websocket-version: 13 与合法 key，然后把 socket 切到非阻塞模式；失败返回 invalid(5)；成功后 request 句柄被消费
sa_http_server_websocket_poll_v2(ws, interests, timeout_ms, &events)按 readable/writable/closed 关注位轮询；零超时未就绪为 would_block
sa_http_server_websocket_read_v2(ws, max_len, &opcode, &data, &len)非阻塞读，重组分片消息，上限 max_v2_message_bytes（16 MiB）
sa_http_server_websocket_write_v2(ws, opcode, &data, data_len, &written) -> u32非阻塞写：socket 发送缓冲打满时返回 would_block(1) 且 written=0（背压可观测）；超限返回 too_large(4)；关闭后再写返回 closed(2)
sa_http_server_websocket_close_v2(ws, code: u16, &reason, reason_len) -> u32执行协议级关闭握手
sa_http_server_websocket_free_v2(ws: ptr) -> u32关闭并释放

背压恢复路径：写满 → 收到 would_block → 用 writable 关注位 poll， 就绪后继续写。该行为有专门测试 （http server v2 websocket reports and recovers from bounded backpressure， 其中把 SO_SNDBUF 压到 4096 字节来制造背压）。

CLI 命令：scaffold 与 serve

sa http-server scaffold <dir>

生成一个具体的 HubProxy 起步工程。参数只有一个目标目录；产物三个文件 （实现见 src/plugin.zig 的 runHttpServerCommand）：

产物内容
<dir>/sa_http_server.sai编译期嵌入的 interface_source，与插件真实契约逐字节相同（有测试断言一致性）
<dir>/main.sa入口骨架 @export hubproxy_main(): L_ENTRY: panic(102)
<dir>/README.md生成的说明文字：要求填好 HTTP handler 并接到 sa_http_server；并注明「http-server serve 是本插件的最小运行时冒烟测试」

成功时 stdout 打印目录名并以 0 退出；用法错误提示形如 usage: sa http-server scaffold <dir>，未知子命令则提示 「supported HTTP server subcommands are scaffold and serve」。CLI 错误统一带前缀 error[SA-HTTP-SERVER-CLI]: 并附 help: 行。

sa http-server serve <host> <port> [max-requests]

usage: sa http-server serve <host> <port> [max-requests]
  • 第三个操作数之后可跟可选的最大请求数；不给则无限循环（poll 间隔 1000ms）， 给了则在处理完 N 个请求后以 0 退出（poll 间隔 100ms）。
  • 监听 socket 以 reuse_address + force_nonblocking 建立；每接受一个连接就把该连接 切回阻塞模式并设 2000ms 接收超时。
  • 内置三条路由（handleRoute）：
    • /echo —— 读入请求体并原样回发，附带请求的 content-type；stdout 记录 route=echo path=/echo body=<n>。
    • /stream —— chunked SSE：依次推 data: first\n\n、data: second\n\n （块间 sleep 10ms），stdout 记录 route=stream path=/stream。
    • 其他路径 —— 回复 404 not found\n，stderr 打印 error: unknown route <path>。
  • 端口与地址行为：host 必须能被 parseIp 解析（例如 127.0.0.1）， 端口是 u16 十进制。host 不是 IP 字面量或端口不是合法数字时，报 error[SA-HTTP-SERVER-CLI]: invalid HTTP server path or address 并附 usage 行； 端口已被占用等其它 listen 错误不在这条 CLI 诊断映射里，会以插件失败状态结束而不是带 help 行的诊断输出。
  • serve 循环本身单线程串行处理请求：一个请求处理完才 accept 下一个。 它是冒烟工具，不是并发服务器。

SSE / 流式特性小结

  • 流式响应固定 text/event-stream + chunked + connection: close， 无需手工拼头即可对接 EventSource。
  • SIGPIPE 已在运行时层处理，客户端中途断开不会击杀进程。
  • 请求侧 body 上限 2 MiB（v1 默认 accept 行为），响应侧 v2 消息上限 16 MiB。
  • 真正的 SSE 消费端示例见 vite 插件： 浏览器经 /__sax_live SSE 接收 reload/error 事件，其服务端正是本插件核心。

@const HOST    = utf8:"127.0.0.1"
@const HDR_KEY = utf8:"content-type"
@const CHUNK_1 = utf8:"data: first\n\n"
@const CHUNK_2 = utf8:"data: second\n\n"

@main() -> i32!:
L_ENTRY:
    server_slot = stack_alloc 8
    server_status = call @sa_http_server_new(&server_slot)
    server = load server_slot+0 as ptr
    start_status = call @sa_http_server_start(server, &HOST, 9, 18091)

    req_slot = stack_alloc 8
    accept_status = call @sa_http_server_accept(server, &req_slot)
    req = load req_slot+0 as ptr

    path_status = call @sa_http_server_req_get_path(req, &path_ptr_slot, &path_len_slot)
    hdr_status  = call @sa_http_server_req_get_header(req, &HDR_KEY, 12, &hdr_ptr_slot, &hdr_len_slot)
    body_status = call @sa_http_server_req_get_body(req, &body_ptr_slot, &body_len_slot)

    resp_status = call @sa_http_server_resp_stream_new(req, 200, &resp_slot)
    resp = load resp_slot+0 as ptr
    write_1_status = call @sa_http_server_resp_stream_write(resp, &CHUNK_1, 13)
    flush_1_status = call @sa_http_server_resp_stream_flush(resp)
    write_2_status = call @sa_http_server_resp_stream_write(resp, &CHUNK_2, 14)
    flush_2_status = call @sa_http_server_resp_stream_flush(resp)
    end_status     = call @sa_http_server_resp_stream_end(resp)

    call @sa_http_server_resp_stream_free(^resp)
    call @sa_http_server_req_free(^req)
    call @sa_http_server_free(^server)

配套的出站调用方见 http-client 页的 rosetta 301 示例， 两者构成一对回环互测程序（301 打 :18090/echo，302 监听 :18091/stream）。

注意上面两处 rosetta 摘录为了排版把原文件里的 #def XXX_LEN = n 常量内联成了字面数字（如 9 = HOST_LEN、 13 = CHUNK_1_LEN），并省略了部分状态槽声明；逐字可编译版本请以 sci/demos/rosetta/302_http_server_saasm/main.sa 与 301_http_client_saasm/main.sa 为准。demo 中形如 !server_status 的独立语句是 SA 的所有权释放写法（「! 显式释放拥有的资源或结束借用」，出处 sci/docs/tutorial/beginner_guide.md），不是断言；编译器不插入 drop，返回前须逐一释放。

CLI 会话示例

# 先生成起步工程（产物目录名会被打印）
sa http-server scaffold ./hubproxy-demo

# 最小冒烟服务：127.0.0.1:18080 上处理 1 个请求后退出
#   curl 式验证：GET /echo 会回显 body；GET /stream 推两块 SSE
sa http-server serve 127.0.0.1 18080 1
# stdout 期望输出：route=echo path=/echo body=5   （当客户端 POST "hello" 到 /echo）

v2 WebSocket 服务端形态

仓库中暂无 v2 WebSocket 的 SA 源码级示例，只有 Zig 测试 （tests/plugin_test.zig 的 http server v2 websocket polls fragmented messages and performs protocol close）。 基于契约签名的调用顺序如下：

srv = sa_http_server_new_v2()
sa_http_server_start_v2(srv, "127.0.0.1", 18087)
req = sa_http_server_accept_v2(srv, 1000)          ; would_block / timeout / ok
ws  = sa_http_server_websocket_upgrade_v2(req)     ; 要求 Sec-WebSocket-Version: 13
                                                    ; 成功后 req 已被消费，勿再 free
loop: st = sa_http_server_websocket_poll_v2(ws, 1 /*readable*/, 250, &events)
      st == 0 且 events & 1 时：
        opcode/data = sa_http_server_websocket_read_v2(ws, 16MiB)
        written     = sa_http_server_websocket_write_v2(ws, 1, reply)
      写满得到 would_block 时改 poll writable(2) 等恢复
sa_http_server_websocket_close_v2(ws, 1000, "done")
sa_http_server_websocket_free_v2(ws)
sa_http_server_free_v2(srv)

边界：明确不做的事

警告以下各项以文档为准明确划出范围（评估文档 §1.4、§6.4）： 不做 TLS/HTTPS 监听（定位明示靠 nginx/caddy 反向代理）；不做生产监听 （不允许 0.0.0.0 或自定义端口范围）；无 IPv6 [::1]； 不做反向代理、mTLS、HTTP/2 / HTTP/3；无大文件 multipart 流式上传； 无连接超时 / keep-alive 调优 API、access log、metrics hook； handler 路由与中间件抽象不在 native 层做（建议在 sa_std 加一层宏 facade）。 完成度评分（2026-06-15 口径）：ABI 设计 95%、HTTP/1.1 子集 80%、TLS/WebSocket 当时均 0%、 生产监听 0%、测试覆盖 30%、文档 10%、安全模型 100%，整体约 60-65% —— 定位是 localhost dev / 内部 IPC server，而非生产级 HTTP 服务器。
另一份资料需要区分口径：SCI 侧的 docs/http_server_plugin.md 把 「路由分发、中间件流水线、多租户转发（Proxying）、io_uring 零拷贝」描述为目标架构方向， 其示例 API（如 sa_http_server_route、sa_http_req_from_ticket、返回 -> i32!）与插件仓库真实的 sa_http_server.sai 并不一致； 该文档自己也声明「真实实现以该工程源码和 smoke tests 为准」。因此判断当前能力时， 以 .sai 契约与本页所引源码为准；反向代理等能力属于设计方向而非现状。
