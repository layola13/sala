http-client — HTTP 客户端

本页给出 sa_plugin_http_client 的完整参考：它在插件族中的位置与依赖关系、 安装验证命令、sap.json 能力段与权限白名单、v1 与 v2 两套 ABI 的全部函数签名， 以及可直接复制的端到端示例。读完本页你可以判断某个出站请求该用哪套函数、句柄由谁释放、 以及哪些能力被明确声明为「范围外」。

http-client 为 SA 程序提供原生 HTTP/1.1、HTTPS（TLS）、流式响应与 WebSocket 传输。 v1 ABI 保持可用且返回值不变；v2 ABI 增加稳定的网络状态码、请求截止时间与响应体上限、异步取消， 以及基于 TCP / TLS / Unix 域套接字的 WebSocket。

与其他插件的分工

  • http-server：方向相反的另一半。server 负责入站监听 localhost； client 只做出站请求。两者互不依赖，可单独使用，也常配合做回环自测 （见下文示例：client 打到 127.0.0.1 的本地服务上）。
  • vite：dev server 编排插件，依赖的是 http-server 而非 http-client； 静态服务与 SSE 复用 sa_http_server_* 核心 API。
  • deno 与 node：JS 生态兼容门面，位于应用层， 按 sap.json 声明复用 http-client 的少量符号（deno 声明使用 sa_http_client_new / sa_http_client_req_send / sa_http_client_resp_body_slice）。 即：门面在上、通用网络能力在下。
  • sax：UI 方言插件，与本插件无直接关系；SAX 页面的热重载由 vite 借助 http-server 完成。
注意依赖关系的口径随时间变化： 四插件合并评估文档（docs/plugin_evaluation_cn.md，评估日期 2026-06-15）曾记录 http-client 反向依赖 node 并将其列为风险；随后 docs/dependency_refactor_plan_cn.md 的 Step 1 删除了这条声明。当前仓库里的 sap.json 中 dependencies 为空对象， http-client 是零依赖的叶子能力层。

请求生命周期与句柄约定

两套 ABI 都遵循同一条所有权流水线：

  1. 构造客户端：sa_http_client_new（或 _new_v2）产出不透明 ptr 句柄。use_tls 非 0 时启用 TLS；v2 可额外传入 CA bundle 路径。
  2. 构造请求：req_new（或 req_new_v2 / req_new_joined） 绑定 method、URL；随后 req_add_header*、req_set_body* 追加头与体。 方法用 u8 判别值表示：GET=1、POST=2、PUT=3、DELETE=4 （见 src/http_saasm_api.zig 的 HttpMethod 枚举与 docs/http_client_v2_abi.md）。
  3. 发送：同步走 req_send（阻塞直到响应就绪）；异步走 req_send_async 得到操作句柄，再 async_poll / async_take_response。 异步实现会克隆并持有请求数据，因此调用方在发出异步后即可释放自己的请求句柄。
  4. 读响应：resp_status 读状态码；响应体两条路——一次性 resp_body_slice / resp_body_ptr + resp_body_len（小响应）， 或 resp_body_reader + resp_read_chunk（大响应 / 流式分块）。
  5. 释放：按创建的逆序显式调用 ..._free 系列。响应体与响应头的指针由 response 持有，response 释放后立即失效；reader 由 body_reader_free 单独释放。
警告v1 函数的返回值沿用宿主描述符的 AbiStatus 口径（src/plugin_api.zig）：ok=0、 unknown_command=1、failed=2 等。空指针参数、非法方法等一律返回 failed(2)。v2 的七种状态码与此无关，是另一套独立取值，不要混用判断逻辑。

CLI 子命令

插件同时暴露宿主命令（用法字符串逐字取自 src/plugin.zig 的错误提示）：

usage: sa http-client get    [--ca-bundle <path>] [--header name:value] <url>
usage: sa http-client post   [--ca-bundle <path>] [--header name:value] <url> <body>
usage: sa http-client stream [--ca-bundle <path>] [--header name:value] <url> [body]
  • get 成功时先打印 status: <code> 再输出响应体 （响应缓冲上限 max_append_size = 2 MiB）。
  • post 把第一个非选项参数当 URL、第二个当 body，并把 --header 逐条转发。
  • stream 以 1024 字节为一块增量转发响应体（chunked/SSE 不落盘缓冲）；给了 body 则自动用 POST。
  • --ca-bundle 加载自定义 CA 证书（绝对路径化后注入信任链，并关闭系统证书重扫描）。
  • CLI 错误统一带前缀 error[SA-HTTP-CLIENT-CLI]: 并附 help: 行，进程退出码 1。

v2 面：七种状态码逐条解释

每个 v2 操作返回下列稳定状态码之一（README 与 docs/http_client_v2_abi.md 双重确认， 测试 tests/plugin_test.zig 断言了每个取值）：

值名称含义与触发场景
0ok操作完成。对写操作意味着 out_written 等于载荷长度
1would_block零超时的 poll 或非阻塞操作未就绪。例如 websocket_poll_v2(..., timeout_ms=0) 时没有所关注的事件
2closed对端关闭、取消已完成，或传输不再可用。合法的对端 close 帧在读接口上表现为 closed；被取消的异步操作 poll/take 也返回它
3timeout正的截止时间到期。请求级 deadline（req_set_timeout_v2）到期时 req_send_v2 返回此值且不产出响应
4too_large超出配置的体/消息上限。响应体超过 req_set_max_response_bytes_v2，或 WebSocket 帧超过上限（超限帧在分配前就被拒绝）
5invalid参数、URI、请求头、握手或 WebSocket 帧非法。例如方法判别值不在 1..4、把上限设为 0、URI 无法解析
6io_error传输或分配器失败，且没有更具体的状态码可用

WebSocket 轮询的关注位与事件位共用一套取值：readable=1、writable=2、closed=4。 输出槽在任何校验或 I/O 之前都会先清零，避免读到脏值。

v2 请求增量

签名（节选自 .sa 契约）语义
sa_http_client_new_v2(use_tls: u8, &ca_bundle_path: ptr, ca_bundle_path_len: u64, &out_client: ptr) -> u32创建客户端时可指定 CA bundle 路径（可空）
sa_http_client_req_new_v2(client: ptr, method: u8, &url: ptr, url_len: u64, &out_req: ptr) -> u32经校验的请求构造（方法判别值沿用 v1）
sa_http_client_req_add_header_v2(...) / sa_http_client_req_set_body_v2(...)经校验的头与体写入
sa_http_client_req_set_timeout_v2(req: ptr, timeout_ms: u32) -> u32设置整个请求的截止时间（毫秒）；0 表示禁用。传输建立完成后该 deadline 可观察生效
sa_http_client_req_set_max_response_bytes_v2(req: ptr, max_bytes: u64) -> u32调用方自定义响应体上限；必须非 0，默认 16 MiB
sa_http_client_req_send_v2(req: ptr, &out_resp: ptr) -> u32同步发送；302 直接交给调用者，不隐藏跟随
sa_http_client_req_send_async_v2 / sa_http_client_async_poll_v2(op, timeout_ms, &ready) / sa_http_client_async_take_response_v2 / sa_http_client_async_cancel_v2(op) / sa_http_client_async_free_v2条件化的异步轮询（带超时）、取消、响应移交。poll 对每种终态（超时、取消=closed、超限、I/O 失败）都返回 ready=1；响应只能取一次
注意取消的实现方式是把已发布的 socket 关停以唤醒阻塞中的 send/read。Zig 0.14.1 在 DNS 解析、TCP connect、TLS 初始化完成之前不暴露 socket，因此这三段无法被本 ABI 硬中断——取消会在其之后立刻被观察到，而 async_free_v2 可能等待操作系统完成 connect 收尾。 不跟随重定向也让取消始终绑定在一个文件描述符上。

v2 WebSocket 增量

签名语义
sa_http_client_websocket_connect_v2(client, &url, url_len, timeout_ms, &ws)ws:// 走 TCP、wss:// 走 TLS
sa_http_client_websocket_connect_unix_v2(client, &socket_path, socket_path_len, &url, url_len, timeout_ms, &ws)Unix 域套接字作为物理传输，另给一个逻辑 URL 提供 Host、path、query 语义；Unix 模式拒绝 wss://
sa_http_client_req_websocket_connect_v2(req, timeout_ms, &ws) / ..._unix_v2复用请求句柄里的自定义头去握手（TCP/TLS 或 Unix 传输）
sa_http_websocket_poll_v2(ws, interests, timeout_ms, &events)按关注位轮询；timeout_ms=0 未就绪返回 would_block，正超时到期返回 timeout
sa_http_websocket_read_v2(ws, max_len, &opcode, &ptr, &len)poll 之后非阻塞。文本 opcode=1、二进制 opcode=2；重组 continuation 帧、内部应答 ping/pong、校验 close；非法或超限帧会关闭传输以免流错位。返回的消息指针借用自 ws 句柄，在下一次成功 read 或 free_v2 之前有效，调用方不得释放
sa_http_websocket_write_v2(ws, opcode, &data, data_len, &written)写出一条完整的、已加掩码的客户端消息；ok 时 written == 载荷长度，其余状态为 0。文本必须 UTF-8；ping/pong 载荷 ≤125 字节；所有消息 ≤16 MiB
sa_http_websocket_close_v2(ws, code: u16, &reason, reason_len)接受合法 RFC 6455 关闭码与 ≤123 字节的 UTF-8 reason
sa_http_websocket_free_v2(ws)关闭传输并归还保留的 client 引用

消息上限 16 MiB 来自 max_v2_message_bytes。TLS 模式保留原始连接对象及其 TLS 状态与升级后 已缓冲字节，绝不复制裸 TLS 文件描述符。

v2 所有权规则

  • v2 request 保留其 client 直到 request 释放；async 操作保留克隆请求与 client 直到 async 释放； WebSocket 保留 client 与连接直到 ws 释放。
  • 因此拥有者可以在创建这些句柄之后立即调用 sa_http_client_free， 句柄依然有效。
  • 响应体/头指针归 response 所有，response 释放后失效。
  • 同一句柄上的并发 free 与其他调用并发执行属非法；WebSocket 的 poll/read/write/close 内部串行化。

v1 → v2 迁移对照

需求v1 做法v2 做法
判断结果AbiStatus（0=ok / 2=failed），信息量有限七种稳定状态码，可区分超时、超限、取消、对端关闭
超时无任何超时 API（评估文档列为缺口）req_set_timeout_v2 请求级 deadline；poll 带毫秒超时
响应体上限无req_set_max_response_bytes_v2（默认 16 MiB，须非 0）
取消无async_cancel_v2，通过关停 socket 唤醒阻塞 I/O
重定向底层行为302 原样交给调用者，不隐藏跟随
WebSocket4 个遗留阻塞导出TCP/TLS/Unix 三种传输 + 轮询事件位 + 分帧重组 + 掩码 + 协议关闭
句柄寿命需自行维持 client 存活request/async/ws 各自保留 client 引用，owner 可提前 free client

范围外项（文档明确声明不做）

警告产品目标是 Linux x86_64。以下各项由 README 与 v2 ABI 文档明确划出基础范围：HTTP/2、HTTP/3、严格的非阻塞 TLS record 恢复 （部分超时的 TLS record 会使连接不可用并被关闭而不是重放）、自动重试、可中断 DNS。 此外 v2 不自动跟随重定向、不重试请求；遗留阻塞 WebSocket 仅作兼容保留。 评估文档还指出缺少 mTLS 客户端证书 API（建议形态 client_set_cert）——当前契约中确实没有。
同样要区分口径：SCI 侧的 docs/http_client_plugin.md 把「与 sa_net_uring 的零拷贝协作」标注为目标方向，并把 "grants": ["net_tx:..."] 与证书锁定 pinning 描述为宿主权限层的目标设计；其示例签名 （如带 body 参数的 req_send、返回 -> i32!）也与真实契约不同。 实际权限模型是本页前文的 sap.json net/env/证书目录白名单，而非 grants/pinning 字段。

@const URL  = utf8:"http://127.0.0.1:18090/echo"
@const KEY  = utf8:"content-type"
@const VAL  = utf8:"text/plain"
@const BODY = utf8:"hello from saasm"

@main() -> i32!:
L_ENTRY:
    client_slot = stack_alloc 8
    req_slot    = stack_alloc 8
    resp_slot   = stack_alloc 8
    reader_slot = stack_alloc 8
    buf         = stack_alloc 64        ; #def Buf_SIZE = 64

    client_status = call @sa_http_client_new(0, &client_slot)
    !client_status                       ; 显式释放该临时值（所有权语句）
    client = load client_slot+0 as ptr

    req_status = call @sa_http_client_req_new(client, 2, &URL, 27, &req_slot)
    !req_status                         ; 方法 2 = POST，27 = URL 字节数
    req = load req_slot+0 as ptr

    hdr_status  = call @sa_http_client_req_add_header(req, &KEY, 12, &VAL, 10)
    body_status = call @sa_http_client_req_set_body(req, &BODY, 16)
    send_status = call @sa_http_client_req_send(req, &resp_slot)

    resp   = load resp_slot+0 as ptr
    status = call @sa_http_client_resp_status(resp)      ; 期望 200
    reader_status = call @sa_http_client_resp_body_reader(resp, &reader_slot)
    reader = load reader_slot+0 as ptr
    read_status = call @sa_http_client_resp_read_chunk(reader, &buf, 64, &read_len_slot)

    call @sa_http_client_body_reader_free(^reader)
    call @sa_http_client_resp_free(^resp)
    call @sa_http_client_req_free(^req)
    call @sa_http_client_free(^client)

同一 demo 里 ^resp / ^req / ^client 形参写法展示了 SA 层「释放即置空」的所有权标记。摘录为排版起见把原文的 #def URL_LEN = 27 等常量内联成字面数字并省略了部分状态槽声明，逐字可编译版本以上述出处文件为准； 其中形如 !client_status 的独立语句是 SA 的所有权释放写法： 按 sci/docs/tutorial/beginner_guide.md，「! 显式释放拥有的资源或结束借用」， 编译器不会自动插入 drop，返回前必须把活跃寄存器逐一 ! 掉 （llm_cheat_sheet.md 把漏写列为 MemoryLeak 陷阱）。

CLI 会话示例（出自 tests/plugin_test.zig 的断言）

# 回环 GET：stdout 为 "status: 200\nhello from loopback\n"
sa http-client get http://127.0.0.1:<port>/hello

# POST 转发自定义头与 body
sa http-client post --header content-type: text/plain http://127.0.0.1:<port>/submit "payload body"

# chunked SSE 增量转发，stdout 逐块得到 "data: first\n\ndata: second\n\n"

# 自签名 HTTPS + 自定义 CA bundle（测试里用 openssl s_server 起本地 TLS 服务）

这些命令行在仓库中是以 argv 数组形式经 runHttpClientCommand 调用的 （D:/projects/sla/sa_plugin_http_client/tests/plugin_test.zig）； 缺 URL 时的诊断输出为 error[SA-HTTP-CLIENT-CLI]: missing required HTTP client URL 外加 usage 行。

v2 异步与取消的调用形态

仓库中没有 v2 的 SA 源码级示例（examples/get.sa 是刻意留空的占位文件， 仅提示用 sa http-client get https://example.com 走 CLI）。 基于契约签名的调用形式如下（伪代码，仅示意顺序）：

c   = sa_http_client_new_v2(0, null, 0)                 ; 或传 CA bundle 路径
req = sa_http_client_req_new_v2(c, 1, url)
sa_http_client_req_set_timeout_v2(req, 20)              ; 20ms 截止时间
sa_http_client_req_set_max_response_bytes_v2(req, 65536)
op  = sa_http_client_req_send_async_v2(req)
sa_http_client_req_free(req)                            ; op 已克隆请求
sa_http_client_free(c)                                  ; op 同时保留 client 引用
loop: st = sa_http_client_async_poll_v2(op, 100, &ready); until ready == 1
st  = sa_http_client_async_take_response_v2(op, &resp)  ; closed 表示已被取消
sa_http_client_async_free_v2(op)

v2 的行为细节（deadline 到期返回 timeout、超限返回 too_large、 取消两次幂等、poll 返回 closed 且 take 返回空句柄等）均有 Zig 测试佐证， 出处同样是 tests/plugin_test.zig。
