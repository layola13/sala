Runtime Permissions and Auditing: Design Overview

StatusThis page is a design draft (discussion finalized on 2026-10-24), describing the target form of SA's runtime permission and auditing system. Implementation progress (2026-10-25): phase-one slice 1 (the policy core, sci 109f7caf), slice 2 (native acquisition-point interception wiring + the dedicated denial code SA_STD_ERR_PERMISSION_DENIED=10, sci 0e184e26), and slice 3 (artifact binary policy bootstrapping, sci df69882d, 5dc14339) have all landed and been pushed: slice 3 lets artifacts bootstrap from the environment — SA_POLICY_JSON (highest) ＞ SA_POLICY_FILE ＞ SA_POLICY_ALLOW_ALL=1 (an explicit allow-all, which must leave an audit trace); with SA_POLICY_REQUIRED=1 and no policy, startup is refused (exit code 1); when a policy is in place but unreadable/invalid, it hard-fails (exit code 2); the audit destination is SA_AUDIT_FILE or the policy's audit.sink; end-to-end verification of the four scenarios and re-verification with a real sa build-exe artifact both pass, and sa-std-unit is 130/130. One real defect was fixed during implementation: when policy-constructor entries were aligned to 16 in the .init_array section, the zero padding the linker inserted was called by glibc as a function pointer and the program segfaulted before main; changing the entry alignment to 8 solved it. Two gaps remain against the design draft: first, when there is no policy, artifacts currently default to legacy allow (closed off via SA_POLICY_REQUIRED), which is still one step short of the "there is no running state without a policy" default-deny described below, and the default value awaits a final ruling; second, slice 2b has completed policy execution on all three backends (wasm lazy bootstrapping, sci e942c0c5; the emit_js runtime-header policy module, sci 0240e7fd; the emit_c directory-style C policy runtime, sci 8ff362c1 — all measured with probes and regressed against the js/c matrix), with the remaining detail gaps listed honestly: the wasm audit file cannot yet be opened due to WASI rights (interception execution is unaffected); the js backend has no env/net acquisition points (the shims are local stubs — an absence of capability, not a policy gap); slice 3b has completed the sa run interpreter surface (interp intrinsic gating + CLI policy resolution from the same env, sci 5777cba8) and the three native time bypasses (gates added for unix_s/unix_ns/utc_now). All rules in the text are confirmed design decisions; parts marked "phase two" are outside phase one's scope. Phase-one addendum (2026-10-25, driven by D9): one-time tokens previously had only an in-host-process API (PolicyContext.mintToken), and artifact binaries and sa run had no delivery surface; the SA_POLICY_TOKENS_JSON environment surface has now been added — after the launcher approves on the host side, it delivers the token specifications ([{category, key, ttl_s?}], strictly parsed, with an unknown field causing a hard failure) via the environment, to be minted into the root context during bootstrapping, with interp on the same surface in sync; when a token is present but the policy is absent, it explicitly errors and exits, never silently. For end-to-end verification see scenario C of sa_plugin_sla demos/cxu/09_vm_tools (ask + token: each file is opened exactly once, a second read is denied, and the audit contains exactly two source=token allowances).

The SA runtime will have a built-in permission and auditing system: all of a program's effect-class operations (network, files, environment variables, processes, time, random sources) are uniformly intercepted at sa_std's extern boundary and adjudicated against the policy given by the deployer — allow, deny, or record an audit entry — rather than the program's code vouching for itself. This page gives the system's complete design: the three-layer structure, policy sources and precedence, interception granularity, the hooks' power model, policy contexts, and one-time temporary authorization.

Why the Interception Route, Rather than Purity Annotations

Introducing a pure fn-style purity system at the SLA layer (declarations + compile-time proof) was evaluated. The conclusion was to downgrade it, for three reasons:

  • SA is not meant for human readers. SA is a machine-generated intermediate layer with no readers; purity is "a contract for readers", resting on honest annotation and proof by the frontend, and is naturally out of place at this layer.
  • The proof route cannot govern the boundary. Almost all of SLA's standard library capabilities are externs, so purity annotations can only rest on trust, and the checking strength is weakest exactly at the most important boundary. The interception route depends on no frontend's honesty: hand-written SA, plugins, programs compiled by any frontend, and LLM-generated code are all treated alike.
  • The target domain wants auditing and control. For scenarios such as finance, compliance wants "the effects that have occurred are completely recorded, and can be controlled at deployment time", not a type-level proof. Interception + an event log directly produce audit material.

Purity is kept only as a possible future development-time lint at the SLA layer, and is no longer on the main roadmap.

Relation to Deno's Permission Model

In form it resembles Deno's runtime permissions (restricted by default, explicit grants, allowances by category and resource list), but it sits one layer lower, and has two more layers:

DimensionDenoThis design
CheckpointThe API boundary where JS calls Rust ops; it governs only code using the Deno APIs, and fails wholesale once FFI is allowedThe sa_std extern boundary — the single funnel for all frontends and extern calls, with no lower API to go around it
Static layerNoneThe SA Capability Mask fixes the capability ceiling at link time
Dynamic layerStartup flags, immutable at runtime, no audit event streamPolicy callbacks can adjudicate inside the envelope, with a full structured audit event stream
Policy contextOne per processOne physically isolated context per host session (such as each CXU conversation)

One premise that must be held: sa_std's effect-class APIs must stay semantic (for example, connect receives a hostname string and DNS resolution is built in), so that the policy can see hostnames and does not degenerate into being writable only by IP range (in CDN scenarios, IP-based policies shatter).

The Three-Layer Structure

Effective permission = the intersection of the three layers; all must pass for an operation to be allowed:

LayerDeciderWhat it decidesTiming
Static layer: Capability MaskCompilation/linkingWhat capabilities the program "can have at most"; an extern for an undeclared capability cannot be linkedBuild time
Configuration layer: policy file / command lineThe deployer (operations)"What this machine and this deployment allow"; no recompilation needed, and it can be retroactively applied to already-compiled old binariesStartup time
Hook layer: auditing and adjudication callbacksPolicy callbacks assembled by the deployer / audit hooks registered by the program itselfPer-call adjudication inside the envelope, and full audit recordingRuntime

Policy Sources and Precedence (Finalized)

  • Two sources: command-line arguments and a configuration file; either one suffices, and both may exist at once.
  • Precedence: command line > configuration file. Merging is computed by category: a category mentioned on the command line is governed wholesale by the command line; one not mentioned falls back to the configuration file; a category mentioned in neither defaults to denial.
  • There is no running state without a policy: when neither source yields a policy, the runtime refuses to start and reports a clear error (indicating how to provide a policy), rather than silently allowing everything. This means existing programs running on the new runtime for the first time need a policy supplied — that is the plainly priced migration cost, in exchange for "every run's permission boundary has a provenance".
  • The counterpart of Deno's -A is retained: an explicit command-line allow-all switch, with the highest precedence; once used, the audit log must leave a trace. It is an active decision by operations, not a default state.

Configuration File Draft

{
  "permissions": {
    "net":    { "mode": "allow-list", "allow": ["api.bank.com:443", "10.0.0.0/8:*"] },
    "fs":     { "read": ["/data/inbox"], "write": ["/data/outbox"] },
    "env":    { "allow": ["APP_ENV", "TZ"] },
    "run":    { "mode": "deny" },
    "time":   { "mode": "allow" },
    "random": { "mode": "audit" }
  },
  "audit": { "sink": "file:///var/log/sa-audit.jsonl", "events": ["deny", "ask", "net", "run"] }
}

Five modes per category: allow (allow), deny (deny), allow-list (allow by resource list), audit (allow but record), and ask (hand it to the policy callback assembled by operations for adjudication inside the envelope).

Interception Points and Granularity

  • The interception points are the entry points of sa_std's effect-class externs, and they sit only at resource acquisition points: connecting (connect), listening (listen), opening a file (open), starting a process (spawn), reading environment variables (env), and time and random sources. Two reasons: first, performance — reads and writes on an already-authorized handle no longer pay the hook cost on every call; second, avoiding TOCTOU races — what is checked is the acquisition action itself, after which the handle is the credential.
  • Handles must not be passed across policy contexts for use (see policy contexts below), otherwise the isolation is bypassed by borrowing a handle.
  • When no policy hook intervenes, the checking overhead stays at one atomic read plus a branch, close to zero; with hooks installed, only the selected event categories pay the cost.

Denial Semantics and Audit Events

  • A denial does not trap: it returns a dedicated status code (permission-denied, reserved within the existing AbiStatus system), and the caller must be able to distinguish "policy denial" from "operation failure". A denial is a normal adjudication outcome, not a crash.
  • Each adjudication produces a structured event (category, target resource, adjudication result, source context), in the same style as the toolchain's existing JSON diagnostics; the audit log is machine-readable and can be consumed directly by compliance tools and LLMs.
  • The audit records only metadata, never the sensitive values themselves — for example, an env read records only the key name, not the value read.

The Hooks' Power Model

There is only one iron rule for the flow of power: authorization flows only top-down. Operations grants it via configuration/the command line; the program side can only ever be more restricted than the policy, never wider. The two kinds of hook have different powers:

HookAssemblerPower
Audit hookRegistered by the program itselfRead-only observation of all events; it can change an allowance into a denial (self-tightening); it can never change a denial into an allowance
Policy callbackThe deployer, assembled with the configurationAdjudicates ask categories per call within the envelope drawn by the configuration; never exceeds the envelope
  • No in-dialog confirmation: managed code popping up a dialog on the call path to ask a human for permission is a source of UAC-style fatigue clicking, and headless environments such as servers, daemons, and CI have no human available to confirm at all. While an adjudication callback executes, hooks automatically deactivate, preventing recursion.
  • Special allowances go through an out-of-band channel: change the configuration, or re-run with command-line authorization — approval is a deployment action, with versions, records, and reviewability. The dynamic version for financial scenarios is the four-eyes principle (phase two): the call first fails with an approval-required status code, an approver approves in a separate interface, the system generates a scoped, time-limited authorization, and the program passes with that authorization when it retries.

Policy Contexts

A policy is not one per whole process; there can be several, with the runtime switching "which one is currently in effect" — a policy context. This is a hard CXU requirement: each conversation holds one physically isolated permission configuration, and one conversation's authorization is nowhere to be found in another conversation. Implementation points:

  • Contexts are carried by the runtime with the current task (concurrent conversations do not interfere with each other), and effect-class calls consult the current context rather than a global policy.
  • When a new context is derived, its permissions can only be fewer than the parent's (one-way tightening, the same principle as top-down authorization); no code can expand its powers by switching contexts.
  • A context lives and dies with the host session: when the conversation ends, the context and all its temporary authorizations are destroyed together.

The typical form: the host's own code runs in the normal context; an executed plugin or model-generated code segment switches into a tightened context (no network, files only in a temporary directory, no spawn), and however uncontrollable the code is, it cannot get out of the context.

Temporary Authorization: One-Time Tokens

When a single conversation temporarily needs one permission outside the policy (typically: temporarily reading some env), the configuration is not changed and no long-term authorization is given; instead it goes through a one-time token — the same philosophy as all kinds of API tokens, "produced once, shown once":

  • Approval is minting: the host presents a structured application in that conversation's interface (which conversation, which category, which concrete resource); after the user approves, the runtime mints a token bound to the triple "context + category + concrete resource". The scope must be precise to the resource — reading env is approved down to the key name, not to "the env category as a whole".
  • Consumption is destruction: the first matching call consumes the token, which is void after consumption; to read a second time, go through approval once more. Replay is naturally prevented: however many times denied code retries, it is useless — if the token does not exist, it does not exist.
  • Expiry: an unconsumed token expires after a short time, so that an approval does not lie around in the context to be ridden on by later code.
  • The user can view and revoke unconsumed tokens at any time in the conversation's permission panel; the audit records both the approval and the consumption events (metadata only).

A complete statement of one temporary authorization is a single sentence: "Allow conversation #3 to read the env OPENAI_API_KEY once." The cost is on the table: the same kind of operation happening repeatedly requires approval each time — convenience yields to security, which is the correct trade-off for categories holding real credentials.
