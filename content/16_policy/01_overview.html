运行时权限与审计：设计总览

状态本页是设计稿（2026-10-24 讨论定案），描述 SA 运行时权限与审计系统的目标形态。实现进度（2026-10-25）：一期切片 1（策略核心，sci 109f7caf）、切片 2（原生获取点拦截接线 + 专用拒绝码 SA_STD_ERR_PERMISSION_DENIED=10，sci 0e184e26）、切片 3（产物二进制策略自举，sci df69882d、5dc14339）均已落地并推送：切片 3 让产物经环境自举——SA_POLICY_JSON（最高）＞ SA_POLICY_FILE ＞ SA_POLICY_ALLOW_ALL=1（显式总放行，必留审计痕迹），SA_POLICY_REQUIRED=1 且无策略时拒绝启动（退出码 1），策略在位但不可读/不合法时硬失败（退出码 2），审计目的地 SA_AUDIT_FILE 或策略 audit.sink；四场景端到端验证与 sa build-exe 真实产物复验均通过，sa-std-unit 130/130。实现中修掉一个真缺陷：策略构造器条目在 .init_array 段对齐为 16 时，链接器补的零填充会被 glibc 当作函数指针调用、程序在 main 前段错误，条目对齐改 8 已解决。与设计稿尚存两处差距：其一，无策略时产物目前默认为 legacy 放行（靠 SA_POLICY_REQUIRED 关闭），与下文「不存在无策略的运行状态」的默认拒绝尚差一步，默认值待定案；其二，切片 2b 已补齐三后端策略执行（wasm 惰性自举 sci e942c0c5、emit_js 运行时头策略模块 sci 0240e7fd、emit_c 目录式 C 策略运行时 sci 8ff362c1，均经探针实测与 js/c 矩阵回归），剩余细节缺口如实列明：wasm 审计文件因 WASI rights 尚打不开（拦截执行不受影响）；js 后端无 env/net 获取点（shim 为本地桩，属能力缺席而非策略缺口）；切片 3b 已补齐 sa run 解释器表面（interp intrinsic 门控 + CLI 同 env 策略解析，sci 5777cba8）与原生 time 三条旁路（unix_s/unix_ns/utc_now 补门）。文中规则均为已确认的设计决定；标注「二期」的部分不在第一期范围内。

SA 运行时将内置一套权限与审计系统：程序的一切效果类操作（网络、文件、环境变量、进程、时间、随机源）在 sa_std 的 extern 边界上被统一拦截，按部署方给定的策略裁决——放行、拒绝或记录审计——而不是由程序代码自证清白。本页给出该系统的完整设计：三层结构、策略来源与优先级、拦截粒度、钩子权力模型、策略上下文与一次性临时授权。

为什么走拦截路线，而不是纯度标注

曾评估过在 SLA 层引入 pure fn 式纯度系统（声明 + 编译期证明）。结论是降级处理，理由有三：

  • SA 不是给人看的。SA 是机器生成的中间层，没有读者；纯度是「给读者看的契约」，靠前端诚实标注与证明，在这一层天然水土不服。
  • 证明路线管不住边界。SLA 的标准库能力几乎全部是 extern，纯度标注只能靠信任，检查强度在最重要的边界上恰恰最弱。拦截路线不依赖任何前端的诚实：手写 SA、插件、任何前端编译出的程序、LLM 生成的代码，一视同仁。
  • 目标域要的是审计与控制。面向金融等场景时，合规要的是「已经发生的效果有完整记录、部署时能管控」，而不是类型层面的证明。拦截 + 事件日志直接产出审计材料。

纯度仅保留为 SLA 层未来可选的开发期 lint，不再列入主线路线图。

与 Deno 权限模型的关系

形态上类似 Deno 的运行时权限（默认受限、显式授权、按类别与资源清单放行），但下沉一层，且多两层：

维度Deno本设计
检查点JS 调 Rust op 的 API 边界，只管用 Deno API 的代码；FFI 放行后整体失效sa_std extern 边界——所有前端与 extern 调用的唯一漏斗，无更低 API 可绕
静态层无SA Capability Mask 在链接期先定能力上限
动态层启动旗标，运行时不可变，无审计事件流策略回调可在信封内裁决，全量结构化审计事件
策略上下文进程级一份每宿主会话（如 CXU 的每个对话）一份物理隔离的上下文

一个必须守住的前提：sa_std 的效果类 API 必须保持语义化（例如 connect 接收主机名字符串、DNS 内置解析），策略才看得见主机名，不至于退化到只能按 IP 段书写（CDN 场景下按 IP 的策略会碎）。

三层结构

有效权限 = 三层取交集，全部通过才放行：

层决定者决定什么时机
静态层：Capability Mask编译/链接程序「最多能有什么能力」；未声明能力的 extern 链接不上构建期
配置层：策略文件 / 命令行部署方（运维）「这台机器、这次部署允许什么」；不需重编译，可事后追认到已编译的旧二进制启动期
钩子层：审计与裁决回调部署方装配的策略回调 / 程序自注册的审计钩子信封内的逐次裁决与全量审计记录运行期

策略来源与优先级（定案）

  • 两种来源：命令行参数与配置文件，任一即可，也可同时存在。
  • 优先级：命令行 > 配置文件。合并按类别计算：命令行提到的类别整类以命令行为准；未提到的回落到配置文件；两处都未提到的类别默认拒绝。
  • 不存在无策略的运行状态：两处都拿不到策略时，运行时拒绝启动并明确报错（提示如何提供策略），不静默放行。这意味着存量程序首次在新运行时上运行需要补一份策略——这是明码标价的迁移成本，用以换取「任何一次运行的权限边界都有出处」。
  • 保留 Deno -A 的对应物：命令行显式总放行开关，优先级最高；一旦使用，审计日志必须留痕。它是运维的主动决定，不是默认状态。

配置文件草案

{
  "permissions": {
    "net":    { "mode": "allow-list", "allow": ["api.bank.com:443", "10.0.0.0/8:*"] },
    "fs":     { "read": ["/data/inbox"], "write": ["/data/outbox"] },
    "env":    { "allow": ["APP_ENV", "TZ"] },
    "run":    { "mode": "deny" },
    "time":   { "mode": "allow" },
    "random": { "mode": "audit" }
  },
  "audit": { "sink": "file:///var/log/sa-audit.jsonl", "events": ["deny", "ask", "net", "run"] }
}

每类五种模式：allow（放行）、deny（拒绝）、allow-list（按资源清单放行）、audit（放行但记录）、ask（交给运维装配的策略回调在信封内裁决）。

拦截点与粒度

  • 拦截点是 sa_std 效果类 extern 的入口，且只在资源获取点：建连（connect）、监听（listen）、打开文件（open）、启动进程（spawn）、读取环境变量（env）、时间与随机源。两个理由：其一是性能——已授权句柄上的读写不再逐次付钩子成本；其二是避开 TOCTOU 竞态——检查的就是获取动作本身，之后句柄即凭证。
  • 句柄禁止跨策略上下文传递使用（见下文策略上下文），否则隔离被句柄借道绕过。
  • 无策略钩子介入时，检查开销保持在一次原子读加分支，接近于零；装了钩子也只让被选中的事件类别付出成本。

拒绝语义与审计事件

  • 被拒不 trap：返回专用状态码（在现有 AbiStatus 体系内预留 permission-denied），调用方必须能区分「策略拒绝」与「操作失败」。拒绝是正常裁决结果，不是崩溃。
  • 每次裁决产生一条结构化事件（类别、目标资源、裁决结果、来源上下文），格式与工具链现有 JSON 诊断同风格，审计日志机器可读，可被合规工具与 LLM 直接消费。
  • 审计只记元数据，绝不记录敏感值本身——例如 env 读取只记 key 名，不记读到的值。

钩子的权力模型

权力流向只有一条铁律：授权只能自上而下。运维经配置/命令行给予；程序一侧永远只能比策略更受限，不能更宽。两类钩子权力不同：

钩子装配者权力
审计钩子程序自注册只读观察全部事件；可以把放行改判为拒绝（自我收紧）；永不能把拒绝改判为放行
策略回调部署方，随配置装配对 ask 类别在配置划定的信封内逐次裁决；永不超出信封
  • 不做对话确认：被管代码在调用路径上弹窗向人要权，是 UAC 式疲劳点击的来源，且服务器、守护进程、CI 等无头环境根本没有可确认的人。裁决回调执行期间钩子自动失效，防止递归。
  • 特殊放行走带外通道：修改配置或以命令行授权重跑——批准是部署动作，有版本、有记录、可复盘。金融场景的动态版是四眼原则（二期）：调用先以 approval-required 状态码失败，审批人在独立界面批准，系统生成有范围有期限的授权，程序重试时凭授权通过。

策略上下文

策略不是全进程一份，而是可以有多份、运行时切换「当前生效的是哪一份」的策略上下文。这是 CXU 的硬需求：每个对话持有一份物理隔离的权限配置，一个对话的授权在另一个对话里查无此物。实现要点：

  • 上下文由运行时随当前任务携带（多对话并发时互不串扰），效果类调用查的是当前上下文而非全局策略。
  • 派生新上下文时权限只能比父级更少（单向收紧，与授权自上而下同一原则），任何代码不能借切换上下文扩权。
  • 上下文随宿主会话生灭：对话结束，上下文及其全部临时授权一并销毁。

典型形态：宿主自身代码在正常上下文运行；被执行的插件或模型生成代码段切入收紧的上下文（禁网、文件仅临时目录、禁 spawn），代码再不可控也出不了上下文。

临时授权：一次性令牌

单个对话临时需要策略外的一项权限时（典型：临时读取某个 env），不改配置、不给长期授权，而是走一次性令牌——与各类 API token「只生产、只展示一次」同一哲学：

  • 批准即铸造：宿主在该对话的界面呈现结构化申请（哪个对话、哪个类别、哪个具体资源），用户批准后运行时铸造一枚令牌，绑定「上下文 + 类别 + 具体资源」三元组。范围必须精确到资源——读 env 就批到 key 名，不批「env 整类」。
  • 消费即焚：第一个匹配的调用消费令牌，消费后作废；想再读第二次，重新走一次批准。天然防重放：被拒代码重试多少次都无用，令牌不存在就是不存在。
  • 逾期作废：未被消费的令牌短时过期，避免批准躺在上下文里被后续代码蹭用。
  • 用户在对话的权限面板可查看并随时撤销未消费的令牌；审计记录批准与消费两条事件（只记元数据）。

一份临时授权的完整表述就是一句话：「允许对话 #3 读取 env OPENAI_API_KEY 一次。」代价是明牌的：同类操作重复发生就要逐次批准——便利让位于安全，这对装着真实凭证的类别是正确取舍。
