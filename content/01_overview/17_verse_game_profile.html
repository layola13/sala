状态：定位记录（2026-10-29，用户定）。本页登记 Verse 特性集因「将来为游戏服务」前提变更而升级的定位，及其插件承载形态；实施排程以 13 号文档第九节定序链为准，Verse 调研事实见 16 号文档第二节。

一、前提变更：从「只观察」到远期完全吸纳

用户定（2026-10-29）：本生态的 SA / SLA 将来可能要为游戏服务。16 号文档里 Jev 对「联机预测 / 并行 STM」的裁定是只观察（0.86），但那条裁定建立在一个明确前提上——我们的交付物不做联机预测。该前提现已变更，裁定的地基随之失效：Verse 特性集的定位由「只观察」升级为远期完全吸纳目标。

吸纳视野按 16 号第二节的调研事实全量圈定，不分已发货与未发货：已发货的本地失败回滚事务与函数签名效应标注；未发布的并行 STM（推测执行 + 冲突重试）与 <predicts> 客户端预测（客户端预测运行、服务器权威纠正）。后者在 Epic 侧尚不存在成形机制，吸纳的是其设计目标与语义形态，落地时以我们的运行时条件为准重新设计，不是对 Epic 实现的移植。

二、承载形态：插件承载、三层拆分

主会话方案，用户批准：Verse 这一套不进 SLA 本体，按性质拆成三层、分别归位。

  • 语言语义层 → 语言插件 / 方言前端。失败回滚语义（失败上下文内的写入暂定、失败即整体撤销）、decides / transacts 式可回滚代码圈定，都是编译器语义，进不了运行时插件。但插件体系里早有 kind=language 一类：SLA、slars 皆以语言前端挂在宿主上、由宿主按扩展名分发。故形态 = Verse 向语言插件 / 方言档，承 slars 的硬条件——不动 SLA、另开前端、lowering 与 codegen 与 SLA 共享同一份代码，落点同为 SA；SLA 本体不被游戏语义污染。
  • 运行时引擎层 → 领域插件。事务推测引擎（写日志 / 撤销）、预测与回滚的 netcode 骨架（快照环、输入延迟、回滚重演）是领域能力，不是 HTTP / TCP 那类基础核心，不适用「基础核心进 sa_std」的归位。先例现成：db 插件即「领域引擎 + 宿主注册」的形态。既有的游戏向种子 sla_ecs 归此线名下，作为该引擎层的存量起点。
  • 通用部分 → SLA 本体。效应标注对非游戏场景同样成立，已按 16 号文档裁定（0.66）采纳进 SLA goroutine 语法批，走本体路线，不随游戏档走——游戏档将来无论是否启动，这一部分都照常落地。

三、边界

吸纳的是 Verse 的机制（事务推测、预测回滚、效应圈定），不是把 SLA 改成 Verse：语法表面、检查器纪律与所有权模型仍是本生态自己的。游戏档是可选挂载——服务器三台（slanginx / slaredis / db）的代码路径永不被迫背上推测执行的成本，不用游戏档就一字不付。SA 规约照旧冻结：三层全部落在 sa_std 之外的上层与插件面，与底座定案不冲突。

四、排程

全程序总定序（用户 2026-10-29 定）：先完成 Erlang + goroutine 综合体（运行时一期 → SLA 语法批，定序见 13 / 15 / 16 号文档），再完成三台（slanginx / slaredis / db）的并发性能改进，两者都完成之后，才考虑加入 Verse、Haskell（STM 等）的特性。故本线的启动门是「综合体 + 三台改进双双完成」，不是综合体一完就开。属远期线。当前只改登记定位、不动任何施工面——在建的运行时一期、已排的语法批与三台改造均不受本页影响。启动时点与分期（语言档与引擎层的先后、首期语义子集的圈定）候届时另行裁定。
