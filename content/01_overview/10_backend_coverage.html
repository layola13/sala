Backend Service Coverage Map: Existing, Planned, and Missing

StatusCensus of 2026-10-28 (the finalized record after the user asked "Backend services can basically cover most applications by now, right? What's still missing?"). The conclusion up front: the backend building blocks for single-machine to small-scale applications are basically complete; the gaps are concentrated in two directions: "distributed" and "connecting to existing ecosystems." This page is a rolling checklist: each time an item is filled in, its status is updated here with a note of the page that documents it.

Covered (Built, or Planned and Under Way)

  • Web and APIs: sangx (HTTP/1.1/2/3, WebSocket, reverse proxy; plan finalized); native SLA application backends have already been proven by the full CXU rewrite.
  • Cache / KV: sardis (Redis rewrite, candidate name to be decided) plan finalized — RESP, the five major types, expiration, persistence, and replication in phases; in-process collections are ready-made.
  • Relational storage: SQLite is used through the std access surface (CXU's thread storage is of this kind).
  • Columnar storage: sa_plugin_db (compile-time schema, read-handle scanning); its VM programmable query layer is planned.
  • Files and transfer: fs is comprehensive; an SSH server + SFTP are in std (judged an area of overtaking in the cross-language census).
  • Networking periphery: DNS record-type queries (the resolution side), an SMTP client (in production in STD wave two), a proxy surface, SSE parsing, the IP/CIDR value layer, and the TLS configuration surface — all landed or in production.
  • Foundations: timers + process spawn (task scheduling), crypto/HMAC/bcrypt (the authentication library surface), WebSocket + SSE (real-time push), bit-level packing (protocol codec primitives).

Gap List (Ordered by Value of Filling Them)

  1. Distributed consensus (Raft-like) — the biggest missing piece. All current services are single-machine in form: sardis's Cluster, sangx's cross-node shared state, and the db plugin's replication are all jointly stuck on the absence of a consensus protocol and replication-log primitives. It is a missing foundation piece, not a missing product piece: fill it in, and three registered products unlock their multi-node forms at once.
  2. External database client drivers (PostgreSQL / MySQL wire protocols). Our own storage is complete, but real applications often need to connect to existing PG/MySQL; without a driver the only option is a detour. Pure protocol work, of a magnitude comparable to the SMTP client.
  3. Log-style message queues + MQTT. sardis's Pub/Sub and Streams only cover lightweight scenarios; a Kafka-class queue with consumer groups, replay, and backlog capacity is a different species; MQTT is a separate category for IoT scenarios (neither broker nor client exists).
  4. Full-text search. A search service with an inverted index + BM25 + tokenization has not been proposed as a project; it can grow directly on top of the db column store (the column store + VM query layer are a ready-made base), and SQLite FTS only counts as a stopgap.
  5. Object storage (S3-compatible). fs exists, but the S3 API, object versioning, and lifecycle are all absent; a single-machine gateway version could ride on sangx, while a distributed version with sharding and erasure coding is not within current range.

Small Gaps (Scenario-Driven, Not Scheduled Separately)

  • protobuf / gRPC codecs: mechanical work; the HTTP/2 base already exists.
  • An authoritative DNS server: only a resolution client exists; the server side is a small job (the UDP surface is ready).
  • The full IMAP mail stack: only SMTP sending exists; receiving and mailbox storage do not.
  • Time-series database: the db column store is a half fit, lacking time partitioning and downsampling policies.

Suggested Order for Filling the Gaps

  1. Raft consensus — unlocks the multi-node forms of the sangx / sardis / db products in one go.
  2. PG / MySQL client drivers — the integration surface with existing ecosystems, which decides whether SA applications can enter existing systems.
  3. Full-text search — rides the db column store's ready-made base, at the lowest marginal cost.
  4. MQTT, S3, and the remaining small items — open them when a concrete scenario appears; do not invest in advance.
