后台服务覆盖图：已有、立项与缺口

状态2026-10-28 盘点（用户问「后台服务基本能覆盖大部分应用了吧？还漏哪些」后的成案记录）。结论先行：单机到小规模应用的后端积木基本齐备；缺口集中在「分布式」与「对接存量生态」两个方向。本页滚动销项：每补齐一项即更新状态并注明出处页。

已覆盖（建成或已立项在途）

  • Web 与 API：sangx（HTTP/1.1/2/3、WebSocket、反向代理，规划成案）；SLA 原生应用后端已由 CXU 全量重构实证。
  • 缓存 / KV：sardis（Redis 重构，候选名待定）规划成案——RESP、五大类型、过期、持久化与复制分期；进程内集合现成。
  • 关系存储：SQLite 经 std 接入面使用（CXU 的 thread 存储即此类）。
  • 列式存储：sa_plugin_db（编译期 schema、读句柄扫描），其 VM 可编程查询层 已规划。
  • 文件与传输：fs 全面；SSH 服务端 + SFTP 在 std 内（跨语言普查判定为反超面）。
  • 网络周边：DNS 记录型查询（解析侧）、SMTP 客户端（STD 第二波在制）、代理面、SSE 解析、IP/CIDR 值层、TLS 配置面——均已落地或在制。
  • 基础件：定时器 + 进程 spawn（任务调度）、crypto/HMAC/bcrypt（认证库面）、WebSocket + SSE（实时推送）、位级打包（协议编解码原语）。

缺口清单（按补齐价值排序）

  1. 分布式共识（Raft 类）——最大漏项。当前全部服务均为单机形态：sardis 的 Cluster、sangx 的跨节点共享状态、db 插件的复制，三者共同卡在没有共识协议与复制日志原语上。它是地基缺件而非产品缺件：补上它，三个在册产品同时解锁多节点形态。
  2. 外部数据库客户端驱动（PostgreSQL / MySQL 线协议）。自家存储已齐，但真实应用常需对接存量 PG/MySQL；无驱动只能绕道。纯协议活，量级与 SMTP 客户端相当。
  3. 日志型消息队列 + MQTT。sardis 的 Pub/Sub 与 Streams 只覆盖轻量场景；带消费组、回放、堆积能力的 Kafka 类队列是另一物种；MQTT 是物联网场景的独立门类（broker 与客户端均无）。
  4. 全文搜索。倒排索引 + BM25 + 分词的搜索服务未立项；可直接长在 db 列存之上（列存 + VM 查询层是现成底座），SQLite FTS 只算应急。
  5. 对象存储（S3 兼容）。fs 已有，但 S3 API、对象版本、生命周期均无；单机网关版可骑 sangx 实现，分片纠删码的分布式版不在当前射程。

小件缺口（场景驱动，不单独排期）

  • protobuf / gRPC 编解码：机械活，HTTP/2 底座已有。
  • 权威 DNS 服务器：只有解析客户端，服务端为小活（UDP 面现成）。
  • IMAP 邮件全套：只有 SMTP 发送，收件与邮箱存储没有。
  • 时序数据库：db 列存半适配，差时间分区与降采样策略。

补漏顺序（建议）

  1. Raft 共识——一次解锁 sangx / sardis / db 三个产品的多节点形态。
  2. PG / MySQL 客户端驱动——存量生态的集成面，决定 SA 应用能否进入既有系统。
  3. 全文搜索——骑 db 列存的现成底座，边际成本最低。
  4. MQTT、S3、其余小件——有具体场景再开，不预先投入。
