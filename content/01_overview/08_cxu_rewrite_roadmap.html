CXU Full SLA Rewrite Roadmap

StatusProject approved (2026-10-25, set by the user: plan SLA/SA in detail, fully rewrite CXU, set priorities, and start work immediately). Based on the CXU Frontend/Backend SLA Rewrite Readiness Audit in the same chapter. This page is the authoritative version of the execution plan: phases, priorities, acceptance criteria, and status are updated here on a rolling basis; each completed item is checked off with its commit noted.

Overall Goals and Principles

  • Goal: Rewrite the CXU (codex-react-ui) server (about 59k lines of TS), the various CLI bridges (about 65k lines of TS), and the Web frontend (about 88k lines of TSX) entirely in SLA, with the final form being an SLA-native backend + SAX/WASM frontend; the Electron desktop shell is decided separately in P4.
  • Behavioral alignment: The rewrite uses the existing TS version as the behavioral baseline (HTTP/WS API surface, bridge protocols, and configuration formats unchanged); before P3 the frontend can point at the new backend unchanged; differences must be explicitly accounted for, with no silent changes.
  • Foundation first: Fill the blocking items in sa_std and the SLA compiler first, then write business code; all basic cores are built into sa_std, plugins only wrap (existing policy).
  • Concurrency model fixed: Backend concurrency uses threads + mpsc, not betting on async (nested await across async fns has not yet converged, see the Feature Maturity Matrix).
  • No silent fallback: When hitting UnsupportedSabDirectFeature or a missing capability, record it in the gap table on this page and fill the foundation first, do not work around it.
  • Pace: Serial progress (local machine and Colab resource constraints), commit and push as each item completes, Colab-side 15-minute checkpoints as usual.
  • Target repository: Demos (D1–D12) are first refined in sa_plugin_sla/demos/cxu/; once real project builds begin, code is committed to layola13/slacxu (set by the user on 2026-10-25, currently an empty repository).

P1 Backend Pilot Vertical Slice (codex Bridge)

  • Form: A new SLA workspace (layout following scodex-mini's packages split): config (TOML/env), bridge-core (bidirectional spawn + JSON-RPC framing/multiplexing), http-ws-server (routing and session layer based on the sa_std built-in server), codex-bridge (full protocol adaptation for the codex app-server), store (SQLite session/history persistence via the node plugin sqlite facade).
  • Acceptance: A real codex CLI runs a full conversation round through the SLA backend (initiate, streaming events, tool calls, interrupt, resume); the existing React frontend points at the SLA backend with no code changes and works normally (API surface subset aligned); a behavior comparison table against the TS version in the same scenarios is checked item by item.
  • Output: A “wall-hit list” — all Unsupported/missing capabilities hit during the pilot and their workaround costs, fed back into P0/P2 scheduling.
  • Progress 2026-10-25: Target repository layola13/slacxu has its first commit (11b7128): workspace scaffolding + packages/cxu-bridge vertical slice No. 1 — a bidirectional stdio pump selecting a child process via CXU_AGENT_CMD (from D1), cat echo and fake-agent fixed-response dual-round smoke tests all green. Next cut: multi-line multi-round pumping + real codex integration (needs codex CLI and login prepared on the Colab side).

P2 Full Backend Migration

  • The remaining CLI bridges are migrated one by one (claude, opencode dual backends, agy, auggie, cline, command-code, grok, pi, mini, etc.), reusing P1's bridge-core; each bridge follows the discipline of “only via the SDK/standard surface” (on the SLA side that means sa_std + sla_std).
  • Other server surfaces: free-key server, accounts and authentication (bcrypt/keyring landed), postgres (if proven in use), static file and artifact serving, tunnel/public entry form alignment, configuration schema sync tooling.
  • Acceptance: Before the TS server is taken offline, all bridges and API surfaces pass comparison tests; during the dual-version parallel period, cross-validate with the same frontend.

P3 Frontend (SAX Application Frameworking → Screen-by-Screen Migration)

  • Framework before UI: SAX gains application-level capabilities — state management and data binding (leaving the static placeholder model), routing, form/keyboard-shortcut system, stress testing and optimization of airlock high-frequency stream updates (token stream scenarios), virtualized lists.
  • Heavy components decided one by one: code view and diff (can be built on tree-sitter outline/highlighting), terminal (PTY is already in the backend, frontend rendering needs xterm-level capability, WASM self-built or JS island coexistence, choose one and account for it), a Monaco-level editor is an independent sub-topic (start with light editing + JS island transition, do not pretend equivalence).
  • Acceptance: Migrate screen by screen, each screen with a feature comparison table against the React version; only discuss taking React offline after all main flows (conversation, terminal, files, settings, tasks) work.

P4 Desktop Shell and Release

  • Electron shell keep-or-drop decision: keep it (only swap the page artifacts) or replace it with a native/Web form; Windows packaging, signing, PTY native parts, obfuscation and installer flow are aligned in this phase with the TS version's current state.
  • npm distribution and plugin channels follow the existing forms (backend artifacts as sa plugins / standalone binaries, the two forms decided at kickoff).

ts2sla line-drawing (decided 2026-10-26): Do not write another full SLA emission backend. Third-party libraries may first go via wrapping: use tsgosa's existing ts→sa artifacts (.sai) plus a thin SLA wrapper (signature translation and forwarding); this project's own TS must always be truly converted to SLA, wrapping must not substitute for it. Measured: the project's backend third-party surface is only about 15 packages, and most are already covered by existing sa_std surfaces (SQLite, TOML read side, keyring, PTY, WebSocket, tree-sitter); the pure TS libraries truly needing compilation plus wrapping are in single digits (zod, js-tiktoken, pngjs, qrcode, etc.).

Battlefield shift (decided 2026-10-26, goal unchanged): Separate pit probing from construction — first compile the full CXU backend surface with tsgosa (apps/server, sdk-*, packages, backends, mini-codex, duck2api, free-key-server; frontend TSX only an intelligence sweep, not a gate), probe rejections and failures in one pass, classify into three categories — sci compiler / sa_std / tsgosa emitter — and fix the foundation first; once each rejection has an owner and a disposition, withdraw (native plugins such as node-pty, sharp are handled at the declaration boundary surface), then return to the SLA main battlefield and continue repair following the existing repair map. Development Environment Memo: Using the Colab Global Variable GIT_TOKEN (2026-10-26)

SA/SLA development, compilation, testing, and pushing all take place on Colab runtimes (repositories located at /content/sa_all/). The push credential is the global variable GIT_TOKEN set by the repository owner in Colab (injected via google.colab.userdata into the environment of notebooks and service processes, along with GIT_URL, BRANCH in the same batch). Key fact: the SSH login shell does not inherit that environment, and /root/.bashrc generally does not have this variable either — concluding “no token” from checking only .bashrc is a wrong conclusion.

How to obtain it: in the remote shell, traverse process environments to extract it (/proc/<pid>/environ holds each process's startup environment, NUL-separated):

TOK=$(for p in /proc/[0-9]*/environ; do tr '\0' '\n' < $p 2>/dev/null | grep -m1 '^GIT_TOKEN='; done | head -1 | cut -d= -f2-)

During the scan, individual pids that have already exited produce harmless No such file warnings. Once obtained, splice it only within that remote shell into the push URL (https://layola13:${TOK}@github.com/…) for use; command output must be redacted before viewing, and push results are verified with git ls-remote. Fallback chain: if the process environment yields nothing, then check /root/.bashrc (github_pat_ or GIT_TOKEN= lines); only if both sources are empty may it be judged that there is no token. Security discipline: the token value must never be printed, never written to any file, log, or document; each new Colab runtime is automatically re-injected by the account side, so after environment recovery (restore-colab) pushes always use this method, with no need to write credentials onto the box. This method applies to all git pushes on Colab: manual commits, 15-minute checkpoints, and catch-up pushes after recovery.

Development Environment Memo: One-Click Toolchain Recovery for a New Runtime (restore-colab.sh, 2026-10-27)

After a Colab runtime expires, a new runtime only automatically pulls the repositories; the toolchain (compiler, plugins, CLI, etc.) is not retained. The recovery entry point is tools/restore-colab.sh, version-managed with the sala repository: once SSH to the new runtime is reachable, running it once idempotently reinstalls — apt dependencies (LLVM 14/20, libssh, libsecret, QUIC), Zig 0.17.0, wasmtime 25.0.2, serially builds sci and the sla/http/node/sax plugins and dev-installs and confirms them, codex/opencode CLI, Kilo configuration and smoke test. The script does not include repository cloning (repositories are automatically pulled by the Colab startup flow).

Usage: for a formal recovery, run tools/restore-colab.sh directly (long-running, best run detached in the background while watching the log); tools/restore-colab.sh --verify is a read-only check (17 items: zig, llvm, wasmtime, sa binary, libsa_std.a, each plugin's installed state, node, codex cli, etc.), performing no installation. On 2026-10-27 the new runtime c8bbff8ecc89 was measured to pass: detached execution about 16 minutes, --verify 17/17 OK. Note: uncommitted work under /content on the old runtime (bulk work trees, corpus TSVs, etc.) is lost with the runtime and is not within the script's recovery scope; important progress can only be preserved via checkpoint commits and pushes.
