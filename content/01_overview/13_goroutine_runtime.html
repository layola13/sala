状态：讨论记录（2026-10-29）。命题由用户提出并定性为「非常亮点」；落点已收敛（见第一节），一期范围已由 Jev 裁定（见第七节）。实施定序（用户 2026-10-29 定）：cpp2sa / go2sa 暂缓、goroutine 先行，一期实施线已启动（本机 staging goroutine-local，基点 sci main 5509766b）；go2sa 暂缓期间一期表面形态为 sa_std extern 面 + SLA 直调 extern 验收；SLA 内建语法面经 S3 重裁改为紧随运行时一期验收之后（见第八节）。

一、命题与落点

命题：能否把 Go 的 goroutine 引入 SA。讨论收敛的落点是：不进 SA 规约——SA 底座冻结（寄存器 + 所有权/能力规约保持稳定，不为任何单一前端让路）；goroutine 本质是一个运行时能力，应落在 sa_std 运行时核心，上层语法面（SLA 的 spawn 面、go2sa 的 go 语句）只是表面糖。定位上它属于基础核心，合「一切基础核心 built-in sa_std、插件只做包装/框架层」的架构 doctrine：没有它，goroutine 语义的每个上层消费者都要各自造调度器轮子。

二、为什么 SA 装 goroutine 反而更顺

  • 无 GC 缠绕：Go 调度器最难的一半是与 GC 的配合——栈扫描找根、栈拷贝时逐指针修正。SA 是所有权模型、无 GC，这一半成本直接不存在：栈不需要为 GC 扫描，v1 不做栈拷贝也就没有指针修正问题。
  • 通道可静态防竞争：channel 传所有权值可由检查器按类 Send 语义静态验证（发送即移交、接收即取得），构成「无 GC 的 goroutine + 编译期防数据竞争的 channel」组合——这是 Go 本身给不了的，也是本命题区别于「又一个协程库」的核心亮点。
  • 地基已备两块：F-perf-1 的 sa_std_net_poll_wait 就是 Go netpoller 的对应物（已落地、slaredis 已采用）；std 的 pthread 面也在。缺口只有中间一层：上下文切换 + M:N 调度器。

三、v1 形态（讨论稿，范围以裁定为准）

  • 栈式协程，不走 stackless（stackless 无法在任意函数深处挂起，与 goroutine 语义不符）。
  • 每 goroutine 固定虚拟栈预留 + guard page 按需提交，栈溢出显式 trap；首期不做 Go 式拷贝扩栈，上限写明、不静默。
  • 上下文切换先做 x86_64（每架构约百行汇编量级），其余架构是否同批见 S5。
  • 调度器以 Zig 写在 sa_std：运行队列 + work stealing + park/unpark；网络 I/O 全部经 netpoller（sa_std_net_poll_wait）不阻塞载体线程。
  • 抢占首期协作式：前端在调用点、循环回边、通道操作处插入 yield 点（Go 1.14 之前同款）；信号异步抢占留二期——是否一期即做见 S2。
  • 阻塞文件 syscall 会堵住载体线程：调度器线程池代偿，或首期明确只保证网络 I/O 非阻塞、文件走线程卸载——两种处理都必须显式登记，不许静默降级。

四、硬边界

  • wasm 目标：原理上可支持 goroutine（用户 2026-10-29 指正：Go 官方 wasm 移植即实证；可行路径为 Asyncify 式二进制变换、编译器级栈状态变换、Wasm 栈切换提案 / JSPI 等），但不能用一期 x86_64 的原生栈指针切换机制实现，须走独立降低轨道。故一期对 wasm 仍明示 UNSUPPORTED，登记性质为机制差异、非原理否定，写进契约。
  • goroutine ≠ GC：引入 goroutine 不解决 go2sa 的堆对象内存故事，那是独立未解项，不要混为一谈。
  • 在 goroutine 内调用阻塞型 extern（FFI）会堵住载体线程，此约束须入运行时契约文档，调用方自担。

五、下游价值

此运行时不只为 go2sa 的 go 语句铺路：slanginx 的 per-connection 模型、slaredis 的连接处理、db 的服务化候选都吃同一个 M:N 运行时。它是 sa_std 继网络核心之后，第二个「上层没有它就得各造轮子」的基础核心候选。

八、SLA 语法面与生态提升讨论暨 S3 重裁（2026-10-29）

讨论命题（用户）：若真的引入 goroutine，SLA 也要增加对应语法——这对整个生态提升多少？主会话评估收敛：提升主要在应用层，且是结构性的。

  • 服务器形态归位：slanginx / slaredis / db 三台服务器不再各自手搓并发模型——slaredis 的单线程 poll 循环 + 分片等待集、slanginx 的 F2 并发 serve 至今没有原生答案、db 的并发困在 Zig 层 epoch 模型里 SLA 够不着；有了 go + channel + select，都能写成「每连接一条顺序代码」。
  • 消除函数染色：SLA 现有 async 是 stackless，async/sync 两界分明；栈式 goroutine 让任何函数都可阻塞，日常并发代码不再需要为异步涂色。
  • CXU 后端接缝原生化：桥接泵、长轮询、子进程管理、流式转发这些并发形接缝，现在靠回调与轮询拼接，goroutine + select 是它们的原生形状。
  • 生态定位：SLA 语法面落地后，生态定位收敛为「Go 的并发模型 + 所有权检查 + 无 GC」；仅有 extern 面撑不起这个定位。

不提升项：单线程性能数字（99% 目标拼的是 std 实现质量，调度开销甚至略高于手调事件循环）、编译器存量缺陷，一个都不因此解决。代价：检查器要新增通道载荷所有权规则与 spawn 捕获规则（goroutine 可捕获什么、按移还是按借——Go 不管，我们不能不管），以及与既有 stackless async 的互操作口径，均为真实设计工作量。

前提变更：第七节 S3 原裁（go2sa 先行 0.61 / 两面同批 0.43）的理由是 go2sa 先消费运行时；用户已定 go2sa / cpp2sa 暂缓且无恢复日期，SLA 成为运行时唯一消费面，extern 直调只是验收形态、不是生态形态——排序理由不复存在，故重裁。

Jev 重裁（2026-10-29，jev-1.14.0，裁定文件 ~/workspace/jev-designs/goroutine_s3_reruling.json）：

  • 前提已实质变更：0.89。
  • 新排序：SLA 语法面紧随运行时一期验收之后（0.83）——批内含 go/spawn 语句、channel 类型、select 语句、通道载荷所有权与 spawn 捕获的检查器规则、与既有 async 的互操作口径；检查器设计可与运行时 C 期重叠，但 SLA 编译器代码不得先于运行时验收落地。
  • 未选：维持原 S3 姿态等 go2sa 时代（0.51）；立即与运行时并行开工（0.14）。
