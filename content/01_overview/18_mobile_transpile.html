入门指南 > 移动端转译：sla2swift 与 sla2kotlin
状态：方向裁定记录（2026-10-29，用户定）。本页登记 SLA 写 Android / iOS 的路线裁定（采双转译器）与形态约束；设计普查进行中，细则以普查产出为准。本方向为支线，总定序见 13 号文档第九节与 17 号文档第四节。

一、需求：产物交付客户、客户只用 Swift / Kotlin

用户定（2026-10-29）：SLA 除了能写前端与后端，还要能直接写 Android / iOS。决定性的约束不在技术面、而在交付形态：移动端产物是交付给客户的，客户明确要用 Swift 与 Kotlin 两门语言，且不熟悉 SA / SLA。也就是说，客户须以这两门语言的源码形态接收产物、在自己的工具链（Xcode / Android Studio）内继续维护；交付一个他们读不懂的中间形态不成立。

二、三路线与裁定：A、B 否决，采 C

  • A — SA 原生编译 arm64 + C ABI 薄胶水（否决）。SLA 经 SA 编译为 arm64 原生产物、以 C ABI 对外、宿主侧写一层薄胶水接入平台。此路线让客户面对的不是 Swift / Kotlin 源码，交付形态不合第一节约束。
  • B — 经 SA 的 C 发射器（否决）。产物为 C 源码、再由客户侧桥接进 Swift / Kotlin。客户明确要两门语言本身，中间隔一层 C 同样不合交付形态。
  • C — sla2swift + sla2kotlin 双转译器（采纳）。SLA 源码直接转译为 Swift 源码与 Kotlin 源码，客户以原生工程形态接收并共维。A、B 系主会话分析所提，经用户于 2026-10-29 明确否定；本生态此前唯一成立 C 的情形即「产物须以目标语言源码分发」，移动端恰属此情形。

三、形态约束

  • 发射层级：两个转译器的输入为 SLA 检查之后（宜单态化之后）的 AST，与现有文本 / SAB 双 codegen 同源；不走 SA 寄存器层（寄存器层的形态无法产出客户可读可维护的目标语言源码）。
  • 无忠实映射处响亮拒绝：SLA 语义（所有权与移动、goroutine 并发等）在 Swift / Kotlin 无忠实对应的，一律显式报错拒绝，禁止静默近似——tsgosa 方言的教训即在于此（看似等价的表面转换、语义悄悄变样）。拒绝清单由设计普查逐项圈定并落字，不留隐含行为。
  • 目标语言运行时支持面：String、Vec 与集合、并发原语等 SLA 概念在目标侧由一套随转译器交付的运行时支持代码（Swift / Kotlin 各一份）承接映射，转译产物依赖此面而非逐处内联展开；支持面的范围与形态由设计普查定义。

四、状态与排程

设计普查线已派：产出 sla2swift / sla2kotlin 的映射表、不支持清单与分期建议（存 ~/workspace/sla2mobile/DESIGN.md），完成状态以其终报为准。本方向定位为支线：全程序总定序（Erlang + goroutine 综合体 → 三台并发性能改进 → Verse / Haskell 特性）不变，用户未另行提级之前，本线只做设计普查登记，不挤占主线施工面。
