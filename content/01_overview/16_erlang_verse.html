一、Erlang 候选（主会话评估）

Erlang 的强处在 BEAM 虚拟机上的故障架构：Actor 模型零共享状态、按归约计数预算的真抢占调度、链接/监视加监督树构成的容错体系，外加分布与热升级。它的进程首先是故障隔离域，并行只是副产品。从中取四项候选：

  • 监督结构升格 std 一等件：承 15 号文档已采的 goroutine 边界 recover 之上，把重启策略做成声明式 std 件（一组 goroutine 挂在监督者下，写明 one-for-one / 全组重启 / 重启强度上限），而不是每个服务器各自手写 recover 循环。
  • monitor：死亡通知即消息：goroutine 退出或崩溃时，向监视方投递一条可经通道 / select 接收的信号，把「等对方死」从轮询变成事件。运行时侧只是一个小原语，与已定的通道 + select 表面严丝合缝。
  • 预算式让出检查：Erlang 归约计数的静态版——编译器在循环回边 / 调用点插入计数检查，预算耗尽即让出。这是治「CPU 型 goroutine 不让出饿死同伴」的正解，但要动编译器发射，登记为 goroutine 二期候选。
  • OTP 式服务器骨架作 std 库惯用法：gen_server 形的标准服务器骨架（init / handle / 状态循环）是纯库层模式，等语法批落地后做成 SLA std 惯用法，不动语言。

不取三项：邮箱 + 选择性接收全套（单队列模式匹配接收语义复杂、扫描成本有名，通道 + select 已覆盖主要价值且所有权故事更干净）；不可变 + 拷贝语义（与所有权零拷贝正相反，我们在「无共享」上走通道传所有权这条静态更强的路，不换道）；分布与热升级（三台都是单机对标物，db 还明确拒网络监听面，与本生态无关）。

隔离对照：Erlang 进程的隔离性是靠「每进程 GC + 全拷贝」买的，这正是无 GC 模型付不起也不必付的——我们的监督走边界 trap + 所有权栈，隔离强度够服务器用，成本低一个量级。

二、Verse 调研结论（深研，2026-10-29）

Verse 是 Epic 的 UEFN / UE6 语言：Tim Sweeney 提出构想，Simon Peyton Jones 等人设计，2023 年 3 月随 UEFN 首发；2026 年 6 月 State of Unreal 宣布它是 UE6 的基础语言，UE6 早期访问定在 2027 年底。

血统纠正：Verse 没有 Erlang 渊源。它的根在 Haskell 的 STM（软件事务内存）与逻辑编程——核心演算见《The Verse Calculus》。Erlang（零共享 + 消息传递）与 Verse（共享状态 + 事务）是对「并发为什么难」的两种相反回答，不是亲戚。

已发货的部分：一是本地失败回滚事务——Verse 表达式可以「失败」（无值、非异常），失败上下文内对 var 的写入是暂定的，上下文整体成功才提交、任何一步失败即整体回滚；其运行时 AutoRTFM 是写日志式的单线程事务，已在 Fortnite 服务器生产运行。二是函数签名效应标注：<transacts>（可回滚地改状态）、<decides>（可失败）、<suspends>（异步）、<varies> 等写进签名、由编译器静态检查，不可回滚的函数默认禁止进入失败上下文。

未发货的部分（宣布 / 设计目标）：并行 STM——Sweeney 公开点名 Haskell 的《Composable Memory Transactions》为蓝本（大量更新并行推测执行、无冲突提交、冲突重试）；客户端预测——仅见于 Book of Verse 中一个未发布的 <predicts> 效应设计（客户端预测运行、服务器权威纠正）。两者都是 UE6 的目标，不是现成机制。

Verse 的并发本体是协作式协程：race / sync / rush / branch 与 spawn；且 <suspends> 与 <decides> 不可同体——异步世界与事务世界之间有一道硬接缝。

三、主会话评估：三方对照的收敛

我们的并发选型在光谱上的位置：主体站 Erlang 侧（goroutine 隔离 + 通道 + 监督），事务只在 db 引擎层以显式写集存在（写集暂存 + 原子提交）——等于两边各取了适合无 GC + 所有权模型的那一半。

  • Verse 最有行动价值的是效应标注：它用 Epic 级规模证明了「把 suspends / transacts / decides 写进函数签名、编译器强制」可行。这恰好是函数染色问题的正解形态——不是消灭染色，是把染色变成可检查的契约。正对 SLA 语法批已列的「async 互操作口径」一项：spawn、通道操作、可能 trap 的能力应在签名上可见且被检查。
  • Verse 式隐式回滚不采：「写了再说、失败自动撤销」的隐式语义与我们的显式纪律相冲，且三台都不做推测执行，没有消费场景；我们需要事务的地方（db）已有显式写集这一自己的版本。
  • 联机预测 / 回滚不采（只观察）：那是游戏 netcode（多人联机状态预测与协调）的命题，我们的交付物里没有这个物种；且其机制本身在 Epic 侧也尚未发布。

六、STM 窄形态候选（Haskell 显式式，2026-10-29）

区分在先：本节的 STM 指 Haskell 显式式——atomically 块圈定范围、读写走事务变量、冲突时自动重试，块与块可组合（含 orElse 的「试 A、不行试 B」）。它与第二节所述、第四节已否的 Verse 隐式回滚（写进失败上下文即自动暂定 / 撤销，不采纳确认 0.86）不是一物——否隐式式不等于否显式式，故本节单独裁定。

主会话评估要点：

  • STM 的真本事是可组合性：atomically 可以嵌套合并、orElse 给出协调组合——这是锁与通道都给不了的，理论层不判死。
  • 张力在它预设多方共享可变状态，与我们的所有权纪律相冲：共享状态的答案队列已有次序——属主 goroutine 模式（OTP 骨架）→ Mutex / RwLock（运行时一期 C 期已含）→ db 引擎层，STM 只能排在这条队列之后。
  • 适用面有限：热键冲突下的重试风暴、事务内禁做 I/O（提交后才能落盘）这两条限制它在大状态上的适用；Clojure 的 STM 亦只用在中小协调状态、非数据库引擎——窄形态正是按这个量级圈定的。
  • 检查器是拦路虎：事务会重试意味着块内代码可能执行多次——副作用须静态禁绝（I/O、通道操作不得入块）；事务单元内 owned 值在读 / 写 / 回滚 / 重试各路径上的所有权归属须可判读。这是研究级的检查器设计，不是语法批能捎带的。可行的借力路径是 Verse 的效应标注：用签名效应圈定可回滚代码，接第四节已采纳的效应标注线（0.66）。

Jev 裁定（2026-10-29，jev-1.14.0，裁定文件 ~/workspace/jev-designs/stm_narrow_candidate.json）：窄形态——显式 atomically + 受限事务单元、仅服务小型 goroutine 协调状态、排 goroutine v2 之后、立项前先过检查器可行性普查——登记为远期候选 0.63（温和肯定）。但两扇门当前都偏冷：需求门 0.30（三台改造以属主模式 + 锁落地后，剖析真能揭出「非 STM 不可」的协调痛点的期望低）；检查器可行性门 0.36（在不危及现有裁判机健全性的前提下扩展出事务纪律，把握弱、属研究级风险）。

采纳处置（默认同意）：登记为远期候选、双门制——需求门（三台改造后的剖析实证）与可行性门（检查器普查）任一不过即关闭；不进当前 SLA 语法批，不动三台改造计划。
