CXU Frontend/Backend SLA Rewrite Readiness Audit

StatusAudit draft (2026-10-25, proven from source). The question: with the current SLA / sa_std / plugin ecosystem, can we rewrite the frontend and backend of CXU (codex-react-ui: about 59k lines of TS on the server side, about 88k lines of TSX in the Web frontend, about 65k lines of TS in the various CLI bridges, plus an Electron desktop shell)? The conclusion is split between frontend and backend: the backend foundation is basically complete, lacking three hard gaps and one maturity prerequisite; the frontend is not ready. The network layer was audited separately on 2026-10-24 (all 9 protocol dependencies CXU uses are built in); this page audits the surfaces outside networking.

Backend: Surfaces Already Complete

  • Process management (CXU's core action): process.sai has 54 exports — the spawn family with cwd / arg0 / process group / setsid / pidfd / uid / gid / supplementary groups / chroot variants, the full set of wait / try_wait / kill / process-group signals / pidfd, stdout/stderr pipe reading, and exec_capture. Managing the lifecycles of the various CLI child processes lacks no primitives.
  • Data and text: a standalone JSON module with 51 exports; string 25, fmt 14, regex (text/regex), and a complete set of collections (hashmap/hashset, btree_map/set, vec, vec_deque, binary_heap, sort, iter).
  • Files and environment: fs with 120 exports, env 22, time 19, and a standalone path module.
  • Concurrency: thread with 9 exports + the full sync set (mutex / rwlock / mpsc / condvar / barrier / atomic / once) and the Arc/Rc/Cell/RefCell core libraries. Multi-session concurrency can follow the thread model.
  • Protocols and storage: an HTTP/1.1 server and client, bidirectional WebSocket, SSE, a TLS client (including ClientHello fingerprint shaping, corresponding to CXU's fetch-impersonate) and a TLS server, QUIC/HTTP3, SSH, compress, multipart, and the DNS public API are all built in (see 06_stdlib and the earlier audit); the SQLite entry point is the node plugin's sqlite facade (sa_node_plugin_sqlite_*, wrapped by sci's plugin_sqlite.sa macros; correction: sa_plugin_db is a home-grown columnar engine, not SQLite), as proven by the D3 demonstration (2026-10-25).
  • Existence proof: scodex-mini has already been written in SLA as a single-turn agent CLI (HTTPS POST + tool loop + shell_exec output capture), proving that agent-skeleton programs can be expressed today.

Backend: Hard Gaps (Ordered by How Blocking They Are)

  • ① A child process's stdin is not writable (the number-one blocker): std's spawn implementation creates only stdout/stderr pipes for the child (proven in the spawnProcessConfiguredCwd source); SpawnResult has only the three handles process/stdout/stderr and no stdin pipe. Yet the CXU bridges' core loop is bidirectional stdio: write JSON-RPC requests and prompts into the CLI's stdin and read its stdout. The fix is clear: add a bidirectional spawn variant to std (a stdin pipe + write/close handles); this is a sa_std increment, not an architecture problem.
  • ② PTY is missing: term.sai has only terminal raw mode, window size, and epoll helpers; there is no openpty/forkpty. CXU's terminalPty (node-pty) functionality has no way to land. The fix: build a PTY master/slave pair + resize + read/write into std based on posix_openpt/grantpt or forkpty.
  • ③ fs watch is missing: the fs surface has no inotify/directory-watching wrapper (CXU has 18 uses of fs.watch). Polling can substitute initially; the proper fix is to wrap inotify into std.
  • ④ Small missing pieces: TOML parsing (codex's config.toml is a hard requirement), bcrypt password hashing, and the OS keyring — std has no ready-made piece for any of them. None is large in magnitude: either link a system library via FFI, or write it at the std/SLA layer (a TOML parser and bcrypt are both bounded workloads).

Backend: The Maturity Prerequisite

The compiler itself is still converging (see the Feature Maturity Matrix, a snapshot at the time of writing): sa sla check 306/313, sa sla build-exe 239/313 (about 76%). Everyday features not yet on the direct path include for-in collection iteration (Phase 6), enum payloads / match extraction and @derive (Phase 5); the async/await state machine covers only linear await sequences, nested awaits across async fn boundaries fail on both backends (Phase 8 partially complete), and the executor is still a polling macro. The implication: writing SLA at the backend's scale of hundreds of thousands of lines will repeatedly run into UnsupportedSabDirectFeature on long-tail features (loud failure with no silent fallback, which is a good thing); and the concurrency design should be fixed on the thread + mpsc model rather than betting on async. Also: SLA does not yet have &mut (&self covers both reading and writing, with the SA Referee as the backstop), so the borrowing discipline of a large project differs from Rust's and its ergonomics need validating in a pilot.

Frontend: Not Ready

The SA ecosystem's frontend story is SAX (see What SAX Is and Its Development Model): .sax compiles to app.wasm + airlock.js (the WASM↔DOM bridge) + index.html, the react plugin provides a React-style way of writing, and the mui plugin provides a Material component library. Its official positioning is pure interface engineering: static placeholder data, interactions that only switch state; the sample codex_ui redraws one React interface's skin in SAX and contains no business logic. The CXU frontend, by contrast, is a real application: the Monaco code editor, xterm terminal rendering, three.js, marked, git-diff views, virtualized lists, 53 WebSocket streaming state machines, localStorage persistence, Web Workers, canvas — none of these has a counterpart in the SAX/WASM ecosystem, and the airlock bridge's behavior under high-frequency token-streaming updates is also unverified. The prerequisite for a frontend rewrite is first growing SAX from an "interface dialect" into an "application framework" (state management, routing, editor/terminal-grade heavy components, a component ecosystem), which is another order-of-magnitude project, independent of completing std. Ruling: the frontend is not scheduled; SAX is only suitable for new-interface experiments.

The Desktop Shell

CXU's Electron desktop shell (packaging, node-pty native rebuilds, obfuscation, the Windows installation bundle) is outside SLA's range. If the backend is rewritten first, the desktop shell can be kept for the time being, with only the page artifacts swapped for static files newly served by the backend; a pure Web form needs no shell at all. This item is not a blocker for the backend rewrite, but the trade-off must be made explicit when the project is proposed.

Suggested Path (If a Backend Rewrite Is Proposed in the Future)

  1. First complete two std pieces: bidirectional spawn (a stdin pipe) and PTY, both landed following the established "basic cores built into sa_std" policy and accompanied by tests.
  2. Take one real CLI bridge as a pilot vertical slice (the codex bridge is suggested): bidirectional stdio JSON-RPC + HTTP/WS/SSE forwarding + configuration TOML + session persistence, all in SLA, quantifying how many times it hits Unsupported and what the detours cost.
  3. Only after the pilot passes, evaluate the schedule for a full migration; the frontend stays on React, untouched.

Appendix: The tree-sitter Integration Path

CXU's code intelligence layer (saVmTreeSitter.ts, about 2700 lines, + saVmCodeGraph.ts, about 1300 lines: file outlines, definition lookup, code graphs) is built on tree-sitter (currently using the WASM builds of web-tree-sitter + tree-sitter-wasms). The SA ecosystem currently has zero trace of tree-sitter. The key fact for integration: tree-sitter's core is a C library (tree_sitter/api.h); Rust's tree_sitter crate is only a wrapper over the same C ABI; each grammar exports one C symbol, tree_sitter_<lang>(), and its parser.c is generated C code. So no Rust ABI is needed (it is neither stable nor directly linkable); just follow SA's established pattern for integrating third-party C libraries — exactly the same shape as SSH (dlopen libssh2/libssh), QUIC (dlopen ngtcp2/nghttp3), and brotli.

  • Landing point (following the "basic cores built in" policy): sci adds a runtime module sa_tree_sitter.zig into sa_std, dlopens the libtree-sitter core library, and exposes sa_ts_* externs + a tree_sitter.sai declaration shipped with sci (in the same form as ssh.sai's 26 exports); when the library is missing it is explicitly UNSUPPORTED (the same handling as SSH on js/c/wasm), never silently degraded.
  • API surface: the extern layer thinly wraps the C API — parser construction/destruction, set_language, parse (both string and callback inputs), tree/root, node navigation (type/text/child/named_child/start_byte/row-column points), query compilation and captures (outlines/definition lookup rely on it); the SLA layer then wraps it in managed handles (a Tree's lifetime governs Node reads, the same discipline as sa_http stream handles). Incremental parsing (ts_tree_edit + reparse) is listed for phase two; phase one does full parsing, aligned with CXU's current usage.
  • The grammar supply chain: each language's parser.c (+ an optional scanner.c) is compiled into libtree-sitter-<lang>.so, and the host dlopens its entry symbol on demand; the tree-sitter-wasms CXU uses are WASM builds of the same parser.c, which cannot be reused on the native side — a native .so build pipeline is required (grammar repositories all commit the generated parser.c, so once the pipeline is built, adding a language is just adding an entry). A mismatch between a grammar's ABI version (LANGUAGE_VERSION) and the core library's supported range must produce an explicit error (queryable via ts_language_version). Cores built in, grammars loaded by file: the first batch of languages CXU needs ships with std, and more languages can be added as files without recompiling std.
  • The road not taken: invoking the tree-sitter CLI (a Rust binary) as a child process — usable today (process spawn is complete), but starting a process for every parse + parsing S-expression text back is fit only for temporary verification, not for a formal integration.
  • Workload reference: the same magnitude as the SSH integration (one runtime module + dozens of externs + a declaration file + loopback tests); the grammar build pipeline is counted separately.
