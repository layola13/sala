Getting Started > cpp2sa and go2sa: Proposal Discussion for Two New Frontends
Status: discussion record (2026-10-29). The two routes are completely different in nature: cpp2sa is a "detour" — built as a tier project of bc2sa; go2sa must be "built new" — a source converter, whose concurrency semantics depend on the ruling outcome for the goroutine runtime. Both belong to the upper-layer frontends/converters and do not touch the SA base. Project proposals are postponed (decided by the user on 2026-10-29): the goroutine runtime goes first, and this document is kept as the route basis for when the two frontends' proposals resume.

1. cpp2sa: Take the bc2sa Tier; Do Not Write a Source Frontend

The C++ source surface is the largest among mainstream languages (template instantiation, overload resolution, exceptions, RTTI); a hand-written source frontend would amount to rewriting half of clang, so it is not taken. bc2sa is already connected end to end (the transport wall and the phi wall have been dismantled, the three gaps are being landed by the strengthening line, and real crate functions have been run and compared), and clang++ -emit-llvm-bc does the entire language surface of templates and overload resolution for free — cpp2sa only needs to be built as bc2sa's tier project: a driver + a flag set + a coverage census + regression corpora; the repository can be standalone, with the implementation shared with bc2sa.

  • First-phase sweet spot: -fno-exceptions -fno-rtti, analogous to the Rust route's panic=abort sweet spot, initially sidestepping exceptions and RTTI.
  • Expected new unsupported classes (by the Rust probe's experience, they should be a few concentrated classes, not a long tail): invoke/landingpad (exceptions), variadic arguments, inline assembly, TLS, global construction order, and thunks for vtables and multiple inheritance — to be filled in mechanically class by class per the census, without writing a big translator in advance.
  • The STL's string/vector/map are header templates, already monomorphized in the bitcode, and pass mechanically; the extern surface lands on a few families of libc/libc++abi.
  • First-phase acceptance follows bc2sa's three tiers: the core subset (classes/virtual functions/RAII) → the STL container tier → a pure-logic function from one real small C++ library, compared against a native run.

2. go2sa: A Source Converter; the Difficulty Is the Runtime, Not the Syntax

Go's syntax is small and regular, and the official toolchain ships a parser and type checker (go/ast, go/types), so the converter is written in Go and directly consumes the concrete types from go/types, at a frontend cost far below the TS line. The real cost is in the semantics and the runtime model: goroutines/channels need a scheduler, interfaces need dynamic dispatch, defer/panic/recover are control flow, and heap objects need a memory story.

  • First-phase scope: the sequential subset + interfaces + defer; interfaces land as fat pointers + method tables, and defer lands as scope guards.
  • goroutine/channel: it does not bring its own runtime, but lands directly on sa_std's goroutine runtime (see the goroutine runtime discussion page); its phase-one scope is decided by the S1–S6 rulings at the end of that page, and this page sets no separate criteria.
  • Semantic divergence register (select fairness): when multiple arms are ready at once, SLA's select takes the first ready arm in case declaration order (a deterministic bias), while Go chooses uniformly pseudorandomly (a starvation-prevention mechanism); Go code that depends on selection fairness must rotate the arm order itself when migrated to SLA. This is an already-written contract (see the TS-13 same-origin criteria in section eleven of document 13), not a defect.
  • The GC/heap-object memory story: a standalone unresolved item. Candidates (to be ruled in phase one): a short-lived exemption like TinyGo's -gc=leaking, or per-module arenas/reference counting — it must not silently pretend there is a GC.
  • panic/recover: phase one guarantees only the abort semantics of recover-free code; the scope of recover support is explicitly registered.

3. The TinyGo Route: Only a Probe Tier

TinyGo can emit LLVM bitcode to feed bc2sa with almost zero new code, so it is worth making a small probe sample and letting census data speak. But TinyGo's std subset and reflection limits would discount the promise of "converting real Go projects" — the same shape as the lesson from slars's phase-one scope ruling: the difference list must be decided by a census, not deleted by gut feeling. So it is positioned as a probe/fast-track candidate, not as go2sa's main route.

4. Positioning and Division of Labor

Division of labor with the existing frontend family: slars is our own hand-written frontend, bc2sa is the channel for machine-converting real Rust, tsgosa is the TS converter, cpp2sa is bc2sa's C++ tier, and go2sa is the newly written Go source converter. All five belong to upper-layer evolution; the SA specification does not move. This page is only a discussion record: whether to propose the projects, and the scheduling order of go2sa versus the goroutine runtime, are for the user and Jev to rule on.
