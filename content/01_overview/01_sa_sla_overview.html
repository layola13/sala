Overview of SA and SLA

This page explains the two names that are most easily confused: SA (Safe ASM, safe assembly) and SLA / Sla (the high-level language frontend). After reading it, you will be able to tell which one is the intermediate representation and which one is the high-level language, and which repositories make up the whole system.

What SA (Safe ASM) Is

SA is not a language meant to be written by hand. It is a safe intermediate representation (IR) + runtime: any upstream language can compile code to SA, and the same backend then verifies it and emits it as a native executable or WASM. The compiler repository sci ships with:

  • Compiler core: Flattener → Referee (static ownership verifier) → LLVM-C / WASM emitter;
  • The sa_std standard library: Vec, HashMap, String, Option, Result, Arc, Mutex, and io/fs/net and more, in .sa / .sai / .sal text formats plus a Zig runtime implementation;
  • The sa CLI: the host for subcommands such as sa run, sa build-exe, sa build-wasm, and sa plugin.

SA's design points in one sentence: zero AST, linear scanning, O(1) bitmask borrowing checks, a five-symbol contract (= & ^ ! *), and frontend responsibility. SA is aimed mainly at generation by LLMs / compiler frontends, not at hand-writing.

The Relationship Between SLA and SA

Sla is a Rust-style high-level language frontend built for SA, positioned as “LLM friendly”. Sla source code (.sla) does not run directly; it compiles to SA:

SLA AST / 类型检查 ── 共享 lowering 规则 ──┬── SA 文本 emitter（.sa）
                                          └── SAB 结构化 emitter（.sab）

This is the “Y-shaped” architecture: one shared frontend trunk, two emitters. The current position (2026-11-15): the user-facing output has only one main line, SA text (the production path) — SLA, slars, the Rust implementation, and any third-party frontend output only SA text, and the compiler's default backend is also SA text. The SAB structured emitter still exists, but it was sealed on 2026-11-15 (tag sab-sealed-2026-11-15) and is positioned as an optimization direction: it is enabled only on explicit opt-in (--test-backend sab or the sab named commands), and any feature it does not cover fails loudly, with no silent fallback.

NoteUser-facing .sla code does not need hand-written releases: Sla uses compiler-managed lifetime cleanup. The generated .sa may still contain ! instructions, but those are SA's ownership primitives and do not mean you need to write them in Sla. Also, &mut T / &mut self have not been introduced yet; currently &self covers both reading and writing.

Sla uses the SA standard library directly through top-level imports:

@import "sa_std/io/print.sai"

The Sla compiler loads these .sai/.sal/.sa contracts before type checking, and the extern functions in the contracts are available to Sla code. By default it is resolved from the environment variable SA_STD_DIR (when set) as sa_std/..., otherwise from $HOME/projects/sci/sa_std.

Maturity Expectations

The project is in active development before 1.0. Taking sa_plugin_sla's local measurements on 2026-07-07 as a reference: of 313 demos, 306 passed the sa sla check frontend, and end-to-end sa sla build-exe passed about 76% (239). The gap of about 22 percentage points between the two reflects the gap between “the frontend can parse it” and “the backend lowering can land it”. Features such as enum payload extraction, derive, the for in protocol, and async/await take a fallback path when hit; not everything in the demos/rosetta tree passes end to end. For concrete progress, see the plugin repository's docs/roadmap_status_cn.md.
