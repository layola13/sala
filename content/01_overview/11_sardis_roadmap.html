sardis (Working Name): Redis Rewrite Plan

StatusDiscussion finalized, not yet proposed as a project (finalized on 2026-10-28 after the user continued the Redis discussion; this page is the authoritative record). sardis is a candidate name (a contraction of sa + rdis), awaiting the user's naming decision. Together with sangx it belongs to the home-grown backend service series; its multi-node form depends on gap one (Raft consensus) in the coverage map.

Why Redis Fits This Foundation Better than nginx

  • Its core is a single-threaded event loop plus a set of in-memory data structures, without nginx's twenty years of module and configuration baggage.
  • The RESP protocol is an order of magnitude simpler than HTTP; a pure SLA parser is a small job; the TCP service surface, the async event model, timers (active sampling of expired keys), fs (AOF/RDB persistence), and process spawn are all ready-made in std.
  • sci already has the basic collections (hashmap/btree); the bit-level packing primitives that compact encodings need were landed by the STD wave-two BD line (sa_std/encoding/bitpack.sla).

The Real Work Is in Three Places (None of Them the Protocol Layer)

  • Compact encoding is Redis's moat: specialized structures such as ziplist/listpack, intset, skiplist, and rax (Streams) decide memory efficiency — a naive hashmap version runs, but doubles memory, which amounts to throwing away half the value. They must be implemented one by one in SLA; all of it is deterministic, pure value-layer engineering (of the same nature as the IP/CIDR value layer).
  • The persistence model decision (the only real design question before work starts): Redis relies on fork + copy-on-write for RDB snapshots and AOF rewrites. Whether the SA process surface has fork semantics remains to be checked; if not, there are three choices — a threaded snapshot (with consistency handling), starting with pure AOF, or adding a fork surface to std.
  • Replication and high availability are the long tail: PSYNC + the replication backlog buffer are protocol work and doable; Sentinel and Cluster (gossip, 16384 slots, failover) are another magnitude, and Cluster's foundation is the consensus/replication-log primitives (see gap one in the coverage map), so they are explicitly left for last and discussed separately.

Security: Redis's Signature Vulnerability Classes Are Directly Countered by This Architecture

  • Lua sandbox escape class (Redis's most severe in recent years: RediShell CVE-2025-49844, a Lua garbage-collection UAF, latent for about 13 years, CVSS 10): the root cause is embedding a complete Lua runtime and then hand-patching the sandbox. This project's scripting surface is the SA VM itself — scripts execute as SAB bytecode in a capability-limited VM, with no second language runtime to patch. The same honest accounting: the VM interpreter thereby enters the TCB, and cleaning up its stability is a prerequisite item (shared with sangx).
  • Memory corruption class (such as the HyperLogLog out-of-bounds write CVE-2025-32023): the same ruling as on the sangx page — constructively eliminated at the SLA layer, with consequences reduced to a trap/crash rather than memory corruption.
  • Deployment class: Redis's biggest real-world losses in history came from running with no password, exposed naked on the public internet. This project should default to mandatory authentication + loopback-only listening by default, opened up only by explicit configuration — explicit beats convenient.

Phases (Suggested)

  • M0: the core five types (string/hash/list/set/zset) + RESP + expiration.
  • M1: persistence (following the fork decision) + master-slave replication.
  • M2: the scripting surface (a VM version of EVAL) + Pub/Sub + transactions (MULTI/EXEC/WATCH).
  • M3: the type tail such as Streams / GEO / Bitmap / HyperLogLog.
  • Cluster is discussed separately; its prerequisite is the Raft/replication-log primitives (gap one in the coverage map).
