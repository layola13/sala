1. The Three Side-Track Probes: Overall Verdicts and Positioning

The common positioning of the three side tracks (decided by the user successively on 2026-10-29 18:32–18:38): no project proposal, no code, discussion and research only; the value of the research is not in advancing the directions themselves first, but in using external targets as probes to expose the unwritten semantics and missing surfaces of our own stack (SLA / SA / sa_std / SAX) — the sla2ts line was explicitly corrected to “digging up low-level gaps is the primary purpose; safety / fidelity are not priorities under consideration”. The three research reports are stored locally at ~/workspace/sla2mobile/FEASIBILITY.md, ~/workspace/sax-crossplatform/FEASIBILITY.md, and ~/workspace/sla2ts/FEASIBILITY.md, and the register original is stored at ~/workspace/foundation-gaps/REGISTER.md; Section 3 of this page is the written version of the complete register.

  • Probe 1 · Mobile transpilation (sla2swift / sla2kotlin) — overall verdict: conditionally feasible. The only feasible emission level = after monomorphization + the post-check AST (before lowering): generics are already instantiated (the generic-mapping and constraint-shell problems disappear as a whole), concurrency constructs are still native nodes, ownership information is visible, and this is exactly the common input form of the existing syntax_lowering and the two codegens; emitting at the SA register level is not feasible for customer delivery (the product would be unreadable). The difficulty of the two targets is asymmetric: the Kotlin side is smooth overall (Channel / select map almost directly, the main cost is the ownership copy discipline); on the Swift side the ownership surface fits more closely (~Copyable is nearly 1:1), but the standard library has no channels and no select, so a self-built channel on actors plus multi-way waiting is the single heaviest piece of engineering in the whole case. The direct-mapping surface includes async/await, the status-code model, and trait static dispatch; String needs a byte-string support type on both sides (SLA has UTF-8 byte-string semantics); the rejection surface = raw pointers / layout dependencies / macro definitions / externs outside the subset. The size of the support surface is roughly 4–7 thousand lines for Swift and roughly 2–3.5 thousand lines for Kotlin; dual-target v1 is roughly 2–4 person-months (an uncalibrated estimate); the acceptance method = three-way differential comparison (SA native vs Swift vs Kotlin on the same program).
  • Probe 2 · SAX cross-platform UI (five surfaces: web / Windows / iOS / Android / TUI) — overall verdict: conditionally feasible. All three conditions are at the SAX semantic layer: ① layout / style semantics enter SAX (currently layout relies entirely on browser CSS and SAX itself has zero layout semantics — this is the number-one foundation); ② the primitive contracts gain semantic / accessibility channels and a capability-negotiation channel; ③ the declarative subset profile is written down. The route takes (c) host-glue generalization as its backbone (the web chain is living proof: about 25 host externs, and the JS bridge uses only 8 kinds of DOM operations), (a) native-control mapping is demoted to a host implementation strategy under it, and (b) self-drawing is blocked by zero existing text-engine stock and serves only as a sidecar. Suggested landing order: web baseline → TUI (the cheapest new surface, first to validate the foundation) → Windows via WebView2 → WinUI native later → iOS / Android last (most deeply coupled with the transpilation line). Mobile crossover inclination: transpile the SAX declarative subset to SwiftUI / Compose (what the device-side runtime delivers is an SA black box, which conflicts with the ruling that customers receive only source code); imperative dom_* escapes must be rejected loudly and written down as a profile.
  • Probe 3 · sla2ts (SLA → TypeScript) — primary output: 26 low-level gaps (TS-1…TS-26, see the appendix tables in Section 3); feasibility is only a secondary quick verdict: the differential-testing asset use holds (the most direct return — the attribution process for comparison divergences is exactly the evidence-gathering process for the 26 items); npm pure-logic delivery and the migration fallback path conditionally hold; frontend sharing conflicts with CXU's already-decided wasm route and does not hold. Emission level (b) was re-verified and holds even more firmly: in the current pipeline, monomorphization (:683) comes before checking (:723), so level (a) does not exist in the pipeline at all; numeric representation (number vs BigInt) must be fixed per concrete type.
  • Appendix · Characterization of slats (disambiguation): the GitHub repository layola13/slats (HEAD b5ff4b83) is not sla2ts — it is a project that ports tsrs (the Rust rewrite of the TypeScript compiler) into SLA, in the opposite direction from sla2ts (writing a TS compiler with SLA as the implementation language; it belongs to the X→SLA inflow family). Only the span-map pipeline was truly completed (spanmap 15/15); the rest are pending mirror stubs. The two defects of ours that it surfaced have been registered as candidates 16 / 17 (pending verification).

5. Side-Track Discussion: view types / Partial Borrowing (2026-10-30, Stage One Landed)

This section registers a discussion and its follow-up disposition: on 2026-10-30 the user asked whether SLA is considering support for view types; the current status is that stage one (checker-level disjoint field borrowing) has been implemented and integrated (2026-10-30). The purpose of this section is to preserve the feature itself, our evidence, the assessment, and the ruling, so that it does not have to be argued again in the future.

The Feature Itself (Rust-Side Facts)

view types (view types / partial borrowing) let a function signature declare “only these few fields of the struct are borrowed”, and the borrow checker accordingly tracks disjoint field borrows across function boundaries. The old problem it solves is this: inside a function body the borrow checker instinctively understands that different fields are disjoint, but once a call crosses a function boundary it can only borrow the whole struct — two functions each borrow field_a and field_b, which are plainly disjoint, yet it still reports “cannot borrow as mutable more than once”. Origin and status: the idea comes from Niko Matsakis's 2021 blog post “View types for Rust”, and community demand can be traced to RFC issue #1215 (2015); it is currently an in-tree experiment — enabled on nightly with #![feature(view_types)], tracked in issue #155938, with the RFC not yet formally approved and no stabilization date scheduled (it has been accepted as a project goal, with a target completion date of 2027-04-01); recorded limitations: using it on pub / pub(...) functions is a hard error, and view groups and interaction with pattern types are not yet under consideration. The ready-made alternative on stable is the borrow crate's #[derive(Partial)] (a macro that generates disjoint borrow sets; same idea, zero overhead). Note that it is unrelated to core::sync::SyncView (the exclusive_wrapper surface, which lets a non-Sync type obtain the Sync marker); do not confuse them.

Our Demand Evidence (Defect History, Not Hypotheses)

  • DEF-KB-1: views of handle-type fields cause capability-state conflicts at control-flow merge points — field-level views have no independent bookkeeping, so merge handling can only fall back to whole-object granularity.
  • DEF-5: field extraction semantics were finally ruled by Jev as clone_on_extract (0.86) — extraction is a deep clone and the new binding truly owns it. “Taking a field out” already has a ruled semantics.
  • The (b) surface (before DEF-6b): an inline field of an owned struct used as an argument (such as STR_LEN(a.unit)) triggers BorrowConflict 1008 on both backends; it belongs to the KB-1 mechanism family.

The three cases are of one family and point to the same absence: field-granularity borrow bookkeeping. “Taking out” (extraction) already has a ruling; “borrowing only some fields across a call” (view) is the missing sister surface — the demand is not a fashion copied from Rust; it grew out of our own defect history.

Layer Judgment

The SA base is frozen and untouched: view types require nothing new from the SA specification — once a field borrow is lowered it is a base pointer + offset, at zero runtime cost; it is purely an SLA checker-layer topic (field-granularity borrow bookkeeping). slars phase one does not include it: its syntax position follows the rustc stable list, view types are not stable, and they are not on the phase-one list.

6. Language Evolution: Ordinary Function Overloading (Decided and Landed, 2026-10-30)

This section registers a discussion and its ruling: on 2026-10-30 the user asked about the current state of function overloading in SLA; after verification, they decided on the spot to introduce ordinary function overloading; after one round of “Jev rules extern_only → the user overturns it”, the scope was finalized as full (see “User Overturn and Finalized Position” below), and the current status is: landed — merged with the integration wave into sa_plugin_sla master c97fce9da7a6c1dc3ab03bdd3487e8e016a6eebf (see “Application Record (2026-10-31)” at the end of this section). The purpose of this section is to preserve the current-state position, the reasons for the decision, the resolution discipline, and the application status, so that it does not have to be argued again in the future.

Current-State Position (Verified by the Main Session Against Four Sources)

  • Operator overloading has existed for a long time. The @overload block is an explicit static operator extension layer: a declaration inside the block such as fn +(self: Vec2, other: Vec2) -> Vec2 causes the frontend to rewrite a + b into a same-type static function call — purely a frontend layer, at zero runtime cost. Corpus on record: sa_plugin_sla tests/test_unit_overload_add.sla (“overload add rewrites to static dispatch”), demos/rosetta 301 (add) / 302 (neg) / 303 (scalar mul) / 304 (eq) / 312 (block form); writing bare overload without @ is an error (negative case tests/test_error_bare_overload.sla).
  • Ordinary functions with the same name are a redeclaration error. Same-named functions do not form an overload set — the negative corpus tests/test_error_redeclaration_function.sla is exactly two same-named fn repeated definitions, expected to error; scanning all tests and demos found not one positive use case of a same-named, differently-signed function, and the sala documentation does not record this capability either.
  • Other same-name needs are covered by generics and per-type methods. Type parameterization relies on generics; same-named methods hanging on different types are namespace resolution by receiver type, not overloading.

That is: the overload surface had deliberately been placed where ambiguity cannot occur (operators are resolved by operand type), and free function names were kept unique — this is not a hole grown out of a gap; it was a design trade-off of the time.

User Decision (2026-10-30)

The user's ruling: ordinary functions must also overload, in order to make interaction with third-party languages convenient. The reason is on the binding surface: source APIs such as C++ libraries, .d.ts conversion products, and .sai declarations commonly have many signatures under one name, and the current “unique name” rule forces mechanically generated bindings to use hand-made names (foo_i32 / foo_f64 and the like), so the bindings diverge from the source API from then on and the comparison maintenance cost persists long-term. The binding surface is the real source of the demand for overloading; user-written code does not need to pay the inference-complexity bill for same names — this division of labor is exactly the basis on which the ruling below narrows the scope.

Jev Ruling

This topic was executed under the user's same-day new rule, “gap-type improvements → send to Jev for review → apply on passing”, and the ruling is archived at jev-designs/fn_overload_ruling.json:

  • Scope taken as the extern surface only (extern_only) 0.97, confidence 0.96; the losers were full opening (full) 0.02 and doing nothing (none) 0.01. That is: same-named multiple signatures are allowed only on the extern / imported declaration surface (binding C++ libraries, .d.ts conversions, .sai declarations), while user-written functions keep unique names — the inference and naming discipline of self-written code does not give way to the binding surface, and the existing redeclaration negative cases continue to hold for self-written functions. (This item was later overturned by the user and finalized as full; see “User Overturn and Finalized Position” below; the original text here is preserved as the ruling archive.)
  • Resolution discipline taken as exact matching after inference (exact_after_inference) 1.0, confidence 1.0; C++-style conversion ranking (cpp_ranking) scored 0.0 and is explicitly not adopted. That is: after type inference completes, candidates under the same name are matched exactly by arity + the concrete argument types, and it is legal only when exactly one candidate hits; zero candidates or multiple candidates both fail loudly with an error listing the candidates, with no implicit conversion ranking and no guessing. A repeated declaration of the same signature still errors (that is redeclaration, not overloading); overloading by return type alone is forbidden (the return type does not participate in resolution).

User Overturn and Finalized Position (2026-10-30 21:48)

Current State and Evidence (Verified 2026-10-31)

Rust Reference Facts

Declaring and calling extern C variadics has long been available in Rust (printf-style bindings are an old face); the new surface stabilized in Rust 1.99.0 (2026-10-01) is defining C variadic functions: unsafe extern "C" fn f(mut args: ...), where the type of the ... parameter is core::ffi::VaList (ABI-compatible with C's va_list). This capability is limited to the "C" / "C-unwind" ABIs; ordinary Rust-ABI functions still cannot be variadic to this day. Compared with that, SLA is missing both layers: neither the declaration / call surface nor the definition surface exists — and this batch's scope is aimed at exactly these two layers.

Finalized Position

  • Syntax surface: extern declarations (the extern blocks in .sla and imported .sai declarations) carry a trailing ...; the definition surface defines, in SLA, a variadic function exported for C callers, with a ... parameter + VaList argument reading, modeled on Rust 1.99's form. Writing ... in an ordinary fn, a closure, or a non-C-ABI fn type is still loudly rejected (pinned by negative corpus); a ... not in last position is likewise rejected.

8. Language Evolution: GPU Compilation (Decided into the Plan and Landed the Same Day, 2026-11-01 — SA / SLA Can Now Use GPUs)

Reference Evidence (Bend2, Studied 2026-11-01)

  • Reference object: Bend2 (bendlang/bend, Apache-2.0; the original HigherOrderCO/Bend2 repository has moved there), shallow-cloned locally at ~/workspace/bend-src (faeb02e); its compiler is TypeScript (bend2/comp.ts, about 6,474 lines), and the study surface was its guide, its SHADERS documentation, and the compiler structure.
  • Language surface: a parallel call a b = f(x) g(y) is a fork-join form (promising that the calls are independent and roughly equal in duration); a bang call f!(args) sends that call and all parallel calls inside it to the GPU as a whole; on a machine without a GPU, bang falls back to parallel execution on the CPU pool, and on the JS target to sequential execution — the semantics do not change; the mechanism follows the host.
  • Scheduling: a contention-free binary fork-join machine; a task is dispatched only once and never migrates; on the GPU side, one bang lays out 16,384 lanes (a 128×128 cube), the fork tree expands breadth-first to fill the lanes, each lane runs to completion, and the continuations of further forks enter the next kernel iteration. Performance law: each bang is best with about 4^7 leaves; work with large divergence (each lane taking a different path) is faster on the CPU pool instead.
  • Compilation trick: the compiler emits only one C file, and that file is both the CPU program and the GPU kernel — clang compiles the CPU side, and the Metal (Apple) / CUDA (NVIDIA) toolchains compile the same file into the GPU program (file.gpu); there is no C stack: each def is compiled into one segment of a flat state machine, and a call is a jump; a def with no parallel constructs is compiled into a single native tail loop (the flat discipline).
  • Memory: 64-bit terms + a single heap shared by CPU / GPU (Apple unified memory; on NVIDIA, CUDA managed memory, migrated by page faults), affine values, no GC — near-zero-cost data on the GPU is one of the premises of this form.

Finalized Position (Our Form)

  • Marker position and symbol (correction): @gpu is an SA-layer function-kind prefix, of the same family as @extern / @export / @ffi_wrapper, written before a function definition; it is not a call marker invented on the SLA surface. The symbol was ruled by Jev (@gpu won with 0.51, !! was runner-up with 0.36, # and $ scored 0.05 each, ~ 0.03) and confirmed by the user as final. The SA and SLA spellings agree: in SA, @gpu pow2(n: u32) -> u32:; in SLA, @gpu fn pow2(n: u32) -> u32 { … }. The first version of this section's wording, “SLA adds a bang-like marker, with the form benchmarked against Bend2's f!(args)”, is void — bang is Bend2's call-surface syntax; our finalization is an SA-layer function kind; an independent call inside a function body is a fork point, and the function return is an implicit join.
  • Kind encoding and SAB compatibility: FunctionKind gains gpu = 5 at the tail; SAB's function-signature kind field is one byte, and appending at the tail does not change the encoding length and requires no SAB major-version upgrade; an old host reading an unknown kind value fails loudly with InvalidTag and does not silently misread it.
  • Subset discipline and validation: ours is imperative + ownership, so only a provable subset may go on the GPU (the difference in scope from Bend2, where the whole language can go on the device, is stated as it is: this is a scope demotion, not a semantic discount). Validation is performed by the Referee with a capability mask: inside an @gpu function body, calls to non-gpu functions are rejected (including extern / FFI / host calls; unresolvable ones are treated as host calls), as are call_indirect, raw pointer demotion raw_cast (*), native escapes ($…$), and panic; the violation diagnostic is GpuSubsetViolation (trap 1059, code SA-VER-002) — out-of-bounds use is loudly rejected and is not silently demoted to the CPU pretending to be device execution.
  • Emission route: the same-source dual-compilation route of sci's existing C emitter (the same C is both the CPU program and, through extraction rules, the device translation unit); no independent codegen is opened; the only hand-written part is the thin device runtime layer. Device memory uses CUDA managed unified memory (cudaMallocManaged) — the C backend memory model of SA is itself a single flat byte graph (sa_mem, 16 MiB) plus offset addressing, isomorphic to Bend2's single heap.
  • Fallback semantics: without a GPU, the same @gpu function executes on the CPU carrier pool, with semantics bitwise identical to the device path — the mechanism follows the host, the semantics are constant, isomorphic to the goroutine all-platform semantic parity (the platform-parity doctrine extended to the device surface).
  • Frontend rule: the capability is at the SA layer, so every tool that emits SA inherits it automatically, with no per-frontend additions needed. Authoring languages (SLA, slars) use the same @gpu source spelling; converters (tsgosa, bc2sa) do not invent source syntax — their products may carry @gpu only when the converter itself can prove the subset; normally they do not carry it, at zero loss.
  • Target order: native (CUDA already measured) first; Metal next; WebGPU (the browser surface, with no unified heap) is an explicitly buffered adaptation form and is not under the same position as the native surface.
  • Ownership: the language line (sci / SLA); slaengine's sla_gpu seat is a consumer (such as rendering and physics-type computation) and does not build its own runtime within this item.

Multi-future concurrency and the will event model (added by the user on 2026-11-01): the prediction layer simultaneously maintains multiple candidate futures extrapolated in parallel (the user used quantum mechanics' multiple states / superposition as an analogy: the futures coexist, and as real time advances, the one that actually happens collapses into reality while the rest are corrected or voided). Rejudgment condition: only when an ineliminable form cost is localized and an alternative form is measured to cross that limit under the same correctness requirements will it be rejudged a form problem and the form ruling reopened.

Leaf-blocking gated experiment: leaf blocking is not a prerequisite for this ruling (currently only a design draft, unimplemented, with zero device evidence); it is listed as a gated side-line experiment: measure only three grids — matmul@128, scan@1M, pow2(20) — collecting both the end-to-end and pure-kernel positions simultaneously. Criterion A (any grid's end-to-end time faster by ≥25% and the pow2 cliff eliminated) → reopen the form ruling; Criterion B (pure-kernel time falls while the end-to-end gap remains within ±10%) → confirm that the shared base cost rules, close the leaf-blocking direction, and turn to attacking the base staging / launch overhead.

Status: FS-10 is closed here (evidence package CLOSED + form decision F1); the FS chain's integration actions for entering the mainline under F1 are queued in the mainline queue and scheduled by the main session.

9. Multi-Target Plan: GPUs of All Vendors and TPUs (Decided 2026-11-04)

This section registers the decided next-step plan for @gpu: expanding Section 8's landed single-target GPU capability into multi-target support for GPUs of all vendors and TPUs. Source chain: item two of the @gpu improvement route, “the subset v2 overall design” (the user approved that route on 2026-11-01), was shaped on 2026-11-04 after a mechanism recheck by the main session and review by three external consultation panels (Gemini / GPT / Claude); the target form (“one code base, semantic parity”, target selected at build / release time) was personally decided by the user on 2026-11-04. Status pinned: this section is a design decision — it lands design only and does not schedule implementation — the current state is only Section 8's @gpu v1 single target (NVIDIA, integer per-element / tile kernels) landed; every multi-target statement in this section is a plan and must not be read as already supported. The whole line currently prioritizes fixing bugs and getting all milestones green.

User Surface: One Code Base, Semantic Parity

The target form in one sentence: the user writes only @gpu; within the portable subset, one source does not fork per target; the target is selected at build / release time by a compilation parameter (such as --tpu; the concrete form is undecided), entering the GPU path by default, with the rules for selecting a concrete vendor and architecture to be decided separately. This is the continuation, on the multi-target surface, of Section 8's platform-parity doctrine, “the mechanism follows the host, the semantics are constant”: the unity lives at the source and semantic layer and does not promise unity of the underlying mechanism (one IR, one lowering chain feeding both SIMT and systolic dataflow) — the latter, on checking, has not been seen in any examined reference (see “Reference Facts” below) and is not listed as a goal.

Architecture Layering

  • The GPU family goes through the kernel layer: the kernel form follows Section 8's finalization (the SA-layer @gpu function kind + the provable subset + the Referee capability mask); target backends are dispatched by LLVM family — NVIDIA goes through NVPTX, AMD through the AMDGPU backend, and Apple through MSL source emission (LLVM has no Metal backend and AIR is not publicly documented, so it is not a path).
  • TPUs go through the tensor graph layer: a tensor subset is delimited at the SLA layer (tensor-operator-level programs), emitting StableHLO for PJRT / XLA execution; a graph hangs as an opaque node beside the host control flow, and only a device handle is kept inside SA — this plan preserves and diverts tensor semantics before entering SA and does not design a path for rebuilding a tensor graph from SA, avoiding dependence on recovering shapes, operators, and dependency relations from a low-level representation.
  • The two layers are separate, and SA stays frozen and untouched: the SA specification (registers + ownership) is not changed for the device surface; the tensor layer is a new path at the SLA layer, not a migration or replacement of the kernel layer.

The Portable Subset and Loud Rejection

The range in which “one code base” holds = the portable subset, whose position is a whitelist: entries jointly supported by both paths (the GPU kernel layer and the TPU tensor graph layer) with defined semantics prevail, and the whitelist simultaneously constrains operators, types, shapes, and control flow; the candidate range is tensor-level per-element and reduction programs, and the list is determined by the minimal numeric contract and the spike results. A form that matches but is not on the whitelist is still rejected. Thread-level constructs beyond this boundary (explicit thread / block indices, barriers, shared-memory manipulation), when a TPU target is designated (parameter form to be decided), produce a loud error: no silent demotion, no rerouting through another path in disguise, and no simulated fallback — the same rule as the SAB no-demotion rule. Writing a thread-level construct is itself choosing GPU-only, and the boundary is drawn in the open by the compiler.

Numeric Contract Grades

  • Integers / fixed point: bitwise identical across targets (following Section 8's v1 policy). The enforcement and evidence methods are separated by side: the GPU side is guaranteed by our own backend; the TPU side uses “semantics mapped item by item per the StableHLO definitions + end-to-end comparison tests” as its enforcement and evidence method — the TPU's low-level execution stack is not public, so its bitwise identity is testable but not provable, and external statements are bounded by this; integer overflow wraparound and shift semantics are mapped item by item per the StableHLO definitions and are not assumed to agree with the local ones. The defensible range of this grade is narrowed and written explicitly: it holds only for reductions and sums of modulo-2n wrapping integer addition / multiplication, independent of order; fixed point (including scaling / rounding) and saturation / trap semantics do not satisfy associativity, so their reductions must use a fixed reduction tree shape, with rules defined separately. The bitwise contract lists a whitelist by operator and type; undefined operations do not enter the contract.
  • The strict grade: a narrow floating-point subset, to be defined and to be verified. The candidate scalar operations are +, −, ×, ÷, sqrt; transcendental functions do not enter the first version. The precision, rounding, special values (NaN / signed zero), denormals, how FMA contraction is turned off, and the reduction rules will be decided separately by the numeric contract; before the definition and verification are complete, no bitwise floating-point determinism is promised externally. Cross-backend comparison is its verification means, and it is limited to between GPU backends.
  • The relaxed tolerance grade: cross-backend floating point promises only consistency within a tolerance; the tolerance is pinned per operator in advance and must not be loosened after the fact. Floating-point operators not listed in strict default to the relaxed grade.
  • TPU floating point can land only in the relaxed grade: TPU floating-point results are affected by hardware generation, precision configuration (under a framework's default precision, an f32 dot product is computed as bf16, and higher precision must be explicitly configured), XLA optimizations, and compilation versions; this plan provides no bitwise stability guarantee for TPU floating point and reports only test results, with acceptance in the relaxed grade; TPUs must not be included in the bitwise floating-point promise (the strict grade is limited to controlled GPU backends). The evidence boundary is drawn as it is: StableHLO / PJRT / XLA have public specifications and implementations, but that does not amount to bitwise verification of the complete TPU execution chain.

Ownership Device Semantics

On the device surface, the SA ownership rules are extended by an asynchronous borrowing semantics: a borrow is established when a device task is submitted, and the host side is forbidden to touch that buffer during the borrow period; obtaining a completion token (fence / event) does not equal the end of the borrow — it is released only after waiting / synchronization confirms the task is complete. What compile time intercepts is static out-of-bounds use of the borrow interval and reuse without waiting; completion timing itself is a runtime fact and is not within the compile-time guarantee. The applicable range is labeled as it is: operator-level / kernel-level guarantees land on the hand-written kernel path; the graph-level path maintains the host-side borrow lock only at the boundary of the whole-graph asynchronous call's input / output handles, and intermediate values inside the graph are planned by XLA and are not included in the compile-time ownership guarantee. How the borrow kind (exclusive, or distinguishing reads from writes) is chosen in the first version is labeled as to be decided separately.

Advantage Position (Finalized Wording, Not to Be Inflated)

  1. Asynchronous buffer borrow checking on the hand-written kernel path: reusing the host ownership rules to check the relations among host accesses inside the safe interface, buffer lifetimes, and device-task completion (at graph level it reaches only the whole-graph boundary handles; see the ownership section).
  2. Integer / fixed-point determinism is a contract-level cross-target guarantee (the GPU side guaranteed by our own backend; the TPU side based on semantic mapping + comparison tests; see the numeric contract section): a hard requirement for scenarios such as game lockstep networking, physics reproduction, and audit replay. The accurate statement of the advantage is: writing the integer / fixed-point cross-target semantics of an explicit subset into the language contract, and accepting it with an independent judge and cross-target tests — not arguing from comparison assertions against other stacks.
  3. One general-purpose language across the whole stack: servers / databases / wasm frontends / device kernels / tensor programs in the same language with the same std interface (the usable subset of each target declared separately). AOT and the absence of a resident runtime compiler are limited to our own backend paths (CPU / wasm / GPU kernels); the TPU graph-level path depends on host PJRT / libtpu runtime loading and compilation, and the product volume awaits measurement, so no promise is made here.

The no-claim list: peak-performance leadership (kernel libraries are person-year accumulations; mechanisms can be copied, stock cannot), TPU kernel-level capability (graph level borrows the XLA path; kernel level is not done), floating-point determinism (only the integer / fixed-point grade), and ecosystem breadth. None of the four may be crossed in any external statement.

Implementation Order

Prerequisite: @gpu v1 closing + the FS-10 form ruling complete. The order after that (adjudicated through external consultation): ① the minimal numeric contract first — covering only the first batch of operators, first deciding “what counts as a comparison pass”; ② a quota-limited StableHLO integer spike experiment — on a free TPU venue (Kaggle v5e, subject to what the platform actually provides at the time), establishing graph-level dual emission with one integer tensor program. Here “dual emission” is defined as: the same subset source is executed separately through the existing NVIDIA kernel path and the new StableHLO → TPU path, with an independent CPU judge as the third-party semantic baseline; “quota-limited” means the time / resource ceiling and success conditions are frozen before the run (input range, bitwise acceptance conditions, negative-control expectations), and if any is unmet it is not recorded as a pass. Four anti-self-deception items must be carried: an independent CPU semantic judge (preventing the two backends from sharing the same frontend error and falsely passing against each other), negative-control injection (deliberately injecting an error and verifying the comparison catches it), host–device alternating control-flow cases (not only static pure graphs), and pre-written abandonment conditions (stop if the quota is exceeded without passing); the spike's first round is limited to the integer intersection — v1 has no device floating-point path, and floating-point comparison must not be hidden inside the spike cost; ③ the AMD minimal closed loop — testing the portability of our own GPU stack; ④ layout / parameterized kernel libraries last — abstracting only after measuring the dual-target differences, without laying out a library a priori.

Reference Facts (Mojo / MAX, References, Not Our Implementation)

According to Modular's public materials and HTEC's public reporting (2026): Mojo / MAX's portability mechanism is parameterized kernels (specialized per target at compile time) + the LayoutTensor layout algebra + runtime JIT compilation for the exact chip; high-performance kernels rely on per-architecture specialized variants (one API, multiple implementations), and its own position is “we give you the tools to build portable abstractions; we do not pretend the hardware is the same”. Its TPU support is an early bring-up by the external team HTEC through MLIR → Mosaic, borrowing the Google stack (Gemma-type models running end to end + public matmul performance figures aligned with JAX / Pallas), not its own kernel stack landing on TPUs; its results are limited to the reported models and metrics. This reference proves two things: graph-level dual emission is feasible; and no such mechanism unity has been seen among the examined references — this plan's two-layer form agrees with the layering shape of the examined references.

10. Compilation Speed (vs Rust): Development Plan Registration (Discussed 2026-11-02, Registered Only, Not Started)

Source of this section: a round of discussion on 2026-11-02 between the main session and the user on “how is our compilation speed, compared with Rust”. Positioning pinned: this is a development plan item, not the current mainline. The user decided on 2026-11-02, “discuss for now; first complete the main tasks with the main force” — so this section only registers the structural judgments, the plan order, and the acceptance criteria, and without a further order from the user, neither measurement nor implementation is started.

Current State: No Formal Comparison Data; Claiming a Win Is Not Allowed

As of the registration date, there is still no formal same-machine comparison data against Rust; every comparison in this section is a structural inference and must not be stated anywhere as a win over Rust. What is on hand is only scattered magnitudes, whose positions differ from each other and which cannot support a conclusion; they are archived as notes only: building the toolchain from zero (an 8-core box, the whole install.sh including plugin building and smoke tests) takes about a quarter of an hour; the whole SLA corpus batch (both backends, with real runs) is on the order of minutes. One is the build of the compiler body, the other the total duration of a test batch; neither equals “the time to compile one program”.

Structural Judgments (Inferences, Not Measurements)

  • Checking cost is near-linear: SLA's ownership / borrowing are local rules, with no trait solver and no global data-flow analysis for lifetime inference; frontend checking time basically grows linearly with code volume. One of the large parts of Rust cold compilation (trait solving + borrowck global analysis) does not exist in our structure.
  • DCE is before the backend: we already have dead-code elimination, located at the SA layer, at function granularity, and before the expensive backend (LLVM / codegen) — the unreachable parts of the code brought in by the full sa_std surface and import expansion are pruned before entering the backend, so the backend pays only for reachable code and does not inflate with the backend surface. This is where the structural advantage over Rust lies: Rust also has dead-code elimination, but it is positioned later and at coarser granularity, and its most expensive part — the instances generated by monomorphization — is mostly reachable, so DCE cannot cut it.

Remaining Costs and Gaps (Registered as They Are)

  • The frontend must still pass over the full input: parsing, macro expansion, and checking happen before lowering, and DCE prunes only after lowering — the frontend takes the volume amplification of import expansion in full. The remaining large part of cold compilation is expected to be in this segment (an inference, awaiting segmented timing to confirm).
  • No incremental compilation (currently the largest gap): after a change, everything is fully recompiled + file-level caching; rustc's incremental query graph has the advantage on this item, and the larger the project, the more obvious the gap.
  • The backend is serial: emission is not parallelized per function, and multiple cores are unused.
  • The text route amplifies volume: the text SA route must parse a volume larger than the source itself; the SAB binary route can skip parsing, but it is not yet the default throughout.
  • emit_c is the slow path: it passes through one extra layer of C compiler.
  • The release LLVM optimization segment is the floor: that segment is of the same kind as rustc's and cannot be saved; it can only be bypassed by the debug form's fast path.
  • Warning (Rust's cautionary tale): expansion of the language surface, the generic-use surface, and the std surface naturally raises compilation cost — Rust became slower precisely as its ecosystem succeeded. Every future expansion step must be accompanied by segmented timing as evidence of its compilation tax; silent accumulation is not allowed.

Plan Order (To Be Executed After the User Approves the Project)

  1. Establish the measuring scale first: segmented timing (frontend checking / lowering / DCE / backend / linking segments) + a same-machine comparison baseline — take a Rust project of comparable scale for a same-machine comparison, with cold and hot caches counted separately. This step produces data only and changes no implementation.
  2. Function- / module-level incremental caching: refine the invalidation granularity from file level to function / module level. Hard constraint: the cache key must include the compiler (analysis) version — the current .sla-cache macro index cache key does not include the compiler analysis version, and an old cache can mask new compiler behavior; this is a measured pit (2026-10-27), and the incremental rework must not repeat it.
  3. Parallel backend emission per function: the SA register model is independent per function, so backend parallelism has no semantic obstacle.
  4. SAB throughout: precompile sa_std and imported modules to SAB, so cold compilation skips text parsing and expansion.

Cross-cutting constraint: no modularization / incremental rework may break “DCE is before the backend”; the verification position for a rework is failure name-set comparison + behavioral equivalence, not pass counts alone.

Acceptance Criteria (Applicable When Implemented in the Future)

Any conclusion about compilation speed must simultaneously have: a same-machine, same-scale comparison + cold / hot positions separated + complete segmented timing; if any of the three is missing, no conclusion may be drawn. Only measured numbers may be reported; structural inference must not be passed off as data — the structural judgments in this section remain judgments until the comparison lands.
