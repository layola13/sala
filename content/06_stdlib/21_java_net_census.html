Cross-Language std Census: Java (OpenJDK) net × sa_std

This page is the Java volume of the cross-language std census batch: taking the network surface of the latest OpenJDK GA source as the reference frame, it mechanically extracts the two-side inventories, compares them item by item against sa_std's network surface, and gives the four gap categories and a priority shortlist for closing gaps. Volumes in the same batch: Rust full std (see the std census page in 09_rust_compare), Go net, Python net, .NET net, Android net, iOS net, the Unreal networking system. Conclusions come only from the actually extracted inventories (scripts and data in tools/java_net_census/); presence or absence is never judged from impressions.

Conclusion Summary

The Java side (six source roots, 222 files) extracted 284 types, of which 233 are API types (public, or implicitly public member types of interfaces; the other 51 are package-private/private implementation types), with 1754 members on them (methods 1382, constructors 229, constants 88, enum constants 30, fields 25, including the corrected methodology for interfaces' implicitly public members; see “Coverage Boundaries”). The SA side extracted 1408 rows and 1200 unique symbols from sa_std's network declaration surface (the .sai/.sal/.sla/.sa of net/netx/http_client/http_server/http2/ws_client/tls_client/tls_server/dtls/quic/ssh) and sa_std.h.

Classification of the 233 API types: existing equivalent 85, directly mappable 12, needs modeling 92, model mismatch 44. That is, sa_std already covers the basic ground of Java's network surface (the capabilities for sockets/UDP multicast/TCP options/HTTP client and server/ WebSocket/TLS streams/QUIC/HTTP3 are all there); the real gaps (directly mappable + needs modeling) are 104 types, concentrated in five places: the Cookie surface, the TLS configuration surface (SSLParameters/trust and key management), HttpClient's aggregate configuration (redirects/authentication/proxy), the URI and encoding pure-function cluster, network interface enumeration; in addition, NIO's Selector/AIO cluster is a “model choice” — SA's counterpart is the netx completion-style reactor, not a gap to fill directly.

Coverage Boundaries (Registered Honestly)

  • Java extraction is heuristic parsing, not javac semantic analysis: it sees only the declaration bodies and does not expand inherited members (such as Socket's parent class Object methods or methods inherited from interfaces, which are not in the inventory); compiler-generated members such as record accessors and enums' synthetic members (values/valueOf) are not in the source and are not counted.
  • Members written without modifiers in interfaces are implicitly public in Java; the first extraction round systematically missed them, now corrected by “implicitly public in interface context” (WebSocket 11 items, SSLSession 21 items are the corrected landmark values); nested types' API determination follows “explicitly public, or a non-private member type of an interface”; package-private nested helper classes (such as InetAddressHolder, CookieComparator, verified in source as static class) count as internal.
  • The SA side takes the .sai ABI declaration surface + sa_std.h as the authoritative source; plugin_http_*'s .sa facade symbols were not fully captured by the tag heuristic (plugin_http_server.sla itself is only a 2-line import forwarding), which does not affect the .sai-based counts.
  • Out-of-scope registration: the jdk.sctp module (com.sun.nio.sctp) is outside this volume's scope; java.nio.channels' file channel cluster (6 types such as FileChannel/FileLock) is registered in the gap table as “model mismatch (out of scope · file domain)”, counted in the package counts but not in the network gaps (the 104 methodology already removes its influence: those 6 items belong to the model mismatch category and are not in the sum of directly mappable + needs modeling).
  • DTLS: the Java side has no standalone DTLS API (used via SSLEngine), and the SA side's dtls surface is in server shape; the two sides' shapes have different origins, so no separate gap is listed.

Priority Shortlist for Closing Gaps

Ordered by the “all basic cores built into sa_std” doctrine and real usage surfaces (classification methodology as above):

  1. The Cookie surface (needs modeling): CookieManager/CookieStore/CookiePolicy + integration with sa_http_client (the HttpCookie value type itself is directly mappable). The largest whole-block absence on the HTTP client's real usage surface — the SA side has zero cookie symbols.
  2. The URI/encoding pure-function cluster (directly mappable): URI's resolve/relativize/normalize and quote encoding/decoding, URLEncoder/URLDecoder, IDN (punycode). Pure functions with no modeling risk; a whole blank area beyond sa_std_url_parse, with the lowest fill-in cost.
  3. Network interface enumeration (directly mappable): NetworkInterface/InterfaceAddress's getifaddrs-class system surface (addresses/broadcast/prefix/MTU/hardware address/up/loopback), infrastructure for binding and proxy scenarios.
  4. HttpClient's three gaps (needs modeling/directly mappable): redirect following (Redirect), general authentication callbacks (Authenticator/PasswordAuthentication), proxy support (Proxy/ProxySelector). The three items that decide whether sa_http_client can replace java.net.http in everyday use.
  5. The TLS configuration surface (needs modeling): SSLParameters (cipher suites/protocol versions/ALPN/SNI) + HostnameVerifier callbacks. Complementary to the existing shaped fingerprint client; the dividing line of TLS from “can connect” to “configurable”.
  6. SSLEngine (needs modeling): the wrap/unwrap non-blocking TLS engine shape — the only shape for embedding TLS into the netx reactor, a key puzzle piece for high-concurrency servers.
  7. Streaming request bodies (needs modeling): BodyPublishers' file/stream publishers; the current req_set_body is a whole-buffer model, unusable for large request bodies.
  8. DNS resolution policy hooks (needs modeling): InetAddressResolver (+ the small InetAddress.isReachable surface). Leaves room for custom resolution/Private DNS; handled in the same domain as the net address family double-definition trap registered by the AJ census.
  9. Unix peer credentials (directly mappable): UnixDomainPrincipal (SO_PEERCRED), a small surface for local IPC authentication.

Two categories do not enter the shortlist: jdk.httpserver's HttpContext/HttpExchange/Filter/server authentication cluster belongs to the framework layer (by doctrine it goes to plugin facades, not the std body); NIO's Selector/AsynchronousChannel cluster is a model choice — SA's counterpart is the netx io_uring completion-style reactor; if a Selector readiness shape is wanted in the future, it needs a separate proposal and adjudication.

Surfaces Unique to the SA Side (No Java Counterpart, Registered for Reference)

The comparison also confirmed what sa_std has and Java's network surface does not: the SSH client/server core (sa_std_ssh_*, 26 symbols), the QUIC transport layer (endpoints/connections/streams, sa_std_quic_*) and the HTTP/3 session surface, the TLS fingerprint shaping client (tls_shaped: JA3/JA4 hello shaping + negotiated introspection), the DTLS server, the netx io_uring reactor (ticket model), the SSE client surface (sa_http_client_sse_*). These are SA's leading surfaces and the census counts them as gaps on neither side.
