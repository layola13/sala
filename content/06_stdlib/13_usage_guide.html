Using sa_std: The Import Mechanism and Contract System

This page covers two things: how sa_std's three kinds of contract files (.sai / .sal / .sa) divide the work and work together, and how the Sla and SA assembly sides each import them. After reading it, you will be able to judge “which file should I import for the feature I want”, and understand where the std calls in the compilation output come from.

The Division of Labour Among the Three Kinds of Contracts

ExtensionWhat it carriesWho consumes it
.sai@extern function contracts; the signature is verbatim the ABI, implemented by Zig modules in the sci runtimeSla calls directly by name; SA uses call @符号(...)
.sal#def layouts and constants: _SIZE, +偏移 fields, error codes, enumeration valuesSlot sizes and status codes are taken during macro expansion; hand-written layout code
.sa[MACRO] ... EXPAND ... assembly macros, wrapping on-stack slot allocation and extern calls into a single instructionHand-written SA code; the Sla type method surface expands by rule to these macros

One real excerpt of each. The function contract .sai (the full text of sci/sa_std/io/print.sai):

// Legacy print contract for demos and simple applications.
// Implemented by the Zig-backed sa_std.io library as stdout().write_all(bytes).
@extern sa_print_bytes(&msg: ptr, len: u64) -> void

The layout and constant contract .sal (from sci/sa_std/fmt.sal):

#def SA_FMT_OK = 0
#def SA_FMT_ERR_OVERFLOW = 3
#def SA_FMT_BASE_DECIMAL = 10
#def SA_FMT_BASE_HEX_LOWER = 16
#def SaFmtBuffer_SIZE = 24
#def SaFmtBuffer_ptr = +0
#def SaFmtBuffer_len = +8
#def SaFmtBuffer_cap = +16

The macro implementation .sa (from sci/sa_std/fs.sa). Note that inside the macro it first stack_allocs an out-parameter slot, then calls the extern declared in the .sai — this excerpt is the smallest sample of the three layers working together:

[MACRO] FS_READ_TO_STRING %out_status, %out_buffer, %path, %path_len, %max_bytes
    __fs_read_to_string_handle_%out_status = stack_alloc 8
    %out_status = call @sa_std_fs_read_to_string(&%path, %path_len, %max_bytes, &__fs_read_to_string_handle_%out_status)
    %out_buffer = load __fs_read_to_string_handle_%out_status+0 as u64
[END_MACRO]

How the Three Work Together: A Verifiable Example

Sla writes one line, println("{}", result) (from demos/rosetta/02_mutability/main.sla):

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

fn main() -> i32 {
    let result = immutable_update_value();
    println("{}", result);
    return result;
};

The compiler-generated main.sa in the same directory expands it into a call chain of the fmt contract plus the print contract:

tmp_4 = call @sa_fmt_u64(result, 10)
tmp_5 = call @sa_fmt_buffer_data(tmp_4)
tmp_6 = call @sa_fmt_buffer_len(tmp_4)
tmp_7 = tmp_5
call @sa_print_bytes(&tmp_7, tmp_6)
call @sa_fmt_buffer_free(^tmp_4)
@const SLA_STR_0 = utf8:"\n"
call @sa_print_bytes(&SLA_STR_0, 1)

As can be seen: the .sai provides the symbols being called; the returned owned buffer is read out through the accessor trio and handed to printing; the release is done by the generated ownership instructions.

How to Import on the Sla Side

Write the complete contract path with the sa_std/ prefix, as in demos/rosetta/01_hello_world/main.sla:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"
@import "sa_std/string.sa"

When you need both macros and layouts, import both together, as in demos/rosetta/108_atomic_spin_lock/main.sla:

@import "sa_std/sync/atomic.sal"
@import "sa_std/sync/atomic.sa"
@import "sa_std/core/result.sa"

For the resolution order, see the Standard Library Overview page:

OrderConditionResolution location
1SA_STD_DIR is setResolve sa_std/... from $SA_STD_DIR
2Not setResolve from $HOME/projects/sci/sa_std
NoteThe Sla compiler loads the imported .sai / .sal contracts before type checking, so the @extern functions declared in the contracts are directly available to Sla code, with no additional binding declaration needed.

How to Import on the SA Assembly Side

At the top of an SA file, dependencies are likewise listed with @import, and usually macros, contracts and layouts are all listed together. From the import block in sci/sa_std/string.sa:

@import "core/slice.sal"
@import "core/slice.sa"
@import "char.sa"
@import "ascii.sa"
@import "vec.sa"
@import "vec.sal"
@import "string.sai"
@import "fmt.sai"
@import "hash.sa"
@import "string_format.sa"

Note that internal library imports use paths relative to the sa_std root (without the sa_std/ prefix); a user program writes sa_std/... only when importing from outside. To get all macros at once, you can import the aggregate surface @import "sa_std/prelude.sa" (see below).

The Buffer Trio: Allocating Form / _into / Accessors

Runtime modules that return text or bytes follow a unified three-layer convention, taking sci/sa_std/fmt.sai as an example:

// 分配式：返回 owned 缓冲句柄（u64），用完必须 free
@extern sa_fmt_i64(value: i64, base: u32) -> u64
@extern sa_fmt_f64(value: f64, precision: u32) -> u64

// 写入式：调用者提供缓冲，零分配，返回状态码
@extern sa_fmt_i64_into(value: i64, base: u32, out: ptr, out_cap: u64, &out_len: ptr) -> i32

// 访问器三件套：数据指针 / 长度 / 释放
@extern sa_fmt_buffer_data(buffer: u64) -> &ptr
@extern sa_fmt_buffer_len(buffer: u64) -> u64
@extern sa_fmt_buffer_free(^buffer: u64) -> i32

The same contract also provides a fourth accessor, sa_fmt_buffer_write_to(buffer: u64, writer: u64) -> i32, which writes the buffer contents directly into a writer handle. The convention in env.sai is exactly the same:

@extern sa_env_get(key: ptr, key_len: u64) -> u64
@extern sa_env_buffer_data(buffer: u64) -> &ptr
@extern sa_env_buffer_len(buffer: u64) -> u64
@extern sa_env_buffer_free(^buffer: u64) -> i32

The result buffers of fs (sa_fs_read_buffer_* / sa_fs_dir_entries_* / sa_fs_metadata_* ), json and http2 all follow this naming; see the fmt, env and fs chapters for details. There is only one difference: the handles of fmt/env are u64, while the nodes and buffers of json/io are ptr.

The Sla Method Surface Is Driven by std_surface.sla_meta

In Sla, Vec::new(), values.push(2), Some(9), opt.unwrap_or(fallback) — these “type methods” are not library semantics hard-coded in the compiler, but come from the plugin's rule table, sa_plugin_sla/sla_std/std_surface.sla_meta. The beginning of the file states that it is data, not logic: the direct SAB backend reads the rules generically and lowers method sugar to already-imported SA macros. Entries in the table look like:

associated Vec new sa_std/vec.sa VEC_NEW out deps=sa_vec_new
method Vec push sa_std/vec.sa VEC_PUSH receiver,value,elem_size deps=sa_vec_push,sa_mem_copy
constructor Some Option sa_std/core/option.sa OPTION_NEW_SOME out,value
method Option unwrap_or sa_std/core/option.sa OPTION_UNWRAP_OR out,receiver,value
constructor Ok Result sa_std/core/result.sa RESULT_NEW_OK out,value
method Result unwrap sa_std/core/result.sa RESULT_UNWRAP out,receiver

The corresponding real usage. From sa_plugin_sla/tests/import_fixtures/std_nested/uses_vec.sla: importing only vec.sa is enough to use the whole Vec method surface:

@import "sa_std/vec.sa"

fn imported_vec_sum() -> i32 {
    let values: Vec<i32> = Vec::new();
    values.push(2);
    values.push(3);
    return values[0] + values[1];
}

From demos/rosetta/46_option_default/main.sla:

fn choose(opt: Option<i32>, fallback: i32) -> i32 {
    opt.unwrap_or(fallback)
}

For the complete list of methods for collections and core types, see the collections chapter; to look up which macro a given method lowers to, searching std_surface.sla_meta directly is fastest.

prelude Aggregate Imports

Under sci/sa_std/ there is a pair of aggregate files, for programs that do not want to list imports one by one:

FileAggregated content
prelude.salThe preludes of each subdirectory (alloc, collections, core, encoding, ffi, io, os, sync, text, plus marker / mem / num / thread / time) plus top-level .sai / .sal contracts such as env.sai, fs.sai, net.sai, process.sai, term.sai
prelude.saThe same subdirectory preludes plus top-level .sa macro implementations such as vec.sa, string.sa, hashmap.sa, encoding/json.sa

The header comment of prelude.sa states its positioning clearly: “Explicit public facade aggregation for applications and smoke tests. This is opt-in; the compiler does not inject it implicitly.” — that is, it is explicitly opt-in, and the compiler does not inject it implicitly. The real user in the repository is the SA test sci/tests/unit_framework/std_prelude_import_surface.sa, which writes a single line, @import "sa_std/prelude.sa", to use macros such as CSTRING_FROM_SLICE_WITH_NUL. prelude.sal is the contract surface of the same aggregation idea (constants + externs), suited to scenarios where you want all signatures at once; there is currently no direct importer of it in the repository, and the two preludes do not reference each other.

WarningAn aggregate import pulls the entire library surface into the compilation unit, and both compilation time and symbol volume rise; for real programs other than demos and tests, importing individual contract files as needed is still recommended.
