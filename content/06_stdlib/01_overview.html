Standard Library Overview

This page introduces how the SA/SLA standard library sa_std is organized: how to import modules, where the compiler finds it, what the three kinds of contract files .sai / .sal / .sa each carry, and the general management conventions for handles and buffers. After reading it, you will be able to locate the module you need by path and know which file to check for a function signature.

Importing

Sla imports the SA top-level sa_std package directly, written as a complete contract path with the sa_std/ prefix:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"
@import "sa_std/string.sa"

The Sla compiler loads the imported .sai / .sal contracts before type checking, so the @extern functions declared in the contracts are directly available to Sla code.

NoteSla source code uses compiler-managed lifetime cleanup by default; user-facing .sla code does not need an explicit !x; release; the generated .sa may still contain ! instructions, which are SA's ownership primitives. Sla deliberately does not provide a drop keyword or a drop() function.

The Three Kinds of Contract Files

ExtensionContentTypical example
.sai@extern function signatures (verbatim, i.e. the ABI), provided by runtime modules implemented in Zig, such as io, fs, net, encoding/json@extern sa_fs_read_to_string(&path: ptr, path_len: u64, max_bytes: u64) -> u64!
.salLayout and constant contracts: #def Struct_SIZE = 24, field offsets such as Vec_len = +16, error codes, etc.alloc/vec.sal, hashmap.sal
.saSA assembly macros ([MACRO] ... EXPAND ...), wrapping several instructions and extern calls into reusable operationsVEC_NEW in vec.sa, FS_READ_TO_STRING in fs.sa

The Sla-side type method surface (for example Vec::push, Option::unwrap) is described by the plugin's sla_std/std_surface.sla_meta: this table declares “a given method of a given type lowers to a given macro in sa_std”, and the direct SAB backend generates code according to the rules, without hard-coding library semantics in the compiler.

Resource Management Conventions

  • Most runtime modules return an opaque handle (u64 or ptr) that must be closed explicitly: sa_io_close, sa_fs_metadata_free, sa_json_free, etc.
  • An “owned buffer handle” always comes as a trio: ..._buffer_data to get the data pointer, ..._buffer_len to get the length, ..._buffer_free to release it, such as sa_fmt_buffer_* / sa_fs_read_buffer_* / sa_env_buffer_* / sa_json_buffer_*。
  • stdio handles are held by the process and are borrowed handles; do not close them.
  • A ! in a return type indicates a fallible return, for example -> u64!, -> i32!.
WarningThe signatures listed in each chapter are quoted verbatim from the .sai contract files in the repository. If your SA_STD_DIR points to a different version, please treat your local contracts as authoritative.
