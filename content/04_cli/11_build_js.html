Host-Side sa build-js (JS Compilation Target)

sa build-js is the third emission target alongside build-exe (native) and build-wasm (WASM): it takes .sa source or a .sab binary as input and outputs a self-contained JS module (ESM by default), run directly with node or bun, with no need for a WASI runner and no need to pass argv. After reading this page you can build and run with the JS target.

Syntax

usage: sa build-js <file> [options]

Parameters

NameDescription
fileThe input .sa source file or .sab binary. When omitted, the package entry point is resolved via the workspace.
-o <path>The output path; when omitted, it is derived from the input path (with a .js suffix).
--format esm|cjsThe JS module format, default esm. Both formats run directly under node / bun.
-g / --no-debugKeep / strip debug comments in the artifact.
--project-root <dir>Specify the repository root (so the test matrix can share .sa_cache; generally not needed in everyday use).
Common compilation optionsThe same pass-through compilation options as the other build-* commands (optimization level, jobs, DCE, etc.).
-h, --helpShow usage and return 0.

Examples

# 构建并用 node 运行
./zig-out/bin/sa build-js examples/hello.sa -o hello.mjs
node hello.mjs

# 同一份产物也可以用 bun 运行
bun hello.mjs

# 输出 CommonJS 格式
./zig-out/bin/sa build-js examples/hello.sa -o hello.cjs --format cjs
node hello.cjs

Comparison with the other two targets

TargetBuild commandArtifact size (hello-world)How to run
Nativesa build-exe~6.3MB (including the static runtime), build about 730msExecute directly
WASMsa build-wasm --target wasm32~741KB, build about 390msWASI runner (node uses getImportObject, bun uses wasiImport; argv must be passed as ["sa", "<wasm filename>"], otherwise the program exits with 71 and no output)
JSsa build-js~31KB, build about 365msRun directly with node / bun

Runtime performance basis (10 million u64 additions, median of 5): native 68ms ≈ wasm/bun 67ms > wasm/node 198ms > js/node 3.5s > js/bun 8.7s. Small demos mainly reflect runtime startup overhead (native ~1ms, wasm/bun ~19ms, js/bun ~23ms, wasm/node ~37ms, js/node ~45ms). Conclusion: the JS target builds fastest and produces the smallest artifact, but for compute-intensive loops prefer native or wasm.

npm imports (JS target only)

  • A #npm_bind line in the source binds a declared @extern function to an npm package, lowered only under sa build-js; run, build-exe, build-wasm, build-obj, and test error out directly when they encounter it (NpmImportJsOnly), prompting you to switch to sa build-js.
  • The target of each #npm_bind must be a declared @extern function of the same name, otherwise UnknownNpmBindTarget is reported at the flatten stage, and no backend ever sees a dangling binding.

Troubleshooting

SymptomCause / action
error: sa build-exe does not support '#npm_bind' ... use 'sa build-js'npm binding is JS-only; rebuild with sa build-js.
#npm_bind target must name a declared @extern functionThe bound name has no corresponding @extern declaration, or the spelling differs; align the two names line by line.
The JS artifact runs correctly but very slowlyAs expected: JS emission is unoptimized code based on linear memory; for compute-intensive tasks switch to native / wasm (see the basis in the table above).
WASM exits with code 71 and no output under nodeThis is a WASM-side issue (not JS): WASI argv is missing. argv must be passed as ["sa", "<wasm filename>"], and the build must add --target wasm32.
