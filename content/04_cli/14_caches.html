SLA / SA Caches

The SA / SLA toolchain keeps several caches. Most of them are keyed by file content only — not by compiler or plugin version — so after the compiler or a plugin is rebuilt, a stale cache can silently replay artefacts produced by the old compiler. The symptoms mislead in both directions: a real fix appears to have no effect, or a healthy tree appears broken. This chapter lists every cache surface, what it keys on, how it fails, and how to clear it.

Rule of thumb: before verifying any compiler or plugin change, clear all six surfaces below. When a gate or canary result contradicts the state of the tree, clearing the caches is step one of the investigation, not a last resort. Clearing is always safe — every cache regenerates; the only cost is rebuild time.

The six cache surfaces

Clearing checklist

# in the sa_plugin_sla tree
rm -rf .sla-cache .zig-cache zig-out
rm -rf ~/.cache/sa/frontend
find . -type d -name .sa_cache -prune -exec rm -rf {} +
SLA_NO_FRESHNESS_CACHE=1 <your command>

Related traps (the same family: silent staleness)

  • sa plugin install --dev swallows build errors. It can exit 0 while the build failed, keeping the old .so. After installing, verify two things: the installed .so's mtime / size changed, and a string literal introduced by the new build is present in the .so (grep). Take md5s after the install settles, and compare md5 only within a single build → install round: plugin .so bytes are not reproducible across rebuilds, so a cross-round md5 comparison is meaningless. On a fresh machine, the bare form may also demand an explicit path: sa plugin install --dev .
  • Dev mode loads the installed plugin, not the working tree. sa sla check / test run the plugin under $HOME/.local/share/sa_plugins/installed/, so editing the tree and running zig build alone changes nothing. Every A/B comparison must install the tree under test into that round's HOME and md5-check the installed .so first.
  • zig build test caches successes. A previously successful run is replayed silently (rc=0, empty log, run test cached under --summary all); failures are not cached, which makes the trap easy to miss. Judge a run by four signs together: rc=0, the expected result line present, an empty failure-name set, and — for dual-route features — both routes passing. rc=0 with an empty log is not a run.
  • sa-std-static archive freshness. zig build sa-std-static does not track sa_std/*.sa as step inputs, so a warm rebuild can replay the previous archive. Judge freshness by the archive's mtime / size change plus a behavioural check, not by the build's exit code.

When to clear

  • After any compiler / plugin source change, before running verification.
  • Before canary / gate runs, and as step one when a gate result contradicts the tree.
  • When two copies of identical sources behave differently — cache asymmetry is the first suspect.
  • When an install or rebuild seems to have had no effect at all.
