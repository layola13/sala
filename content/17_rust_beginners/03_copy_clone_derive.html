Copy, Clone, and @derive: Four Questions, Measured

Rust programmers meeting SLA's @derive ask the same four questions: does clone work, does copy really change move semantics, does eq need a separate partial-equality derive, and do derives work on generic structs? All four were answered by measurement on 2026-11-20 (sa 0.1.9 + installed plugin), not by reading the manual:

QuestionAnswer
1. Clone — does @derive(clone) give a working .clone()?Yes. The derived clone() produces an independent value (probe below).
2. Copy — does @derive(copy) change move/copy judgement?Yes, for plain-data structs — assignment copies and the source stays usable. For a struct with a String field the derive is accepted at the declaration, but assignment still moves: the checker stays field-sound and never duplicates heap data silently.
3. Eq — does derived eq work without a separate PartialEq-style derive?Yes. One derive list — @derive(copy, eq, ord, hash, debug) — provides ==, ordering, hash(x), and debug(x).
4. Generic structs — do derives work on Box<T>?Not yet. Derive is verified on concrete structs only; a generic struct cannot currently be constructed with a struct literal at all, with or without a derive (limitation box below).

Clone

The Rust side derives Clone and calls .clone(); the SLA side derives clone (lowercase) and calls the same method. Both programs below were compiled and run; both print 1 and exit 0.

// Rust
#[derive(Clone)]
struct Point { x: i32, y: i32 }

fn main() {
    let a = Point { x: 1, y: 2 };
    let b = a.clone();
    println!("{}", b.x);
}
// output: 1
@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

@derive(clone)
struct Point {
    x: i32,
    y: i32,
}

fn main() -> i32 {
    let a = Point { x: 1, y: 2 };
    let b = a.clone();
    println("{}", b.x);
    return 0;
}

Verified output: 1, exit code 0. a.clone() produces a second, independent Point; the original is untouched and nothing was moved.

Copy, Eq, and the Rest of the Derive Surface

This program exercises the whole verified surface in one file: copy assignment, a by-value call that would consume a non-Copy value, equality, ordering, hashing, and debug formatting. The Rust equivalent needs the full derive list Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug; SLA folds all of that into one lowercase @derive list. Both were compiled and run; both print 1 1, 3, true, true before their final line (the final line differs only in formatting: Rust prints the struct, SLA prints whether debug(a) is non-empty).

// Rust
#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash, Debug)]
struct Point { x: i32, y: i32 }

fn sum(p: Point) -> i32 { p.x + p.y }

fn main() {
    let a = Point { x: 1, y: 2 };
    let b = a;
    println!("{} {}", a.x, b.x);
    println!("{}", sum(a));
    println!("{}", a == b);
    println!("{}", a < Point { x: 1, y: 3 });
    println!("{:?}", a);
}
// output: 1 1 / 3 / true / true / Point { x: 1, y: 2 }
@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

@derive(copy, eq, ord, hash, debug)
struct Point {
    x: i32,
    y: i32,
}

fn take(p: Point) -> i32 {
    return p.x + p.y;
}

fn main() -> i32 {
    let a = Point { x: 1, y: 2 };
    let b = a;
    println("{} {}", a.x, b.x);
    if take(a) != 3 { return 1; };
    if a.x != 1 { return 2; };
    let same = Point { x: 1, y: 2 };
    let later = Point { x: 1, y: 3 };
    if (a == same) != true { return 3; };
    if (a < later) != true { return 4; };
    if hash(a) != hash(same) { return 5; };
    let text = debug(a);
    if len(text) == 0 { return 6; };
    println("ok");
    return 0;
}

Verified output: 1 1, then ok, exit code 0. let b = a; copies, so a is still readable on the next line and can still be passed to take by value. a == same, a < later, hash(a), and debug(a) all come from the single derive list — there is no separate partial-equality derive to remember.

Copy Is Field-Sound: a String Field Still Moves

The subtle case is a struct whose fields are not all plain data. Rust refuses the derive at the declaration; SLA accepts the annotation and keeps move semantics instead. Both outcomes were measured — the Rust diagnostic is error[E0204]: the trait `Copy` cannot be implemented for this type, pointing at the String field:

// Rust — rejected by rustc (E0204)
#[derive(Copy, Clone)]
struct Holder { name: String, id: i32 }
fn main() {}
// error[E0204]: the trait `Copy` cannot be implemented for this type
//   --> this field does not implement `Copy`: `name: String`

The SLA declaration below is accepted; it is the use of the moved source that is rejected:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

@derive(copy)
struct Holder {
    name: String,
    id: i32,
}

fn main() -> i32 {
    let a = Holder { name: format("x"), id: 1 };
    let b = a;
    println("{}", a.id);
    println("{}", a.name);
    return 0;
}

— but the program is still rejected, because let b = a; moves a: the String field cannot be bit-copied, so the checker keeps move semantics for the whole value, and reading a.id afterwards fails:

Type Check Error: failed to verify types: UseAfterMove: identifier `a` was already consumed (error.UseAfterMove)

Rust reaches the same soundness outcome from the other side: rustc refuses to derive Copy for a struct with a String field at all. SLA accepts the annotation and then refuses to treat the value as copied. Either way, heap data is never silently duplicated, and a moved value is never silently readable. When you port code, do not assume @derive(copy) on a heap-carrying struct gives you Rust-style copy semantics — it gives you a move, with a loud error if you use the source afterwards.

In Rust the generic struct is unremarkable — the same program compiles, copies, and prints 7:

// Rust
#[derive(Copy, Clone, PartialEq, Eq)]
struct Box<T> { value: T }

fn main() {
    let a = Box { value: 7 };
    let b = a;
    println!("{} {}", a.value, b.value);
}
// output: 7 7
LimitationGeneric structs cannot be constructed with a struct literal yet. This declaration is accepted, but the program is rejected at the literal:
@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

@derive(copy, eq)
struct Box<T> {
    value: T,
}

fn main() -> i32 {
    let a = Box { value: 7 };
    let b = a;
    println("{}", a.value);
    return 0;
}
Type Check Error: failed to verify types: checkExpr failed at node tag struct_literal (error.NotAStruct)

Round-4 verification (2026-11-20) tested the obvious variations — @derive(copy, eq), @derive(eq) alone, @derive(copy) alone, no derive at all, a concretely typed local (let a: Box<i32> = ...), and construction through a constructor function — and every one fails with the same NotAStruct error at the struct literal. The gap is in generic struct literals, not in @derive. Until it closes: declare generic structs if you need the type, but construct and derive concrete structs.

Key Points of This Page

  • @derive(clone) works: .clone() produces an independent value.
  • @derive(copy) makes assignment copy for plain-data structs; the source stays usable.
  • On a struct with a String field, @derive(copy) is accepted but assignment still moves — field-sound, no silent heap duplication, and use-after-move is rejected.
  • @derive(eq) needs no separate partial-equality derive; one list can add ord, hash, and debug.
  • Generic struct literals are not yet accepted (error.NotAStruct), with or without a derive; derive is verified on concrete structs.
