Ownership: Moves and Borrows

SLA keeps Rust's central bargain: every value has one owner, and ownership is enforced at compile time. What changes is how borrowing is expressed — SLA has one borrow type where Rust has two. This page covers moves first, then the borrow model; the companion page No &mut by Design gives the full measured treatment, including the task-boundary rules.

Passing by Value Moves

A struct with a heap field (here a String) is not Copy, so passing it to a function by value moves it — the caller's binding is consumed, exactly as in Rust.

// Rust
struct User {
    id: u64,
    name: String,
}

fn greet(user: User) -> u64 {
    user.id
}

fn main() {
    let user = User { id: 100, name: String::from("Alice") };
    println!("{}", greet(user));
}
// output: 100
@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

struct User {
    id: u64,
    name: String,
}

fn greet(user: User) -> u64 {
    return user.id;
}

fn main() -> i32 {
    let user = User { id: 100, name: format("Alice") };
    println("{}", greet(user));
    return 0;
}

Verified output: 100, exit code 0. Note the SLA string is built with format("Alice"), per the previous page.

Use After Move Is a Compile Error

The rule has teeth in both languages. This program moves user into user2 and then tries to read the original:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

struct User {
    id: u64,
    name: String,
}

fn main() -> i32 {
    let user = User { id: 100, name: format("Alice") };
    let user2 = user;
    println("{}", user.id);
    return 0;
}

The checker rejects it before any code is generated:

Type Check Error: failed to verify types: UseAfterMove: identifier `user` was already consumed (error.UseAfterMove)

This is the SLA counterpart of rustc's E0382 (“use of moved value”). The phase is the same — compile time, never a runtime surprise — and the moved binding stays dead for the rest of the scope.

One Borrow Type for Read and Write

Here is the textbook &mut example: one function reads a number through a borrow, another adds 10 through a borrow. Rust needs &i32 for the first and &mut i32 for the second. SLA uses &i32 for both:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

fn read(value: &i32) -> void {
    println("{}", *value);
}

fn modify(value: &i32) -> void {
    *value += 10;
}

fn main() -> i32 {
    let number = 100;
    read(&number);
    modify(&number);
    println("{}", number);
    return 0;
}

Verified output: 100, then 110, exit code 0. The direct translation needs no Cell / RefCell detour. The read/write permission is not declared in the signature; after lowering, the SA Referee judges Locked_Read / Locked_Mut from the actual load/store instructions behind the borrow.

RustSLA
Read function signatureread(&i32)read(&i32)
Write function signaturemodify(&mut i32)modify(&i32)
Changing a reader into a writerSignature changes to &mut; every caller changes with itSignature unchanged; only the body changes
Who decides read vs writeThe type system, at the signatureThe SA Referee, from the actual instructions

The practical consequence: function signatures stay stable when an implementation starts writing through a borrow it previously only read. Cell / RefCell still exist, but for genuinely shared interior state — not as a toll-booth for mutating through a borrow. The one thing a signature no longer tells you is whether a function writes; that trade-off, and the Phase 2 plan it belongs to, are covered on the &mut comparison page and in Ownership and Borrowing: Referee vs the Borrow Checker.

Key Points of This Page

  • Passing or assigning a non-Copy value moves it; using it afterwards is a compile-time UseAfterMove error.
  • SLA has a single borrow type, &T, covering read and write; there is no &mut.
  • The SA Referee decides Locked_Read / Locked_Mut from the actual instructions, so signatures do not change when a reader becomes a writer.
  • No Cell / RefCell is needed to mutate through a borrow.
