Modules and Async

Modules: @import a File, Mark Exports pub

There is no mod tree to declare for a file-local module. The imported file marks what it exports with pub, and the importer pulls the file in with a relative @import. The helper:

pub fn create_id() -> u64 {
    return 100;
}

The importer:

@import "helper.sla"
@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

fn main() -> i32 {
    let id = create_id();
    println("{}", id);
    return 0;
}

Verified output: 100, exit code 0. Every program in this chapter imports the standard library the same way — from sa_std/... declaration files (.sai) and implementation files (.sa) — and the generated sla_std thin wrappers are the mainstream import surface for the std; see the Standard Library section. Compared with Rust, the mental model is “one file, one module, explicit pub surface” — closer to including a header than to maintaining a module tree.

Rust counterpart

Rust declares the module with mod helper; (the file is helper.rs) and calls through the module path. This single-file form uses an inline module so it can be compiled on its own; both programs were compiled and run and print 100.

// Rust
mod helper {
    pub fn create_id() -> u64 { 100 }
}
fn main() { println!("{}", helper::create_id()); }
// output: 100

Async: async fn and .await

An async fn returns a future (the future type is spelled future<T>), and .await drives it. In the verified form, even main can await a top-level call:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"

async fn step_one() -> i32 {
    return 1;
}

async fn run_async() -> i32 {
    let value = step_one().await;
    return value + 1;
}

fn main() -> i32 {
    let result = run_async().await;
    println("{}", result);
    if result != 2 { return 1; };
    return 0;
}

Verified output: 2, exit code 0. The reading is the same as Rust's async/.await; what differs is everything around it — tasks here are the runtime's own (the go and channel machinery of the previous page), not an external executor you plug in. For the measured async comparison against Rust, see Standard Library, Error Handling, and async Compared.

Rust counterpart

Rust needs an executor to drive a future; the minimal block_on below uses only std and was compiled and run, printing 42. SLA's runtime drives the future directly — there is no user-written executor in the SLA program.

// Rust
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};

struct Noop;
impl Wake for Noop { fn wake(self: Arc<Self>) {} }

fn block_on<F: Future>(mut fut: F) -> F::Output {
    let waker = Waker::from(Arc::new(Noop));
    let mut cx = Context::from_waker(&waker);
    let mut fut = unsafe { Pin::new_unchecked(&mut fut) };
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => std::thread::yield_now(),
        }
    }
}

async fn step(x: i32) -> i32 { x * 2 }
async fn run() -> i32 { let a = step(10).await; step(a + 1).await }
fn main() { println!("{}", block_on(run())); }
// output: 42

Key Points of This Page

  • File modules: @import "relative/path.sla" plus pub fn in the imported file; no module tree ceremony.
  • Standard surfaces are imported the same way; sla_std thin wrappers are the mainstream std import form.
  • async fn + .await reads as in Rust, on the runtime's own task machinery.
