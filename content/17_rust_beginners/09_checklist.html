Study Checklist

This is this chapter's own study checklist, written from the chapter's pages. (The draft this chapter grew from had a checklist that stopped after its third item; what follows is the completed version.) Use it actively: for every item, write the program first, predict its output — or its diagnostic — before you run it, and only then compile. A wrong prediction is the lesson.

Basics

  • ☐ Write a program with two let bindings, reassign one with +=, and print both — without writing mut anywhere.
  • ☐ Write an add function with an explicit return, call it from main, and make main's exit code visible.
  • ☐ Define a struct, build it with a struct literal, and print one field.
  • ☐ Build a String with format(...), and be able to say why String::from(...) is not used.

Ownership

  • ☐ Pass a struct with a String field into a function by value, and explain what happened to the caller's binding.
  • ☐ Deliberately use a value after moving it; read the UseAfterMove diagnostic and name the identifier it reports.
  • ☐ Write read and modify over &i32 and explain why no &mut is needed — and who judges Locked_Read vs Locked_Mut.
  • ☐ Explain why changing a reader function into a writer does not change its callers in SLA, and would in Rust.

Copy, Clone, and Derive

  • ☐ Derive copy, eq, ord, hash, debug on a point struct; use the source after a copy assignment and after a by-value call.
  • ☐ Derive clone and produce an independent value with .clone().
  • ☐ Put @derive(copy) on a struct with a String field, assign it, and explain — before compiling — what the checker will say when you read the source afterwards.
  • ☐ State the generic-struct limitation: what exactly fails, with which error, and in which construction forms it was tested.

Enums, Traits, and Generics

  • ☐ Define an enum with a payload variant and match every arm.
  • ☐ Implement a trait for a struct and call the method both ways: dot call and Trait::method(&x).
  • ☐ Write max<T: PartialOrd> and call it by bare name; explain where the type argument came from.
  • ☐ Explain why a generic free function bounded by your own trait cannot be called yet, and which two working patterns replace it.

Errors, Closures, and Macros

  • ☐ Return a Result<i32, String> from a function and match both arms; build the error with format(...).
  • ☐ Return an Option and match Some and None.
  • ☐ Write a closure that captures a surrounding binding and call it.
  • ☐ Write a typed macro with a leading output parameter and call it like a function; contrast it with macro_rules! in one sentence.

Concurrency

  • ☐ Start a go worker over a rendezvous channel, complete a request/response round-trip, and join it with sa_task_join.
  • ☐ Run the 50-round two-channel ping-pong under thread::spawn, checking the closed flag on every receive.
  • ☐ Build an Arc<Mutex<i32>> counter with four workers and land on exactly 1000.
  • ☐ State the RwLock caveat: the expected final value, and what the longer measurement series actually showed.

Modules, Async, and Engineering

  • ☐ Split a helper into its own file with pub fn and pull it in with a relative @import.
  • ☐ Write an async fn, await another async call inside it, and await the result in main.
  • ☐ Describe the compile route (check → SA text → native) and the Referee's role in one paragraph.
  • ☐ Say where database and networking support live, and why this chapter prints no code for either.

Key Points of This Page

  • Every item on this checklist maps to a program or a diagnostic that was actually compiled, run, or rejected during this chapter's verification.
  • Predict before you run: the output — or the exact diagnostic — is the check.
