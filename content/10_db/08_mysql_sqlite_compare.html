Three-Way Comparison and Vulnerability Statistics: MySQL / SQLite / the db Plugin

SourceThe comparison part synthesizes this chapter's vs SQLite: Choosing Between Them page and the plugin README's own account; the vulnerability statistics are readings from public-data research on 2026-10-28 (sources: Vulners, stack.watch, CVE Details, Oracle CPU advisories, and the cves page on sqlite.org); the category ranges are classified by disclosure description, not an official CWE census. This page answers two questions: how to choose among the three; and, in the known vulnerability history of MySQL and SQLite, will the db plugin repeat their mistakes?

Three-way comparison

  • Form: MySQL is a server process (network protocol, multiple clients, needs operations); SQLite is an embedded library (single file, zero operations); the db plugin is the local storage layer of an SA program (files inside the project, permissions are only the local file system, no network surface).
  • Storage and queries: MySQL/SQLite are both row-store B-Tree + full SQL + an optimizer, flexible for ad-hoc queries and joins; the db plugin is columnar storage + a compile-time schema, with an advantage in projection queries and bulk column writes (measured in the repository: compact about 3.6× faster, verify about 3.3× faster), but the query shape must be worked out at compile time — there is no SQL to throw at it at runtime.
  • Transactions and concurrency: MySQL is the only one of the three with true multi-writer concurrency (InnoDB MVCC, binlog replication); SQLite's ACID is complete but single-writer, with twenty years of polish on crash recovery and WAL; the db plugin has single-table, single-writer transactions, no WAL, and no crash-recovery promise — the README's own selection wording: if you need SQL, indexes, transactions, or crash recovery, choose SQLite; for production-grade long-term storage, SQLite is still clearly more solid.
  • Types and security: MySQL has strict types and a complete permission system, but its attack surface is a network service; SQLite has weak typing and the file is the database; the db plugin's schema is fixed at compile time, its types are the most static, and it has no SQL string parsing — SQL injection does not exist by construction, at the cost of flexibility.
  • Selection conclusion: multi-user, multi-writer, network services and primary/replica replication → MySQL; a single-machine application needing reliable relational storage → SQLite; inside an SA program the data is already columnar and you need bulk writes + repeated scan projections (telemetry, code graphs, ERP lists) → the db plugin. It is a storage engine customized for SA's data shapes, not a general-purpose database.

Vulnerability statistics (public CVEs)

MySQL Server

  • Cumulative total of about 1,003 CVEs (Vulners product count). Long-term annual highs: 108 in 2018, 147 in 2019, a peak of 179 in 2021, 85 in 2023, and about 103 each in 2024/2025 (stack.watch's Oracle MySQL family scope; CVE Details counts only the Server itself, 57 for 2025 — the difference is the counting scope).
  • Oracle's quarterly CPU rhythm: 140 patches in total in 2025, of which only 16 (about 11%) were remotely exploitable without authorization; average CVSS about 5, and severe grades often mix in holes in bundled components (curl/Kerberos/OpenSSL).
  • Category composition (classified by disclosure description): DoS is the largest (about 50–65%, mostly post-authentication hangs/crashes); explicitly stated memory corruption is about 10–20% (most CPU entries only say “unspecified”); permissions/authentication about 5–10% (representative work CVE-2012-2122: a memcmp return-value misjudgment, about a 1/256 chance of logging in with any password, remotely exploitable without authorization; CVE-2016-6662, a configuration-chain root RCE); information disclosure about 10–15%; SQL injection in the server itself under 2%.

SQLite

  • Cumulative total of 65 CVEs (the Vulners and SynScan counts independently agree), of which about a third in recent years are officially marked “Not a bug” by sqlite.org. The annual pattern is spiky: 18 in 2019 (the Magellan 2.0 batch disclosure), single digits in most other years, and only 1 in 2024.
  • Official position: every historical vulnerability requires one of two preconditions — “can execute arbitrary SQL” or “can open a database file constructed by an attacker”; quite a few entries involve only specific extensions (FTS3/FTS5/session), specific compile options, or command-line tools.
  • Category composition: about 75–85% of true core vulnerabilities are memory corruption (integer overflow/UAF/out-of-bounds); the permission category is about zero (no account system); core SQL injection is zero (officially classed as an application-side bug). Representative works: Magellan (CVE-2018-20346, FTS3), CVE-2022-35737, a large-string overflow (reachable only via the C API; neither SQL nor a bad file can reach it), and CVE-2025-6965, an integer-overflow out-of-bounds read (reported by Google Big Sleep; the precondition is still having an injection point first). Its low count is the product of an extremely small attack surface + dbsqlfuzz and near-total test coverage discipline, not luck.

Will the db plugin repeat them: category-by-category verdict

  • Authentication/network category (MySQL's signature): the entire category does not exist. The plugin has no accounts, no protocol, and no network surface; access control is at the host plugin permission layer (local file capability). There is no gate to bypass, because there is no gate.
  • SQL-triggered memory corruption (SQLite's main category): most of the trigger disappears. With no SQL engine, the “arbitrary SQL” precondition goes to zero; the “constructed file” precondition has a counterpart — the segment file / manifest / meta parsers are this plugin's constructed-file attack surface (when an application opens an untrusted table directory, it is isomorphic to opening a bad .db file). Mitigation: the plugin is implemented in Zig, and the read path has explicit bounds, so the consequence drops from memory corruption to a trap; the decisive factor is discipline — the parsers must be under standing fuzzing from day one, and this should be written into the plugin's acceptance criteria.
  • Integer-overflow category (the 35737/6965 type): the surface is significantly smaller. The schema is compile-time fixed-width columns, with no variable-length string formatting path; the remaining risk is in the length arithmetic of segment reads, a matter of discipline rather than architecture.
  • DoS category (MySQL's largest category): a completely different shape. Local, single-writer, no remote surface; the worst case is a bad file crashing/hanging the host process, and which directory gets opened is the application's own choice.
  • This plugin's own bill (neither of the other two has it): crash consistency without WAL rests on the manifest epoch's atomic advance (every file before the commit point is an orphan segment; a verify command already exists); the advisory lock is a cooperative lock, and a writer that does not cooperate can corrupt a table — this point must be stated plainly in the documentation (just as SQLite declares its position on certain file systems).
  • The overall ledger: MySQL's thousand are the product of “a large networked C++ service + quarterly batch disclosure”, and SQLite's 65 are the product of “an extremely small attack surface + extreme testing discipline”. The db plugin's innate surface is even smaller than SQLite's (no SQL, no network, no authentication); its future vulnerability count does not depend on architecture, but on whether fuzzing and parser auditing become standing engineering — architecture sets the floor, discipline decides the ceiling.
