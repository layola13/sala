The Eight SA API Groups

The db plugin exposes two layers of interface to SA: the native extern declarations in db.sai (about 300 sa_db_* symbols) and the macros of the same names in db.sal as a facade (DB_*). This page divides the native calls into eight groups by function, giving their signatures and semantics; every signature is taken from the db.sai in the repository root. For the macro expansion style and directly compilable examples, see the Macro Usage and a Complete Example page.

Naming and calling conventions

  • Table-level calls share the same prefix: (&root: ptr, root_len: u64, &table_name: ptr, table_name_len: u64, ...). Below, <table prefix> stands for these five parameters.
  • The return value is uniformly a status code (-> u32), and business results are written back through &out_* out-parameter pointers. The macros take care of stack_alloc-ing a slot for you and load-ing it back.
  • Handle-class calls (transactions, column sessions, read snapshots) take handle: ptr as their first parameter, and no longer carry a root/table name.
  • A uniform paging contract: list-type queries all accept offset/limit, and return out_written and out_total. total is the total number of matches after filtering, so paging does not lose rows by filtering first and then truncating.

Group 1: Table creation and table-level writes

// 初始化表：schema_path 是磁盘上的 .sadb-schema 文件，schema_source 是其文本内容
sa_db_init_schema(<table prefix>, &schema_path: ptr, schema_path_len: u64,
                  &schema_source: ptr, schema_source_len: u64, &out_info: ptr) -> u32

// 删除整张表（写锁文件会被保留以维持锁语义）
sa_db_remove_table(<table prefix>, &out_info: ptr) -> u32

// 批量列式导入：columns 是 SaDbColumnInput 数组
sa_db_ingest_columns(<table prefix>, row_count: u64,
                     columns: ptr, columns_len: u64, &out_info: ptr) -> u32

// 插入一条固定宽度行，布局必须与当前 schema 的列 stride 完全一致
sa_db_insert_row(<table prefix>, &row: ptr, row_len: u64, &out_info: ptr) -> u32

// 对一段连续行的某 u64 列做原地加法更新
sa_db_update_u64_add(<table prefix>, column_index: u64, start_row: u64,
                     update_count: u64, delta: u64, &out_updated: ptr) -> u32

Semantic points:

  • init_schema takes both a path and the content, making it easy to create a table in an in-memory root (:memory:) scenario without touching disk.
  • insert_row internally slices a row into column slices and goes through the same column ingest commit path, so it likewise advances the epoch and rebuilds the persisted indexes.
  • All writes advance the table epoch and rebuild existing indexes.

Group 2: The row write path by unique key

The common prerequisite for this group is that the target column already has a unique index of the same type built on it, so it has primary-key semantics rather than ordinary matching. Taking u64 as an example:

// upsert：key 存在则原子替换，out_inserted=0；不存在则追加，out_inserted=1
sa_db_upsert_row_u64_key(<table prefix>, column_index: u64, expected: u64,
                         &row: ptr, row_len: u64, &out_inserted: ptr, &out_info: ptr) -> u32

// update：严格更新，key 缺失返回 SA_DB_ERR_NOT_FOUND，绝不追加
sa_db_update_row_u64_key(<table prefix>, column_index: u64, expected: u64,
                         &row: ptr, row_len: u64, &out_info: ptr) -> u32

// delete：按唯一键删除一行，重写剩余行到新列段
sa_db_delete_u64_key(<table prefix>, column_index: u64, expected: u64, &out_info: ptr) -> u32
Key shapeupsert / update / delete suffixExtra parametersTypical uses

u32 / i32 / u16 / i16 / u8 / i8*_{u32,i32,u16,i16,u8,i8}_keyexpected (of the corresponding width)Status codes, channels, warehouse numbers, line numbers, small foreign keys, priorities

Three hard validation rules (a violation fails and does not advance the epoch):

  • The expected of an upsert/update must equal the value actually encoded in the key column of the row data, otherwise it returns SA_DB_ERR_INVALID_FORMAT. In the blob shape, the row's blob_handle must point to the same bytes as the key parameter.
  • update/delete return SA_DB_ERR_NOT_FOUND when the key is missing.
  • Importing duplicate keys in bulk returns SA_DB_ERR_CONSTRAINT, and the active manifest stays at the previous epoch.
NoteThe hash is used only to narrow the candidate set. The blob_eq path takes the candidate rows hit by the index back to the real blob bytes for comparison, so a hash collision will not select the wrong row.

Group 3: Single-table transactions, tx_*

sa_db_tx_begin(<table prefix>, &out_handle: ptr) -> u32
sa_db_tx_insert_row(handle: ptr, &row: ptr, row_len: u64, &out_info: ptr) -> u32
sa_db_tx_insert_rows(handle: ptr, &rows: ptr, rows_len: u64, row_count: u64, &out_info: ptr) -> u32
sa_db_tx_add_columns(handle: ptr, row_count: u64, columns: ptr, columns_len: u64, &out_info: ptr) -> u32
sa_db_tx_dict_intern(handle: ptr, &dict_name: ptr, dict_name_len: u64,
                     &value: ptr, value_len: u64, &out_id: ptr, &out_inserted: ptr, &out_info: ptr) -> u32
sa_db_tx_blob_put(handle: ptr, &store_name: ptr, store_name_len: u64,
                  &value: ptr, value_len: u64, &out_id: ptr, &out_info: ptr) -> u32
sa_db_tx_commit(handle: ptr, &out_info: ptr) -> u32
sa_db_tx_rollback(handle: ptr) -> u32
  • Every upsert/update/delete key shape has a corresponding tx_* variant; the parameters simply replace <table prefix> with handle.
  • During a transaction, operations act on an in-memory transaction image; before tx_commit, no new table epoch or manifest is published.
  • At commit time it writes out the changed row segments as needed, the versioned dictionary/blob artifacts referenced by the transaction, rebuilds all persisted indexes, and then advances the manifest in one step.
  • A transaction of only dictionaries or only blobs is also legal; it advances the epoch but does not rewrite row segments.
  • Recovery mechanism: commit first writes <table>.tx.<epoch>.pending, and after the transaction's versioned meta lands on disk, writes the verifiable .commit marker. recover ignores meta files that have only a pending marker, verifies the meta hash and byte count in the commit marker, and completes committed transactions when the manifest is stale or corrupted.
  • When a commit fails (for example, a duplicate unique key appears in the batch), the old manifest remains visible and the transaction handle is closed; tx_rollback discards the image directly and publishes no rows or blob handles.
  • This is a single-table, single-writer model; read handles still see only committed snapshots.

Group 4: Column batch sessions, coltx_*

sa_db_coltx_begin(<table prefix>, &out_handle: ptr) -> u32
sa_db_coltx_add_columns(handle: ptr, row_count: u64, columns: ptr, columns_len: u64) -> u32
sa_db_coltx_commit(handle: ptr, &out_info: ptr) -> u32
sa_db_coltx_rollback(handle: ptr) -> u32

A batch-oriented write session; its key difference from tx_begin is that it does not hold the global mutation mutex for the whole session:

  • add_columns validates a batch of fixed-width column data and completes segment-file staging and hash computation outside the commit path; the artifacts are visible only to this session.
  • The ABI handle registry uses a shared lock plus a per-session reference count, so the staging I/O of different coltx sessions is no longer serialized by a single global mutex.
  • coltx_commit takes the table write lock only once, publishes all staged batches as new segments, rebuilds the indexes, and advances the manifest once.
  • coltx_rollback discards all staged files.

The README expressly recommends: multithreaded ERP imports and large member-table loads should prefer this path, rather than calling sa_db_ingest_columns concurrently and bare.

Group 6: Dictionaries and blobs

Low-cardinality string dictionaries

sa_db_dict_intern(<table prefix>, &dict_name: ptr, dict_name_len: u64,
                  &value: ptr, value_len: u64, &out_id: ptr, &out_inserted: ptr, &out_info: ptr) -> u32
sa_db_dict_intern_many(<table prefix>, &dict_name: ptr, dict_name_len: u64, values: ptr, values_len: u64,
                       out_ids: ptr, out_ids_len: u64, out_inserted: ptr, out_inserted_len: u64, &out_info: ptr) -> u32
sa_db_dict_lookup(<table prefix>, &dict_name: ptr, dict_name_len: u64,
                  &value: ptr, value_len: u64, &out_found: ptr, &out_id: ptr) -> u32
sa_db_dict_value_len(<table prefix>, &dict_name: ptr, dict_name_len: u64, id: u64, &out_found: ptr, &out_len: ptr) -> u32
sa_db_dict_value_copy(<table prefix>, &dict_name: ptr, dict_name_len: u64, id: u64,
                      &out_buf: ptr, out_buf_len: u64, &out_found: ptr, &out_written: ptr) -> u32
  • Maps a non-empty byte string (such as active, paid, warehouse_a) to a stable 1-based u64 ID within a named dictionary; ID 0 is reserved for the upper layer to express null/unknown.
  • Interning a duplicate returns the existing ID and does not advance the table epoch; what is stored in a row is still an ordinary u64, so u64 indexes, range reads, projections, and the row API can be reused directly.
  • The dictionary itself is a versioned table artifact, maintained consistently with snapshot/restore/verify/recover/lock/unlock/remove.
  • It is not general varchar/blob storage; it is positioned as deduplication for a stable set of labels.

General variable-length blob storage

sa_db_blob_put(<table prefix>, &store_name: ptr, store_name_len: u64,
               &value: ptr, value_len: u64, &out_id: ptr, &out_info: ptr) -> u32
sa_db_blob_value_len(<table prefix>, &store_name: ptr, store_name_len: u64, id: u64, &out_found: ptr, &out_len: ptr) -> u32
sa_db_blob_value_copy(<table prefix>, &store_name: ptr, store_name_len: u64, id: u64,
                      &out_buf: ptr, out_buf_len: u64, &out_found: ptr, &out_written: ptr) -> u32
  • Appends a value to a named store and returns a stable 1-based handle; 0 is reserved for null/missing semantics.
  • Empty values are legal; writing the same bytes again yields a different handle — this path is for varchar/blob data and does no low-cardinality deduplication.
  • A row stores only an 8-byte blob_handle, with the real bytes in the store, so row queries stay fixed-width.

Aggregation and statistics

sa_db_sum_u64_handle(handle: ptr, column_index: u64, &out_sum: ptr) -> u32      // 另有 sum_i64
sa_db_stats_rows_u64_handle(handle: ptr, column_index: u64, &in_rows: ptr, in_rows_len: u64,
                            &out_count: ptr, &out_sum: ptr, &out_min: ptr, &out_max: ptr) -> u32  // 另有 i64 版
sa_db_group_sum_i64_by_u64_handle(handle: ptr, group_column_index: u64, sum_column_index: u64,
                                  offset: u64, limit: u64, &out_keys: ptr, &out_counts: ptr,
                                  &out_sums: ptr, out_len: u64, &out_written: ptr, &out_total: ptr) -> u32
sa_db_min_u64_handle(handle: ptr, column_index: u64, &out_min: ptr) -> u32
sa_db_max_u64_handle(handle: ptr, column_index: u64, &out_max: ptr) -> u32
  • stats_rows_* returns the count/sum/min/max of a candidate row set in a single snapshot traversal; an empty candidate set returns all zeros.
  • The group family has four basic variants in total (sum / stats, with or without a rows input) plus the corresponding sorted variants; the sorted versions sort by sort_by (0=key, 1=count, 2=sum, 3=min, 4=max) and descending, equal values keep first-appearance order, and Top N reports can page deterministically.
  • min/max have complete coverage for u8/i8/u16/i16/u32/i32/u64/i64/f32/f64.

Point lookups, counting, and ranges

sa_db_count_u64_cmp_handle(handle: ptr, column_index: u64, op: u32, expected: u64, &out_count: ptr) -> u32
sa_db_find_u64_handle(handle: ptr, column_index: u64, expected: u64,
                      &out_found: ptr, &out_row_index: ptr) -> u32
sa_db_range_u64_handle(handle: ptr, column_index: u64, min_value: u64, max_value: u64,
                       offset: u64, limit: u64, &out_rows: ptr, out_rows_len: u64,
                       &out_written: ptr, &out_total: ptr) -> u32
sa_db_range_u64_pair_handle(handle: ptr, column_index: u64, column_index2: u64, key1: u64,
                            min_key2: u64, max_key2: u64, offset: u64, limit: u64,
                            &out_rows: ptr, out_rows_len: u64, &out_written: ptr, &out_total: ptr) -> u32
  • count/find/range/get/min/max cover u8/i8/u16/i16/u32/i32/u64/i64 and finite f32/f64; there are also count_bool_handle and find_bool_handle for logical bool columns.
  • On the composite-key side there are find_u64_pair_handle, find_u64_i64_pair_handle, filter_u64_pair_key1_handle, and filter_u64_i64_pair_key1_handle, as well as convenience wrappers that write the second key as a date/timestamp: range_u64_date_pair_handle, range_u64_timestamp_ms_pair_handle, and range_u64_timestamp_us_pair_handle.
  • Variants with a null bitmap apply the null predicate before paging, and total/offset/limit are all computed on the filtered result.
  • Typed wrappers for decimal/date/timestamp (such as range_decimal_i64_handle, range_date_handle, and range_timestamp_ms_handle) take business parameters directly, encode them internally into a scaled i64 / epoch days, and then go through the signed index; an invalid date or a subday value beyond the units of that day returns SA_DB_ERR_INVALID_ARGUMENT, and the range query is not executed.

Candidate row-set composition (planner building blocks)

sa_db_filter_rows_u64_range_handle(handle: ptr, column_index: u64, &in_rows: ptr, in_rows_len: u64,
                                   min_value: u64, max_value: u64, offset: u64, limit: u64,
                                   &out_rows: ptr, out_rows_len: u64,
                                   &out_written: ptr, &out_total: ptr) -> u32
sa_db_intersect_rows_handle(handle: ptr, &left_rows: ptr, left_rows_len: u64,
                            &right_rows: ptr, right_rows_len: u64, offset: u64, limit: u64,
                            &out_rows: ptr, out_rows_len: u64, &out_written: ptr, &out_total: ptr) -> u32
sa_db_plan_u64_i64_ranges_handle(handle: ptr, u64_column_index: u64, u64_min_value: u64, u64_max_value: u64,
                                 i64_column_index: u64, i64_min_value: i64, i64_max_value: i64,
                                 offset: u64, limit: u64, &out_rows: ptr, out_rows_len: u64,
                                 &out_info: ptr) -> u32
  • filter_rows_*_handle takes an existing row-id list and appends a one-column predicate while preserving the input order; it covers the integer family, finite floats, decimal/date/timestamp, bool, dict_eq, and the four blob predicates.
  • intersect/union/except_rows_handle perform the three combinations AND/OR/exclusion: union and except deduplicate, preserve first-appearance order with the left table first, and all three obey the same paging contract.
  • The plan family estimates the candidate sizes of the predicates on both sides and then scans the smaller side first, completing the second predicate's filtering inside the plugin, and tells the caller which side it chose through SaDbPlanInfo.first_predicate (1 or 2; ties take 1), which, together with first_total/second_total, lets you audit the decision. The two-predicate shapes cover u64+i64, u64+u64, i64+i64, u64+blob_eq, i64+blob_eq, u64+dict_eq, and i64+dict_eq; the three-predicate shapes cover u64+i64+blob_eq, u64+i64+bool, and u64+i64+i64, returning SaDbPlan3Info. The README stresses that these are planner building blocks and not a SQL optimizer; wider shapes still require explicitly composing the building blocks above.

Materialization: sorting, projection, and fetching whole rows

sa_db_sort_rows_u64_handle(handle: ptr, column_index: u64, &in_rows: ptr, in_rows_len: u64,
                           descending: u32, offset: u64, limit: u64, &out_rows: ptr, out_rows_len: u64,
                           &out_written: ptr, &out_total: ptr) -> u32
sa_db_project_rows_handle(handle: ptr, &row_indices: ptr, row_indices_len: u64,
                          &column_indices: ptr, column_indices_len: u64,
                          &out_bytes: ptr, out_bytes_len: u64,
                          &out_written_rows: ptr, &out_required_bytes: ptr) -> u32
sa_db_get_row_handle(handle: ptr, row_index: u64, &out_row: ptr, out_row_len: u64) -> u32
sa_db_get_row_u64_key_handle(handle: ptr, column_index: u64, expected: u64,

  • project_rows_handle outputs rows packed one by one in input row order, with the columns inside a row concatenated in the requested column order; a buffer that is too small returns SA_DB_ERR_CURSOR_OVERFLOW and fills in required_bytes; empty input is legal and returns written_rows=0 and required_bytes=0, so empty pages take the same path.
  • get_row_handle copies a complete fixed-width row by snapshot row number; get_row_*_key_handle requires a matching unique index to exist (u64/i64/u32/i32/u8/i8/u16/i16/(u64,u64)/(u64,i64)/unique blob_eq), and fetches the whole row directly by key, saving one find.

These helpers introduce no new physical format: amounts are encoded as a scaled i64, dates as epoch days, timestamps as epoch ms/us, booleans are normalized to 0/1, and nullable fields use a sidecar null bitmap. The two conversion samples given by the README are DB_DECIMAL_FROM_PARTS(1, 1, 0, 2) encoding -1.00 as -100, and 2024-02-29 encoded as epoch day 19782. Schema annotation spellings look like // i64 decimal(2) nullable, // i64 date, // u8 bool; the scale limit is 18. An old schema without annotations gets SA_DB_LOGICAL_NONE, scale 0, nullable 0.

The seven operations calls correspond one-to-one with the CLI commands of the same names, with identical behavior; the difference is that they can be called embedded in an SA program, and they support a :memory: in-memory root (the snapshot/restore artifacts of an in-memory root stay in the in-process namespace and do not create a real :memory:* directory).

WarningThe API is large in number but highly patterned in semantics. When writing code, do not guess the parameter order by intuition — functions of the same family differ greatly in parameter count across key shapes (for example, a pair key adds two more, column_index/key1/key2, and a blob_eq key adds a set of store/value). We recommend always taking the db.sai in the repository root as authoritative, and using the macros in db.sal to shield the slot-allocation details.

For how read-handle queries are actually orchestrated (filter by index first, then narrow the candidate rows, and finally project), see the Macro Usage and a Complete Example page; for which scenarios are worth writing this way, see vs SQLite: Choosing Between Them.
