Limits, Performance, and Best Practices

This page brings together three things you must know before writing code: what the plugin currently expressly does not do, how its performance numbers should be read, and what actionable writing styles can be distilled from the real use cases in the repository's benchmark_test/. After reading this page you should be able to avoid common misuses, and know how to reproduce a measurement yourself.

Known limitations list

Data model

  • No SQL, and no general query optimizer. The README characterizes the plan family as "a planner building block rather than a SQL optimizer"; filtering beyond the implemented shapes must be completed by explicitly composing building blocks.
  • The schema is immutable once locked. Adding a column requires a new table; database.md §15 expressly lists this as a Non-Goal. A column annotation must match its primitive; for example, // u64 decimal(2) is rejected at compile time.
  • No variable-length string columns. Low-cardinality labels go through a named dictionary (storing a 1-based u64 ID), and general text/bytes go through a blob store (an 8-byte blob_handle in the row).
  • ID 0 is reserved. Both dictionary IDs and blob handles reserve 0 for the caller's null/missing semantics; do not use it to store business data.
  • The blob store does not deduplicate. Writing the same bytes again yields a different handle — this path is aimed at varchar/blob data, not a deduplication container; use a dictionary for deduplication. Empty values are legal.
  • The decimal scale limit is 18. Exceeding it returns InvalidFormat.
  • Float indexes reject NaN and ±Inf, returning SA_DB_ERR_INVALID_FORMAT; exact values such as amounts should use a scaled i64 instead.
  • Physical capacity limit: MAX_ROWS * ROW_BYTES ≤ 64 GB, verified when the schema is compiled.

Indexes and text search

  • Range-type reads require the target column to already have a persisted index, otherwise binary-search paging is impossible.
  • blob_contains goes through a trigram candidate index, and the index is enabled only when the needle is at least 3 bytes; empty strings and 1–2 bytes stay on a snapshot scan to maintain exact semantics.
  • A blob_prefix prefix is at most 64 bytes, and matches only at a token start, not as an arbitrary substring.
  • The tokenization model for token/prefix is limited to ASCII letters, digits, and underscores; it is case-insensitive.
  • After any blob index hit, the real bytes in the snapshot are re-checked for confirmation, so a hash collision cannot cause a false match — at the cost of one extra byte comparison.
  • A unique index constrains the real value: creation rejects existing duplicates, and a later write introducing a duplicate returns SA_DB_ERR_CONSTRAINT with the active manifest staying at the previous epoch.

Transactions, concurrency, and consistency

  • Single-table, single-writer transactions. No cross-table transactions, and no multi-table isolation.
  • No WAL. The README lists an optional WAL in the roadmap; it is future work.
  • A read handle is a snapshot. Any write that happens after it is opened (including new blobs) is invisible to the already-open handle; to see new data you must reopen. This is a feature, not a defect, but it is easy to trip over.
  • A failed commit closes the transaction handle, and the old manifest stays visible; you cannot retry a commit on the same handle.
  • The write lock file <table>.write.lock is deliberately kept when a table is deleted, to ensure later writers keep coordinating on the same inode path. When cleaning a directory by hand, do not delete it as garbage and then still rely on the lock semantics.
  • An in-process mutex guarantees only same-process correctness; it is not equivalent to cross-process transaction isolation or ACID (in the words of sci/docs/db_comparison.md).

Special behavior of the in-memory root :memory:

An in-memory root keeps a whole table inside the process, but its operations semantics are not exactly the same as a disk table's:

  • snapshot/restore artifacts stay in the same in-memory namespace and do not create a real :memory:* directory.
  • :memory:name is a shared named root; writing exactly :memory: resolves to the current thread's local anonymous root, and the two are isolated from each other.
  • An already-open read handle holds its own artifact bytes; removing or reusing a table of the same name does not pollute an old snapshot.
  • recover only verifies and republishes the current in-memory metadata; it does not scan the host file system; a missing in-memory table returns NotFound.
  • lock/unlock/compact likewise act only on in-memory artifacts.

How to read the performance data

WarningAll numbers in this section are uncalibrated micro-measurements: a single machine, small samples (mostly medians of 3–7 rounds), and only two synthetic workload scenarios (a 50k member database and a fixed-scale ERP workflow), with the two 2026-06-27 sets, moreover, measured in the unsafe/no-sync mode SA_DB_UNSAFE_NO_SYNC=1. The README's own wording is "Scope is still limited to this benchmark". These numbers can be used only to judge relative trends; they cannot serve as a basis for capacity planning or an SLA, and should not be extrapolated to your real workload.

Key anchors on the db plugin side

For the item-by-item comparison with SQLite, see vs SQLite: Choosing Between Them. Here we list only the magnitudes of the db plugin itself that are worth remembering:

  • A bulk columnar import of 50k rows × 4 columns is about 19 ms; coltx concurrent insertion is about 72 ms (4 workers, 50k rows in total).
  • A full-table SUM reusing a read handle is about 1.7 ms per call (serial 100 calls, 167 ms); opening the snapshot the first time has an additional one-off cost, so a single query can actually lose to SQLite — this is the most important performance characteristic of the read-handle model.
  • ERP indexed list/projection queries are at the microsecond level (0.005–0.019 ms), more than three orders of magnitude below the init/index build cost; that is, the build cost is one-off, and the query benefit accumulates per call.
  • verify is markedly slower in disk mode (147 ms vs 38.9 ms), but in the unsafe/no-sync ERP group it is the fastest instead (1.2 ms) — the difference comes mainly from sync behavior, which is a direct illustration of why unsafe-mode numbers cannot be extrapolated.

README conclusions, verbatim

  • Reused read-handle queries are still faster than SQLite in this benchmark.
  • The isolated-root rerun removed the earlier benchmark cross-contamination and kept db ahead of SQLite on serial and concurrent read-handle SUM.
  • Read-handle open no longer waits on the global mutation mutex, so active write transactions do not block opening committed read snapshots.
  • Concurrent insert via the coltx batch session is the fastest path in the current benchmark set.
  • ERP indexed list/projection queries favor the db plugin in the current workflow.
  • The concurrent insert suite still does not include explicit secondary-index maintenance, so ERP write-path conclusions should remain scoped to the tested workload.
  • SQLite remains stronger for SQL, index creation, ACID, WAL, crash recovery, compact/vacuum, and integrity checks.

Reproducing a measurement yourself

We recommend using the build-system entry points rather than typing commands by hand; they automatically handle plugin installation and SQLite linking preparation (source: benchmark_test/RESULTS.md):

zig build bench                       # 同时构建 db 与 SQLite control
zig build bench-compare               # 默认对照 gate：disk/memory ERP + concurrent 三组
zig build bench-compare-proof         # 推荐的宽证明入口，默认 runs=7
zig build sqlite-proof                # 先 audit 再做 performance proof
zig build bench-compare-memory        # 只跑 :memory: 对照
zig build bench-compare-concurrent    # 四条 SUM 路径分别作硬门禁

# 可调参数（必须是正奇数，避免中位数来自插值）
zig build bench-compare-proof -Dbench-compare-proof-runs=9
zig build bench-compare-concurrent -Dbench-compare-strict-concurrent-insert=true
NoteTwo points that are easy to overlook: first, the benchmark executable links against the installed libdb.so; if you change the source and only run zig build without redoing sa plugin install --dev …, you are still measuring the old binary; second, -Dbench-compare-*-runs=N must be a positive odd number, otherwise the median comes from interpolating two runs rather than a real sample. The raw output is recorded in each *_runs.txt, and the detailed results are in benchmark_test/RESULTS.md.

Practice recommendations from benchmark_test

Every item below has a corresponding writing style in the repository's .sa use cases.

1. Build indexes first, then do the first write

The order in db_memory_smoke.sa is DB_REMOVE_TABLE → DB_INIT_SCHEMA → DB_CREATE_U64_INDEX(unique=1) → only then DB_TX_INSERT_ROW. The README also specifically mentions that this use case covers "index creation before first write". Building the index first lets the first batch of data enter the index-maintenance path as it is written, avoiding rebuilding a large index afterwards.

2. Always use coltx for concurrent bulk imports; do not call ingest_columns bare

This is the README's direct recommendation ("the preferred write path over raw concurrent sa_db_ingest_columns calls"), and it is also the fastest write path in the current benchmark (72.192 ms vs 95.736 ms). The reason is that coltx's staging phase does not hold the global mutex, so multiple sessions can add_columns in parallel, and only at commit time does it take the table write lock once to publish uniformly.

3. Use the batch form for multi-row atomic appends

db_tx_smoke.sa specifically covers DB_TX_INSERT_ROWS (passing a whole row buffer plus a row count at once), rather than calling DB_TX_INSERT_ROW in a loop. The batch form reduces macro expansions and call counts, and still advances the epoch only once, at commit.

4. Open a read handle once and reuse it for all queries

This is the core of the performance model. When a handle is opened it copies an immutable snapshot, and afterwards no *_handle call touches metadata or column files again. db_memory_smoke.sa performs four kinds of query — snapshot_info, SUM, FIND, and GET — consecutively on one handle before closing it. The anti-pattern is opening/closing once per query.

5. Filter with high selectivity first, then narrow the candidate row set, and project last

The typical orchestration is a three-layer funnel, all completed inside the plugin without moving row data back into SA. Below are the representative macros of each layer (arguments omitted):

EXPAND DB_RANGE_U64_I64_PAIR_HANDLE ...
EXPAND DB_FILTER_U64_I64_PAIR_KEY1_HANDLE ...

EXPAND DB_FILTER_ROWS_BOOL_HANDLE ...
EXPAND DB_FILTER_ROWS_DICT_EQ_HANDLE ...
EXPAND DB_FILTER_ROWS_DECIMAL_I64_RANGE_HANDLE ...
EXPAND DB_FILTER_ROWS_BLOB_CONTAINS_HANDLE ...

EXPAND DB_INTERSECT_ROWS_HANDLE ...
EXPAND DB_UNION_ROWS_HANDLE ...
EXPAND DB_EXCEPT_ROWS_HANDLE ...

EXPAND DB_SORT_ROWS_U64_HANDLE ...
EXPAND DB_PROJECT_ROWS_HANDLE ...
EXPAND DB_GET_ROW_HANDLE ...

The four macro groups, top to bottom, are: the index layer (use a persisted index to get the first batch of candidate row numbers; a composite key can fetch a sub-table by a fixed first key + a second-key range); the narrowing layer (append predicates such as bool/dictionary/decimal range/blob contains to an existing row-number list, preserving the input order and the paging contract); the composition layer (AND/OR/exclude two independently filtered row-number lists); and the materialization layer (sort and page, copy only the needed columns, or fetch a whole row by key).

db_candidate_filter_smoke.sa, db_compact_candidate_filter_smoke.sa, and db_erp_workflow_bench.sa all have this shape — the ERP workflow benchmark's “project order details” is exactly fetching row numbers by order_id first and then using DB_PROJECT_ROWS_HANDLE to copy only the needed columns. When there are only two common predicates, you can hand them directly to the plan family to choose a side automatically, and read SaDbPlanInfo.first_predicate to audit which side it chose.

6. Use an independent root directory for each benchmark / each table

This is the most important lesson of this retest round: three concurrent benchmark sets once shared a root, and historical artifacts and SQLite's WAL/SHM side files contaminated each other, producing both too-good-looking fake numbers and intermittent failures. Only after splitting into .bench_raw / .bench_coltx / .bench_sqlite did the results stabilize. You should follow the same isolation principle in your own stress tests.

7. Distinguish measurement mode from production mode

env SA_DB_UNSAFE_NO_SYNC=1 ./db_erp_indexed_memory_bench.out   # 仅用于测量

SA_DB_UNSAFE_NO_SYNC=1 skips synchronization, to amplify the structural differences of the write path. The numbers it produces (for example, verify in the ERP disk group going from 147 ms to 1.2 ms) must never be taken as expected production behavior.

8. Strict status-code checking and ownership release

All the smoke use cases follow the same template: each step's status code is eqd against its expected value into a boolean one by one, chained with and into a master switch, and finally br ok -> L_OK, L_FAIL, with the failure branch doing panic(错误码). At the same time, every intermediate value has a paired ! release, and the two exit labels each release the shared variables. We recommend following this template in your own business code; it can localize a problem to a specific step.

9. Smoke-test with the CLI rather than only running unit tests

The plugin's tests/smoke_installed.sh verifies the command surface's behavior against the installed plugin, including the full chain of registering, taking the hash, and then exec-ing. This catches problems like “the source is right but what is installed is an old version”.

Summary

  • Use it as an embedded columnar engine: schema fixed, indexes first, bulk writes, reused read handles.
  • Do not expect it to provide ACID, WAL, cross-table transactions, or SQL — the README has listed these as non-goals or follow-up work.
  • When citing any performance number, include its source and the qualifier “uncalibrated micro-measurement”.

Further reading: vs SQLite: Choosing Between Them has the complete comparison tables and all the measured numbers; The Eight SA API Groups explains the semantics of every API mentioned above.
