db Plugin Overview: Positioning and Architecture

Zig 0.17This plugin is built with Zig 0.17: the 0.17 branch builds successfully with Zig 0.17 and passes the Zig unit tests; the old 0.14.1 branch is kept unchanged.

This page answers three questions: what exactly sa_plugin_db is, what it expressly does not promise, and which files on disk its data lives in. After reading this page you should be able to judge whether your scenario is a fit for it, and know which layer each of the following pages (CLI, API, macros) covers.

Positioning: local columnar storage, not a general-purpose database

sa_plugin_db is SA's native database plugin (db v0.1.0), providing local, file-backed columnar storage, exposed through two SA-side interfaces: db.sai (native extern declarations) and db.sal (the macro facade). Both are opened up in sap.json's interfaces.

Its core trade-off is moving both the schema and queries to compile time:

  • No runtime SQL string parsing. The table structure is written in a plain-text .sadb-schema, and queries either go through the *_handle read-handle API, or are precompiled into a qmod and executed with sa db exec <hash>.
  • No B-Tree. Storage is SoA columnar segment files; point lookups / range queries rely on a persisted “key -> row” sorted index plus binary search, rather than a paged tree structure. This positioning is stated explicitly in sci/docs/database.md §0/§1.2.
  • Zero repeated parsing on the read path. When sa_db_open_read_table opens a handle it copies the immutable column bytes once into an in-memory snapshot, and all subsequent *_handle queries scan that snapshot, without repeatedly reading metadata JSON or column files.
WarningBoundary statement (in the README.md's own wording): this is not a replacement for SQLite-style ACID / WAL / multi-table isolation. Transactions are currently a single-table, single-writer model; the write path is serialized by an in-process mutex plus a per-table advisory lock file; commits are completed by atomically renaming a temporary file + advancing the manifest. The README stresses at the end: "SQLite remains stronger for SQL, index creation, ACID, WAL, crash recovery, compact/vacuum, and integrity checks."

The current development API is intentionally breaking

The old direct query ABI has been removed: sa_db_sum_u64, sa_db_count_u64_eq, DB_SUM_U64, and DB_COUNT_U64_EQ are no longer exported from libdb.so. All query code must switch to read handles (the *_handle family). Check this first when upgrading old code.

Permission surface (least privilege)

sap.json's permissions declare only four kinds of file operations inside the project directory; everything else is empty or off:

  • fs: on $PROJECT/**, read / write / create / delete
  • net: empty array, no network access
  • env: empty array, does not read environment variables
  • process: {"spawn": false, "exec": []}, spawning child processes is forbidden

This means database files can only be stored inside the current project directory; the CLI commands also all use the current working directory (.) as the table root directory.

Architecture and storage model

Read path: immutable snapshot + in-memory scan

  1. sa_db_open_read_table opens a read handle and copies the column bytes into an immutable read snapshot.
  2. sa_db_snapshot_info_handle / sa_db_column_info_handle / sa_db_column_logical_info_handle read the row count, column count, row width, epoch, column stride, primitive type code, and logical type annotation directly from the snapshot, so callers do not need to parse the meta JSON themselves.
  3. Each *_handle function scans or binary-searches the snapshot; when a persisted index exists, find_u64, count_u64_cmp, and the various ranges go through the index.
  4. sa_db_close_read_table releases the snapshot.

A handle is a snapshot: writes that happen after it is opened are visible to new handles, but not to already-open handles.

Write path: serialization + atomic replacement + manifest epoch

  • The SA ABI layer has an in-process mutex; the table layer adds one advisory write lock file per table, <table>.write.lock, so that the three kinds of writers — CLI, qmod, and extern — serialize on the same table across processes. The lock file is deliberately kept when a table is deleted, to avoid another process recreating a file of the same name and breaking the lock semantics.
  • Storage writes use file-level atomic replacement: write a temporary file in the same directory first, sync, rename over the live file, and on Linux sync the parent directory on a best-effort basis.
  • A table commit selects a versioned metadata file (<table>.meta.<epoch>) through the active manifest; modifying existing column data writes a new versioned column file and then advances the manifest, so a crash before the manifest replacement can still read the previous epoch.
  • Newly written column segments record the whole-file SHA-256, the byte count, and a list of 64KB block-level SHA-256s; indexes, dictionaries, and the blob store are likewise versioned, hashed, and included in snapshot/restore/verify/recover.

Disk layout (one set of files per table)

Below are the file shapes that actually appear in the repository root and in benchmark_test/; the naming rules follow README_cn.md §5:

<table>.sadb-schema          # 源 schema（纯文本 #def）

<table>.manifest             # active manifest，指向某个版本化 meta
<table>.meta                 # 当前元数据副本
<table>.meta.<epoch>         # 版本化元数据文件
<table>.col<i>.<seg>.dat     # 第 i 列第 seg 个列存段
<table>.idx.u64.<col>.<e>.dat            # u64 单列索引（如存在）
<table>.idx.u64_pair.<c1>.<c2>.<e>.dat   # u64 组合索引（如存在）
<table>.idx.blob_eq.<col>.<store>.<e>.dat # blob exact 索引（如存在）
<table>.dict.<name>.<e>.dat  # 低基数字符串字典（如存在）

.sa/db/snapshots/<table>/<epoch>/  # snapshot 备份

Differences between the design document and this implementation

sci/docs/database.md is a more aggressive design blueprint (zero-trust mmap read-only slice injection, Referee X-ray scanning, cold/hot tiering to S3, the Blob Arena bit layout, and so on). The current plugin implements its CLI shape, compile-time schema expansion, qmod registration/execution, columnar segments, and blob storage; while mmap snapshots, block min/max indexes, predicate pushdown, and SIMD aggregation are still listed in the README's roadmap as "performance work after the reliability/data-model baseline". When citing that document, take care to distinguish design from what has landed.

Installation and verification

The commands below come from the Build And Install section of README.md; adapt the paths to your actual repository environment.

# 1. 跑测试并构建（Zig 工程）
zig build test
zig build

# 2. 以开发模式安装到本机 SA 环境
SA_PLUGIN_DEV=1 sa plugin install --dev /home/vscode/projects/sa_plugins/sa_plugin_db

# 3. 验证插件与能力段
sa plugin list
sa skills

Verification points:

  • sa plugin list should show db; sa skills should show the database skill section and entries under it such as db init and db lock.
  • A plugin installed in development mode needs SA_PLUGIN_DEV=1 to be loaded outside the normal run mode; the CLI examples in README_cn.md all carry this prefix uniformly.
  • The benchmark executable links against the installed libdb.so — the README specifically warns that rerunning only zig build without reinstalling still measures the old binary.
  • After installation you can smoke-test quickly: enter an empty directory and run SA_PLUGIN_DEV=1 sa db init members.sadb-schema; if a members.sai is generated in the same directory, it succeeded.
NoteThe repository root already has a batch of members.* table files (schema, manifest, meta files for multiple epochs, 8 column segment files, and a write lock file), which you can use directly as a real sample for observing the storage layout.
