SAB Bytecode Format Overview

This page introduces SAB, SA's binary IR file format (current major version v4): what it is and what it is not, how its byte layout is organized, and how to generate and disassemble it. After reading it you will be able to recognize a .sab file and know what information it contains. For the byte-level specification (encoding rules, round-trip contract, version policy), see the SAB Format Whitepaper (Specification) page.

SAB Is a Structured IR, Not a Text Archive

SAB is SA's binary intermediate representation. The user-facing compilation mainline has only one path, SA text (the production path); the two inputs .sa and .sab converge inside the host at the flat instruction array. SAB is not a container that stuffs .sa source into some section — v4 explicitly forbids a complete .sa source section, and instruction payloads no longer retain the original text of each instruction (raw_text is empty), retaining only structured operands and a small number of short strings (such as call bodies and const literal text).

v4 Layout

magic:          4 bytes = "SAB\0"     （十六进制 53 41 42 00）
version_major:  u8 = 4
version_minor:  u8 = 0
section_count:  uleb128

section*:
  id:           uleb128
  len:          uleb128
  payload:      len bytes

Four sections are currently defined:

idNameContents
1symbol_poolSymbol names, function names, labels, short text tokens; the instruction stream references them by symbol id
2function_sigsFunction signatures, parameter capabilities, parameter/return types, function kind, parameter registers and function register sets
3const_declsConstant declarations and structured literals
4instructionsInstruction kind, source line, op kind, atomic metadata, operands

Open a real artifact with any hex viewer and you can immediately see the magic and the names in the symbol pool at the start:

$ xxd .sla-cache/sab/main-8d82ada9cb6f5e91.sab | head -2
00000000: 5341 4200 0400 ...   SAB.....
00000010: 6f6e 6512 6164 645f ...   one.add_one__param_0_x ...
NoteSAB v4 retains the structured metadata the backend needs: function register ids, native register names, package identity, and upstream location. Therefore compiling from SAB can still produce correct DWARF / symbol names, but it cannot restore verbatim .sa source.

Generation and Consumption

Status (2026-11-15)SAB has been sealed (tag sab-sealed-2026-11-15) and positioned as an optimization direction rather than the production path: all frontends such as SLA output only SA text, and the Zig compiler's default backend is also SA text; SAB requires explicit opt-in (sab build and other named commands, or --test-backend sab). The remainder of this page is a factual description of the format and command surface, and remains valid as usual; see §1 of the SAB Format Whitepaper (Specification) page for the full position statement.
# SLA 源直接编译为 SAB（默认托管在 .sla-cache/sab/，--out 额外落盘一份）
SA_PLUGIN_DEV=1 sa sla sab build src/main.sla --out /tmp/main.sab

# workspace 模式：解析 sa.mod 成员后委派给 sa build-exe
SA_PLUGIN_DEV=1 sa sla sab workspace --sab-out /tmp/workspace.sab -o /tmp/app

# SA 工具链直接吃 .sab 输入，跳过文本 flattener
sa build-exe /tmp/main.sab -o /tmp/app

# 反汇编为可读文本（仅调试用，不在编译主链路上）
SA_PLUGIN_DEV=1 sa sla sab disasm /tmp/main.sab --out /tmp/main.disasm.sa

# 从已校验程序直接产生 .sab 二进制（sci 宿主命令，不走 SLA 插件）
sa check --emit-sab /tmp/main.sab /tmp/main.sa
sa check --emit-sab /tmp/from_sab.sab /tmp/main.sab   # 输入也可以是 .sab
NoteSAB was promoted to a first-class format in 2026-09 (no longer experimental), but was sealed on 2026-11-15 as an optimization direction (tag sab-sealed-2026-11-15): the default production path is SA text, and SAB is explicit opt-in only. The “first-class format / accepts .sab input” statements below describe the factual capabilities of the format and command surface, not the current default path. sa build / run / test / build-exe / build-obj / build-wasm / check all accept .sab input; but complete entry points do not mean functional parity — equivalence with .sa is a specification goal (the L2 equivalence requirement in whitepaper §4.1), and the current execution surface still has registered gaps, see §4.1 of the SAB Format Whitepaper (Specification) page. A corrupt .sab directly reports a SAB-specific error (truncation → TruncatedSab, non-SAB file → InvalidSabMagic), and does not silently fall back to .sa text parsing — when you get a SAB error, fix the file; do not count on a text fallback.

On the SA side, decodeModule in src/sab.zig performs the decoding. Structural equivalence between the decode product and the text Flattener is a specification requirement (whitepaper §4.1 divides it into levels L1/L2), and has not yet been fully achieved: in the decoded FlattenResult, loc_table is entirely null, and layout_versions and def_dict are empty, which is asymmetric with the full-information representation of the text path; see §4.1 of the SAB Format Whitepaper (Specification) page for the gaps and evidence. SCI's generic SAB v4 encoder covers all SA InstKind / OpKind / operand tags.
