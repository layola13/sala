SAB / SA-text Parity Progress (2026-09-21)

This page records the real progress and remaining issues of the work aligning SAB direct-codegen with SA-text semantics. Positioning: SA-text is the semantic standard, and SAB is a subordinate product — SAB exists only to solve the problems of slow SA text compilation and large volume, and SA-text prevails in all semantic divergences.

NoteThis page records only verifiable facts: exit codes, pass/fail numbers, commit hashes, and repository state. Any verification that has not finished running is explicitly marked “incomplete”, and a targeted case passing is not described as everything being complete.

Quality Gates (not bypassable)

  • Strict mode must set SLA_SAB_NO_FALLBACK=1: a SAB failure must exit explicitly non-zero; silently falling back to SA-text is forbidden.
  • Application-layer workarounds are forbidden: divergences must be root-fixed in codegen, the flattener, the encoder, or the verifier.
  • Capture the tested command's own $?; do not pass off the pipeline-end status as the result.
  • Development/debug builds use zero optimization (O0); O1/O3 are used only with explicit --release-small / --release-fast.

Addendum (5), 2026-09-24: By-value ptr pass-through read root fix + macro index cache v8 (pushed)

Symptom: in tests/test_unit_protocol_json_balance_cleanup.sla, protocol_json_test_first_byte_value(STR_PTR(json)) (by-value argument passing + PTR_READ_U8(data)) panics with 19049 on the SA-text backend, while strict SAB passes 5/5 and SA-text 4/5. SA-text is the semantic standard and must be root-fixed first.

Two root-cause layers (sa_plugin_sla@e8d1d66 + @363ff07, both on fix/toolchain-reliability, pushed):

  • Scalar/pointer/fn-ptr macro arguments have no projectable fields; materializing them into a slot and then load slot+off reads the value's own bytes (such as the low byte of a pointer address) rather than a pass-through read, so they are now passed through directly; a purely numeric displacement (load %p+0 as u8) is a pass-through read/write via the address, and is no longer wrongly marked addressable — only a named displacement is a field projection.
  • After the classification fix above, SA-text still failed: the on-disk macro index .sla-cache/macros/*.idx reused an old mask at idx-format-v7 (the stale addrslot=0b10 of PTR_READ_U8), and raising the cache format to v8 invalidated and rebuilt it, restoring correct behavior.

Addendum (23), 2026-11-02: Deep-drop traverser count-offset root fix — a silent fallback mistook the cap offset for len (sa_plugin_sla@db15737f, pushed)

Symptom: a deep drop of a Vec<struct> on the SAB backend SIGSEGVs (fault_addr=0x2b, a garbage pointer fed into sa_vec_free), while the SA-text backend is normal. The trigger condition, proven by a shape matrix, is ⟺ any Vec layer at drop time has cap>len (pushing 3 elements into an inner layer, with cap growing to 4, triggers it; cap==len always passes, unrelated to “nesting” itself). The SAB leg of the corpus tests/test_unit_deep_drop_vec_struct_elems.sla is the minimal reproduction.

True cause: emitVecElementDrops in the plugin's src/sab_codegen.zig computed the traverser's loop-count offset with a decl-style fieldLayout(vec_ty, "len"); Vec is a decl-less handle type (the checker has no struct decl for Vec), so fieldLayout must error, and the code used else |_| 8 to silently swallow the error and land the literal 8 (the ptr side likewise landed 0, which happens to be correct, so only the count was wrong). But sa_std's authoritative layout (sa_std/alloc/vec.sal) is ptr@+0, cap@+8, len@+16 — 8 is cap's offset. The SAB traverser therefore iterated by cap, releasing the uninitialized slots in [len, cap) as boxed element pointers. The plugin already had the correct constants lowering_rules.VecAbi (0/8/16, the same source as the other SAB Vec emission points), which that traverser did not use; a comment beside it even stated a layout inconsistent with the sa_std facts, “ptr@0, len@8”. The SA-text backend is immune: it emits the symbolic offset +Vec_len, which the flattener resolves to +16 — the entire reason for the dual-backend fork.

Attribution correction (recorded truthfully): this defect was originally registered as “a SAB nested walker independent DEF, suspected to be sci's SAB frame model / stack_alloc index-cell nested aliasing”, and the Plan B integration record attributed it the same way. Sci-side triage falsified it with a decisive A/B: decoding the plugin-produced .sab and changing only the 3 drop blocks × inner and outer layers, 6 count load offsets in total, from 8 to 16, with all other bytes' semantics unchanged, turned signal 11 into PASS; disassembly also proved index-cell reads/writes normal, with the only wrong values being the +8 on the two count loads. sci is innocent; no “fix” is needed or should be made in sci (guessing and correcting emission offsets in the loader would break layering and the SA freeze rules); a correction section has been appended to the integration record.

Fix: the ptr/len offsets in emitVecElementDrops directly take lowering_rules.VecAbi.ptr_offset/len_offset (0/16), and the fieldLayout error-swallowing fallback path was deleted. Commit db15737f9ae8e2072eee57037dfdea54b177197a (current master head, change surface: only one place in src/sab_codegen.zig + 4 new corpus items: the cap/len shape matrix …_cap_both_spare / …_cap_outer_spare (red on SAB before the fix, green after) and …_cap_inner_exact / …_cap_inner_single (the cap==len control group, green both before and after the fix)). A census of the same shape (handle types going through fieldLayout + a literal fallback) found only this one place in the whole repository: the other roughly 15 fieldLayout call sites in sab_codegen all use try, so a handle type loudly reports UnsupportedSabDirectFeature there and never emits a wrong offset; emitStructFieldDrops's skip-on-error for a real struct decl is a “skip” shape, not a literal shape; planValueDrop swallowing an error and landing a shallow drop belongs to the drop-plan family, not layout offsets.

Acceptance evidence (normative standard: repository-root cwd, cleared .sla-cache/.sa_cache, SLA_NO_FRESHNESS_CACHE=1, fixtures inside the repository, an independent HOME with installation mtime+cmp dual confirmation): before the fix, 3 forms of SAB signal 11 were reproduced by hand; after the fix, the deep-drop corpus group of 9 items × dual backends = 18/18 fully green; zig build test is 335/338, with the failure name set character-for-character identical to the baseline trio (import-scan #59/#110/#111), with zero additions; slaredis text emission and the integration line's build are byte-identical (the SAB-side change does not affect the text surface); after pushing, a fresh clone of the new master from GitHub was smoke-tested, and the originally-red corpus leg is green on both backends, with the installed .so md5 56c53a7a… dual-confirmed.

Lessons:

  • A silent error-swallowing fallback of the form else |_| <literal> at a layout/offset computation site is always treated as a suspect point, and is censused first during defect triage — it belongs to the same “silent fallback concealing a true error” pattern as sa plugin install --dev swallowing build errors (the same origin as this page's quality gate “no silent fallback”).
  • A PASS claim is recognized only under the normative standard: a rig standard during triage once gave “the new regression passes on both backends”, which did not reproduce under the normative standard, so that conclusion is void; green outside the standard does not count.
  • Attribute only after falsification: the original registration put the suspicion on sci; “fixing” in sci per the original attribution would have been a misplaced fix; a minimal A/B first (changing only the 6 offsets), and only then fixing the emitter.

Addendum (35), 2026-11-15: SAB sealed, the parity line closed

By user ruling (2026-11-15): SAB is fully paused and sealed, with the sealing tag sab-sealed-2026-11-15 placed on sci 3d7e8042, sa_plugin_sla 4f204e24, and sla (Rust) 5c24b828, the then-current heads of the three repositories. Position changed: the production path is SA text (all frontends output SA text only; the Zig compiler's default backend has been flipped to SA text, and SAB requires explicit --test-backend sab opt-in); SAB is an optimization direction, not a production threshold. The SAB / SA-text parity work line recorded on this page is closed with the sealing: its remaining cells are demoted to the optimization queue and are no longer a prerequisite for close-out / tagging; the positioning at the head of this page, “SA-text is the semantic standard, and SAB is a subordinate product”, is consistent with the new position and is retained. If SAB is unsealed in the future, its only form will be a text → SAB one-way conversion inside the SA toolchain (see whitepaper §1), and the frontend-side parallel lowering and parity maintenance will not be restored.
