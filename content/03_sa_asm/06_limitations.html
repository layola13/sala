Known Limitations

This page summarizes the known limitations at the SA architecture level and at the SLA→SA/SAB compilation level, and classifies the common borrow / move compilation errors so you can match your symptom. It is based on SA_LIMITATIONS.md, the official error-code document, and the regression records in the sa_plugin_sla/docs/issue0*.md series.

SA Language Level (encountered when hand-writing .sa)

LimitationImpactWorkaround
No structured switch/matchMulti-way branching can only be implemented with individual eq + br chains; each additional branch adds another chain levelOrganize code with label jump tables or layered comparisons
No shared cleanup / unified exitEvery exit must repeat the release of live registers; the more branches, the more code volume and error rate grow roughly quadratically (real case: a 351-instruction parsing function with 6 exits each repeating 8–12 !reg)Macros can only eliminate textual duplication, not merge semantics; minimize the number of exits
No stack_alloc inside a loop bodyAllocating in only one branch of a br triggers PhiStateConflict; and stack slots cannot be explicitly released (StackEscape)Hoist the stack_alloc before the branch, even if some branches do not use it
Affine single usereturn call @fn(...) is not supported (the flattener treats it as a register named call @fn(...) and reports UnknownRegister); a value becomes invalid after useSplit it into r = call @f(...) + return r
Macros cannot define labelsMacro-expanded lines are all indented, while a label must be at column 0; the “check + two-way branch + define label” pattern cannot be macro-izedExpand by hand
Macros cannot reference later-defined constantsSymbols in a macro body must already be defined at @import time; a #def that appears after the import in the caller's file is unavailable, and behavior depends on expansion orderPut constants in a .sal file and define them before the import
No register allocator / no scoped symbol tableAll alloc/! are managed manually; reuse and nested-scope shadowing are not supportedHave the frontend (such as SLA) generate lifetime cleanup
No peephole optimizationNo constant folding, dead-code elimination, or register reuseReduce redundancy at the frontend or macro level
Diagnostic skew at branch mergesWhen the live-register sets of two branches disagree, the verifier error may point at the wrong register name (internally it looks up names by slot index rather than globalId)Manually cross-check the registers list in the JSON against the source line numbers

SLA → SA/SAB Compilation Level (2026-07 snapshot)

  • Measured maturity: sa sla check passes about 306/313, and sa sla build-exe about 239/313 (76%) — there is a gap of about 22 percentage points between “the frontend can parse it” and “the backend lowering can land it”.
  • (Historical, 2026-07 snapshot) Features not covered by direct-SAB at the time (enum payload/match extraction, derive, the for in protocol, async/await, parts of the collections std metadata, etc.) took the SA compatibility fallback path, with significantly higher compilation time; since 2026-09-28 the compatibility fallback has been removed and uncovered features fail explicitly, and since 2026-11-15 SAB has been sealed as an opt-in optimization path with SA text as the default production path — this item is historical explanation only.
  • &mut T / &mut self have not yet been introduced (Phase 2 plan); currently &self covers both reading and writing, backed by the SA Referee.
  • The demos/rosetta tree does not all pass end-to-end; please verify each one individually.
  • SAB v4 does not retain per-instruction original text, so .sa source cannot be restored from a .sab.

Classification of Typical borrow / move Problems

Symptom (trap)Typical causeApproach
UseAfterMoveThe same value is read again after being moved: continuing to use it after repeated field loads, releasing it again at the tail after passing it as an argument by ^, poor coordination of assignment and cleanup inside a loop (plugin regression records issue004, issue034, issue043, etc.)For values that must be retained, load/copy one first before consuming; do not add a ! for a register that has already been handed over
MemoryLeakAn exit misses a release; aggregate/struct literal fields are not cleaned up; an imported macro argument is double-released, causing a leak on another path (issue006, issue041, issue048, etc.)Check that the live-register set is consistent at every exit
BorrowConflict / ReadWriteConflictPassing a borrowed field out as an argument and then writing it back; the borrow handle's lifetime covers a subsequent exclusive accessNarrow the borrow scope; end the borrow before doing the write
PhiStateConflictAsymmetric stack_alloc inside branches, inconsistent state across branches (the SLA frontend also has corresponding regression records)Hoist stack-slot allocation before the branch; on the frontend side, avoid introducing new slots inside conditional blocks
RegisterRedefinitionRepeated assignment to scalars in a long function causes register redefinition (issue011); macro expansion rebinds a live registerUse a new register name for each logical assignment, or release the old value before redefining
CapabilityMismatchThe capability prefix of an argument at the call site does not match the callee function's contract (issue012, issue017)Check that the &/^/* prefixes on the formal parameters match how the arguments are written
FallibleContractMismatchUsing ? on a non-fallible return value; offset/return contract mismatch for a fallible payload (issue007, issue029, issue039)Confirm the function signature carries !, and let ? act only on fallible values
UnsupportedSabDirectFeature (internal signal)Direct lowering does not cover the feature; the compatibility fallback was removed on 2026-09-28 and it is now an explicit loud failureAdd direct lowering for the gap; SLA_SAB_NO_FALLBACK is defunct — do not use it again
WarningThe classifications above come from the titles and conclusions of historical regression records, and the specific trigger conditions may already have been fixed as versions evolved. When you encounter a new error of the same kind, prefer reading the trap, register(s), and mask fields in the current round's JSON diagnostics, rather than applying old conclusions.
