Compilation Pipeline: Direct and Fallback

This page describes the complete path from source code to a native executable: the Y-shaped dual-input architecture, the SLA plugin's direct SAB fast path and SA compatibility fallback path, and the cost of each path. After reading it you will be able to judge which stage a slow compilation is slow in. Current position (2026-11-15): compilation uses the SA text path by default (the production path); the SAB paths on this page apply only on explicit opt-in (--test-backend sab or the sab named commands), and SAB has been sealed as an optimization direction.

Y-Shaped Dual-Input Architecture

The text and binary inputs converge at the flat instruction array, after which all stages are fully shared:

.sa 文本   --> Flattener (解析/宏展开/#def)  --\
                                                +--> Instruction[] --> Referee
.sab 二进制 --> SAB Decoder (sab.zig decodeModule)-/        |
                                                            v
                              LLVM bitcode Emitter / WASM Emitter / Interpreter
                                       |                    |
                                 zig cc -O{1,2,3}       .wasm
                                       v
                                .exe / .o / .a

The Referee performs capability mask verification, airlock checks, and atomic ordering checks, and outputs AnnotatedInstruction[] (which may carry Trap, Gas, and upstream_loc).

The SLA Frontend's Two SAB Paths

Status (2026-11-15)This section describes the plugin-internal paths when SAB is explicitly selected. The default path is SA text: the frontend emits .sa text via compileSlaToSaString, which is then parsed by the host Flattener — this is also the unified output form of all frontends (SLA, slars, the Rust implementation, and third parties). SAB has been sealed (tag sab-sealed-2026-11-15), and parity maintenance between it and the text path is no longer advancing.

The direct path of sa_plugin_sla does not go through .sa text:

SLA source -> source_expand -> parser AST -> import expansion
           -> monomorphizer -> type checker
           -> sab_codegen.generate -> SAB binary bytes

It does not call compileSlaToSaString, does not write a temporary .sa, and does not re-parse through the SA text flattener. When direct lowering encounters an SLA feature it does not yet cover (historically, for example, function-pointer indirect calls, enum payload/match extraction, derive, the for in protocol, async/await, etc.), it explicitly reports UnsupportedSabDirectFeature, and then switches to the compatibility fallback: in-memory SA-compatible lowering + SCI flattener + SAB encoder. The output is still .sab, and does not revert to the old .test.sa.

2026-09-28 update: the compatibility fallback has been removed (sa_plugin_sla@e96e6b3), and UnsupportedSabDirectFeature is now an explicit loud failure; the fallback row in the table above and the cost figures below are retained only as historical explanation.

Core conclusion: the direct path is very fast, and almost all of the bottleneck comes from fallback coverage — hitting an uncovered feature means paying the extra flatten + encode costs.

Three Coverage Metrics

  • No-fallback sweep: the number of tests passing under SLA_SAB_NO_FALLBACK=1 (58/69 on 2026-07-01). This switch makes direct lowering failure report an error directly rather than entering fallback.
  • Y/shared-lowering: the share of lowering implemented via the shared rules in lowering_rules.zig (72%).
  • Direct SAB fallback-removal: compilation coverage that does not take the fallback path (88%).

To check whether a file took the fallback:

SLA_SAB_NO_FALLBACK=1 SA_PLUGIN_DEV=1 sa sla test src/main.sla --test-backend sab --filter "..."

Backend and Local Optimization Hints

The LLVM path uses O1 by default; O3 is an option. If compiling a program containing a large constant array (such as an all-zero byte buffer) hangs or times out, this is an already-optimized issue: LLVM constant generation takes a dedicated branch for .repeat repeated constants, using a one-shot fill instead of per-element generation, bringing projects containing large instruction buffers from over 5 minutes down to seconds (see the plugin document compilation_optimization_cn.md for details). In addition, the SLA compiler generates a separate .sa/.sab per module and references them via imports, avoiding a “fully expanded merge” that produces a giant single file of tens of thousands of lines and burdens the Referee.
