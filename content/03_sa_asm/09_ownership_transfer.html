transfer: Visible Ownership Transfer

StatusThis page describes the transfer instruction, landed on 2026-11-17 via sci bcafc71f and sa_plugin_sla ac2e2486. It is a new primitive of SA assembly, and also ownership infrastructure that is maturing: it was first adopted internally by the Sla compiler, and hand-written .sa generally does not need to use it directly.

Why transfer Is Needed

Before it, handing ownership of a value to a container (for example, pushing a struct element into a VecDeque) could only be written at the emission layer as a targetless ^ (move-out): ^tmp. That instruction only changes the source register from Active to Consumed, and the Referee cannot see where the ownership went. The consequences are:

  • The verifier cannot check whether the target really is a live container that can receive ownership (pushing a value into a borrowed view, an immutable binding, or an interior pointer was undetectable in the old spelling).
  • The fact of “where the value was transferred to” existed only in the compiler frontend's metadata, leaving a gap between it and the SA instructions actually emitted. Once an emission point omits the ^, the source register stays Active and triggers MemoryLeak at the function exit (typical code 1012) — the error is located at the exit, not at the real omission. DEF-TEXT31-VECDEQUE-STRUCT-TEMP is exactly this class of defect.

transfer turns this transfer into a first-class fact visible to the verifier: the instruction carries the target container, and the Referee checks its legality on the spot and records the ownership transfer.

Instruction Form

transfer <container>, <value>

Both container and value are registers. Ownership of value moves into container; the actual byte move is performed by the preceding store, and transfer itself is a runtime no-op — none of the five backends (LLVM / WASM / JS / interpreter / C) generates machine code for it. It has only verification semantics. A minimal example:

    v = alloc 64
    tmp = alloc 8
    store v+0, tmp
    transfer v, tmp        # 所有权进入 v；tmp 转为 Consumed
    !v

Contrast: if the same program writes only the store and not the transfer, tmp is still Active at the exit and reports MemoryLeak. This shows precisely that what retires the source register is the transfer, not the store.

Referee Checks

On encountering transfer c, v, the Referee decides in the following order:

SideRuleViolation trap
Target container cMust be a live owned root: a stack-allocation root or an Active registerTransferIntoBorrow (1061)
Target container cMust not be a borrow_view / ffi_borrow / interior_ptr, and must not have an interior-pointer subtree attachedTransferIntoBorrow (1061)
Target container cMust not be @const data, and must not be a Rust-style immutable binding (the immutable capability bit)TransferIntoImmutable (1062)
Target container cMust not already be consumed, and must not hold a live borrowUseAfterMove / BorrowConflict
Source valueChecked by the ^ read rules and then turned to Consumed (0x08); transferring the same value twice triggers UseAfterMoveUseAfterMove (1009)

After passing, the target container is stamped with a new capability bit owns_children = 0x0400, meaning “this container received an owned value transferred into it”.

Noteowns_children is a boolean bookkeeping bit, not a child-object counter, and the Referee does not perform deep-drop pairing verification. The deep-drop sequence is emitted by the Sla compiler according to its DropPlan and hidden inside sa_std macros; its register-level effects are not observable by the Referee, so pairing is the compiler layer's responsibility, not within the verifier's checking scope.

Relationship to the Five-Symbol Contract

transfer is not a sixth symbol, but the verifiable form of ^ (transfer ownership) in the “there is a definite receiver” scenario:

  • ^x — moves x out and consumes it, without caring where it goes (for example, discarding a value, or when the calling convention is already expressed by the function signature).
  • transfer c, x — moves x into the definite container c, letting the verifier check the target and record the ownership transfer.

Both paths turn x to Consumed, so both satisfy the no-leak check at the function exit; the only difference is whether the target is visible and checkable. The old bare ^ remains valid; this instruction is an added capability and does not break existing .sa artifacts.

Emitted Automatically by the Sla Compiler

Hand-written SA rarely uses transfer directly; its main producer is the Sla compiler. When SLA source pushes a struct element with owned fields into a VecDeque:

q.push_back(VdJob { id: 7, cost: 3 });

The compiler now emits transfer q, tmp_1 (previously a bare ^tmp_1, or omitted entirely). Two entry points are covered: VecDeque::push_back and VecDeque::from([...]). The instruction is a runtime no-op and does not change the runtime result of the generated program (verified by end-to-end compile-and-run).

In structured JSON diagnostics, these two trap kinds carry expected_mask=Active and the actual actual_mask (such as 0x11 = Active|BorrowView), making it easy to locate which container prefix is at fault. See the Error Codes and Diagnostics page for the full error-code table.

Design Boundaries

  • Zero runtime cost: a no-op in all five backends; the byte move belongs to the preceding store.
  • No deep-drop pairing check: see the owns_children explanation above. This is a deliberate division of responsibility.
  • SAB encoding compatibility: the new InstKind is appended at the end of the enum, without changing existing values, preserving the stability of SAB's raw byte encoding.
  • Backward compatibility: the old ^ remains valid forever, and migration on the Sla side proceeds container family by container family.
