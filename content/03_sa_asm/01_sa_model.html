The SA Conceptual Model

This page explains the core abstractions of Safe ASM (SA): the flat instruction stream, registers, stack/heap memory, and = & ^ ! * the semantics of the five ownership symbols. After reading it you will be able to understand the structure of any .sa file, and understand why the SA verifier (Referee) imposes various restrictions on how registers are used.

Zero AST: Only a Flat Instruction Array

SA has no AST and no structured control flow. The entire program is a flat array of instructions, indexed by u32 subscripts; control flow is expressed entirely with labels and jumps. The design document defines this array as the convergence point of the compilation pipeline: the two inputs, text assembly (.sa) and binary SAB (.sab), produce a completely equivalent Instruction[] here. The compiler performs a single forward linear scan; the only exception is the intersection of Phi states at branch merge points.

Registers and Affine Use

All SA values live in named registers (such as x, tmp_0, ok). Registers are affine: each value can be consumed only once, and becomes invalid after consumption. Therefore, after passing a value to a function, store-ing it out, or using it in a return, it must be treated as already moved; if you still want to read it afterwards, you need to alloc or load again. This also explains two common idioms:

  • return call @fn(...) is not supported — the flattener treats it as returning a register named call @fn(...) and reports UnknownRegister; it must be split into r = call @fn(...) plus return r on two lines.
  • Every branch exit must manually release registers that are still live (a string of !reg), otherwise it triggers MemoryLeak.

Stack, Heap, and Field Offsets

alloc N allocates N bytes on the heap and returns a pointer register; stack_alloc N allocates a stack slot (used for mutable local variables, which cannot escape the current frame). Field access is not syntax, but convention: declare an offset constant with #def Point_x = +0, then use load point+Point_x as i32 / store point+Point_x, v as i32 to read and write.

NoteThe SLA compiler automatically homes function parameters and let bindings to stack slots, that is, you will see instructions such as ch = stack_alloc 8 in the lowering output. At that point the register holds the slot address: the compiler automatically inserts a load in value contexts, while &ch directly yields the slot address. When a macro performs textual substitution it must be aware of this layer, otherwise it will store an address as if it were a value. For the language-level semantics, see the Ownership and Lifetimes page.

Capability Mask (CapabilityMask)

The Referee tracks the state of each register with a bit mask, and all checks are O(1) bit operations. The mask is stored as a u16:

bit 0  (0x0001)  Active        bit 6  (0x0040)  Untracked
bit 1  (0x0002)  Locked_Read   bit 7  (0x0080)  Fallible
bit 2  (0x0004)  Locked_Mut    bit 8  (0x0100)  Immutable   （@const 全局常量）
bit 3  (0x0008)  Consumed      bit 9  (0x0200)  InteriorPtr
bit 4  (0x0010)  BorrowView
bit 5  (0x0020)  FfiBorrow

The expected_mask / actual_mask fields that appear in diagnostic JSON refer to exactly this set of bits; traps such as BorrowConflict, UseAfterMove, and CapabilityMismatch all arise when the mask does not satisfy the requirement.

Frontend Responsibility

SA deliberately performs no scope analysis: Drop insertion points, Phi consistency, and cleanup paths are all the responsibility of the upstream frontend (a human or the SLA compiler), and the Referee only verifies after the fact. “Laundering” operations such as assume_safe / assume_borrow / raw pointers may only appear inside @ffi_wrapper functions, otherwise they report IllegalUnsafeContext.
