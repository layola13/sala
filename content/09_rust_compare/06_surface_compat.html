Rust Surface Compatibility: What Code Parses As-Is

This page answers a very concrete question: if you paste a piece of Rust code into a .sla file, what passes directly, what is silently absorbed, and what must be hand-edited? The basis is docs/rust_surface_compat_report_cn.md (assessment date 2026-06-15) — that document positions itself as a point-in-time snapshot, and the concrete phase status follows the roadmap.

Target Positioning: Not “Becoming Rust”, but a “Surface-Compatible Subset”

The goal given in the report is:

Let a large amount of Rust code parse as-is in SLA, with the compiler silently absorbing Rust's redundant surface declarations (lifetime / pub / where) into SA's implicit behavior during lowering.

That is, the SLA compiler plays the role of “translator + intelligent filter”: an LLM or a human can paste Rust-style code directly, while what the SA side receives is still a clean, flat stream of ownership instructions, with no safety constraint missing.

Two Red Lines (Corresponding to SA Design Principles)

Red lineCorresponding principle
Do not give up ^The “five-symbol contract” (= & ^ ! *) + the core physical input of the affine state machine
Do not introduce the mut spellingShared read vs exclusive write is dynamically decided by the Referee in the runtime context, not distinguished at the syntax level; the Referee already automatically distinguishes Locked_Read / Locked_Mut under the single & syntax (by looking at whether there is a store after the borrowed view)

The root reason let mut is judged “silently misleading” is: SLA and Rust have exactly opposite default mutability — SLA's let is mutable by default, and const is the immutable one. And SLA's ^ prefix unary (Move) and Rust's infix binary XOR belong to different parser contexts and do not conflict.

Category 3: Looks Like Rust, Actually SLA Semantics

This category is the most dangerous: the code parses and looks right, but the semantics differ from Rust. You must remember these four.

SurfaceActual semantics
let mut xNever accepted; SLA's let is mutable by default
&TCurrently covers both read and write uses; after lowering it is always SA's &, with the physical layer backed by the Referee. It is distinguished only after Phase 2 introduces &mut T
Drop traitNot supported; users cannot write impl Drop; release is still implicitly injected by the compiler
'a annotationsParsed only; cross-function borrowing safety follows the frontend responsibility model, with no checking
unsafe blocksDegrade to a “declaration of intent”; real raw-pointer descent is allowed only at the @ffi_wrapper function level, otherwise a compile-time error
panic!("string")panic(numeric code); the string variant goes through sa_std's panic_msg
Send / SyncParseable; the actual semantics are backed by the Referee's affine mask + cross-core validation, with no trait solving exposed

Category 4: Explicitly Refused

  • The let mut x spelling (permanently refused)
  • &mut as a separate type — corrected in v0.2: Phase 2 (before the sa3d ECS launch) will introduce &mut T / &mut self, for the ECS scheduler's static read/write sets
  • The Drop trait
  • Implicit GC / unwind / panic catch
  • Full NLL / Polonius lifetime inference
  • Arbitrarily complex expansion of proc-macro / macro_rules! (SLA's own macro hygienic macros are kept)

Exact Parser Rules for ^ and !

The split rules for the two symbols in “Rust compatibility mode” are as follows (report §4, recommended to be written into parser tests):

prefix  '^' expr          → Move（Sla 既有）
expr   '^' expr           → XOR（Rust 风）
'^' 出现在 type 位置       → 非法

prefix '!' expr           → 逻辑非（唯一接受的语义）
ident '!' (...)           → 短期不引入（与 SA 的 ! 释放原语在 lexer/视觉上易混淆）
单独 '!' 后跟寄存器        → SA 释放原语，但 .sla 用户层禁止显式书写

The discrimination method for ^: when the token appears, look at whether there is an expression ending on the left that can serve as an operand (identifier / literal / ) / ]). If yes → infix XOR; if no → prefix Move.

NoteThe ! macro suffix is not introduced in the short term rather than refused forever: it can be re-evaluated once SA's ! has completely disappeared from the .sla user surface. Until then, the report recommends that the parser treat a ! immediately adjacent to an identifier as “syntactic noise”, strip it, rewrite it to println("..."), and continue parsing, thereby honoring the surface compatibility promise without polluting SLA's own ! semantics.

Compatibility Targets and Phase Roadmap

The pragmatic targets given in the report (snapshot framing of 2026-06-15, not a commitment):

PhaseRust surface compatibilityKey actions
Phase 1 (current at the time)≈ 70%let mut x / &mut T / &mut self all need manual removal of mut; convention that &self covers read and write
Phase 2 (before the sa3d ECS launch)≈ 85%Introduce &mut T / &mut self; let mut is still never introduced
Semantic layer (long term)≈ Rust safe single-threaded subset − Drop trait − full lifetimes − proc-macro

The corresponding implementation order is ranked by ROI into six Phases: ① lexical/type table expansion → ② silently absorbed syntax + use/mod dual track → ③ control-flow completion (loop/labeled break/as/compound assignment/if let/while let/let else) → ④ match expansion + real enums → ⑤ trait static dispatch → ⑥ standard library surface (println/print/format/panic/assert bridged without the ! suffix, Vec/Box/Rc/Arc/Option/Result/String/&str bridged via @extern + .sal with names aligned to Rust).

Warning“70% / 85%” are design target values, not measured pass rates. For measured comparison data, see the item-by-item registration in the rosetta tree (see the The rosetta Comparison Set and the bc2sa Bridge Ecosystem page): in demo.md, 114 lines are marked ✅ direct 1:1 and 90 lines are marked ❌ alternative or subset implementations, and it also explicitly records examples that fail on the local checked path (such as 09_async_await); the introductory chapter also notes that not everything in this tree runs end to end.
