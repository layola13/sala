SLA vs Rust vs Go 性能实测（native / WASM / 编译 / 网络）

这一页是 2026-10-24 在 slarust 项目上复测的完整对比（上一版快照为 2026-10-22）：10 个核心负载 + hello、native 与 WASM 两条产物链、 冷/热编译、产物体积、峰值内存、优化等级与编译可扩展性。所有 SLA/Rust 程序输出逐项一致的校验和， 因此下面的倍数是同一算法的实现差异，而不是负载差异。本轮复测包含 2026-10-24 合入的冷/热启动修复 （SLA 插件内容哈希新鲜度门 + SA 并行 CGU 分支缓存回写），热编译结论已整体反转。

注意本页是可复现的实测快照，不是永久结论。 工具链为 sla 插件 master（2026-10-24，含冷/热启动修复）/ SA 0.1.8（sci 346f68b9）、Rust 1.99.1、Go 1.27.3、Wasmtime 25.0.2， 平台为 Linux x86_64（AMD EPYC 7B12，8 vCPU，50GB 内存）。“优化等级与变体”一节未在本轮重测，仍为 2026-10-22 数据，已在节内注明。

一句话结论

在当前版本上，Rust release 的 native/WASM 运行时中位数分别比 SLA 快约 1.43× / 1.43×（不含 matmul 异常点）。编译结论本轮整体反转：冷编译常规项目 Rust 仍更快（用时为 SLA 的 0.42×（native）/0.53×（WASM）），但热编译 SLA 已与 Rust 持平（native 几何平均 Rust/SLA ≈ 1.02）， WASM 热编译 SLA 反而快约 2.24×——内容未变的重建现在被新鲜度门整体短路，不再全量重编。 SLA 的 WASM 产物体积在剥离 DWARF 后典型负载约为 Rust 的 1/6、最优口径下仅约 1/10，但 matmul 反而大约 1.2×；native 体积仍约 28×。 网络吞吐 SLA 已全面超过 Go，c=256 较上一版修复后快约 3.3×。

摘要

  • 正确性：11 个程序（10 个核心负载 + hello）的 SLA/Rust 校验和全部一致。
  • Native：排除 hello/matmul，Rust 几何平均快 1.43×；含 matmul 快 1.97×。 SLA 在 sort 上仍快 1.35×；hashmap 本轮基本持平（Rust 略快，0.92×）。
  • WASM：排除 hello/matmul，Rust 快 1.43×；含 matmul 快 1.93×。 上一版 SLA 的 mandelbrot 优势（1.87×）本轮消失，两边持平；loopsum 差距从 3.2× 收窄到 1.17×。
  • 编译：常规源码 Rust 冷编译约为 SLA 的 0.42×（native）/0.53×（WASM）用时； 热编译（touch 不改内容）SLA 与 Rust 持平（native），WASM 快约 2.24×。 matmul native 冷编译是异常点，SLA 需要 13.5s（上一版 70.1s），Rust 0.13s。
  • 体积最优：native SLA 约 8,910KB vs Rust 约 276KB（约 32× 大）； WASM 典型 SLA 1.8–4.8KB vs Rust 31.8–34.3KB（约小 10×；matmul 例外，SLA 大约 1.65×）。
  • 内存：大数组场景 SLA RSS 高 2–20×（sieve 422MB vs 21MB，bytes 528MB vs 35MB）。
  • 默认优化（2026-10-22 数据，本轮未重测）：SLA 默认构建大致是 Rust debug 量级（sieve/bytes 慢 3–9×），且 matmul/sort 默认构建段错误；必须使用 --release-fast。
  • 网络并发：4 个独立进程、每进程 1 个监听器时，SLA 31k–182k rps，已全面超过 Go（13.8k–113k）； Rust 36k–378k（快 1.2–2.7×）。SLA 的 RSS 全程稳定在约 19–21MB，无每请求增长。

测试口径

源码在 benchmarks/sla/*.sla 与 benchmarks/rust/src/bin/*.rs。 SLA 用 build-exe/build-wasm --release-fast；Rust 用 cargo build --release （opt-level=3、lto=false、codegen-units=16、panic=abort）和 wasm32-wasip1。 冷编译删除 SLA .sa_cache/.sla-cache 并加 --no-incremental，Rust 使用全新 CARGO_TARGET_DIR；热编译保留缓存，并 touch 两边源文件（内容不变）后重建——该口径下 SLA 会命中 内容哈希新鲜度门（见“热编译”节）。运行时取 7 次（native）/5 次（WASM）中位数， 计时包含进程启动，WASM 使用 Wasmtime 25.0.2。

关键限制：单线程；SLA 当前 Vec<f64> push 后读到 0，因此 matmul 两边都用固定 [f64; 4096] 数组；SLA 没有导出 WASM 函数的语法，只能以 _start 命令运行； Node 20.19 的 WASI 在部分大内存模块退出时会让 SLA/Rust 同时触发 V8 trap，故 WASM 数据统一用 Wasmtime。

网络并发（HTTP/1.1 keep-alive）

结论与建议

  1. 运行时：SLA 在多数负载上比 Rust release 慢约 1.4×（几何平均，native/WASM 一致）；matmul 差距 35.7×。 SLA 的优势集中在无序索引访问（sort，native/WASM 均反超），可能与生成代码省略边界检查有关（未做汇编确认）；hashmap 本轮与 Rust 持平。
  2. WASM：整体差距与 native 接近；fib/nbody/mandelbrot 与 Rust 持平，loopsum 差距大幅收窄。上一版 mandelbrot 的 SLA 优势本轮未复现，不再作为结论。
  3. 编译：冷编译 SLA 仍慢（Rust 用时为其 0.42×/0.53×）；热编译已反转——内容未变的重建由新鲜度门整体短路， native 与 Rust 持平、WASM 快约 2.24×，“零变更全量重编”问题已关闭。matmul native 冷编译 13.5s（上一版 70.1s）仍是首要修复目标， 应继续排查 --release-fast 在固定数组 + 嵌套循环上的 LLVM 优化爆炸；matmul WASM 冷编译本轮回升到 2.36s，亦待排查。
  4. 体积：体积最优配置下 native 仍是 SLA 明显更大（约 8.9MB vs Rust 约 0.28MB，约 32×）。 WASM 在双方最优配置下典型负载 SLA 约小 10×，但 matmul 反而大约 1.65×；报告体积时必须注明构建配置与是否 strip。
  5. 内存：修复 Vec 增长时旧块回收与容量策略；sieve/bytes 的 15–20× RSS 差距会限制边缘部署。
  6. 默认构建（2026-10-22 数据）：默认优化等级大致是 Rust debug 量级（部分负载慢 3–9×），且 matmul/sort 会崩溃；文档应明确要求 --release-fast， 并修复聚合类型的默认代码生成。
  7. 网络：SLA 吞吐本轮再上台阶（c=16 达 182k、c=64 达 168k、c=256 达 124k），已全面超过 Go，与 Rust 的差距收窄到 1.2–2.7×； 每请求约 56KB 的 RSS 泄漏早已修复（见根因），本轮 RSS 全程稳定。剩余差距主要在高并发下的延迟（c=256 SLA p50 1.95ms vs Rust 0.43ms）， 下一步应排查多 worker accept 的共享池锁竞争。
  8. 后续：数值/WASM 部分只覆盖单线程负载；网络只覆盖 HTTP/1.1 keep-alive。 async、FFI、包管理等需要单独基准。

根因

修复 1 — 符号绑定：sci/src/runtime/sa_std.zig 给 mmap/munmap/signal/dlopen/dlsym/dlclose/pthread_join/sqlite3_* 加上 .visibility = .hidden。插件不再绑定到宿主中什么都不做的桩函数（no-op）。

修复 2 — 分配器：sa_plugin_http_server 的 HttpServer.init 从 page_allocator 换成 c_allocator， 这样每个请求不再需要执行一次 mmap 和一次 munmap；WebSocket 帧缓冲也同步替换。

验证：运行 LD_DEBUG=bindings，libhttp-server.so 的 munmap/mmap64/mremap/pthread_join/malloc 全部绑定到 libc； nm -D --defined-only 确认 sa 与 server 均不再导出这些符号； 测试 pthread-vtable-smoke、sa-std-unit、plugin-host-smoke 及插件 zig build test（17 pass / 1 skip）全部通过。
