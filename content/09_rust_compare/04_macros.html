Macros and Metaprogramming Compared

When you move Rust code to SLA, macros are often the bulk of the work: SLA has only one kind of hygienic functional identifier macro, with no pattern sublanguage like macro_rules!, and there will never be proc-macros. This page gives a structural comparison of the two systems, a capability matrix, a four-level classification of conversion difficulty, and the realistic path in SLA for derive-heavy scenarios such as Bevy.

NoteThis page is based on docs/macro_vs_rust_cn.md (v0.1 draft, 2026-06-15) and its architecture correction of 2026-06-23: ECS semantics such as Component/Resource do not enter the SLA compiler; they belong to the sla_ecs library and project-level attributes, and the compiler only provides language-neutral capabilities.

Structure of the Two Macro Systems

SLA's Current Macros

SLA's macro keyword defines a hygienic functional macro whose parameters are a pure identifier list (no type annotations, no patterns):

macro swap(a, b) {
    let temp = ^a;
    a = ^b;
    b = ^temp;
}

Measured implementation points (parser.zig / ast.zig / codegen.zig): the AST node contains only three parts, name, params: []identifier, and body; before expansion, α-conversion is performed, and local variables inside the macro are renamed to <macro_name>_<local_name>_uniq_<N>, so the macro body does not pollute the caller's scope; it is finally lowered 1:1 to SA's [MACRO] ... [END_MACRO] plus EXPAND name x, y at the call site.

Rust's Two Systems

Rust has two mutually independent macro systems. Declarative macro_rules! supports multiple arms and fragment types (:expr/:ty/:ident/:pat/:tt, etc.), variadic repetition $($x:expr),*, and partial hygiene:

macro_rules! swap {
    ($a:expr, $b:expr) => {
        let temp = $a;
        $a = $b;
        $b = temp;
    };
    ($a:ident; $b:ident) => { ... };   // 第二个 arm
}

Procedural macros (proc-macros) are separate proc-macro = true crates that receive a TokenStream and return a TokenStream, manipulated with arbitrary Rust code (syn/quote are the de facto standard), in three forms — functional, derive, and attribute — which is exactly where #[derive(Component)] comes from.

Four-Level Classification of Conversion Difficulty

Easy: SLA Can Already Cover It Directly (estimated 20-30% of simple declarative macros in Rust projects)

Rust spellingSLA equivalent

macro_rules! debug { () => { ... } } no-argument markermacro debug() { ... }
Simple text expansion (no type context)Convert directly

Medium: Feasible with Hand-Written Rework (about 30-40%)

Rust spellingSLA handling
($x:expr) => { ... } taking an expressionCaller first does let tmp = expr; then passes an identifier
($t:ty) => { ... } taking a typeCall manually once for each concrete type, or switch to SLA generics
Multi-arm dispatch by typeSplit into multiple differently named macros, or replace with traits
($f:ident: $t:ty = $v:expr) mixed fragmentsSplit into several identifier parameters + caller evaluates first
Simple variadic $($x),+Expand manually N times, or switch to array literals

Hard: Requires Compiler Extensions to Convert (about 30-50%)

Rust spellingWhy it is hard
#[derive(Debug)] / #[derive(Clone)]Needs to read struct field metadata to generate methods; SLA macros have no such capability
#[derive(Component)] and other Bevy ECS coreAlso needs to register component id / layout / vtable
#[derive(Serialize, Deserialize)]Needs recursive traversal of types
#[command] / #[get("/api")] attribute macrosSLA has no attribute macro system at all
Bulk tuple impls, proc macros depending on syn/quoteNeeds a TokenStream API, which conflicts with SA's philosophy

Impossible: Refused at the Design Level

  • Using arbitrary code as a macro implementation (violates SA's “zero AST, zero implicit logic” philosophy)
  • Arbitrary compile-time computation (const eval, already rejected by SA)
  • Rewriting another package's AST across packages (forbidden by zero-trust package management)

Conclusion: 90%+ of Bevy ECS's conciseness comes from derive macros, and SLA scores zero in this cell. Without derive, a three-field Component needs hand-written registration constants and read/write functions:

// Rust：4 行
#[derive(Component)]
struct Position { x: f32, y: f32, z: f32 }
// Sla 无宏版：15-20 行
struct Position { x: f32, y: f32, z: f32 }

const COMPONENT_ID_POSITION: u32 = 1;
const COMPONENT_SIZE_POSITION: u64 = 12;
const COMPONENT_ALIGN_POSITION: u64 = 4;

impl Component for Position {
    fn component_id() -> u32 { return COMPONENT_ID_POSITION; }
    fn size() -> u64 { return COMPONENT_SIZE_POSITION; }
    fn align() -> u64 { return COMPONENT_ALIGN_POSITION; }
    fn write_to(self: &Position, dst: ptr) {
        store dst+0, self.x as f32;
        store dst+4, self.y as f32;
        store dst+8, self.z as f32;
    }
    fn read_from(src: ptr) -> Position { ... }
}

At this ratio, 50 Components in a game are 750-1000 lines of boilerplate. The biggest bottleneck for ECS porting is not the SLA language itself, but the missing derive capability.

Capabilities That Have Already Landed

  • macro: hygienic functional identifier macros, equivalent to the simplest single-arm subset of macro_rules!.
  • @expand_tuple(min, max, T): restricted arity templates, with placeholders including $N, $TYPES/ $TYPE_PARAMS, $I/$T, $ORD, the iteration directive @each(T) and the joining directive @join(T, ", "); used to generate tuple/arity families in bulk; does not support token-tree matching, multiple arms, recursive macros, or arbitrary compile-time execution.
  • @derive(copy, eq, ord, hash, debug): value-semantics derives are already visible in real source code; ord provides <=> support and can chain .then(...); default is still under evaluation.
  • @overload Type { fn +(...) }: the operator overload block has landed, limited to explicit static dispatch for + - * /; bare overload is not a valid entry point; comparison operations are not automatically opened by the mechanism. @derive(Add/Sub/Mul/Neg/PartialEq/Eq/Hash/PartialOrd/Ord) belongs to a future whitelist path.
WarningECS-related derive names (Component, Bundle, Resource, Event, Message, Relationship) will, per the architecture correction of 2026-06-23, not enter the compiler's Zig whitelist: they are interpreted and expanded by the sla_ecs library with project-level attributes/generation rules, and the compiler keeps only language-neutral capabilities. Do not promise them as built-in features in language documentation.

Why the ! Suffix Is Not Introduced

Rust uses ident!(...) to distinguish macro calls; SLA does not introduce this suffix in the short term, because it is easily confused with SA's ! release primitive both in the lexer and visually. All Rust macro calls are written as ordinary functions or literals:

// Rust
println!("x = {}", x);
let v = vec![1, 2, 3];
assert!(x > 0);
// Sla
println("x = ", x);      // 普通函数
let v = [1, 2, 3];       // 数组字面量
assert(x > 0);           // 普通函数

The parser does a fault-tolerant downgrade for a ! immediately adjacent to an identifier: it strips it as syntactic noise and continues parsing, which preserves the “Rust surface-compatible subset” promise without polluting SLA's own ! semantics. Once SA's ! has completely disappeared from the .sla user surface, whether to open this entry point will be re-evaluated — it is not introduced in the short term, not permanently refused.

Key Points of This Page

  • SLA's macro is a “hygienic functional identifier macro” that only covers the simplest single-arm subset of Rust's declarative macros.
  • Attribute macros, proc-macros, and compile-time reflection will never be done; this is a design decision, not a to-do item.
  • The derive gap is filled by the compiler's built-in @derive whitelist + generation rules on the sla_ecs library side, rather than by introducing a user-writable macro system.
  • Rust macro calls are always written without ! as function calls; the parser will fault-tolerantly strip a ! immediately adjacent to an identifier.
  • For a review of the positioning differences see the Positioning and Design Philosophy: SLA Is Not a Rust Clone page; for the ownership level see the Ownership and Borrowing: Referee vs the Borrow Checker page.
