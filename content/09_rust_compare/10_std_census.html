Rust std × sa_std Surface Census and Gap Table

This page is a bilateral mechanical census done on 2026-10-27: the public surface of the latest stable Rust library source code was extracted item by item into a list, then compared and classified item by item against the full surface list of sa_std. It serves two established purposes: first, the gap ledger for the doctrine that “all basic cores are built into sa_std”, and second, predicting surface collisions when the two Rust routes, bc2sa / slars, plan their extern surfaces. All numbers come from the scripts and lists checked in with the page (tools/rust_std_census/), are reproducible, and no conclusions are drawn from impressions.

Method and Coverage Boundaries

Extraction is a source-level mechanical scan: on the Rust side, a “purified view (comments removed, literal contents emptied) + brace context tracking” is used to identify pub items and inherent / trait declarations / trait impl methods, including Rust 1.99's const impl and multi-line impl headers (where clauses); on the SA side, extraction is done separately by each layer's syntax (@extern, #def, [MACRO], @export / function definitions, SLA's fn/const/struct, and the header file's functions and #defines). Four SA-side counts were cross-validated by independent grep and match exactly (macro 9413, extern 997, sal_def 1552, sa_fn 131+209).

Coverage boundaries (stated honestly):

  • pub use re-exports are not tracked: entries are recorded under their defining module; individual crate-internal pub items (such as core::unicode's generated tables) remain in the public count; the magnitude is small and can be checked in the raw list; internal implementation modules such as std::sys, core::intrinsics, and alloc::raw_vec are listed separately as “non-public surface” and removed from the denominator.
  • cfg platform variants are counted line by line: the same API counts as one line in each of the unix/windows definition files, so a distinct (kind, owner, name) framing is also given; the ffi_os domain is most affected by this.
  • macro_rules are only counted, not expanded (310 definition lines); macro-generated impls are not expanded, so individual macro-generated methods may be missed; procedural macros are outside the scope of the three library crates.
  • “Already has an equivalent” is name/family-level evidence: if sa_std has a symbol with the same name or in the same family it is recorded as an equivalent (such as String::push_str → STRING_PUSH_STR, HashMap::get → sa_map_get), with no claim that the semantics have been checked item by item — semantic checking is the work of the follow-up gap-filling lines.

Four classification tiers: already has an equivalent (already covered by sa_std, including renamed correspondences), directly correspondable (the semantics can land directly in sa_std, it just has not been done), needs modeling (requires a modeling layer such as handles/state machines/trait expansion), model mismatch (depends on mechanisms outside the SA model, with a reason given for each). Each classification record includes the rule number it hit, auditable in rust_classified.tsv.

Key Points of the Gap Classification

Directly Correspondable (4,383): The Main Body Is “Per-Type Expansion” and “Platform Extension Surface”

The three largest blocks are num's 1,206 (per-type expansion of the basic types' inherent methods — each integer/floating-point type has dozens of methods; SA covers most of them with operators/builtins + math externs, and the rest is a long tail of mechanical checking), ffi_os's 1,112 (the unix/windows extension trait methods of std::os, counted as one line per platform, a direct syscall/handle access surface), and mem's 426 (pointer/memory primitives, which are SA's native surface in the first place). Together these three blocks account for more than 60% of all directly correspondable gaps; there is no design dispute, only workload. collections (458), string_str (309), and slice (200) are pure data structures and byte algorithms, of the same nature. There are 353 public-surface consts in total scattered across the domains, mostly associated constants of the basic types, which can be handled together with AJ-style constant completion.

Needs Modeling (1,453): Five Modeling Questions

  • Iterators: 221 in the iter domain + 35 methods in the various collection/string/slice domains that “return an iterator” (rule R-iter-return), plus methods that take an iterator as input (such as the extend family). sa_std's existing ts_arr_* are eager array functions that only cover the “array in, array out” subset, and are not equivalent to lazy adapter chains — this is the most wide-reaching of the five questions.
  • The io handle surface: 229 of the 235 lines in the io domain need modeling. sa_std does not lack concrete read/write externs (fs/net each have their own); what is missing is the unified handle object surface for Read/Write/Seek/BufRead. Note that Rust 1.99 has already moved the basic parts of io down into core::io / alloc::io, and this census assigns the io domain by defining module as the sum of these three places.
  • Formatting: all 157 lines in the fmt domain need modeling (the Display/Debug/Formatter system), and another 266 lines needing modeling on the macro surface include the format!/println! family (macros are classified by their defining domain).
  • Synchronization: 256 lines in the sync domain need modeling, mainly the mpsc/mpmc channels and the poison/nonpoison lock families, and Once/LazyLock lazy initialization; the atomics and reference-counting surface (99 already have equivalents + a batch of direct correspondences) already has a foundation; what is missing is the state model for blocking waits and channels.
  • The rest: thread 56 (handles/join/TLS), async 53 (the Waker surface), process_env 52 (the Command builder and child-process pipes), error 26 and convert 34 (the expansion surface of the trait system), and 166 trait bodies themselves (rule R-trait, scattered across the domains).

Model Mismatch (124): A Conclusion, Not a Defect

The panic domain's 75 lines (the unwinding mechanism, panic hooks, backtraces — SA has no panic unwinding model, and the error surface is expressed with status codes and explicit failure paths) and marker_meta's 44 lines (Any/downcast depend on RTTI, and marker traits such as Send/Sync are type-system-level declarations that are erased in the SA model) together account for 96% of the model mismatches. These entries should not enter the gap-filling list; when writing Rust-side code, they should be replaced with explicit errors and explicit resource management.

Priority Short List for Gap Filling

  1. Iterator modeling layer (iter 221 + 35+ cross-domain): the highest-frequency construct in Rust code, the first wall shared by the slars hand-written surface and the bc2sa machine surface; first build an Iterator state-machine handle + the common adapters (with map/filter/zip/enumerate/chain/collect landing points).
  2. Formatting modeling layer (fmt 157 + the format macro family): format!/println! are the shared landing point for the slars macro whitelist and bc2sa probe (b)'s format_args tier, and are the foundation of Rust's output surface.
  3. Unified io handle model (io 229): the upper-level io of fs/net/process all step on it; align it with the internal interfaces of built-in cores such as http/ws in the doctrine, to avoid each domain building its own read/write surface.
  4. sync modeling batch (sync 256): mpsc/mpmc channels + Once/LazyLock + the poison lock families, expanding the existing mutex/mpsc foundation into a complete model.
  5. num per-type checking batch (num direct correspondences 1,206 + public consts 353): the largest “just not done yet” item in the whole census, with no design risk, suitable for batch processing; bc2sa's integer/floating-point instruction semantics ultimately land on this batch as well.
  6. The direct long tail of collections / string / slice / mem (458+309+200+426): among them, Vec/String/slice are exactly the alloc surface that bc2sa probe (b) needs to land on after hitting the wall, so filling them is equivalent to laying the extern foundation for the bc2sa route.
  7. Direct completion for net / fs (163+140): the main body of net is IpAddr/SocketAddr parsing and socket options (that family has already moved down into core::net in Rust 1.99), and the main body of fs is the path and metadata extension surface, small steps with no dispute, fitting “all basic cores built in”.
  8. async alignment surface (async 53): the surface is small but its position is key — SLA already has a task poll runtime, and what is missing is the alignment layer with the Rust Future/Waker shape, which bc2sa will necessarily hit when converting async code.

How to Re-Run

The scripts and lists are in tools/rust_std_census/: extract_rust.py (arguments: the rust-src library directory, output path), extract_sa.py (arguments: the sci repository root, output path), classify.py (arguments: the two lists, output path, and it also prints the contents of summary.json). All classification rules are inside classify.py and record the rule number line by line, so after adjusting the framing you can re-run to refresh the numbers on this page.
