Troubleshooting Build Failures

This page addresses the two most common kinds of compilation problems: sa sla check passes but build-exe/test fails, and the explicit SAB path (--test-backend sab, opt-in) reports an “unsupported feature”. After reading it, you can tell which stage a failure belongs to and use environment variables to locate the specific feature the SAB path does not cover.

check Passes, but build/test Fails

sa sla check and the build/test backends do not share exactly the same parsing and lowering logic. A real case (issue026): writing ptr_add directly in a struct literal field or a let initializer is accepted by check, but build/strict SAB reports found ',', expected colon at the import-expansion stage, or a later Trap. The project-side workaround was to change the pointer-offset slicing to allocate/copy the basename first and then return it.

When you hit this kind of divergence, troubleshoot in this order:

  1. Move the suspect expression out of the inline position into a local variable, narrowing the trigger surface piece by piece;
  2. Run once with --test-backend sa and once with --test-backend sab to confirm whether it is a backend difference or a frontend parsing difference;
  3. Add --trace-panic --jobs 1 to get more complete Trap information.

Identifying the Failing Stage and Its Phase

The explicitly chosen SAB path uses the direct AST->SAB encoder; when a feature is not covered it fails loudly with no fallback (the SA compatibility fallback was removed on 2026-09-28). The default SA text path does not go through SAB, so the errors in this section appear only on the SAB path. Typical errors on the direct path are:

SAB Direct Error: direct SLA-to-SAB lowering failed without fallback: error.UnsupportedSabDirectFeature
SAB Error: failed to encode SAB ... error.VerificationTrap

A VerificationTrap is usually a Trap from the underlying SA verifier bubbling up (for example, UseAfterMove: moved value is no longer usable); in that case, switching to the SA text backend often shows more detail, such as register names, expected state, and actual state.

Locating the Unsupported Point on the SAB Path

The SA compatibility fallback has been removed: the SAB path errors by default when it meets an uncovered feature, and there is no silent fallback. To locate the first uncovered point, run a single file in trace mode (with the working directory at the plugin repository root):

SLA_SAB_TRACE_UNSUPPORTED=1 timeout 120s ./zig-out/bin/sla-local-cli sla test tests/test_unit_xxx.sla \
    --test-backend sab --jobs 1 --trace-panic
  • SLA_SAB_NO_FALLBACK=1: the historical strict switch; after the fallback was removed, no-fallback is the default, and keeping it is only for compatibility with old scripts.
  • SLA_SAB_TRACE_UNSUPPORTED=1: prints exactly which features are not covered on the SAB path.
  • SLA_PROFILE=1: outputs per-stage timings (parse / import expand / type check / sab direct codegen, etc.), for confirming where the time goes.
  • --jobs 1 + --trace-panic: runs serially and keeps the panic trace, making reproduction easier.
SLA_SAB_TRACE_UNSUPPORTED=1 SLA_SAB_NO_FALLBACK=1 timeout 180s \
    ./zig-out/bin/sla-local-cli sla test tests/test_unit_xxx.sla \
    --test-backend sab --jobs 1 --trace-panic
