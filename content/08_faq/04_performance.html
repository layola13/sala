Performance and Optimization Expectations

This page explains the time scale of the SLA compilation pipeline: how much the direct path and the fallback path differ, what the macro-template cache brings, and what the large-array initialization optimization solved. After reading it, you can form reasonable expectations about “why is compilation so slow” and know which tool to measure it with.

WarningAll numbers below come from internal documents in the development repository (roadmap_status_cn.md §6, compilation_optimization_cn.md) and are uncalibrated micro-measurements: a single machine, single files, specific versions. They only illustrate orders-of-magnitude differences and do not constitute any performance guarantee.

The Gap Between direct and fallback

The following is a historical measurement snapshot (from the period when SAB was still the mainline and the SA compatibility fallback still existed): at that time the SAB path preferred the direct AST->SAB encoder, and on meeting an uncovered feature it fell back to SA compatibility lowering + the SCI flattener; the time gap between the two paths could exceed an order of magnitude. Taking the single-file measurements recorded in roadmap_status_cn.md §6 as an example:

Input / pathTimeNotes
test_unit_vec_remove_direct.sla — direct SAB (with macro-template cache)About 257msAnnotated in the record as a 16× speedup
test_unit_vec_remove_direct.sla — direct SAB (no cache)About 4094msThe bottleneck point at the time
parallel_table_erased.sla — SA compatibility flattening (fallback)About 4.04sFallback-path bottleneck
parallel_table_erased.sla — SAB encodeAbout 5.22sThe largest single bottleneck at the time
parallel_table_erased.sla — sa test (host-side backend)About 13.50sSA backend time
NoteThe core conclusion at the time was: the direct path itself is fast (in the same batch of records, on the order of 24-257ms); what was slow was “falling back wholesale on meeting an unsupported feature”; the fallback was removed on 2026-09-28. The current position (2026-11-15): SAB has been sealed as an optimization direction, and SAB does not speed up a single compilation — the bulk of cold-compile time is in the host backend (the host-side sa test time in the last row of the table above is that bulk), regardless of whether the input is text or SAB; hot compilation / incremental caching is an independent mechanism keyed by source hash and has nothing to do with SAB. If a file errors on the explicit SAB path, use SLA_SAB_TRACE_UNSUPPORTED=1 from the “Troubleshooting Build Failures” page in this chapter to locate the uncovered point.

The Large-Array Initialization Optimization

For sources containing large numbers of constant arrays (for example, the 16384-length instruction buffer in the Lua VM rebuild), the sci compiler's LLVM constant generation introduced a .repeat repeated-constant optimization: when it detects large areas of repeated default values, it fills the byte stream in one go with @memset and emits the LLVM aggregate constant directly, avoiding per-element generation. The effect recorded in compilation_optimization_cn.md:

  • The clean-rebuild compile time of lvm.test.sa dropped from >5 minutes to about 4.6 seconds;
  • lparser.test.sa dropped to about 6.6 seconds;
  • It also solved unit tests and incremental compilation hanging / terminal timeouts.

Repeated Builds: Zero Changes No Longer Recompile Everything

Early versions had a serious incremental-build defect: with zero source changes, every sla build-exe amounted to a full recompilation. The root cause had two layers. On the SA side, the build-exe project cache (.sa_cache) was written back only on the serial emission path; the CGU parallel path taken when --jobs was passed explicitly and the function count was ≥ 100 never wrote the cache — it compiled and discarded. On the SLA side, --jobs auto was appended unconditionally to the delegated SA command, so every sla-driven build was pushed onto that cache-less path.

The cache division of labor after the fix:

  • SA build-exe cache: all emission paths (including CGU parallel) write back .sa_cache entries; on a hit the product is restored directly and native compilation is skipped; the cache key is independent of --jobs, so serial and parallel builds hit the same entry as each other.
  • sla no longer forces --jobs auto: the delegated SA command takes the serial + cache path by default; a --jobs passed explicitly by the user is still forwarded as-is.
  • SLA frontend freshness gate: the frontend stores each compilation's dependency closure (the root file, all imported modules, contract import files, the sibling sa.mod) together with the product in .sla-cache/fresh/, recording a content hash per file. Afterwards, if all closure hashes match, the product is reused directly and the whole pipeline — parsing, import expansion, monomorphization, type checking, encoding — is skipped; any file whose content changes misses and recompiles normally, and no stale product is ever emitted. The environment variable SLA_NO_FRESHNESS_CACHE=1 can disable this gate. sla check uses a separate inline pipeline and is not yet connected to it.

Order-of-magnitude reference (a 288-module synthetic project, shared host, uncalibrated): a zero-change sla build-exe dropped from about 0.70s to the order of about 0.05s (after a frontend hit, only process startup and SA cache restoration remain). When only a comment changes, the freshness gate correctly misses and the frontend reruns, but the generated SAB bytes do not change, so the SA cache still hits; changing a function body produces a new SAB and a new executable.

How to Measure Your Own Pipeline

The plugin repository ships a benchmark harness that outputs JSONL timings (with the working directory at the plugin repository root):

tools/bench_sla_pipeline.sh --runs 3 --out /tmp/sla_pipeline_bench.jsonl

Built-in projects include sla_to_sab_cold (timed after clearing the managed SAB cache), sla_to_sab_warm (keeping the cache), sla_to_native (the build-exe main chain), and sab_test_fallback_allowed and sab_test_direct_no_fallback (comparing the test paths with fallback allowed vs no-fallback). You can also add SLA_PROFILE=1 to a single command to see the per-stage timings:

[sla-profile] parse: 12ms
[sla-profile] import expand: 45ms
[sla-profile] type check: 15ms
[sla-profile] sab direct codegen: 24ms

Known Structural Pressure

At @import time the SLA frontend currently uses a “fully expand and merge” model: multiple modules are merged into a single .sa/.sab, and real projects have seen single files with tens of thousands of SA instructions after expansion, which puts pressure on the flattener, the verifier, and the backend. A modular compilation scheme that splits output by module and reuses SA's native @import linking is planned in the design documents but is not yet the current behavior — do not assume compilation is cached per module today. The freshness gate above works at whole-compilation granularity: with zero changes the whole thing is skipped, but a change to any file in the closure is still a full-expansion rebuild, and the product form does not change.
