Layers: From psa Down to SA

A psa program stands on five layers. Each layer has one duty, and no layer borrows the semantics of the one above it:

LayerDuty
psaThe language and its compiler: the Python-shaped surface, type and ownership inference, the two-layer semantics of the stance page, and emission of SLA text. psa emits SLA only — never SA directly, never a second backend.
psa_stdThe standard library written for psa authors, in psa/SLA form: modules with Python-shaped interfaces (json, the networking surface, and the rest of the library programme), so psa programs write import json rather than knowing what sits below.
sla_stdThe SLA standard library: the typed containers, string, formatting, math and systems facilities that psa’s static layer and psa_std are built on.
sa_stdThe SA standard library: the verified substrate facilities — I/O, networking cores, channels, concurrency — expressed at the SA level.
SAThe foundation: the register and ownership model, the borrow/move/release rules, native and WASM code generation, and the Referee, which re-verifies every program after lowering. No frontend claim is trusted; the Referee decides.

Where the dynamic layer ends and the static layer begins

The two layers of the semantic stance are not two languages and not two modes the author selects. The boundary is drawn value by value, inside one program, by a single criterion: does the compiler have usable static type information for this value?

  • Where inference proves one static type — a variable first bound to an integer, a homogeneous list of integers, a function whose parameters are pinned by their uses and call sites — the value is a plain SLA-level value: value semantics, ownership and borrowing checked at compile time, no dynamic representation involved.
  • Where it cannot — a heterogeneous list, a dict with values of mixed kinds, a payload decoded from JSON — the value is carried by the dynamic layer: a tagged dynamic value with Python reference semantics and dynamic dispatch, its memory still deterministically managed (Perceus-style reference counting with in-place reuse), never by a tracing garbage collector.
  • The two coexist in one program and meet at function boundaries and assignments: a dynamic value flows into a statically pinned variable only through a checked conversion, and a variable’s type is pinned by its first binding — psa refuses, loudly, to let a statically pinned variable quietly become dynamic later (measured diagnostic PSA-E2032).

The author does not manage this boundary. It is the compiler’s bookkeeping, and when a program leans on it in a way that would change meaning, the stance’s first iron rule applies: refusal with a repair hint, or an explicit form — never a silent change. The next page shows both styles, and the boundary, in running programs.

Key Points of This Page

  • Five layers: psa → psa_std → sla_std → sa_std → SA; each keeps its own duty and its own semantics.
  • The dynamic/static boundary is per value, drawn by the compiler from the type information the code itself provides.
  • Dynamic values are reference-counted deterministically; there is no tracing GC anywhere in the stack.
  • Crossings between the layers are checked; a pinned variable cannot silently become dynamic.
