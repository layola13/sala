Status and Limits

Everything on this page is stated at the measurement standard of the rest of this documentation: what is measured is quoted with its conditions, what is not finished is named as not finished.

Where psa stands

psa v1.0.0 is released (sapy commit 37d0fb6, tag psa-v1.0.0, 2026-11-26). The v1 acceptance batch passes 25/25: 23 programs byte-identical to CPython and 2 negative cases refused loudly. Development continues past v1: the post-release integration steps (parser gaps, closure capture, structured errors) are merged, the wave-1 psa_std wiring (29 modules) is written and verified, and the remaining syntax batches proceed as task 171. The design record is the SA-Py blueprint.

Syntax coverage, as censused

The item-by-item syntax census (sapy repository, updated 2026-11-26) counts 46 constructs: 35 supported, 8 partial, 3 gaps (2 frontend gaps and 1 dynamic gap). “Partial” means the construct works in the shapes the census names and refuses loudly outside them; the companion chapter’s coverage matrix (Modules and the Full Coverage Matrix) gives the per-construct state.

The registered gaps

  • The walrus operator := — frontend gap, refused at compile time.
  • Bytes literals b"" and raw strings r"" — frontend gap, refused at compile time.
  • Arbitrary-precision integers — dynamic gap. v1 integers are i64; an integer literal beyond i64 is refused loudly rather than silently truncated (the bigint work is registered separately, as a substrate item).
  • Loop else (while/else, for/else) — a frontend gap recorded in the census under the control-flow constructs.
  • is / is not — the census records identity as a gap (v1 defines no identity semantics). An implementation has since been completed in the task 171-B batch — identity defined as tag-and-payload equality, with NaN identical to itself — and is awaiting integration into the master; until it lands, the census state is the operative one.

Per the stance’s second iron rule, each of these is a loud compile-time refusal, not a simulation and not a silent approximation.

Performance, as measured for v1

On the v1 benchmark set, measured in a single window against CPython: fib ≈24×, loopsum ≈99×, listsum ≈40× on statically compiled programs, and dynsum ≈1.4× on a dynamic-style program. These are the v1 figures under the conditions recorded with them in the blueprint (section 6.3); they are quoted here as the current reference points, not as guarantees for arbitrary programs — dynamic-style code is faster than CPython by a small margin, static code by a large one, and the honest summary is that the margin depends on which layer a program’s values live on.
