Two Styles in One Language

Every program in this chapter was run before it was written down: the psa programs with the psa compiler (a retained build of the current master), emitted to SLA and built and run on the SLA→SA text route, on 2026-11-26; the one SLA program with the same text-route toolchain. The output quoted is the output the program really printed.

Dynamic style: values carry their types at runtime

A tool-call payload is the natural shape of the dynamic style: a dict whose values are of mixed kinds, a heterogeneous list, member access and arithmetic resolved at runtime. Nothing here has a provable static type, so every value travels on the dynamic layer — with Python semantics.

payload = {"tool": "search", "args": ["sla", 42, True]}
print(payload["tool"])
print(payload["args"][1] + 1)
print(payload["args"][2])

Measured output:

search
43
True

Static style: inference pins the types, SLA semantics apply

No annotations are written here either — but every value’s type is pinned by its uses: n is compared with an integer and recursed on with integer arithmetic, so fib is inferred as an integer function throughout and compiled on the static path, under SLA semantics, with ownership checked at compile time.

def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

print(fib(15))

Measured output:

610

The boundary, in one example: aliasing

In Python, ys = xs makes a second name for the same list, and mutating through one name is visible through the other. psa’s answer depends on which layer the list lives on — and in neither layer is the change silent.

On the dynamic layer (a heterogeneous list is a dynamic value), Python’s reference semantics hold, exactly as the stance promises:

xs = [1, "a"]
ys = xs
ys.append(3)
print(xs)
print(ys)

Measured output — both names see the appended element:

[1, 'a', 3]
[1, 'a', 3]

On the static layer (a homogeneous list of integers is statically pinned), assignment moves the container. The Python-shaped program is refused at compile time, with the reason and the repair stated (diagnostic measured verbatim):

xs = [1, 2]
ys = xs
ys.append(3)
print(xs)
print(ys)
error[PSA-E1001]: use of `xs` after it was moved
  --> ex_alias.psa:4
   = site: move (line 2)
note: container assignment moves the value; the binding is dead until it is re-bound
hint: re-bind `xs` before line 4, or bind a copy at line 2

And when the same program is written in SLA directly, shared mutation is something the author writes explicitly, with a borrow:

@import "sa_std/io/print.sai"
@import "sa_std/fmt.sai"
@import "sa_std/vec.sa"

fn append3(v: &Vec<i64>) {
    v.push(3);
}

fn main() -> i32 {
    let xs: Vec<i64> = Vec::new();
    xs.push(1);
    xs.push(2);
    append3(&xs);
    println("{}", len(xs));
    println("{}", xs[2]);
    return 0;
}

Measured output:

3
3

This is the short form of the aliasing story. The full treatment — nine hazards, each shown as the psa risk, the direct SLA translation, the verbatim compiler diagnostic or measured behaviour, and the safe form — is the companion chapter’s page Ownership and Memory Safety.

Key Points of This Page

  • Dynamic style: mixed-kind values, runtime dispatch, Python semantics — measured output matches Python.
  • Static style: no annotations needed; inference pins the types and the program compiles under SLA semantics.
  • Aliasing is layer-dependent and never silent: reference semantics on the dynamic layer, a loud move error on the static layer, an explicit borrow in SLA.
