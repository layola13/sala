Interpreter Internals

This page expands on vm’s implementation details: what the two-pass preprocessing does, how the stack-frame model expresses a piece of .sa, how instruction dispatch cooperates with basic blocks, and whether vm consumes .sa or .sab. After reading this section you will be able to explain “why --stats outputs this string of counters”, and be prepared to read src/vm.zig / src/parser.zig.

Input Recognition: Source vs SAB Bytecode

vm’s entry point (src/plugin.zig::runVmCommand) does not look at the extension to decide which path to take, but uses the "SAB\x00" magic:

const input_is_sab = blk: {
    const file = std.fs.cwd().openFile(file_path.?, .{}) catch break :blk false;
    defer file.close();
    var magic_buf: [4]u8 = undefined;
    const read_len = file.readAll(&magic_buf) catch break :blk false;
    break :blk sab_loader.isSabMagic(magic_buf[0..read_len]);
};

On a hit, sab_loader.loadProgram rebuilds a Program of the same shape as the text parsing path (basic blocks, register table, signature table) and goes directly into binding/execution; on a miss it enters the text flow:

  1. Preprocessing (parser.Parser.preprocessWithCache)
  2. Parsing (parser.Parser.parse)
  3. Binding (inside src/vm.zig::VM.init)
  4. Execution (run / runTests)
NoteAfter the two entry points merge, they share the same Program structure — this guarantees that --stats has the same output shape on SAB and .sa; the SAB path only skips preprocessing and re-lexing, so “bytecode has a faster cold start” mainly comes from that skip.

Two-Pass Preprocessing

src/parser.zig::preprocessWithCache is vm’s “frontend entry point”. Its design goal is to support forward references, i.e. EXPAND FOO appearing before [MACRO] FOO still expands correctly.

Pass 1: Pre-Scan

The first step of preprocessLines is to extract all [MACRO] / #def from the original line list and put them into the macros / defs tables in the parser state. Note that this step has not yet actually expanded any EXPAND; it only makes all macro definitions “known first”.

This makes code like tests/hygiene_macro.sa, which puts the macro after @main with the caller in front, legal, because by the time Pass 2 runs, BAR is already known.

Pass 2: Expansion

In Pass 2, lines are processed one by one:

  • @import "...": resolved relative to the current file’s directory; if not found in the filesystem, falls back to looking up the standard library root ($HOME/.sa/std/, source is the description in README.md). Once found, preprocessFile is called recursively.
  • EXPAND MACRO %p1, %p2: formal parameters in the macro body are replaced with the call arguments; local variables of the form _xxx are suffixed with __sa_hyg<N> (a monotonic counter from expansion_counter) to ensure that a macro written twice in a row does not overwrite the other’s stack slots.
  • #def NAME = VALUE: pure text replacement, effective at the constant level.
  • @const NAME = utf8:"...": puts the string literal into the constants table, while automatically deriving NAME_len.
  • @const NAME = struct { f: SIZE = hex:...\xNN }: binary struct literals are decoded field by field.
  • [REP N] ... [END_REP]: loop expansion; each iteration replaces %i with the current index, and likewise adds a hygiene suffix to local identifiers.

Expansion is recursive: if EXPAND / [REP] / @import / #def / @const appears again inside a macro body, preprocessLines is called again.

Persistent Preprocessing Cache

When SA_VM_DISABLE_PREPROCESS_CACHE is not set, vm writes the cache using SA_CACHE (otherwise $HOME/.cache/sa/vm/preprocess) as the root directory. The cache granularity is a single @import file, and the validation dimensions are size + mtime; any change to an import dependency makes that entry stale. The status appears in the --stats report as disabled / hit / miss / stale / write_failed.

Parsing and the Program Structure

The parser outputs a parser.Program, whose core fields are:

  • functions: StringHashMap(Function): one entry per @fn, containing params, return_type, blocks, instructions.
  • externs: StringHashMap(ExternSignature): one entry per @extern, containing parameter types, return type, ABI shape.
  • constants: StringHashMap([]const u8): the raw literal bytes of all @const (used for utf8:"..." / binary structs).
  • Auxiliary tables such as labels, memory_layout.

Each Function.blocks is a []BasicBlock; a BasicBlock describes a run of consecutive instructions ending in br / jmp / return. At bind time vm precomputes each block’s start_inst / end_inst, and the dispatch table can locate a block by binary search on pc ∈ [start, end).

Parse Cache (In-Process LRU)

Multiple sa vm run invocations within the same process reuse LRU parse results (PARSE_CACHE_MAX_ENTRIES = 8):

  1. Compute a fingerprint of the preprocessed lines + constants table using Wyhash (parseCacheFingerprint).
  2. On a hit, parser.cloneProgram clones a copy for the execution thread; the original AST template is not modified.
  3. Only on a miss is parser_inst.parse called; after completion a template is stored using c_allocator.
The status in the --stats output is disabled / hit / miss / clone_failed / store_failed.

Stack-Frame Model

vm’s “stack” consists of 3 segments (inside src/vm.zig):

SegmentSourceLifetime
host stackOS thread stack (the interpreter’s own recursion)Same as the process; TEB / pthread provide their own guard pages
guest frameA []u64 buffer borrowed from frame_pool on an internal subroutine callReleased via defer on return, counted by frame_pool_releases
heap allocalloc N goes through QuotaAllocator to request memoryRecorded in heap_allocs, freed uniformly when the function returns

Each guest frame is a []u64 buffer; vm internally maps virtual register numbers to indices into that buffer (the register mapping of basic blocks is computed at bind time); parameters are copied from the caller’s parameter registers into the callee’s new frame slots according to the calling convention, and after the call ends they are explicitly returned in the !param form (consistent with the ownership notation of .sa).

Linear Stack Safety

All segments borrowed from heap_allocs / stack_alloc are released all at once in the frame’s defer block, so the typical interpreter bug of “a guest function returns early and misses an alloc release” does not occur. Combined with QuotaAllocator, every byte can also be reclaimed precisely (QuotaAllocator.free subtracts in reverse using memory.len).

Stack Depth and the Host-Stack Gate

src/sandbox.zig exposes two constants:

  • default_max_call_depth = 100_000: the guest recursion limit, overridden by --max-call-depth.
  • default_stack_headroom_bytes = 256 * 1024: below this value, further recursion is refused, to prevent crashing through the TEB.

On Windows, the TEB guard usually triggers before max_call_depth (about 2.7k frames under a 1 MiB main stack are intercepted). tests/vm_tail_arena.sa specifically covers “tail self-call functions that need arena-backed stack_alloc frames” — it puts stack_alloc explicitly inside a loop, ensuring that tail self-calls do not exhaust the host stack.

Instruction Dispatch

The shape of the main loop is “PC advancement + block switching”:

  1. Find the BasicBlock containing pc (findBlockForPc, a linear search over the block table; the number of blocks is usually in single digits).
  2. Execute instructions one by one inside the block; on encountering br cond -> L_T, L_F, jump directly to the precomputed target block index.
  3. On encountering call @fn(args...), recursively enter executeFunction, with the new frame borrowed from frame_pool.
  4. On encountering return val, take one of two paths, tail call or non-tail call: a tail call preferentially triggers tail_restart (reusing the same stack frame), while a non-tail call returns normally and writes the return value back to the caller’s register.

The Typed Val Union

All operands (register / immediate / stack slot / offset) are normalized at parse time into the Val union, whose variants correspond to immediates, register slots, stack offsets, and external references. When the result is fed into an instruction, sign extension / truncation is then performed. For example, load addr+off as i8 explicitly sign-extends to 64 bits, ensuring that sgt / slt / srem have correct semantics in negative-number scenarios (the README’s “Correct Sign Extension” section).

Fuel Charging Model

Sandbox fuel is charged at the granularity of “compiled basic blocks”, with the formula (src/sandbox.zig::blockCost):

cost = body_words * 1 + slow_words * 15 + call_words * 31 + terminator(1)
fast-arm 固定 = 4
空块也至少 = 1（否则 while(true){} 是免费的）

An empty-body block (the typical example is a dead loop formed by a backward jmp L_ENTRY) still costs 1 — this lets even a minimal dead-loop fixture like INFINITE_LOOP_SA exit stably in tests due to fuel exhaustion.

Relationship with SAB v4 Bytecode

SAB (“SA Bytecode”) is the intermediate code of the SA toolchain, produced by the compilation stage of sa build-exe. A SAB module starts with the 4-byte "SAB\x00" magic, with the symbol table / signature table / constant table / instruction stream packed together. vm’s src/sab_loader.zig parses SAB and folds it back into a Program, so the subsequent execution flow is fully shared with .sa.

Key mappings (source src/sab_loader.zig):

  • .move_ / .release / .fence are folded into no-op assigns (VM does not emit ownership diagnostics).
  • A “bare const name” operand of borrow CONST_NAME is decoded as .register (pointing to the const data pointer).
  • &CONST_NAME is decoded as a pointer load in take form.

Therefore the answer to “does vm consume .sa or .sab” is: it consumes both, automatically split by magic, and ultimately executes on the same Program.

Known Implementation Pitfalls

  • No backtrace: panic / panic_msg only print PANIC[code] and then terminate.
  • Synchronous threading model: the pthread_* shims are placeholders (src/ffi.zig); there is currently no host-level scheduler.
  • Floating-point comparison not implemented: bit storage is implemented; fcmp_* only has full support on the SAB path; the text path has not completed some comparison branches.
  • Call cache is memory-sensitive: memory_epoch is bumped after every extern that “may read impurely”; pure functions keep hitting.
