End-to-End Examples

This page takes real scripts from the plugin repository’s tests/ directory and explains them section by section, covering both run and test modes, macro expansion, memory operations, dynamic dispatch, and controlled execution. Each section notes the source file path; the scripts in the sandbox section are taken from the test fixtures embedded in src/plugin.zig.

Minimal Program Structure (run Mode)

Source: D:/projects/sla/sa_plugin_vm/tests/hello_world.sa

@import "sa_std/io/print.sai"

@const HELLO_MSG = utf8:"hello, saasm\n"

@main() -> i32:
L_ENTRY:
    call @sa_print_bytes(&HELLO_MSG, 13)
    return 0
  • @import pulls in the standard library’s print contract declarations, making sa_print_bytes resolvable.
  • @const NAME = utf8:"..." defines a byte constant; the preprocessor also automatically generates the companion constant HELLO_MSG_len = 13, so the length does not need to be counted by hand — writing 13 explicitly here is consistent with it.
  • @main() -> i32: is the entry signature, L_ENTRY: is the first basic-block label; &NAME takes the constant’s address, and the return value 0 is the process exit code.
# 运行
SA_PLUGIN_DEV=1 SA_PLUGINS_PATH="$PWD/zig-out/lib/libvm.so" sa vm run tests/hello_world.sa

Recursive Calls and Exit Codes

Source: tests/fibonacci.sa (excerpt)

@const RESULT_OK = utf8:"21\n"
@const RESULT_ERR = utf8:"error\n"

@fib(n: i32) -> i32:
L_ENTRY:
    base = sle n, 1
    br base -> L_BASE, L_REC

L_BASE:
    !base
    return n

L_REC:
    !base
    n1 = sub n, 1
    n2 = sub n, 2
    a = call @fib(n1)
    b = call @fib(n2)
    sum = add a, b
    !n
    !a
    !b
    return sum

@main() -> i32:
L_ENTRY:
    result = call @fib(8)
    ok = eq result, 21
    !result
    br ok -> L_OK, L_ERR

L_OK:
    !ok
    call @sa_print_bytes(&RESULT_OK, 3)
    return 0

L_ERR:
    !ok
    call @sa_print_bytes(&RESULT_ERR, 6)
    return 1

Key points:

  • Recursion of internal functions is implemented by the interpreter by instantiating subframes; parameters fill the first few slots of the new frame by position.
  • !reg is an ownership-consumption hint; in the interpreter it is a harmless no-op, but it preserves traces of the source language’s ownership semantics.
  • The failure branch’s return 1 makes the process exit code 1, which can be used directly for shell decisions. fib(8) == 21 is consistent with the string literal.

Conditional Branches and Memory-Write Loops

Sources: tests/if_else.sa, tests/loop.sa. if_else.sa uses sgt comparison and a two-way br branch to implement max(10, 20), with the same structure as the example above. loop.sa shows a complete on-stack counter loop and pointer arithmetic:

@fill_zero(&arr: ptr) -> void:
L_ENTRY:
    i_slot = stack_alloc 8          # 栈槽：8 字节局部变量
    store i_slot+0, 0 as u64        # 带偏移的类型化存储
    jmp L_COND

L_COND:
    i = load i_slot+0 as u64        # 类型化读取
    more = ult i, 4                 # 无符号小于
    br more -> L_BODY, L_END

L_BODY:
    slot = ptr_add arr, i           # 指针算术
    store slot+0, 0 as u8
    next = add i, 1
    store i_slot+0, next as u64
    ...
    jmp L_COND

stack_alloc storage such as i_slot is exactly what causes the containing function to be marked as “needs an arena”: the frame is released as a whole on return, and the heap segment does not leak. The main function first allocates a heap buffer with alloc 4, writes 1..4, then calls the zeroing function, and finally reads back byte by byte for verification.

Macros: Hygienic Renaming

Source: tests/hygiene_macro.sa

[MACRO] BAR %out, %x
    _tmp = add %x, 1
    %out = _tmp
[END_MACRO]

@main() -> i32:
L_ENTRY:
    EXPAND BAR _a, 5
    EXPAND BAR _b, 10

    # Verify parameter substitution and register isolation:
    oka = eq _a, 6
    okb = eq _b, 11
    ok = and oka, okb
    ...

The _tmp in both expansions starts with _, so it is a “macro-body local name”, and is rewritten to names with a monotonic-counter suffix (of the form _tmp__sa_hyg<N>), so the two expansions each occupy independent register slots and do not overwrite each other — this is the register isolation mentioned in the comment. %out/%x are replaced positionally with the actual arguments.

Macros: [REP N] Loop Expansion

Source: tests/rep_macro.sa (excerpt)

    _sum_slot = stack_alloc 8
    store _sum_slot+0, 0 as u64

    [REP 3]
    # Each iteration has its own hygienic label L_ITER and local register _step_val
    # as well as substituting the loop index %i
    L_ITER:
        _step_val_%i = add %i, 1
        _curr_sum = load _sum_slot+0 as u64
        _next_sum = add _curr_sum, _step_val_%i
        store _sum_slot+0, _next_sum as u64
        !_step_val_%i
        !_curr_sum
        !_next_sum
    [END_REP]

    final_sum = load _sum_slot+0 as u64
    ok = eq final_sum, 6 # 1 + 2 + 3 = 6

[REP 3] repeats the block body three times, each time replacing %i with step number 0/1/2, and hygienically rewrites labels such as L_ITER to avoid duplicate definitions. The accumulated result 6 is consistent with the assertion.

TipThe standard library relies heavily on this mechanism: after tests/generics_monomorph.sa imports sa_std/core/option.sal, it uses EXPAND OPTION_IS_SOME has_value, opt, EXPAND OPTION_GET value, opt, EXPAND OPTION_SET_SOME opt, 42 to manually instantiate @unwrap_or_i32 for i32 — i.e. the “monomorphization via macro expansion” pattern also holds under the interpreter.

Tail Self-Calls and Arena Frames

Source: tests/vm_tail_arena.sa (excerpt)

@count_with_slot(i: u64, n: u64) -> u64:
L_ENTRY:
    done = eq i, n
    slot = stack_alloc 8
    store slot+0, i as u64
    br done -> L_DONE, L_STEP
L_STEP:
    one = 1 as u64
    ni = add i, one
    result = call @count_with_slot(ni, n)
    !slot
    ...
    return result
L_DONE:
    !slot
    !done
    return i

# main 里：n = 2048，result 应等于 n

This function both performs a tail self-call and needs an arena frame for stack_alloc. After the interpreter recognizes the tail self-call, it does not create a new frame, but updates the arguments in place and restarts the current frame from block 0, so 2048 levels of recursion only occupy one frame of space. This is exactly the regression point mentioned in the README: “covers tail self-calls in functions that need arena-backed stack_alloc frames”.

Vtables and Indirect Calls (Dynamic Dispatch)

Source: tests/trait_vtable.sa (excerpt)

@const BUTTON_VT = vtable { draw = @button_draw }

#def DynDraw_SIZE = 16
#def DynDraw_DATA = +0
#def DynDraw_VTABLE = +8
#def VTable_draw = +0
#def Button_SIZE = 4
#def Button_id = +0

@render(&item: ptr) -> i32:
L_ENTRY:
    data_ptr = load item+DynDraw_DATA as ptr
    vtable_ptr = load item+DynDraw_VTABLE as ptr
    draw_fn = load vtable_ptr+VTable_draw as ptr
    result = call_indirect draw_fn(&data_ptr)
    ...
  • vtable { draw = @button_draw } is preserved as-is during preprocessing, and is only concretized into a function-pointer array at the binding stage.
  • Fat-pointer layout: the data pointer and the vtable pointer each occupy one slot; the method address is loaded from the vtable offset and then called via call_indirect.
  • #def constants take effect in the second-pass replacement, so field offsets can be written in a readable form without affecting performance.

test Mode

Source: tests/vm_test_mode.sa (complete contents)

@test "vm harness"():
L_ENTRY:
    sum = add 2, 3
    ok = eq sum, 5
    br ok -> L_PASS, L_FAIL
L_PASS:
    return
L_FAIL:
    panic(11)
  • Function names defined by @test "...": start with test ; this is the sole basis on which vm recognizes test functions.
  • Test functions cannot take parameters, otherwise an error is reported with exit code 1.
  • The framework itself does not judge boolean values: the test case branches itself, and the failure side terminates with panic(11) — the process exit code is 128 + (11 & 0x7f) = 139.
  • All @test functions are executed in name-sorted order; if all run to completion with no panic, the exit code is 0.
sa vm test tests/vm_test_mode.sa

The two companion fixtures demonstrate the behavior of the same dead-code chain in the two modes: tests/vm_dead_pure.sa (containing @main) and tests/vm_dead_pure_test_mode.sa (changed to @test "dead pure chain"). Both dereference a never-initialized pointer value at load p+0 as u64, used for regression verification that such a “pure but invalid” load chain does not make the VM touch illegal memory and crash.

Observation: Counting Loop and --stats

Source: tests/bench.sa (excerpt)

@const RESULT_OK = utf8:"[PASS] Loop benchmark completed successfully!\n"

@main():
L_ENTRY:
    sum_ptr = stack_alloc 8
    i_ptr = stack_alloc 8
    store sum_ptr+0, 0 as u64
    store i_ptr+0, 0 as u64
    limit = 100000
    jmp L_COND

L_COND:
    i = load i_ptr+0 as u64
    cond = ult i, limit
    br cond -> L_BODY, L_EXIT

L_BODY:
    sum = load sum_ptr+0 as u64
    sq = mul i, i
    next_sum = add sum, sq
    next_i = add i, 1
    store sum_ptr+0, next_sum as u64
    store i_ptr+0, next_i as u64
    ...
    jmp L_COND
...

This is a typical “register promotion blocked” loop: both the sum and the counter live in stack slots and must be loaded/stored every iteration. With the observation switches you can see the actual share of each interpreter path:

sa vm run --stats tests/bench.sa
# 关注 fast_block_hits（快速臂命中）、slow_ops（慢路径回查）、
# tail_restarts、call_cache_* 与 frame_pool_* 各项

SA_VM_DISABLE_BLOCK_FASTPATH=1 sa vm run --stats tests/bench.sa   # 关掉块快速路径再对比
sa vm run --profile=5 tests/bench.sa                              # 附带最耗时函数排行

FFI: Calling Symbols from an Installed Plugin

Source: tests/http_client_test.sa

@extern sa_http_client_new(use_tls: u32, &out_client: ptr) -> u32
@extern sa_http_client_free(client: ptr) -> u32

@main() -> i32:
L_ENTRY:
    client_slot = stack_alloc 8
    status = call @sa_http_client_new(0, &client_slot)

    ok = eq status, 0
    br ok -> L_FREE, L_ERR

L_FREE:
    client = load client_slot+0 as ptr
    status2 = call @sa_http_client_free(client)

    ok2 = eq status2, 0
    br ok2 -> L_SUCCESS, L_ERR

L_SUCCESS:
    call @sa_print_bytes(&MSG_OK, 55)
    return 0

L_ERR:
    call @sa_print_bytes(&MSG_ERR, 52)
    return 1
  • @extern declares a typed signature; at the binding stage it is resolved to a symbol exported by the installed http-client plugin and then dispatched via libffi.
  • &client_slot passes the stack slot’s address as an out parameter, and afterwards load client_slot+0 as ptr retrieves the handle.
  • This symbol is listed in sap.json’s dependencies."http-client".symbols, so it can be hit by lazy loading; if that optional plugin is not installed, the call ends with an unresolved symbol, but this does not affect the running of other programs that do not involve it.

Sandbox Behavior Demonstrations (Embedded Test Fixtures)

Source: the test fixture constants in src/plugin.zig. These three scripts are specifically used to trigger resource limits, and are the most direct material for verifying the exit code table.

Infinite Loop → E_FUEL_EXHAUSTED / E_TIMEOUT

@main() -> i32:
L_ENTRY:
    jmp L_ENTRY
sa vm run --fuel=1000 infinite.sa       # 退出码 229，事件行 code=101
sa vm run --deadline-ms=40 infinite.sa  # 退出码 230，事件行 code=102

An empty-body back-edge block still burns at least 1 unit of fuel, so fuel can kill this kind of loop; the wall clock is another independent means.

Allocation Storm → E_MEM_QUOTA

@main() -> i32:
L_LOOP:
    p = alloc 1048576
    jmp L_LOOP
sa vm run --mem-cap-bytes=8388608 memhog.sa   # 退出码 231，事件行 code=103

Non-Tail Self-Recursion → E_STACK_OVERFLOW

The DEEP_RECURSION_SA fixture defines a counting function @count(i, n) that adds one to the return value before returning; the main function calls it with 200000 — because of the extra add r, one step, this call is not a tail call, and frames genuinely accumulate. Running it directly with no flags shows a clean abort rather than a host crash:

sa vm run deep.sa                        # 退出码 235，事件行 code=107
sa vm run --max-call-depth=1000 deep.sa  # 显式收紧深度上限

Capability Denial → E_CAPABILITY_DENIED

The repository tests also contain a set of policy end-to-end cases: a file read inside the allowed subtree executes successfully, while the same kind of call outside the subtree fails with exit code 228, and the event line’s detail gives both a reason label (such as fs_not_allowed, host_not_allowed, extern_not_allowed) and the target string. One conclusion from them is worth remembering: when a URL is not in the domain allowlist, whether or not --allow-ffi is given makes no difference at all, because the capability decision happens before any FFI mechanism intervenes.
