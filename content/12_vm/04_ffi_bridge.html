FFI 桥与宿主互操作

本页说明 vm 如何把 SA 汇编里的 @extern 调用、call @fn 内置函数以及 对宿主插件符号的引用，桥到 libffi / POSIX dlopen / Windows LoadLibraryExW 这一层。 读完本节可以理解 sap.json 依赖块如何生效、--allow-ffi 究竟打开什么、策略引擎在分发点的拦截位置， 以及 vm 自带 shim 的全部清单。

三类互操作通道

通道SA 端写法vm 端实现典型代表
类型化 FFI@extern fd_open(path: ptr) -> i32 + call @fd_open(&PATH)src/ffi.zig::callSymbolWithPtr 经 libffi 调入全部 @extern 声明
原始 libc FFI@extern dlopen(...)仅当 --allow-ffi 时 resolveSymbol 才会返回这些符号dlopen / dlsym / dlclose / dlerror
内置 shim直接 call @fd_open(...)（无 @extern 也可）解析期就把名字映射到 vm 自带的 pub export fnfd_* / mmap / signal / pthread_* / sqlite3_* / sa_time_*

类型化 FFI：libffi 桥

每个 @extern 在解析期被折叠为 parser.ExternSignature，结构为「返回类型 + 参数类型数组」。 vm 在执行 call @fn 时把 guest 寄存器里的值按签名 pack 到 FfiValue extern union（来源 src/ffi.zig::writeArgValue），然后用 ffi_prep_cif + ffi_call 走 libffi。

参数类型支持：void / i1 / u8 / i8 / u16 / i16 / u32 / i32 / u64 / i64 / f32 / f64 / ptr。 指针和整型在 64 bit 平台上宽度一致；i32 会做符号扩展，u32 走零扩展。

Windows 上的 libffi

Windows 平台 libffi 不在系统 DLL 中。vm 在第一次 callSymbolWithPtr 时尝试按 libffi-8.dll → libffi-7.dll → ffi.dll 顺序 LoadLibrary + GetProcAddress，解析所有 ffi_type_* 静态量。失败则返回 error.WindowsLibffiUnavailable。

原始 libc FFI：--allow-ffi

POSIX dlopen、dlsym、dlclose、dlerror 在 vm 中以 pub const 包成 与平台无关的函数指针（Linux / macOS 走 @cImport，Windows 走 LoadLibraryExW / FreeLibrary）。 它们只在 FfiManager.allow_ffi = true 时由 resolveSymbol 返回——

if (std.mem.eql(u8, symbol_name, "dlopen")) return if (self.allow_ffi) ... else null;
if (std.mem.eql(u8, symbol_name, "dlsym"))  return if (self.allow_ffi) ... else null;
if (std.mem.eql(u8, symbol_name, "dlclose")) return if (self.allow_ffi) ... else null;
if (std.mem.eql(u8, symbol_name, "dlerror")) return if (self.allow_ffi) ... else null;

也就是说：

  • 不加 --allow-ffi：guest 即使声明 @extern dlopen 也会在符号解析阶段得到 null，最终 Symbol not found。
  • 加 --allow-ffi：上述 4 个符号可直接调用，但能力仍然由 sa.vm.policy/1 的 extern.allow / fs / http 等进一步收紧。

插件依赖加载（sap.json）

FfiManager.loadDeclaredDependencies 不扫描 SA_PLUGINS_PATH，而是读 $SA_PLUGINS_HOME/installed/vm/current/sap.json（Windows 默认 C:/Users/Public/.sa_plugins， Linux 默认 $HOME/.local/share/sa_plugins），从 dependencies 段拿到全部依赖名（按 sap.json 顺序）。

之后每次 resolveSymbol 第一次需要某依赖时，loadInstalledPlugin 用 {plugins_home}/installed/{name}/current/lib{name}.so（Windows 是 {name}.dll）走 dlopen(..., RTLD_NOW=2)； 成功则把句柄加入 handles 列表，后续 dlsym 直接在新句柄上查找。

在 sap.json 里 vm 钉死了 4 个可选依赖：

name版本符号数作用
http-client>=0.1.014同步 HTTP 客户端桥
http-server>=0.1.019同步 HTTP 服务端桥
deno>=0.1.01sa_deno_plugin_hostname
node>=0.1.07os.cpus / timers.sleep / dgram.*

如果某个依赖未安装，dlopen 失败会被打印到 stderr，但 vm 不会因此终止——它是 "Declared FFI dependency not loaded" 的软错误，其余不依赖该插件的符号仍可解析。

内置 shim 清单

下列符号在 src/ffi.zig::resolveSymbol 里被强制映射到 vm 自带的 pub export fn，不依赖任何 .so / .dll：

族符号实现
fdfd_open、fd_read、fd_close目前为占位（fd_open 恒返回 3、fd_read 恒返回 3、fd_close 恒返回 0），用于兼容现有 demo
mmapmmap、munmapmmap 用 std.heap.page_allocator.alloc；munmap 占位返回 0
signalsignal占位：返回原 sig
pthreadpthread_spawn、pthread_spawn_detached、pthread_join、pthread_drop占位：s 系列返回 0、pthread_drop no-op
sqlite3sqlite3_prepare、sqlite3_step、sqlite3_finalize占位：prepare/finalize 返回 0，step 恒返回 100（SQLITE_DONE）
sa_timesa_time_sleep_ms、sa_time_sleep_ns真实实现：std.time.sleep
警告fd_* / mmap / signal / pthread_* / sqlite3_* 当前是 占位实现，仅用于让现有 demo / 标准库 facade 在 vm 上跑通；不要把它们当作真实 OS 行为。 生产路径请走 sa build-exe。

策略引擎在 FFI 路径上的拦截

能力策略（src/policy.zig，schema sa.vm.policy/1）在 src/io_classify.zig 的协助下， 对每条 call @fn 做两层检查：

Layer 1：extern.allow 名称白名单

默认拒绝。被调用的 extern 符号名必须在策略的 extern.allow 列表里，否则抛 extern_not_allowed，且发生在 libffi / dlopen 解析之前。 这意味着：策略拒绝时不会泄露目标文件 / 句柄加载错误信息——调用方只能看到 "NAME denied by run policy"。

Layer 2：fs / http / env / process 参数路由

通过 io_classify 把每个已知符号族映射到对应的策略检查：

符号族策略段检查函数
fd_*、sa_print_bytes、sa_fmt_*fspolicy.checkFs
sa_http_client_*、sa_http_server_*httppolicy.checkHttp
env 读 / 写envpolicy.checkEnv
process spawn / execprocesspolicy.checkProcessSpawn

每条 deny 都以 E_CAPABILITY_DENIED（panic code 100，退出码 228）形式报告，并在 sa-vm-event: {...} 的 detail 中给出可读的 DenyReason.label() （fs_not_allowed、host_not_allowed、extern_not_allowed 等）。 位于拒绝路径上的源码位置与具体目标（如越界 URL）也会被嵌入事件。

能力边界速查

  • 已强制：extern.allow 名称白名单、fs.read/write 子树匹配（glob + Windows realpath）、 http 域 / 方法 / 路径 / 端口 / IP literal / 私有地址 / 重定向次数 / 降级拦截、env 名单、process spawn 与 exec 白名单、ffi / threads / net_raw 总开关。
  • 未强制：原生插件内部自发的 redirect（不在 vm 调度点）、单次 shim 调用内部的 check-to-use TOCTOU 窗口。
  • 符号族分类：见 src/io_classify.zig。未在分类里的符号只走 Layer 1 检查。
注意策略与 --sandboxed 内置 profile 的关系：--sandboxed 等价于强制一份默认拒绝策略 （资源 caps + 最小 extern 集），不能与 --policy 或 --allow-ffi 同时使用——冲突会触发 E_SANDBOX_MISCONFIG，退出码 234。
