vm Overview: Positioning and Architecture

Zig 0.17This plugin is built with Zig 0.17: the 0.17 branch builds successfully with Zig 0.17 and passes the Zig unit tests; the old 0.14.1 branch is left untouched.

This page explains where sa_plugin_vm sits in the SA / SLA toolchain: it is a standalone dynamic interpreter virtual machine plugin that registers a vm subcommand to intercept sa vm ... invocations, and interprets SA assembly (.sa / .sal) and SAB v4 bytecode modules directly on the host OS. After reading this page you will be able to distinguish the division of labor between the “interpreted execution” path and the “compile to a native executable” path, and understand vm’s four-layer architecture and capability map.

Position in the Toolchain

By default, the SA / SLA toolchain only compiles .sa to a native executable (sa build-exe follows the SLA → SA → backend path). sa_plugin_vm registers a vm subcommand through SA’s dynamic command dispatch ABI (saasm_plugin_descriptor_v1), so all sa vm ... invocations are intercepted by it, without modifying the mainline compiler.

PathEntry pointArtifactTypical use
Native pathsa build-exe app.saExecutable / shared libraryRelease, performance benchmarking, needing full OS capabilities
Interpreted pathsa vm run app.saNo artifact (direct execution)Local development iteration, CI smoke tests, sandbox fixtures, TheAlgorithms compatibility self-checks

The two paths share the same frontend semantics — vm consumes parsed IR that is fully equivalent to the compilation path; but vm does not emit target code, instead interpreting each instruction on stack frames. A common development workflow is to first verify logic with sa vm run --stats, then switch to sa build-exe to produce the artifact.

Clear Division of Labor with build-exe

  • vm is responsible for: dynamic interpretation, built-in debug output (--stats, --profile=N), resource sandboxing (fuel / clock / memory / recursion depth), capability policy (sa.vm.policy/1), @test mode, SAB bytecode loading, cross-plugin FFI.
  • build-exe is responsible for: executable linking, link-time optimization, JIT/AOT-unreachable features (inline_assembly, architecture-specific SIMD intrinsics, pkg_bin_multiple multi-entry packages), release signing.
  • Overlap: vm itself can be produced by build-exe compilation (zig build -Doptimize=ReleaseFast generates libvm.so / vm.dll), so “vm is a target program of build-exe” and “build-exe compiles vm” both hold — this is a plugin host relationship, not a replacement relationship.
Notevm has fairly broad permissions (full project FS operations, local networking, cache directories), and in formal run mode requires the sandbox permissions.lock; for local verification always add SA_PLUGIN_DEV=1. See the Resource Limits and Exit Codes page for details.

Four-Layer Architecture

Capability Map

The capability surface that vm formally registers can be read from the permissions section of sap.json. During local development these declarations are used for the SA_PLUGIN_DEV=1 path; in production they are tightened by permissions.lock.

  • fs: $PROJECT/** full operations (read / write / create / delete / metadata), $SA_PLUGINS_HOME/** read-only, $HOME/.sa/std/** read-only, $SA_CACHE/** read/write.
  • net: declared domains (example.com / api.example.com / localhost / 127.0.0.1 / [::1] / port 18395), but at runtime policy.zig filters a second time, and only targets allowed in policy.http.allow are permitted actual access.
  • env: HOME, SA_PLUGINS_HOME, SA_STD_DIR, SA_CACHE and all variables starting with SA_.
  • process: spawn allowed; the exec list only lists /bin/echo, /usr/bin/echo; other binaries are rejected with process_exec_not_allowed.

Optional dependencies (dlopen already-installed plugins on demand): http-client, http-server, deno, node; each symbol list is pinned by sap.json. vm does not require them to exist; their absence does not affect resolution of other symbols.

Runtime Components

The main flow of a single sa vm run invocation (src/plugin.zig::runVmCommand):

  1. Parse argv; collect sandbox options; decide the mode by argv[2] ∈ {run, test}.
  2. Detect the SAB magic ("SAB\x00") to decide whether to use sab_loader or parser.
  3. Preprocess (with optional persistent cache) → parse (with optional in-process LRU) → bind (resolve @extern / function symbols).
  4. When FFI is needed (--allow-ffi or the program contains @extern), FfiManager.loadDeclaredDependencies lazily loads according to the dependency list.
  5. Resolve policy (--policy / --sandboxed / environment variables / explicit CLI overrides), and compose the final Limits in the order “explicit CLI > env > policy”.
  6. Construct the QuotaAllocator (if mem-cap is enabled), the VM instance, setPolicy, configureSandbox.
  7. Emit sa-vm-event: {"event":"start", ...} (only when a cap / policy is present).
  8. vm.run() or vm.runTests() interprets and executes. The exit code is the return value; panic goes through 128 + (code & 0x7f).
  9. If --stats / --profile=N is present, emit the statistics block.

Sandbox Security Model at a Glance

vm’s “sandbox” is the superposition of three layers (see the Resource Limits and Exit Codes page for details):

  • Resource limits: fuel / wall clock / mem quota / call depth; violations uniformly go through panic → exit code.
  • Capability policy: sa.vm.policy/1 JSON, extern.allow (default-deny symbol allowlist) + fine-grained fs / http / env / process controls.
  • Raw libc FFI gate: dlopen / dlsym / dlclose / dlerror are only exposed with --allow-ffi.

Compliant failure paths are all reported through the single-line JSON sa-vm-event: {"v":1,"event":"violation","code":N,"name":"...",...}, which host scripts can grep directly.

WarningKnown out-of-scope items: inline assembly, SIMD intrinsics, multi-binary packages; floating-point comparison is not yet supported (bit storage is implemented); the threading model is synchronous; panic has no backtrace. See the Interpreter Internals page and the Resource Limits and Exit Codes page for details.
