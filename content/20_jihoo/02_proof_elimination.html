Proof-Based Check Elimination (Farkas Certificates)

Every Vec index and arithmetic operation in SA carries a runtime bounds or overflow check. On hot paths — the Redis and nginx workloads built on sci — those checks are a fixed tax on every operation, and they also block LLVM from vectorizing the loops around them. jihoo's answer is to prove checks away at compile time and delete the proved ones, keeping a small trusted core. This is the most valuable single idea in the evaluation for sci: measured on jihoo's own compiler source, the prover deletes 1,544 of 4,624 bounds and overflow checks (33.4%) in 19 seconds.

The recipe

  • Obligations are generated from MIR, not from source. Only linear integer inequalities are targeted — no dependent types, no general theorem proving.
  • The certificate is a Farkas combination: non-negative weights over known facts whose linear combination contradicts the negated goal. Checking a certificate is pure multiply-and-add.
  • The trusted checker is 155 lines (compiler/linear.jh). The prover itself (Fourier–Motzkin with a Bellman–Ford difference-constraint preference) is untrusted: a wrong proof is simply discarded, never believed.
  • Loops are handled with cut-point invariants proposed by an untrusted Houdini-style inference (propose — check — keep what verifies).
  • Every fact is annotated with its basis (path condition, type range, a callee's ensures, a type invariant), and the assumption set is a greatest fixed point, so one wrong ensures cannot silently poison the whole program.
  • Failure is bounded: a function with more than 2,000 paths gets no proofs at all instead of stalling the compile.

Why it fits sci

SA is already an explicit IR, so obligations can be generated directly on SA functions — sci does not need to grow a dependent type system first. The trust split is the part to copy faithfully: the obligation generator defines the integer semantics and is trusted (in jihoo it is the expensive part, vc.jh 2,061 lines + obligations.jh 2,551 lines), the certificate checker is tiny and trusted, and everything clever is untrusted. Copying only the 155-line checker without budgeting for the generator would not reproduce the proof rate.

Adoption plan for sci

  1. Start with the highest-yield obligation class: loop induction variable vs. length — index-against-len facts inside loops, which dominate the proved set in jihoo's data.
  2. Keep the trusted checker at the hundred-line scale; certificates are Farkas weight vectors, verified by multiply-and-add only.
  3. Prove-or-keep semantics: an unproved check stays in the output with a recorded reason, exactly as today — the prover may only delete, never weaken.
  4. Measure on the real hot paths (the slaredis / slanginx workloads), not on micro-benchmarks: proof rate on hot functions and end-to-end bench delta are the acceptance numbers.

Sources: jihoo compiler/linear.jh, vc.jh, obligations.jh at HEAD 5f18751…; jihoo verify compiler/main.jh measured 2026-11-27: 19.059 s, 7,597 checks, 1,761 proved (bounds+overflow 1,544/4,624). jihoo's own docs mark this line as research-grade since 0.6, but verify is a shipping command that runs by default in every build, and its engineering viability is demonstrated by jihoo's own byte-identical bootstrap.
